Swati Khandelwal2026年11月04日漏洞 / Web 安全

Ruby on Rails 中的一个严重漏洞可能允许未经验证的攻击者上传特制文件，从而在应用服务器上写入任意文件，前提是该应用使用 ImageMagick 处理上传。Rails 项目在 一份公告 中披露了该漏洞，并在 8.1.4.1 和 8.0.5.2 版本中修复了它。

该漏洞存在于 Active Storage 中，这是 Rails 中负责处理文件上传的部分。一些应用使用 Active Storage 的 Disk 服务存储上传文件，该服务会将文件存储在服务器磁盘上。在这些应用中，攻击者还可以读取应用有权读取的任何文件。

据 Rails 称，这些文件通常包括应用的 secret_key_base 及其用于其他系统的凭据。读取这些文件可能进而导致远程代码执行，或横向移动到这些系统中。

Rails 在 CVSS 评分体系中将该漏洞评为 10 分中的 9.8 分。其追踪编号为 GHSA-f3w6-w445-fwh9，目前尚无 CVE 标识符。

ImageMagick 会根据文件内容选择一种格式处理器，并将其称为 coder。有些 coder 会对图像内命名的其他文件执行操作，而不是对图像本身执行操作。Active Storage 未对上传可使用的 coder 设置任何限制，因此服务器自身的 ImageMagick 策略是唯一的限制。

附加文件时，Active Storage 中的 ImageMagick 分析器会运行。仅附加上传文件就足以触发该漏洞。应用不必创建变体（图像的转换副本）或预览，也不必调用 analyze。

据 修复该漏洞的提交记录 所述，一个上传的 SVG 文件通过该分析器到达了 ImageMagick 的 MSL coder。MSL 是一种脚本处理器，可读取和写入由其脚本命名的文件。

Rails 表示，已向其报告了一条攻击链，但它并“不认为这是唯一存在的攻击链。”公告未说明该漏洞是否已被利用。

该漏洞由 GMO Flatt Security 的研究员 RyotaK 通过 HackerOne 报告。

哪些 Rails 应用受影响

仅当以下三项条件全部成立时，应用才会受到影响：

  • 它使用 ImageMagick 进行 Active Storage 图像处理。该设置为 config.active_storage.variant_processor = :mini_magick，这是 load_defaults 6.1 或更早版本应用的默认设置。
  • 其 ImageMagick 安全策略尚未阻止相关 coder。Rails 表示，Debian 和 Ubuntu 随附的策略不会阻止它们。
  • 它接受不受信任用户上传的文件。

要检查第一个条件，请查看 config.active_storage.variant_processor。如果未设置，则默认值取决于 load_defaults：7.0 之前为 :mini_magick，7.0 及之后为 :vips。同一设置不仅决定哪个库创建变体，也决定哪个库分析上传文件。

8.0.5.2 之前的每个 Active Storage 版本都受到影响，8.1 系列中 8.1.4.1 之前的版本也受到影响。8.0 之前的发布系列已不再受支持，Rails 不会为这些版本发布修复版本。

今年 7 月，Rails 修复了另一个严重的 Active Storage 漏洞 CVE-2026-66066，该漏洞影响使用 libvips 而非 ImageMagick 的应用。使用 ImageMagick 的应用不会受到该漏洞攻击路径的影响，但可能受到此漏洞的影响。

相同的发布版本还修复了第二个 Active Storage 漏洞 GHSA-v924-7rp8-4mxh，Rails 将其严重程度评为高，CVSS 分数为 8.8。Active Storage 将上传文件传递给 ImageMagick 和 FFmpeg 时，所用的临时文件名保留了上传文件的扩展名。

当文件内容未显示其格式时，这些工具可以从扩展中选取解码器。因此，能够选择上传文件名并声明其内容类型的攻击者，可以选择处理该文件的解码器。

该怎么办

Rails 强烈建议尽快升级。这两个版本总共修复了 21 个安全问题。

修复版本附带了 ImageMagick 安全策略。MiniMagick 是 Active Storage 用于调用 ImageMagick 的 Ruby gem。在默认配置下，它运行的每条 ImageMagick 命令都会应用该策略，而不仅仅是来自 Active Storage 的命令。

该策略会阻止 MSL coder；读取或删除图像以外文件的 coders；获取远程或本地引用或将其显示在屏幕上的 coders；所有由 Ghostscript 支持的 coders，以及 gs delegate；还有 @filename 间接引用。

  • 升级到 Rails 8.1.4.1 或 8.0.5.2。运行在 :mini_magick 上的应用还需要 mini_magick 5.1 或更高版本，否则会在启动时抛出错误。根据 Rails 的维护政策，Rails 8.0 只会获得安全修复，直至 2026 年 11 月 7 日。
  • 按照 Active Storage 指南 中的说明，通过运行 bin/rails runner 'puts MiniMagick.identify { |i| i.list "policy" }'，确认应用加载了新的策略。
  • 检查随附策略是否完全到达应用。如果应用在启动后替换 MiniMagick.cli_env、使用 MiniMagick.cli_prefix 清除环境，或安装自己的 MiniMagick::Shell，该策略就不会到达应用。此类应用必须将这些规则放入 ImageMagick 的系统策略中。
  • 使用 GraphicsMagick 的应用无法从随附策略中获得保护，因为 GraphicsMagick 不读取 ImageMagick 策略。
  • 检查服务器自身的 ImageMagick 策略。随附策略是对其进行补充，而不是替换。其中允许某个 coder 的规则（包括 pattern="*" 这样的通配符）会覆盖随附策略对该 coder 的阻止。
  • 如果应用通过 ImageMagick 渲染 PDF 或 PostScript 文件，请重新允许 gs delegate 及其使用的 coders，位置在服务器的 policy.xml 中。
  • 如果暂时无法升级，请将随附策略 activestorage/lib/active_storage/image_magick/policy.xml 中的规则复制到 ImageMagick 的系统策略中，例如 /etc/ImageMagick-7/policy.xml。至少应阻止 MSL coder、Ghostscript coders 以及 gs delegate。Rails 还以补丁形式发布了针对 8.1 和 8.0 的修复。
  • 版本系列早于 8.0 的应用可以使用该临时解决方案，或升级到 8.0 或更高版本。
  • Rails 针对第二个缺陷的临时解决方案只会改变 FFmpeg 的使用方式。其中没有任何一个涵盖 ImageMagick。
  • 如果应用使用 Disk 服务存储附件，请更换 secret_key_base 以及应用进程能够读取的所有其他机密。其中包括主密钥、config/credentials.yml.enc 持有的所有内容、存储和数据库凭据以及第三方令牌。不要将已暴露的机密保留作为后备选项。

公告没有说明如何检查应用是否已成为攻击目标。
