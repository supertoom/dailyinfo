· 勒索软件　· 虚拟化安全　· GERT 披露　· 2026.11.20

没有利用虚拟机逃逸，也没有触发 Hypervisor 内存破坏，攻击者仍然摧毁了整套虚拟化环境。卡巴斯基全球应急响应团队（GERT）近期披露的一起事件中，四台 ESXi 主机及其承载的全部虚拟机、两台 vCenter Server Appliance（VCSA）和连接的备份基础设施均遭到破坏。赎金记录将攻击者标识为 BlackNevas，而所有针对 ESXi 的关键操作都通过合法的 VMware 管理接口完成。

这起事件值得关注的，不只是又一个支持 ESXi 的勒索软件家族，而是攻击者如何把凭据、远程管理工具、vCenter Host Profiles 和备份系统串成一条完整的破坏链：先取得管理面控制权，再改写主机访问状态，先削弱恢复能力，最后才在虚拟化层引爆载荷。对防守方而言，真正的预警窗口也由此从虚拟机内部转移到了身份、管理面与恢复链路。

01 事件核心：失守的是管理信任链，而非单个虚拟机

在传统终端勒索场景中，一台主机失陷通常首先影响该主机本身；而在虚拟化环境中，vCenter 集中管理多台 ESXi，ESXi 又同时承载域控制器、应用服务器、数据库等关键工作负载。攻击者一旦获得管理面权限，便可能把单点权限转化为批量控制与批量破坏能力。

本次事件没有证据表明攻击者利用 ESXi 漏洞进入虚拟化层。卡巴斯基披露的路径是：攻击者使用从组织内部非虚拟化系统获取的凭据访问 VCSA；在备份基础设施上取得管理执行能力后，还提取了其中保存的凭据。有效账户、备份系统的集中信任关系和虚拟化管理权限由此被串联起来。

补丁管理仍然必要，却不能覆盖这类风险。即使 Hypervisor 没有暴露已知漏洞，只要合法凭据能够跨边界复用、vCenter 能被普通企业网段访问、备份与生产共享同一套高权限身份，攻击者仍可能沿着正常管理通道抵达 ESXi。

02 攻击链还原：从合法登录到批量破坏

1. 在 VCSA 上建立双通道持久化

攻击者首先通过 SSH 以 root 身份登录负责虚拟化灾难恢复管理的 VCSA。登录后仅 43 秒，便通过 Shell 脚本下载并部署 MeshAgent——合法远程管理平台 MeshCentral 的终端组件。整个 SSH 会话持续 2 分 26 秒；会话结束后，攻击者不再通过 SSH 回访该设备。

约四小时后，攻击者改经 MeshAgent 返回，并将 Ligolo-ng 反向隧道配置为 systemd 服务，形成第二条持久化通道。相关配置刻意采用近似 VMware 组件的命名与路径：

Unit file：/etc/systemd/system/vmware-vdma.service

Service：vmware-vdma

Description：DNS, time, VM settings sync (v2.03.24766)

ExecStart：/opt/vmware/bin/agent

Restart：always

该二进制中可见 Ligolo-ng v0.8.2 与 api.cloudvflare[.]com:443 字符串。这里的关键不在于某个名称天然恶意，而在于新出现的服务、未被基线批准的二进制和外部隧道地址形成了组合异常。只监控交互式 SSH 登录，会漏掉登录结束之后才真正开始使用的远控与隧道通道。

2. 滥用 Host Profiles，把 SSH 从策略关闭改为运行

vCenter Host Profiles 本来用于提取、校验并统一 ESXi 主机配置，也可以包含 Tech Support Mode（TSM）与 TSM-SSH 等服务状态。攻击者控制 vCenter 后，没有从主机下方绕过这项策略，而是直接利用集中管理功能，从上方改写了目标主机的期望状态。

日志还原出的序列非常紧凑：T+0 读取主机配置；T+10 分 18 秒推送启用 SSH 的配置变更；T+10 分 51 秒，TSM-SSH 进入 RUNNING。配置推送与服务启动之间仅相隔 33 秒。随后，对目标 ESXi 的直接 SSH 访问来自 VCSA 的 IP 地址——一个在日常管理中通常被高度信任的来源。

这条链路说明，Host Profile 合规检查或修复操作本身并不等于安全。判断其风险必须结合变更窗口、操作账户、目标服务以及后续连接：如果一次未获批准的配置修复启用了 TSM-SSH，紧接着又出现 vCenter 到同一台 ESXi 的新 SSH 会话，其风险远高于任一单独事件。

3. 通过 SFTP 投递载荷，并在正式破坏前自测

ESXi 载荷通过 SFTP 投递。auth.log 中记录了与 Bitvise FlowSsh 相关的客户端标识；shell.log 则保留了后续命令序列。FlowSsh 支持 SFTP、远程执行、交互式 Shell 和隧道，但对工具的识别应以日志中的客户端标识为主要依据，而不是仅凭行为猜测。

T+0 true

T+1s chmod +x /tmp/esx64

T+1m48s true

T+1m49s ./tmp/esx64 /selftest

仅执行 true 的会话可视为自动化通道建立的行为线索，但并非 FlowSsh 的独有特征。真正有检测价值的是完整组合：异常客户端或来源、向 /tmp 暂存可执行文件、赋予执行权限、短暂自测，以及随后访问 /vmfs。此次 /selftest 运行约 16 秒，发生在最终引爆前约三小时，为防守方留下了一个明确但短暂的预破坏窗口。

4. 停止虚拟机后，对 VMFS 路径执行破坏性操作

成熟的 ESXi 加密器通常会在修改虚拟磁盘前停止虚拟机，以释放活动状态与文件锁。本次灾难恢复主机上的全部虚拟机在 23 秒内停止，vmksummary.log 中每小时记录的运行虚拟机数量也由正常值降为零。不过，现有证据无法确认攻击者究竟使用 esxcli、vim-cmd 还是其他方式终止虚拟机，不能把某一家族的惯用命令直接套入本案。

卡巴斯基记录到的最终执行命令为：

./tmp/esx64 /p /vmfs/ /depth 5 /wipe /allsys /detach /-showvolumes

其中，/p/vmfs/ 指向虚拟机文件所在的 VMFS 根路径，/depth 5 控制目录递归深度；/wipe 与数据存储中出现的 ._wipe 痕迹相互印证；/detach 与 SSH 断开后破坏活动仍持续的现象一致。/allsys 和 /-showvolumes 的含义主要借助 BlackNevas／Trigona 的公开家族资料辅助解释，由于没有取得本次 ESXi 加密器二进制，不能视为已完成样本级验证。

事件痕迹还显示，虚拟磁盘文件约前 2 KB 被覆盖。这足以破坏保护性 MBR、主 GPT 头及其他早期启动或文件系统结构，使系统无法启动，但不能据此直接断言分区元数据完全不可恢复。GPT 在不同位置保存主、备份头及分区项数组；实际可恢复程度仍取决于备份 GPT、其他文件系统结构、描述文件和具体虚拟磁盘布局是否也被破坏。

5. 在 ESXi 引爆前，先拆除恢复能力

备份基础设施并非本次事件的附带受害者。攻击者在主要攻击发生前数日便关闭了备份环境的防病毒保护；在最后阶段，又依次停止备份服务、加密备份服务器、实施 SMB 传播并阻断管理员访问，最后才引爆 ESXi。

卡巴斯基给出的相对时间线为：T+0 停止备份服务，T+7 分钟备份服务器被加密，T+52 分钟出现 SMB 传播，T+2 小时 08 分管理员被锁定，T+2 小时 31 分 ESXi 载荷引爆。这个顺序使受害组织在最需要恢复生产时，同时失去备份服务、管理入口和部分恢复路径。

“备份不可变”并不自动等于“业务可恢复”。不可变存储无法单独保护恢复所需的身份、备份管理服务器、存储库、网络路径、凭据与操作流程。恢复系统必须作为独立安全边界设计，并在 vCenter 与生产 AD 均不可用的假设下验证恢复流程。

03 为什么传统终端监控难以看见关键动作

ESXi 基于 VMware 专有的 VMkernel。虽然它接受部分类似 Linux 的命令并运行部分类 Linux 软件，但并不是通用 Linux 发行版。Broadcom 明确说明，面向通用操作系统的现成安全工具不能直接在 ESXi 上运行，也不支持在 ESXi 与 VCSA 上直接安装第三方代理或防病毒软件。

由此形成一种可见性落差：虚拟机内部的 EDR 能监控客户机进程，却无法直接观察或归因 ESXi 侧进程对 VMDK 或数据存储文件的修改。客户机可能只记录到突然关机、磁盘 I/O 失败等结果，而真正的恶意执行发生在其监控边界之外。

另一类误区：把管理设备 IP 或合法管理工具直接视为可信。vCenter 发起的 SSH、Host Profile 推送和正常服务配置，在协议与接口层面都可能是合法操作；只有把这些动作与身份、时间、变更审批和后续行为关联起来，才能识别管理权限已经被滥用。

04 BlackNevas 家族背景与本案归因边界

SentinelOne 将 BlackNevas（又称 Trial Recovery）描述为 2024 年 11 月首次出现、由 Trigona 衍生而来的勒索软件家族，其公开样本覆盖 Windows、Linux、NAS 和 ESXi，并支持 /p 或 /path、/wipe、/depth、/detach 等参数。本案赎金记录中的 BlackNevas 标识，以及最终命令的参数风格，与这些公开特征相吻合。

但家族相似性不能替代样本证据。卡巴斯基未能取得本次 ESXi 加密器、Ligolo-ng 二进制、代理安装脚本和凭据提取脚本，因此也没有这些文件的哈希。对本次事件的可靠判断应建立在赎金记录、日志、服务配置、网络指标和破坏痕迹之上，而不是将其他 BlackNevas 样本的全部能力自动归入本案。

同样需要区分的是，CVE-2024-37085 等虚拟化漏洞可以用于说明行业风险，但并非本次事件的入口。微软曾披露该漏洞被多个勒索攻击者用于在加入 AD 的 ESXi 上取得完全管理权限，并导致 Akira、Black Basta 等勒索软件部署；这一案例说明身份与管理组映射需要独立防护。

05 防守方应优先抓住的六个预警窗口

  1. Host Profile 异常变更。在未批准的变更窗口内，Host Profile 修复或合规操作修改 TSM、TSM-SSH，且服务在短时间内进入 RUNNING，应直接触发高优先级告警。若 15 分钟内又出现 vCenter 或管理设备到同一 ESXi 的新 SSH 会话，应升级为严重事件，并同步保存 vCenter Events／Tasks、vpxa.log、vobd.log 与 auth.log。
  2. VCSA 出现未基线化的持久化组件。重点检查 /etc/systemd/system 下新增或修改的单元，以及其引用的 /opt/vmware 等路径中的二进制。服务名称类似 VMware 并不能证明恶意或合法，关键是它是否存在于组织批准的服务与文件基线中，是否伴随远控、隧道或异常外联。
  3. /tmp 暂存与 /vmfs 访问形成连续链路。将 SFTP 上传、新可执行文件出现、chmod、短时自测和随后访问 /vmfs 关联检测。单独一次 chmod +x 可能含义有限，但新投递文件从临时目录进入执行并接近虚拟机存储，是必须立即核查的预破坏信号。
  4. 虚拟机在秒级或分钟级集中停止。跨多台虚拟机连续出现 power-off 或 world-kill，尤其在非维护窗口内发生，应视为高置信度预警。可关联 shell.log、hostd.log、vCenter Tasks 与 vmksummary.log，但不能只依赖后者，因为其运行虚拟机计数按小时记录，时间粒度较粗。
  5. 备份与安全能力先于生产异常失效。备份服务停止、备份环境防病毒被关闭、恢复服务器被加密或管理员突然失去访问，都应与虚拟化管理面告警联动。备份侧异常不是独立的运维问题，而可能是生产勒索破坏即将开始的前置信号。
  6. ESXi 执行控制被削弱。监控 Host Acceptance Level 是否降至更低信任级别，以及 execInstalledOnly 运行时或内核强制设置是否被关闭。Broadcom 指出，ESXi 8.0 及以后版本默认启用 execInstalledOnly 内部运行时选项，用于阻止未通过 VIB 安装的二进制执行；相关状态变化应纳入配置基线与审计。

06 加固与应急：把管理面、身份面和恢复面分开保护

将 vCenter 按 Tier 0 资产管理

  • 使用专用虚拟化管理身份，避免域管理员、工作站管理员等普通企业高权限账户直接复用于 vCenter 或 ESXi。
  • 通过受支持的身份联邦配置抗钓鱼多因素认证，严格限制管理网络来源、工作站与账户，并监控特权会话。
  • 将 Host Profile、集群级配置、权限映射和 TSM-SSH 状态变化纳入审批与审计；在适合业务运维的前提下使用 Lockdown Mode，把 SSH 和 ESXi Shell 作为例外通道而非常态入口。
  • 持续检查 ESXi 的 AD 集成与组映射。对于 CVE-2024-37085，应按照 Broadcom 公告升级至受影响产品对应的修复版本；旧版本缓解措施不能替代生命周期管理。

让日志独立于被攻击的平台

ESXi 本地日志使用空间有限的 ramdisk，重启可能清除相关证据；持久化 scratch 有助于重启后的留存，但仍无法抵御主机或本地数据存储被破坏。应将 ESXi 与 VCSA 的远程 syslog 发送到虚拟化信任域之外的集中日志或 SIEM，并确保日志路径不依赖同一套生产身份与管理控制面。

优先级最高的来源包括 auth.log、shell.log、vpxa.log、vobd.log、vCenter Events／Tasks，以及 VCSA 的 systemd 配置与被引用二进制。它们分别回答“谁从哪里登录”“执行了什么命令”“vCenter 对主机做了什么”“安全与服务状态如何变化”“哪个账户对哪个对象发起了任务”以及“攻击者如何留下持久化”。

把恢复能力建设成独立安全边界

  • 为备份配置独立管理身份，减少与生产 AD 的依赖，隔离备份管理接口和存储库。
  • 保留离线或逻辑隔离的恢复副本，并确保生产凭据无权删除或改写这些副本。
  • 定期演练在 vCenter、生产 AD 或备份管理服务器不可用时，干净的管理员能否完成认证、连接存储库、验证数据并恢复业务。
  • 将备份服务状态、凭据库访问和安全工具状态纳入与生产环境联动的监控，而不是只在备份任务失败时查看。

事件发现后的前 30 分钟，先保住证据再清理

在不影响紧急止损的前提下，先隔离 vCenter 与普通企业网段之间的管理访问，同时保留受控调查通道；导出 vCenter Events／Tasks、SSO 审计、活动会话和当前 Host Profile；收集各 ESXi 的认证、Shell、主机管理、内核、存储与 Host Profile 日志；保存 VCSA 可疑服务单元及其引用二进制；同时固定备份服务器服务状态、凭据库证据和网络日志。

不要为了“踢掉攻击者”而首先重启 ESXi。重启可能破坏 ramdisk 中的证据。完成关键日志复制或确认远程留存后，再撤销或轮换失陷凭据、关闭未批准的 SSH／ESXi Shell、移除未授权远控与 systemd 服务，并防止 Host Profiles 或自动化任务重新开启这些入口。大规模恢复前，还应先隔离已失陷的备份设施并建立干净的恢复控制面。

07 结语

这起事件最具警示性的地方，是攻击者没有必须突破某一项 Hypervisor 安全技术，而是接管了本就有权管理它的系统。vCenter 的集中权限、跨环境复用的身份和与生产耦合的恢复链路，共同放大了最终影响。

对应的防守重点也不应停留在“是否给 ESXi 安装了终端代理”。更有效的路径是：保护 vCenter 这一 Tier 0 控制点，分离企业、虚拟化与恢复身份，收窄直接管理通道，把高风险配置变更识别为连续行为，并确保关键日志与恢复能力不会随生产环境一起失效。勒索软件引爆前的每一个异常管理动作，都可能是阻止批量破坏的最后窗口。
