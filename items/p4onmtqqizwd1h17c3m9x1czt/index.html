作者复现并分析了 WordPress Core 竞争条件远程代码执行漏洞 CVE-2026-119977。

值得关注

文章从暂存目录、安装器与文件复制三个环节还原竞争条件，并提供可复现 PoC 和修复版本，便于理解漏洞成因与处置重点。

正文

一、背景

最近笔者看到某测绘平台在2026年11月的检索数据，WordPress Core 竞争条件远程代码执行漏洞(CVE-2026-119977)关联的全球风险资产总数为1219476个，关联IP总数为379271个，国内风险资产总数为48714个，关联IP总数为14700个。涉及的资产还挺多，竞争条件导致的远程代码执行，刚好有时间，在这里搭环境研究下。

（以下所有环境均为笔者本地搭建环境复现，根据文章内容可复现）

二、漏洞详情

CVE官网介绍：https://www.cve.org/CVERecord?id=CVE-2026-119977

Score

Severity

Version Vector String

8.1

HIGH

CVSS:3.1/AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H

WordPress 核心程序 4.7 至 7.1.3 版本存在远程代码执行（RCE）漏洞。漏洞成因：完整内核包升级过程中，会生成可被外网访问、路径可预测的临时过渡目录。未经身份验证的攻击者可在升级窗口期内，在服务器上执行恶意代码。

该漏洞源于完整包核心升级过程中，升级程序将更新包解压至 wp-content/upgrade/ 下基于包名生成的可预测、Web 可访问临时目录（相关代码位于 class-wp-upgrader.php、class-core-upgrader.php、update-core.php 等）。临时目录包含安装程序 setup-config.php，且在升级窗口期间可被外部 HTTP 请求直接执行。攻击者可利用该漏洞，在升级窗口内通过竞争条件注入恶意配置，最终实现任意代码执行，导致服务器完全沦陷。

八、利用流程

1、攻击者提前轮询

在管理员操作之前，持续请求目标站点的 wp-content/upgrade/ 和暂存安装器路径，等待升级开始。

2、管理员点更新

在后台点击“更新到 7.1.3”，WordPress 进入核心升级流程，向 downloads.wordpress.org 请求更新包。

3、下载更新包

官网返回 wordpress-7.1.3.zip，并带 Content-Disposition: filename=wordpress-7.1.3.zip，download_url() 据此把临时文件重命名。

4、解压到暂存目录

升级器把包解压到 wp-content/upgrade/wordpress-7.1.3/，目录名直接来自包文件名，可预测。

5、暂存目录可访问

该目录在 Web 根下，且没有禁止 PHP 执行，攻击者可以直接请求里面的 setup-config.php。

6、发送未认证 POST

攻击者向暂存安装器提交 dbname、uname、pwd、dbhost 等参数，不需要任何登录。

7、安装器接受参数

暂存副本没有 wp-config.php，安装器认为站点未安装，于是用攻击者给的参数去连数据库。

8、写入暂存配置

连接攻击者 MySQL 成功后，安装器把这些参数写进暂存目录的 wp-config.php。

9、校验和撑开窗口

升级器在复制前请求官方校验和，这个外网请求让“解压完成”到“开始复制”之间多出几秒。

10、复制时拍快照

copy_dir() 在复制开始时才读取目录，攻击者刚写下的 wp-config.php 因此进入快照。

11、覆盖正式配置

快照被复制到站点根目录，正式的 wp-config.php 被替换，站点改为连接攻击者的数据库。

12、登录后台

站点从攻击者库读取 wp_users 和角色，攻击者用 attacker / Attacker#2026 登录，成为 administrator。

13、上传插件

管理员本来就能上传插件，攻击者传入一个含 PHP 的插件包，文件落到 wp-content/plugins/。

14、执行系统命令

wp-content/plugins/目录下php文件可直接访问执行。

九、漏洞分析

1、入口：后台点更新

wp-admin/update-core.php -> do_core_upgrade()

点击更新，会传给do_core_upgrade()函数version=7.1.3&locale=en_US，接着传值给find_core_update()

$version = $_POST['version'] ?? false;
$locale  = $_POST['locale'] ?? 'en_US';
$update  = find_core_update( $version, $locale );

wp-admin/includes/update.php -> find_core_update()

221: function find_core_update( $version, $locale ) {
222: 	$from_api = get_site_transient( 'update_core' );
223: 	if ( ! isset( $from_api->updates ) || ! is_array( $from_api->updates ) ) {
224: 		return false;
225: 	}
226: 	$updates = $from_api->updates;
227: 	foreach ( $updates as $update ) {
228: 		if ( $update->current === $version && $update->locale === $locale ) {
229: 			return $update;
230: 		}
231: 	}
232: 	return false;

find_core_update()的作用是在 update_core 这个 transient 的更新列表里，按“版本 + 语言”精确查找一条更新记录，找到返回整个对象，找不到返回 false。

这里是在本地数据库里找，默认升级到7.1.4版本。

SELECT option_name, option_value
FROM t712_options
WHERE option_name LIKE '%update_core%';

这里笔者没有使用默认的升级方式，因为复现漏洞需要从7.1.2->7.1.3版本，这里使用插件完成阻拦替换

使用pin-upgrade.php插件，返回挂 pre_site_transient_update_core，强制返回 7.1.3 的更新 offer。

https://downloads.wordpress.org/release/wordpress-7.1.3.zip

4、临时文件名：6 位随机后缀

wp-admin/includes/file.php -> wp_tempnam()

先取包名、去掉扩展名，得到 wordpress-7.1.3，再拼 - 加 6 位随机字符和 .tmp。下载到本地的文件因此形如 wordpress-7.1.3-AbC123.tmp。下载完成后 Content-Disposition 会该会重命名，接着往下

7、暂存目录：在 Web 根下，且没有 index.php

wp-admin/includes/class-wp-upgrader.php -> unpack_package()

369: 		// Clean up contents of upgrade directory beforehand.
370: 		$upgrade_files = $wp_filesystem->dirlist( $upgrade_folder );
371: 		if ( ! empty( $upgrade_files ) ) {
372: 			foreach ( $upgrade_files as $file ) {
373: 				$wp_filesystem->delete( $upgrade_folder . $file['name'], true );

wp_content_dir() 就是站点根下的 wp-content/，所以 upgrade 目录天然可被 Web 访问。7.1.4 之前这里既不放 index.php，也不拒绝 PHP，清空时还会把所有内容都删掉、不留占位文件。如果服务器开了目录列表，攻击者能直接看到 wordpress-7.1.3/。

8、安装器：以“自己所在目录”为 ABSPATH

wp-admin/setup-config.php -> 文件顶层

30: 	define( 'ABSPATH', dirname( __DIR__ ) . '/' );
33: 	require ABSPATH . 'wp-settings.php';
...
59: if ( file_exists( ABSPATH . 'wp-config.php' ) ) {

ABSPATH 是 setup-config.php 自己所在的目录，也就是暂存目录，不是正式站点根。升级包本身不带 wp-config.php，所以第 59 行判断为假，安装器认为这是一个全新站点，继续走安装流程。

9、输入：四个数据库字段全部来自 POST

wp-admin/setup-config.php -> case 2

282: 		$dbname = trim( wp_unslash( $_POST['dbname'] ) );
283: 		$uname  = trim( wp_unslash( $_POST['uname'] ) );
284: 		$pwd    = trim( wp_unslash( $_POST['pwd'] ) );
285: 		$dbhost = trim( wp_unslash( $_POST['dbhost'] ) );
286: 		$prefix = trim( wp_unslash( $_POST['prefix'] ) );

没有 nonce、没有登录校验、没有来源检查；prefix 只做了空值和字符集校验。任何人只要能访问这个文件，就能提交自己的数据库参数。

10、连接与落盘：把攻击者参数写进暂存配置

wp-admin/setup-config.php -> case 2 与写文件

317: 		define( 'DB_NAME', $dbname );
...
325: 		require_wp_db();
331: 		$wpdb->db_connect();
...
469: 			$handle        = fopen( $path_to_wp_config, 'w' );
477: 					fwrite( $handle, $line );

先按攻击者的参数连数据库，连接失败就 wp_die；成功则把参数写进暂存目录的 wp-config.php。到这里，攻击者已经控制了一份“升级目录里的配置文件”。这里写进暂存目录的文件，怎么会被当成升级内容，接着向下分析。

11、关键：复制逻辑来自“目标版本”

wp-admin/includes/class-core-upgrader.php -> upgrade()

163: 		if ( ! $wp_filesystem->copy( $working_dir . '/wordpress/wp-admin/includes/update-core.php', $wp_dir . 'wp-admin/includes/update-core.php', true ) ) {
...
171: 		require_once ABSPATH . 'wp-admin/includes/update-core.php';
...
178: 		$result = update_core( $working_dir, $wp_dir );

解压后，升级器先把新包里的 update-core.php 覆盖到站点并 require。也就是说，接下来执行复制的是目标版本的代码，不是当前正在跑的版本。7.1.2 升 7.1.3，执行的是 7.1.3 的 update_core()。

12、目标 7.1.3：skip 名单里没有 wp-config.php

wp-admin/includes/update-core.php -> update_core()

1549: 	$skip = array( 'wp-content', 'wp-includes/version.php' );
...
1639: 	$result = copy_dir( $from . $distro, $to, $skip );

跳过名单只有 wp-content 和 version.php。wp-config.php 不在名单里，只要它出现在要复制的目录中，就会被复制到站点根目录。接着看 copy_dir 是什么时候读目录的

13、copy_dir：复制开始才拍快照

wp-admin/includes/file.php -> copy_dir()

2025: 	$dirlist = $wp_filesystem->dirlist( $from );
...
2042: 	foreach ( (array) $dirlist as $filename => $fileinfo ) {
2043: 		if ( in_array( $filename, $skip_list, true ) ) {
2044: 			continue;

它在复制开始时才 dirlist，而不是用原始包清单。解压之后、这一行之前被创建的文件，都会被当成“升级内容”。攻击者的 wp-config.php 就是在这一步进入清单的。那么攻击者写入和这一行之间，有多长时间，接着看

14、窗口：checksums 的外网请求

wp-admin/includes/update-core.php -> update_core()

1553: 	if ( function_exists( 'get_core_checksums' ) ) {
1555: 		$working_dir_local = WP_CONTENT_DIR . '/upgrade/' . basename( $from ) . $distro;
1557: 		$checksums = get_core_checksums( $wp_version, $wp_local_package ?? 'en_US' );

在 copy_dir 之前，update_core 要先拉官方校验和。这是一次外网请求，几秒量级——正好把“解压完成”到“拍快照”之间的窗口撑开。攻击者的 POST 必须在这几秒内完成写入。

15、完整总结

三处代码分别是：

  • 目录名来自包名，本身是为了“可读、可复用”；

  • 安装器接受 POST，本身是为了“全新安装”；

  • copy_dir 重新读目录，本身是为了“复制实际文件”。

单独看都没写错。叠加起来：目录可预测 → 暂存目录可访问 → 安装器接受匿名输入 → 写入的文件被复制 → 正式配置被覆盖。

触发条件缺一不可：

  1. 目标版本的 update-core.php 的 skip 不含 wp-config.php；

  2. 暂存目录名可预测（本地包，或官网带 Content-Disposition）；

  3. 暂存目录在 Web 根下且 PHP 可执行；

  4. 暂存树里没有 wp-config.php（升级包不带）；

  5. 受害机能连到攻击者数据库；

  6. POST 落在 dirlist 之前。

16、对比：7.1.3 升 7.1.4 改了什么

wp-admin/includes/update-core.php -> update_core()（7.1.4）

1548: 	 * Never copy a wp-config.php, which could have been written to the working directory.

354: 	private function get_working_dir_name( $package ) {
358: 		return $name . '-' . wp_generate_password( 16, false );
...
404: 		if ( ! $wp_filesystem->exists( $upgrade_folder . 'index.php' ) ) {
405: 			$wp_filesystem->put_contents( $upgrade_folder . 'index.php', "<?php\n// Silence is golden.\n", FS_CHMOD_FILE );

三处修复分别对应：目录名不可预测、upgrade 目录不可列、复制时排除 wp-config.php。

但要注意执行顺序：7.1.3 升 7.1.4 时，跑的还是 7.1.3 的 unpack_package，所以随机目录和 index.php 这两处这次并不生效；真正生效的是新包里的 update-core.php，它的 skip 把 wp-config.php 排除了。
