Microsoft Entra Agent ID 凭据注入与钓鱼攻击链分析

Microsoft Entra Agent ID 凭据注入与钓鱼攻击链分析及检测

AI 导读

文章分析 Microsoft Entra Agent ID 的代理蓝图、蓝图主体、代理身份与代理用户对象，复现凭据注入和管理员钓鱼两条利用链。测试覆盖 79 个资源、1041 项权限，97 项被阻止、944 项仍可通过，并发现可继承权限、跨租户蓝图及 AgentIdentity.CreateAsManager 可用于创建子代理身份和提权。

值得关注

文章拆解了 Entra Agent ID 的对象与令牌交换机制，并用凭据注入和管理员钓鱼复现代理身份提权链及日志检测方法。

正文

前言

Entra Agent ID 是微软给 AI agent 用的一套身份体系。M365 发布了公告说 11月后普通 Entra 用户默认可以创建代理蓝图，这就把某些攻击场景所需要的管理员权限扩大到了全员。

代理身份是 Entra 里有权限身份， 一旦有人在租户里建起蓝图并配上凭据，凭据一旦落地，访问不再依赖任何人的实时认证，本文从基础知识点入手用完整的攻击链展示：这个载体是怎么被建起来的、权限是怎么流到它身上的、 以及防御方在哪些环节还能看见它。

Entra Agent ID

在 Entra ID 里，Microsoft Entra Agent ID为 AI 代理设计了一套独立的身份体系。它建立在与服务主体（service principal）相同的对象模型之上，同时加入了一组新的目录对象和它们之间的关联关系：agent blueprints, blueprint principals, agent's identities, 以及可选的 agent user。并配套 OAuth 2.0、OBO 与客户端凭据之上的代理专用令牌交换流程。

站在安全的立场上，光判断租户里有没有这类 AI 代理还不够。更需要弄明白的是，代理身份和传统服务主体（比如企业应用）到底哪里不同。具体来说，就是控制权归谁、凭据由谁持有并以何种方式完成认证、它最终能触达哪些资源。

本篇不打算逐个讲明白 Entra Agent ID 的所有对象和认证流程，这里只是简单过一遍这些概念，让读者有个基本背景，为后文的安全分析提供必要的概念背景。

01 对象模型

1.1 四个新对象

Microsoft 通过 Entra Agent ID 为 Entra ID 引入了新的对象、新的关联方式。这些跟以前那种先注册应用、再变成企业应用的模型不一样。以前传统的模型很直白：应用注册负责管这个应用是什么，企业应用负责管它在这个租户里是谁，两句话就说完了。现在换成 Entra Agent ID，层级就多起来了。到底牵涉哪几个东西，依具体场景而定，可能包括代理蓝图、蓝图主体、一个或多个代理身份，以及可选的代理用户。

关系如下图：

1）Agent identity blueprint（代理蓝图）

可以把蓝图理解成一张模板：代理身份照着它来生成，而凭据、需要访问哪些资源这类全局设置，都放在蓝图里，其实就跟传统模型里应用注册承担的角色差不多

官方定义：代理标识蓝图是 Microsoft Entra ID 中的一个对象，用作创建代理标识的模板，参考 Microsoft Entra Agent ID | agent-blueprint

2）blueprint principa（蓝图主体）

蓝图主体可以理解为蓝图落地到某个租户后的那份实例。它是替这张蓝图来管下面那批代理身份的，自己不当代理身份。

官方定义：表示特定租户中是否存在代理标识蓝图，令牌的 oid 声明引用智能体标识蓝图主体在审核日志中记录为由代理标识蓝图主体执行，参考 Microsoft Entra Agent ID | agent-blueprint

代理身份按需创建，代理用户在其上再叠加一层。那么两个身份对象就会分别产生代理实例：代理身份和代理用户。

3）agent identity（代理身份）

AI 代理去访问不同系统时，用来完成认证的那个主账户，就是代理身份。一个蓝图主体底下可以带好几个代理身份，不限于一个。

官方定义：其蓝图定义身份验证设置，并持有所有客户端凭据凭据是在蓝图上配置的，而不是代理标识。

参考 https://learn.microsoft.com/zh-cn/entra/agent-id/agent-identities

4）agent's user（代理用户）

除了主账户之外，AI 代理还可以选用一个附加账户去访问各类系统，这就是代理用户。它只在代理需要访问那些要求用户对象的系统（如邮箱、Teams）时才必要，并且与代理身份严格一对一。

官方定义：代理的用户帐户表示 Microsoft Entra 中的用户标识子类型与代理标识 1:1 映射接收具有声明 idtyp=user 的令牌，参考 了解 Microsoft Entra 智能体 ID 中的智能体用户帐户 - Microsoft Entra Agent ID | agent-users

1.3 凭据为何只存在于蓝图

1、跟老的企业应用那套相比，不同的点是：凭据只放在蓝图这一个地方。
2、这些新对象所支持的凭据类型有3种：

02 认证令牌

2.1 三种认证流程

Autonomous app OAuth flow（自主应用流）代理以自身身份运行，只取应用权限
On-behalf-of OAuth flow（代表流）代理代表已登录用户行事，取委派权限
Agent's user account OAuth flow（代理用户流）以代理专属用户账户的身份行事
三种流程都建立在两级令牌交换上。

2.2 两级令牌交换过程

Entra Agent ID 这套专属的认证流程的关键在于，代理不再自己持有凭据直接换令牌，改走两级令牌交换（由蓝图代认证，再由代理身份完成访问资源）。

第一步交换 Blueprint principal token

该蓝图的身份凭证被用于 client_credentials 操作，以获取作为蓝图主体身份的令牌。其中一个属性( fmi_path )用于指定令牌所对应代理对象的 ID（OID）。这个令牌的接收者为 api://AzureADTokenExchange/.default ，因此可以在后续的令牌交换中使用它。示例请求如下：

POST https://login.microsoftonline.com/[Tenant ID]/oauth2/v2.0/token HTTP/2
Host: login.microsoftonline.com
Content-Type: application/x-www-form-urlencoded

client_id=[Blueprint_Application_ID]
&scope=api://AzureADTokenExchange/.default
&fmi_path=[Agent_Identity_Object_ID]
&client_secret=[Blueprint_Secret]
&grant_type=client_credentials

请求会返回一个可用于认证令牌，以作为蓝图主体的身份进行认证。

第二步交换 Agent identity token

认证令牌被用作第二个 client_credentials 权限授予的凭证代理身份进行请求。示例请求如下：

POST https://login.microsoftonline.com/[Tenant ID]/oauth2/v2.0/token HTTP/2
Host: login.microsoftonline.com
Content-Type: application/x-www-form-urlencoded

client_id=[Agent_Identity_Object_ID]
&scope=[Target_Application_Scope]
&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
&client_assertion=eyJ[Blueprint_Token]
&grant_type=client_credentials

请求会返回一个令牌作为代理身份，令牌可以与 Microsoft Graph 一起使用。至此，该蓝图凭证已被用于实际充当代理身份。

过程可以这样理解：蓝图先用自己的凭据登录，换出一张交换令牌，这张票是给某个具体子代理身份的，子代理身份拿着这张票再去换真正能访问目标资源的那张访问令牌。 这个认证相当于做了一个分工：凭据放在蓝图那，权限放在代理身份那，日志留下的是代理身份。风险是蓝图凭据要是被偷，它底下所有子代理身份等于一起凉。

出于这项研究的需要，我扩展了 EntraTokenAid（一款用 PowerShell 写的认证工具），把前面提到的几种认证流程都补了进去。文中的示例就是拿它跑出来的。

03 权限的四个来源

代理身份的权限来源有四条路径：能通过加进组里拿权限，能被分到 Entra ID 的角色上，也能通过 OAuth2 的委派权限，以及应用角色的授权：
1）加入安全组，继承组上已授予的权限
2）被直接授予 Microsoft Entra 内置角色或 Azure RBAC 角色（与标准服务主体一致）
3）通过 OAuth 2.0 委派权限，代表用户访问资源
4）通过应用角色（app role）获得应用权限，以自身身份访问资源

前两条决定它在目录里有多大权力，后两条决定它能拿到下游资源的什么权限

3.1 安全组

组在 Entra 里其实是两类东西：
1）普通安全组，涉及的范围只是一个作用域。权限是从别处来的，例如资源授权、许可证、条件访问范围、Windows 365 供给策略
2）可分配角色组（isAssignableToRole = true），成员身份直接等于该组绑定的目录角色
实际攻防场景中，看到代理出现在某个组里，先查 isAssignableToRole 的属性，如果结果 false，则应该记为作用域。

3.2 Entra ID 与 Azure RBAC

1) Entra ID Roles（目录角色）

微软对代理身份和代理用户能拿哪些高权限角色做了限制。
用的是白名单机制。比如全局管理员、特权角色管理员、用户管理员就被做了限制，代理身份也不能成为可分配角色组（role-assignable group）的成员。
但机制内，像 Exchange 管理员、SharePoint 管理员、365 管理员这些还是能给的。

2) Azure RBAC Roles（Azure RBAC 角色）

代理身份也能被授予 Azure RBAC 角色。实际攻防遇到的场景中，这一块对方基本没有配任何限制。结果就是代理身份和代理用户可能拿着 Azure 资源的特权权限。

3.3 API 权限：四处位置、限制、直接授予、继承

委派权限与应用角色同属一套 Graph 权限模型，差别只在于是代表用户行事还是以自身身份行事。有了 Entra Agent ID 之后，API 权限不再集中在一处。

1）权限可能出现在四个位置

权限配置散布在多个对象上，因此判断起来更有难度。同样是权限，可能是在蓝图明确声明出来的，可能沿层级继承下来，也可能在模型的某个环节被直接授予。具体落在哪儿，要看这四种位置：
1）Agent Blueprint: required resource access
2）Agent Blueprint: inheritable permission
3）Agent Blueprint Principal
4）Agent Identity
前两项都挂在蓝图对象上，但是两份不同的配置，作用也不同。

2）总体限制

微软确实给代理身份封装了些 API 权限，委派的、应用的都封了，像 Graph 的 Chat.Read.All、Application.ReadWrite.All 这种直接授不了。

但别以为特权权限被一刀切了。我拿 79 个资源、1041 项权限挨个试了一遍：97 项被拦，944 项照过。过的里面还有六项算是危险级别的 Graph 应用权限。麻烦就在这儿——拦的和放的，威力差不多：Application.ReadWrite.All 关了，Application.ReadUpdate.All 还留着，加个凭据、改改应用对象，一样能干。

再举个例子，ADSynchronization.ReadWrite.All 那个（在 Microsoft Entra AD Synchronization Service 上），我测的时候也能授给代理身份。

3）权限直接授予

直接授在对象上是最方便的一种给法，委派权限、应用权限都行，跟老式企业应用拿权限是一个意思。

但委派权限有个前提：代理身份不能自己单干，得有个用户先通过某个应用登录进来，而这个应用在蓝图主体上得有 access-agent 这个权限。这样，应用才能顶着这个用户的身份去用代理身份：

4）权限继承

1、一个蓝图主体底下常常挂着好几个代理身份，一个个去授同样的基础权限太麻烦，不如在蓝图主体上同意一次。下面的代理身份就直接继承。在使用可继承的权限时，委派与应用权限都可继承（ inheritable Permissions ）。如果这些委托权限被授予蓝图主体，那么这些权限就会被与蓝图关联的所有代理身份所继承。

2、权限要真在代理身份身上生效，两个条件缺一不可。
第一，蓝图得先"允许"。哪些权限能被继承，可以点名某个权限（比如 Graph 的 User.Read.All），也可以对某个资源开 allAllowed。对 Graph 开了 allAllowed，那授予蓝图主体的 Graph 权限就都能继承。
第二，这项权限得在蓝图主体上真的授了、也同意了。
两个都满足，它才会被塞进代理身份的令牌里。

3、另外，光看代理身份对象（比如用 Microsoft Graph 查）是看不到继承来的权限的。想知道到底生效了哪些，得把蓝图配置和蓝图主体手上的权限合起来分析。

4、蓝图主体本身也不是什么权限都能用。测试下来，给它签的令牌里只有 AgentIdUser.ReadWrite.IdentityParentedBy 和 AgentIdentity.CreateAsManager 这两项。
还有个细节挺关键：AgentIdentity.CreateAsManager 在蓝图主体的令牌里一直有，哪怕门户和 Microsoft Graph 上都看不到它被同意过。换句话说，蓝图主体随时都能造个新的子代理身份。

3.4 其他途径与跨租户

其他授权途径

上文列举的授权方式并非所有可用方式。代理身份还能通过其他渠道取得访问权，官方文档就另外提到了几类：Exchange 的 RBAC 角色、Teams 的 RSC 分配、访问包，以及针对自建或第三方 API 的应用角色。

至于代理用户，它看起来跟普通用户对象没什么两样，除了前面说的那些角色分配限制，授权方式基本可以照普通用户来办。但这部分我没有系统地去测。

跨租户场景

1、蓝图跟应用注册一样是有多租户的。蓝图一旦是多租户，蓝图可在对方租户实例化出蓝图主体，并在那边创建本地代理身份：蓝图放在原来那个租户，蓝图主体和手下的代理身份、代理用户，则建在使用方租户里。
2、此外，代理身份本身始终是单租户的，只能在创建它的租户里被签发令牌；跨租户的是蓝图，以及由它在各个租户分别生成本地身份的能力。
可继承权限跨租户也照用。原租户的蓝图开了这个口子，等蓝图主体被拉进另一个租户时把权限同意掉，那边生出来的代理身份就能继承。
这里有个要留意的点：谁能拿到蓝图凭据（凭据在原租户管着），谁就能在对方租户里冒充蓝图主体登录。而蓝图主体的令牌里总有 AgentIdentity.CreateAsManager，所以它还能在这张蓝图下面继续造新代理身份。
拿这样的代理身份一登录，继承的权限就活了，对方租户里也能直接用。例子里就是靠这个用上了 Group.Read.All。

04 攻击链

测下来看，Agent ID 是一批新的、底子还是服务主体的身份，行为跟老的应用注册、企业应用不一样。微软虽然封了些高权限角色和 API 权限，但代理身份照样可能握着危险权限，所以它能被塞进提权链条，最后一路干到租户沦陷。
下面两个例子，都是攻击者怎么把某个代理身份拿到手的路子，一个是凭据注入，一个是诱导目标点链接。

4.1 案例一：凭据注入

这里的情形是，攻击者先拿下了一个蓝图已登录的会话，走完认证流程后拿 Global Administrator

1、拿宿主应用的 refresh token

PS> $tokensTmp = Invoke-Auth -ClientID 'c44b4083-3bb0-49c1-b47d-974e53cbdf3c' -RedirectUrl 'https://startups.portal.azure.com/auth/login/' -Origin 'https://doesnotmatter'

PS> $tokensTmp.refresh_token

拿到 access_token 和 refresh_token，只使用其中的 refresh token

ClientID 对应的是 Azure Portal，完整对照表可以在 entrascopes.com 里查
RedirectUrl 是门户已注册的回调之一
Origin 只是请求头，值不参与判定

2、拿 Graph 访问令牌

借 Azure 门户的那张 refresh token，换一张属于另一个应用（“应用注册” blade）的 Graph 访问令牌。

5、利用继承来的权限

例如上文提到的 RoleAssignmentSchedule.ReadWrite.Directory 角色

这个蓝图所有者往蓝图里加个凭据，拿它登进关联的代理身份，再用这身份的权限把自己升成 Global Administrator

从这个案例来看，代理身份把传统应用的三件事拆给了三个不同的对象：谁能创建（蓝图创建权）、谁能配置凭据（蓝图 owner）、谁能授予权限（管理员同意）。攻防的着力点从拿到一个角色变成分别打到这三条线上的薄弱点。

4.2 案例二：钓鱼

诱导用户点击也能拿代理身份来打。套路跟以前对服务主体搞的点击同意来钓鱼差不多，只不过在 Entra Agent ID 里玩法会多几步

1、新建代理蓝图

1、攻击者在已控制的租户里配置一个代理蓝图，把想要的权限填进需要访问的资源，再对 Graph 开 allAllowed，让蓝图能往下继承权限。

2、钓鱼链接

2、然后编一条带着蓝图应用 ID 的同意链接，发给别家组织里的管理员。管理员一同意，受害租户里就建出了蓝图主体，权限也跟着给了。
对于代理身份来说，授权过程与 OAuth 应用程序的授权过程是差不多的。攻击者搞一个钓鱼链接，让受害者管理员去点。

`https://login.microsoftonline.com/{tenant}/v2.0/adminconsent?`  
`client_id={blueprint_id}`  
`&scope=https://graph.microsoft.com/.default`   
`&redirect_uri={redirect_uri}`

受害者访问链接后，如果是点的同意，相当于把外面的蓝图加进自己组织。
同意得点两次：一次是同意在本租户建出蓝图主体，一次是把蓝图要的权限在蓝图主体上授权。

user consent 只对委派权限生效；蓝图申请的应用权限（.default）始终要管理员同意，且受 verified publisher 约束。如果受害者管理员做了这个设置，普通用户也能同意

https://login.microsoftonline.com/925c2cd8-xxxx-xxxx-xxxx-1257ffd75334/adminconsent?client_id=298c659a-f715-41c1-a5dd-c29f6a022a18
管理员只要点了链接、把蓝图和权限都同意掉，受害租户里就多了一个蓝图主体。

受害者同意后，受害者的客户端中会创建一个蓝图主体

默认拥有的权限 AgentIdentity.CreateAsManager 会允许创建代理身份，所以攻击者可以在受害租户里顶着蓝图主体登录，再一个接一个造子代理身份。

4.3 两条链的共同点

总结下来如果把这条链和 MC1506733 放在一起看，结论确实有点不好看。从实际攻击场景来看，公告改变的方向主要是在搭建成本，过去我要建一张蓝图得先有相应角色，但现在任何一个被钓到的普通账号就能建蓝图了。而且创建者自动成为 owner，连给自己加凭据都不需要额外授权。
在受害者方面，两次同意相当于 inheritable permissions ，之后的操作落地到蓝图主体上，流水线反复造一个造令牌，造一个子身份就相当于复制一份继承权。此后每一次访问都不再需要任何人同意。

05 检测

5.1 检测优先级

既然存在这个盲区，检查时按以下优先级排：
1）首先是蓝图上的新凭据，特别是联合身份凭据，多出来的不是你能对上账的部署，就是被人埋了后门。
2）其次是蓝图创建的行为，多出来的蓝图不在正常供给流程里，或创建者根本不是常规主体。
3）而后是 AgentIdentity.CreateAsManager 被用在不该用的地方
4）还有蓝图层面的同意：新 OAuth 权限一落到蓝图上，底下所有子对象全跟着继承。

5.2 查询与判读

查蓝图上的新增凭据

在 Entra 审计日志里筛选创建应用对象和给应用对象加凭据这两类动作，再把范围缩小到 Agent ID 相关对象上，从而找出谁创建了蓝图、谁给蓝图加了密钥。KQL 查询语句如下

AuditLogs | where OperationName has_any ("Add application", "Update application", "Certificates and secrets management") | extend TargetAgentType = tostring(TargetResources[0].agentType), BlueprintId = tostring(TargetResources[0].blueprintId) | where TargetAgentType == "agenticApp" or isnotempty(BlueprintId) | extend Actor = iff(isnotempty(tostring(parse_json(tostring(InitiatedBy.user)).userPrincipalName)), tostring(parse_json(tostring(InitiatedBy.user)).userPrincipalName), tostring(parse_json(tostring(InitiatedBy.app)).displayName)) | project TimeGenerated, OperationName, Actor, BlueprintId, TargetAgentType, Result, CorrelationId | sort by TimeGenerated desc

查蓝图的创建

蓝图创建时走创建时走这条操作 OperationName == "Add application"、agentType = agenticApp 这是判断该对象是 Agent 蓝图的标志

AuditLogs | where OperationName == "Add application" | extend TargetAgentType = tostring(TargetResources[0].agentType) | where TargetAgentType == "agenticApp" | extend Actor = tostring(parse_json(tostring(InitiatedBy.user)).userPrincipalName), ActorIP = tostring(parse_json(tostring(InitiatedBy.user)).ipAddress) | project TimeGenerated, Actor, ActorIP, TargetResourceName = tostring(TargetResources[0].displayName), Result, CorrelationId | sort by TimeGenerated desc

查每个蓝图造了多少个子身份

子 agent identity 本质就是服务主体，创建时走这条操作 OperationName == "Add service principal"、agentType == "agenticAppInstance"：这是子身份的标记

AuditLogs | where OperationName == "Add service principal" | extend AgentType = tostring(TargetResources[0].agentType), BlueprintId = tostring(TargetResources[0].blueprintId) | where AgentType == "agenticAppInstance" | summarize AgentsCreated = count(), FirstSeen = min(TimeGenerated), LastSeen = max(TimeGenerated) by BlueprintId | sort by AgentsCreated desc

查子 Agent identity 拿令牌的登录记录

查的是子身份用换取资源令牌（例如案例中的 Graph 令牌）的记录，主要是看结果返回的appId（子身份）、resourceDisplayName（它申请了哪个资源的令牌）

GET https://graph.microsoft.com/beta/auditLogs/signIns?$filter=signInEventTypes%2Fany(t%3A%20t%20eq%20%27servicePrincipal%27)%20and%20agent%2FagentType%20eq%20%27AgentIdentity%27%20and%20createdDateTime%20ge%202026-11-16T00%3A00%3A00Z&$top=50&$orderby=createdDateTime%20desc&$select=createdDateTime,appDisplayName,appId,ipAddress,status,resourceDisplayName,agent
