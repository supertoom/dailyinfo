早在 2017 年，我就对 Windows 上的 Oracle VirtualBox 做过一些研究。具体来说，我重点关注了它用于保护其虚拟机进程免受宿主机用户影响 mechanisms。该保护机制用于控制谁可以打开内核驱动程序，而由于其设计方式，这可能会导致权限提升。当时我发现了 3 种绕过该保护的方法，此外还在 2020 年报告了 COM 运行时中的一个额外问题。这些问题均已记录在这篇文章中。

时间快进到 2026 年，我决定再次研究 VirtualBox，看看它是否发生了很大变化。这一次，我发现了 3 个针对受保护进程的新绕过方法，另外还有一个漏洞：由于 Windows 发生变化，对 2020 年绕过方法的修复失效了。 在这篇博文中，我想重点讨论一个具体问题 CVE-2026-87268。它滥用了 .NET Framework 的一个特性；该特性与 VirtualBox 实现的 DLL 加载器钩子结合后，可以绕过检查，并使我能够将任意代码加载到受保护进程中。让我们先深入了解该问题在 .NET 中的根本原因，然后再讨论如何利用它在 VirtualBox 中实现绕过。

.NET 程序集加载

.NET Framework 在绕过进程加固方面非常有意思，因为只要仅使用托管代码，它就支持从内存缓冲区加载程序集。如果受保护进程通过验证哪些 DLL 可以或不可以加载来维护安全，这显然很有用，因为这样可以绕过传统的映像映射过程。由于 .NET 运行时的实现带有 Microsoft 签名，因此这类检查通常会允许加载它。

从内存缓冲区加载的标准方式是使用 Assembly::Load 静态方法，它接受一个字节数组。但这确实要求你先运行一些 .NET 代码，或者找到一个困惑代理来替你完成这项工作。我在 2017 年曾使用这个 API 方法绕过 VirtualBox的进程加固；当时我能够通过 JScript 脚本引擎访问该 API，最终发布了通用的 DotNetToJScript 工具。

我一直以为，从内存缓冲区引导加载任意 .NET 代码的上限就在这里。如果尝试从文件加载 .NET 程序集，它会将其映射为映像节区，从而触发任何 DLL 加固检查，并阻止加载未签名且不受信任的二进制文件。然而，在一个“糟了”的瞬间，我意识到自己从未验证过这一行为是否属实，于是决定看一看。

将 .NET 程序集映射到内存中最重要的函数似乎是 PEImageLayout::Map，在实现运行时的 CLR.DLL 第 4 版中，其大致如下：

PEImageLayout *PEImageLayout::Map(HANDLE file) {
  PEImageLayout* image = new MappedImageLayout(file);
  if (!image->Image) {
    image = new FlatImageLayout(file);
  }
  if (image->Image) {
    if (!PEDecoder::CheckFormat(image->Image))
       ThrowWin32(ERROR_BAD_EXE_FORMAT);
  }
  return image;
}

有趣的是，这段代码会基于文件创建一个 MappedImageLayout 对象。如果失败，它会退回到使用另一个对象 FlatImageLayout。这些名称多少透露了它们的用途，但为了确认，我们来看一下这些构造函数的实现：

void MappedImageLayout::MappedImageLayout(HANDLE file) {
  HANDLE mapping = CreateFileMapping(file, nullptr, SEC_IMAGE | PAGE_READONLY);
  if (mapping) {
    this->Image = CLRMapViewOfFileEx(mapping);
  } else {
    if (GetLastError() != ERROR_BAD_EXE_FORMAT)
      ThrowLastError();
  }
  
  DWORD policy = 0;
  if (EEConfig::EnforceCodeIntegrity() 
   || (SUCCEEDED(WldpGetLockdownPolicy(nullptr, &policy, nullptr)) 
   && !WLDP_LOCKDOWN_IS_OFF(policy) && !WLDP_LOCKDOWN_IS_CONFIG_CI(policy))
  ) {
     ThrowWin32(ERROR_BAD_EXE_FORMAT);
  }
  // ...
}

MappedImageLayout 的构造函数使用 CreateFileMapping API 将文件句柄转换为节区对象。代码传入 SEC_IMAGE 标志，指示内核假定该文件是 PE 可执行文件，并创建一个映像节区对象，其中包含映射到可执行内存页面的内容。任何依赖验证映像签名或位置的保护机制都可以收到通知并采取适当行动。然而，如果 CreateFileMapping 调用失败，代码会检查最后错误是否为 ERROR_BAD_EXE_FORMAT；如果不是，则抛出异常并彻底终止加载。

这里还会额外进行一次检查，确认是否通过 Windows Lockdown Policy (WLDP) API 强制执行了“Code Integrity”。该检查会查看是否启用了“Dynamic Code Security”代码完整性策略，或者是否强制执行了 User Mode Code Integrity (UMCI) 策略。如果启用了，就会抛出错误并终止加载过程。等该项检查变得相关时，我们会再回来讨论。

假设映射因 ERROR_BAD_EXE_FORMAT 错误而失败，那么加载过程会继续，转而创建一个 FlatImageLayout 对象：

void FlatImageLayout::FlatImageLayout(HANDLE file) {
  HANDLE mapping = CreateFileMapping(file, nullptr, PAGE_READONLY);
  if (mapping) {
    this->Image = CLRMapViewOfFileEx(mapping);
  } else {
    ThrowLastError();
  }
  // ...
}

这个构造函数更简单，只是调用 CreateFileMapping，而不设置 SEC_IMAGE 标志。因此，该文件会作为纯数据节映射到内存中。它没有可执行页，但这对 .NET 来说无关紧要。最后一项检查位于第一个代码片段中，它会调用 PEDecoder::CheckFormat 来验证 PE 文件是否有效；如果无效，则抛出异常。

由此可以得出，如果我们能让 .NET 加载一个有效的程序集文件，同时让首次调用 CreateFileMapping 因 ERROR_BAD_EXE_FORMAT 错误而失败，就能够使其从内存中执行该文件。任何预期检查已加载映像节的保护代码都不会察觉这次加载，而不受信的任意代码将被执行。

请注意，此行为似乎仅适用于 .NET Framework v4，而不适用于较旧的 .NET Framework，例如 v3.5 和 v2。根据我的了解，在早期框架中，尽管可以用同样的方式绕过这项检查并创建 FlatImageLayout 对象，但运行时会在加载过程的后续阶段将程序集传递给 LoadLibrary API，届时加载将失败。我没有花太多时间检查这是否可以绕过，因为较旧的 .NET Framework 默认已不再安装，在最新版本的 Windows 11 中甚至也未作为可选组件包含。出于类似原因，我也未调查现代 .NET 运行时（v5 及更高版本）是否存在类似行为。

VirtualBox DLL 加载钩子

既然我们已经找到一条可能利用 .NET 绕过进程加固映像检查器的路径，接下来就深入研究它是如何在 VirtualBox 中被利用的。之前的博客文章介绍过，Windows 上的 VirtualBox 会向 DLL 加载器添加钩子，以阻止不受信的映像加载到进程中。就我们的目的而言，重要的钩子连接到 NtCreateSection 系统调用；CreateFileMapping 会在底层调用它来创建映像节对象。以下是钩子函数的开头：

NTSTATUS supR3HardenedMonitor_NtCreateSection(PHANDLE phSection, 
                                     ACCESS_MASK fAccess, 
                                     POBJECT_ATTRIBUTES pObjAttribs,
                                     PLARGE_INTEGER pcbSection, ULONG fProtect, 
                                     ULONG fAttribs, HANDLE hFile) {
  bool const fExecProt = (fProtect & 
         (PAGE_EXECUTE | PAGE_EXECUTE_READ | PAGE_EXECUTE_WRITECOPY | 
          PAGE_EXECUTE_READWRITE)) != 0;
  if (hFile != NULL && hFile != INVALID_HANDLE_VALUE) {
    bool const fImage    = RT_BOOL(fAttribs & (SEC_IMAGE | SEC_PROTECTED_IMAGE));
    bool const fExecMap  = RT_BOOL(fAccess & SECTION_MAP_EXECUTE);
    if (fImage || fExecMap || fExecProt) {
      bool fCallRealApi;
      NTSTATUS rcNt = supR3HardenedScreenImage(hFile, fImage, 
                          true /*fIgnoreArch*/, &fAccess, &fProtect, 
                          &fCallRealApi, "NtCreateSection", 
                          true /*fAvoidWinVerifyTrust*/, NULL /*pfQuiet*/);
      if (!NT_SUCCESS(rcNt))
        return rcNt;
      if (!fCallRealApi)
        return STATUS_TRUST_FAILURE;
    }
  }

  NTSTATUS rcNtReal = g_pfnNtCreateSectionReal(phSection, fAccess,
                pObjAttribs, pcbSection, fProtect, fAttribs, hFile);
// ...

如果 NtCreateSection 调用请求可执行节，例如通过 SEC_IMAGE 标志请求，那么该文件会被传递给 supR3HardenedScreenImage 支持 API；该 API 会检查 PE 文件是否符合 VirtualBox 的加载条件，只有检查成功或文件未作为可执行映像映射时，才会调用原始的 NtCreateSection 系统调用。重要的是，FlatImageLayout 中的 CreateFileMapping 调用不会触发这些检查，因为它并未请求映像或可执行映射。

为了让 CreateFileMapping 设置 ERROR_BAD_EXE_FORMAT 这个最后错误，NtCreateSection 需要返回 STATUS_INVALID_IMAGE_FORMAT。我们有两种方式返回此状态码：通过 supR3HardenedScreenImage 的返回码，或通过调用原始系统调用。看看加固代码是否确实能够返回此状态码？

static NTSTATUS supR3HardenedScreenImageCalcStatus(int rc) {
    if (rc == VERR_LDR_ARCH_MISMATCH)
        return STATUS_INVALID_IMAGE_FORMAT;

    return STATUS_TRUST_FAILURE;
}

结果表明，可以。映射内部错误代码到状态时，supR3HardenedScreenImage 函数可以返回此错误代码。具体而言，如果错误代码为 VERR_LDR_ARCH_MISMATCH，那么 supR3HardenedScreenImage 将返回 STATUS_INVALID_IMAGE_FORMAT。因此，是什么设置了 VERR_LDR_ARCH_MISMATCH？

This error is set in the PE parser implementation in VirtualBox, specifically in the rtldrPEOpen API. This is reachable via RTLdrOpenWithReader which is called by the supHardenedWinVerifyImageByHandle function which itself is called by supR3HardenedScreenImage.

长话短说，由于解析器的调用方式，当 PE 文件的架构与主机架构不匹配，但 PE 文件包含可执行节时，就会返回 VERR_LDR_ARCH_MISMATCH 错误。事实证明，这一点正合适：当我们将仅包含托管代码的 .NET 程序集编译为 AnyCPU, 时，它会生成一个 32-bit x86 PE 文件，以便能在任何系统上运行。这样做是为了兼容性：64-bit（或 ARM64）Windows 系统可以将 32-bit PE 文件映射为映像，但反过来则无法保证。然而，如下方 dumpbin 工具的输出所示，该文件包含可执行代码，可选头中的 size of code 字段对此作了标识。

因此，要让映像强化检查返回 STATUS_INVALID_IMAGE_FORMAT，我们只需将任意 .NET 程序集编译为 AnyCPU，它就会绕过 VirtualBox 的映像检查，而无需改动文件格式。关键在于，由于该 .NET 程序集 DLL 未被修改，它仍然是有效的程序集，可以由 FlatImageLayout 类加载，从而实现代码执行。

拼图的最后一块是如何让程序集 DLL 被加载到 VirtualBox 中？仅通过 LoadLibrary 促使 DLL 被加载是不够的，我们需要让 .NET 将该文件作为程序集文件加载。通过 COM 劫持很容易实现这一点。我们可以针对一个已知会被强化的 VirtualBox 进程加载的类，将 .NET COM 注册项写入当前用户的注册表配置单元。然后启动一台虚拟机，它会加载该 COM 对象，进而加载 .NET 运行时，最终加载我们不受信任的程序集。完整 PoC 可在问题跟踪器中找到。

还有一个小的注意事项，我尚未提及 WLDP 检查。对于 VirtualBox 而言，此检查不太可能产生影响；只有当 Windows 配置了启用 Dynamic Code Security 或 UMCI 选项的代码完整性策略时，它才会适用。系统可能存在此类策略，同时也允许 VirtualBox 自身的二进制文件运行，但这种可能性似乎不大。

VirtualBox 修复了该问题，不再从 supR3HardenedScreenImageCalcStatus 方法返回 STATUS_INVALID_IMAGE_FORMAT。他们还引入了新代码，通过在 COM 中使用未公开的全局选项来禁用对当前用户注册表配置单元的查找，从而更难劫持 COM 对象。

攻击 WDAC 和受保护进程

读到这里，你或许会 wondered .NET 的这种行为是否普遍适用于 Windows 代码完整性强制机制。例如，Windows Defender Application Control（WDAC）和受保护进程都依赖内置的代码完整性机制来阻止不受信任的 DLL 被加载；它们是否容易受到攻击？

是的，前提是能找到一种方法让 NtCreateSection 返回 STATUS_INVALID_IMAGE_FORMAT，从而迫使 .NET 使用 FlatImageLayout 选项。在 VirtualBox 中，由于 NtCreateSection 挂钩对未经修改的 .NET 程序集文件的处理方式，可以诱导出现这种情况。

对于内置代码完整性机制，没有可供滥用的用户模式挂钩，只有对 NtCreateSection 的调用。我们需要能够从系统调用中诱发 STATUS_INVALID_IMAGE_FORMAT 状态码，同时做到：a) 不会首先触发代码完整性检查；b) 生成的映像不会因无效而无法由 .NET 加载。后一个问题似乎最为棘手：签名验证很可能只会在文件被验证为有效 PE 映像后才运行，但如果过多修改文件，.NET 就会拒绝加载它。

我们可以编写一个简单的测试工具，先用文件调用 NtCreateSection，如果失败，再用 STATUS_INVALID_IMAGE_FORMAT 调用 Assembly::Load，传入文件路径以加载并查看是否成功。随后你就可以编写模糊测试工具来寻找合适的修改，或者直接手动研究这种文件格式。

我发现，几乎可以轻易地创造所需条件。如果清除 COFF File Header 的 Characteristics 标志字段中的 IMAGE_FILE_EXECUTABLE_IMAGE 标志，那么 NtCreateSection 将无法把该文件作为映像节加载，但 .NET 在加载 PE 文件时会忽略这一点。只需更改这一位，就足以加载不受信任的 .NET 程序集。

正是在这种情况下，WLDP 检查变得重要。如果企业正在部署 WDAC 代码完整性策略，那么他们很可能启用了 UMCI 或 Dynamic Code Security 选项，而这些选项会阻止此类攻击。Dynamic Code Security 选项默认未启用，而且由于它会禁用 .NET 中的所有动态代码加载，包括 Assembly::Load 的字节数组版本，因此可能导致重要应用程序无法正常运行。

不过，UMCI 是部署 WDAC 策略的主要原因之一，因为它限制了允许运行哪些用户模式代码。尽管如此，我还是决定针对 Windows 11 S Mode 的安装版本尝试此攻击；该版本确实启用了 UMCI，但未启用 Dynamic Code Security。

为了进行测试，我需要强制 .NET 加载该程序集文件。在 Windows 11 S Mode 中，你可以运行许多内置 .NET 实用工具，它们会从命令行接受程序集。例如，可以使用 Assembly Registration Tool 加载 .NET 程序集，并调用开发者定义的任意注册和注销函数。例如，将以下代码编译为 .NET 程序集，并把你自己的代码添加到 UnregisterFunction 中：

using System;
using System.Runtime.InteropServices;

public class ComClass
{
   [ComUnregisterFunction]
   public static void UnregisterFunction(Type t)
   {
      //Insert code here.
   }
}

修改生成的程序集以移除 IMAGE_FILE_EXECUTABLE_IMAGE 标志。你不需要修正映像校验和等其他内容；只需用十六进制编辑器更改一个位。然后，你可以把修改后的程序集 DLL 的路径传给 .NET 运行时目录中的 RegAsm 可执行文件。请注意，应传入 /unregister 选项以运行 UnregisterFunction，因为注销不需要管理员权限。

C:\Windows\Microsoft.NET\Framework64\v4.0.30319\regasm.exe c:\path\to\assembly.dll /unregister

理论上这应该会失败，但实际上并没有。即使启用了 UMCI，修改后的程序集仍被加载到内存中并执行了任意代码。事实证明，WLDP 检查存在错误，至少在仅启用 UMCI 时如此。它检查策略标志是否不等于已设置 WLDP_LOCKDOWN_CONFIG_CI 标志的状态，而后者表示：

WLDP_LOCKDOWN_DEFINED_FLAG | 
   WLDP_LOCKDOWN_CONFIG_CI_FLAG | 
   WLDP_LOCKDOWN_UMCIENFORCE_FLAG

遗憾的是，这恰好是 Windows 11 S Mode 中 WldpGetLockdownPolicy 返回的标志设置。因此，检查会通过并继续加载，随后便绕过 UMCI 强制策略。

对于默认安装的 Windows 中的受保护进程，WLDP 检查甚至不会发挥作用。实际上，.NET 同样应当检查受保护状态，但它并未这样做。还应指出，你只能利用 Protected Process Light（PPL）进程。原有的 Protected Process（PP）要求 DLL 在其 Authenticode 签名中包含页哈希，而 .NET 运行时 DLL 缺少这些哈希。因此 .NET 无法加载，我们也无法到达存在漏洞的代码。

对于受保护进程，你还可以再次滥用 COM 劫持。我发现 WerSecureFault.exe 会在运行时加载一个 COM 对象，因此通过劫持该注册项并使用修改后的 .NET DLL，我可以在无需管理员权限的情况下，以 TCB 级别在 PPL 中获得任意代码执行。

向 Microsoft 报告

当我弄清楚如何滥用这一行为后，我 wondered 这个漏洞是否需要提交给 Microsoft 修复。根据 MSRC Security Servicing Criteria，任何 PPL 绕过都不在处理范围内。WDAC 是受支持的安全边界，不过引用其安全目标的话：“只有符合设备策略的可执行代码（包括由启用了脚本的 Windows 脚本宿主运行的脚本）才能运行……”这可以被解读为：如果存在某种可以启用的策略来阻止代码运行，那么该问题就不符合修复条件。

我原本以为 WLDP 检查是按设计工作的，真正禁用这一行为的是 Dynamic Code Policy。因此我决定不报告它，而是在 2026 年的 44Con 会议上做了演示。

然而，在与一些 .NET 开发者讨论该问题后，他们明确表示，尽管启用 Dynamic Code Policy 会阻止这一绕过，但那是出于偶然，而并非该策略的预期用途。他们要求我将它提交给 MSRC。遗憾的是，到 2026 年 9 月下旬，我已经在公开场合披露了它，因此它被当作零日漏洞处理，分配了 CVE-2026-108398，并于 2026 年 10 月修复，也就是报告后不到一个月。

修复方式是 将 WLDP 检查更正为如下内容：

DWORD policy = 0;
  if (EEConfig::EnforceCodeIntegrity() 
   || (SUCCEEDED(WldpGetLockdownPolicy(nullptr, &policy, nullptr)) 
   && !WLDP_LOCKDOWN_IS_OFF(policy) && WLDP_LOCKDOWN_IS_ENFORCE(policy))
  ) {
     ThrowWin32(ERROR_BAD_EXE_FORMAT);
  }

使用 WLDP_LOCKDOWN_IS_ENFORCE 具体来说是检查是否启用了 UMCI 并禁用从内存加载。但这不会改变 PPL 中的行为，因此它仍然应该可以被绕过。

结论

与我之前关于 Windows 上 VirtualBox 进程加固的研究一样，我能够复用这一绕过手法来利用 Windows 内置的代码完整性功能。在这个问题中，.NET 代码本意是遵守策略，只是开发者犯了一个错误。

遗憾的是，这一行为让我以为它不符合 MSRC 的安全服务标准，因此该漏洞最初并未被报告。虽然这些标准很有用，但在诸如此类预期行为不明确的情况下，这意味着一个真实问题可能不会被上报。我要感谢 .NET 团队如此迅速地推出修复。
