中文原文

稳定的 Linux 版本缺少现有的安全修复，是因为回移这些修复既耗时，又往往是一项得不到认可的工作。我们正在使用 Codex 将每个修复的回移流程从数天缩短到数小时，让人工补丁审查员能够快速为 Ubuntu Long Term Support、Fedora 和 Linux 内核等关键软件提交修复。截至 10 月 29 日，我们的项目已帮助将 149 个不同的 CVE 的修复交付到稳定的 Linux 内核版本中，并为 Fedora 和 Ubuntu 软件包交付了 若干 修复。

将修复部署到较旧的软件需要多个步骤，包括将修复适配到旧版代码、检查依赖关系，并确保修复没有引入新 bug。单项任务（例如追踪一个有问题的提交中的 bug）可能需要 一周或更长时间，而这些投入既不为人所见，也不被认可。

我们的 Codex 工作流减少了准备和审查修复所需的人工投入。不计项目特定的初始设置，准备并审查一项 straightforward 的回移大约需要 30 分钟的人工关注；更复杂的情况则可能需要约三个小时。该工作流采用双轨方式：智能体负责识别缺失的修复、适配补丁、收集验证证据、运行测试和准备提交材料包，工程师则审查补丁并将其提交给维护者。

这些估算仅涵盖补丁准备和审查；回归测试和维护者验收仍然必不可少。但人工投入的减少，使大量原本被忽视的安全工作变得切实可行。补丁积压量很大，但我们现在有了一种可行的处理方式。

我们必须在稳定性和安全性之间做出选择吗？

软件存在 bug，而我们会在力所能及时尝试修复。修复首先会应用到软件的最新版本中。遗憾的是，那往往也是修复唯一落地的地方。

回移是将修复从最新源代码移植到旧版本的过程。对于知名且关键的 bug，修复确实通常会很快得到回移。但许多其他 bug 的回移流程从未发生。其原因不难理解：软件打包通常由已经超负荷工作的志愿者完成，而回移既繁琐又得不到认可，几乎没有功劳或曝光度。对于由志愿者团队组成的开源项目，回移（可以理解地）优先级较低。正如 XFS 开发者 Dave Chinner 曾描述的，这项工作“实际上相当于一份全职工作”，但若没有充足资源，就根本无法完成。

缺少回移是一个问题，因为几乎没有人运行刚刚用今天的代码变更构建出来的最新最优版本。人们绝大多数更倾向于使用略旧、经过更多测试、以“长期稳定”版本形式打包的软件。例如，约 95% 的 Ubuntu Linux 安装都是 Long Term Support（LTS）版本。查看 Debian 的 popcon 中已安装的 Linux 内核软件包，绝大多数都基于较旧的稳定分支：

用户面临一个选择：要么继续使用稳定且熟悉的软件版本，尽管其中存在安全漏洞；要么升级到修复了这些漏洞的新版本，但这会引入其他变化以及他们可能并不想要的新功能。

许多人故意不更新到新版本；我认为这完全合理，也是普通终端用户的正常行为。就在最近，我将我的 Mac 更新到了 macOS 27，却无法使用一台多年来一直运行正常的打印机（直到 Codex 编写了一个新的兼容打印机驱动程序）。类似情况实际上需要使用较旧的软件。

我们不应该被迫在稳定性和安全性之间做出选择。

数千个已知 CVE 缺乏稳定分支修复

大量具备网络攻击能力的 AI 代理可以像热刀切黄油一样，突破由稳定且已知存在漏洞的软件构成的网络。问题的规模之大，以至于你当前运行的软件很可能包含尚未修复的安全漏洞，而现代 AI 代理可以利用这些漏洞。随着 AI 辅助的漏洞挖掘让识别旧代码中的漏洞变得更容易，减少这一积压问题正变得愈发重要。这并非只是理论问题。最近引人关注的漏洞 CVE-2026-98432（Linux TCP 栈中一个可远程利用的严重漏洞）的修复，在上游完成修补数周后仍未进入发行版内核。该漏洞足够引人注目，因此很快就会在所有地方得到修复。但较为冷僻漏洞的修复永远不会向后移植。我在自己的沙箱逃逸研究中注意到了这一点，稳定软件中的一个旧漏洞被用作最近披露的 OpenAI 黑客事件的一部分。

让我们量化一下缺失向后移植问题的规模。为简化统计，我们可以将范围限定为已知漏洞（已分配 CVE），这些漏洞已在最新版本中得到修复，但稳定软件包中仍然缺失。在本例中，我们将查看 Linux 内核、Ubuntu 26.04 LTS 和 Debian 13 Stable。我并不是要特别针对这些项目——它们的运行都非常好！我使用它们是因为它们有相关文档，并且会核算未修复的 CVE。其他项目则缺乏这种透明度。

让我们按稳定分支查看 Linux 内核中尚未修复的 CVE 数量。下表显示了每个受支持的稳定分支中未在该分支得到修复、但已在较新分支中得到修复的 CVE。（因此，从定义上说，较旧的分支会有更多未修复的 CVE。）数据来源为截至 2026 年 9 月 18 日的内核 CVE 团队的 vulns.git。由于若干技术因素，这并非精确的漏洞数量，既会高估，也会低估。它也不是可利用性的衡量指标。更确切地说，它是一把标尺，表明有相当数量的已知 CVE 尚未在稳定内核分支中得到修复：

工程师和 AI 可以加速补丁回移

我们意识到这是一个问题，并已开始主动修复。首先，我们从类似于在人行道上捡钱的事情做起：有一些针对已知 CVE 的漏洞修复可以干净地应用到稳定内核树中，但这些修复从未被合入内核。我们使用 Codex 和 GPT-5.6 找到了这些修复，并请维护者应用现有补丁。他们也欣然照做了。随后，我们开始回移无法直接应用的补丁，从最简单、最便于验证和审查的补丁入手，并逐步转向更复杂的更改。目前，稳定树中已应用 149 个 CVE 修复；我们回移跟踪器上的清单还在不断增长。

我们也对 Linux 发行版做了同样的工作：我们使用 Codex 和 GPT-5.6 识别出随发行版提供的稳定软件包中的已知漏洞，然后回移并验证修复。我们已经开始联系 Linux 发行版，并提供第一批补丁。

如果你维护开源项目或 Linux 发行版，并希望获得安全修复回移方面的帮助，请在 trailofbits.com/patch-the-planet 提交申请，我们将很乐意提供协助。

不添加新功能的稳定软件的最大优势在于，理论上，我们可以在攻击者利用漏洞之前修复它们。因此，让我们继续修补这个星球吧！
