Elastic 披露 Java4Shell 远程代码执行漏洞 CVE-2026-114938 的影响与缓解措施

Java4Shell Remote Code Execution (RCE) Vulnerability - CVE-2026-114938

AI 导读

Elastic 确认 CVE-2026-114938 影响 OpenJDK 和 Oracle Java SE，并波及 Elasticsearch 7.17.3 及以上版本与 Logstash 8.6.2 及以上版本。

同一件事，精选收录的是《OpenJDK 披露 Base64 解码远程代码执行漏洞 CVE-2026-114938》

正文 · AI 翻译
中文原文

Elastic 已知晓一个影响 OpenJDK 和 Oracle Java SE 的远程代码执行漏洞（CVE-2026-114938，又称 Java4Shell），该漏洞于 2026 年 11 月 17 日披露。 

Elastic 将持续关注新出现的信息，并会在适用且信息可得时发布更多详情。

受影响组件

Elasticsearch

Elastic 已确认 Elasticsearch 7.17.3 及更高版本受此 CVE 影响，但存在一些缓解因素。该漏洞只能由至少拥有“读取”权限的已认证用户在受影响的 CPU 架构上利用，以实现远程代码执行（RCE）；未认证攻击者则可对 Elasticsearch 节点发起拒绝服务（DoS）攻击。 

Elastic 还在准备通过将捆绑的 JDK 更新至 27.0.1.1+4 来修复此漏洞。预计该修复将随即将推出的 Elastic 8.19.26、9.4.10、9.5.7 和 9.6.0 版本发布。

Logstash

Elastic 已确认 Logstash 8.6.2 及更高版本受此 CVE 影响。Logstash 7.17.x 以及 8.6.2 之前的版本目前不受影响。Logstash API、Ruby 插件和常见输入（如 Beats、HTTP 和 TCP）均不使用受影响的 Java 函数。 

在受影响的 CPU 架构上，该漏洞只能通过 Elastic Integration 过滤器（logstash-filter-elastic_integration）并且在 Elasticsearch 摄取管道对来自不受信任来源的事件进行 Base64 字段解码时利用。在这种情况下，能够向 Logstash 发送事件的未认证攻击者可对 Logstash 节点发起拒绝服务（DoS）攻击。 

Elastic 还在准备通过默认禁用受影响的 JVM 优化来修复此漏洞。预计该修复将随即将推出的 Elastic 8.19.26、9.4.10、9.5.7 和 9.6.0 版本发布。

Elastic Cloud Serverless

Elastic Cloud Serverless 仅在极少数与 CPU 架构相关的情况下存在漏洞。我们已于 11 月 18 日星期三部署热修复，以缓解这些罕见情况。 

Elastic 还针对 Elastic Cloud 基础设施中 CVE-2026-114938 的利用开发了检测规则；Elastic Information Security 团队会持续监控相关警报。 

Elastic Cloud Hosted

Elastic Cloud Hosted 部署中只有一小部分（约为 <5%）在 Microsoft Azure 上使用受影响的 CPU 架构；GCP 和 AWS 上的 Elastic Cloud Hosted 部署目前不受影响。 

鉴于在此运行环境中利用 CVE-2026-114938 的复杂性——包括必须成功完成身份验证——Elastic 正在部署配置变更，以缓解受影响主机上的此漏洞。 

Elastic 还针对 Elastic Cloud 基础设施中 CVE-2026-114938 的利用开发了检测规则；Elastic Information Security 团队会持续监控相关警报。  

Elastic Cloud Hosted 的缓解配置同样适用于自管客户，详情如下共享。Elastic 还在准备通过将捆绑的 JDK 更新至 27.0.1.1+4 来修复此漏洞。预计该修复将随即将推出的 Elastic 8.19.26、9.4.10、9.5.7 和 9.6.0 版本发布。

客户缓解建议

自管 Elasticsearch 客户的缓解措施

缓解方案 1

自管客户可以通过禁用受影响的 JVM 优化来缓解此漏洞。只有运行在 x86-64 CPU 上且支持 AVX512_VBMI 指令集的 Elasticsearch 节点受影响（例如 Intel Xeon Ice Lake 及更高版本，以及 AMD Zen 4 及更高版本）。目前，运行在 ARM CPU 和较旧的 x86 CPU 上的节点不受影响。 

要检查主机，请运行 grep -c avx512vbmi /proc/cpuinfo；结果大于 0 表示该主机受影响。 

要应用缓解措施，请在每个受影响节点的 config/jvm.options.d/ 目录中创建一个文件（例如 config/jvm.options.d/cve-2026-114938.options），其中包含单独一行 -XX:-UseBASE64Intrinsics，然后重启节点。Docker 用户可以将此文件挂载到 /usr/share/elasticsearch/config/jvm.options.d/，ECK 用户可以在 Pod 模板中将该选项添加到 ES_JAVA_OPTS 环境变量中。滚动重启可避免集群停机。要确认缓解措施已生效，请检查 GET _nodes/jvm 的输出中，每个节点的 jvm.input_arguments 是否都包含 -XX:-UseBASE64Intrinsics。 

客户仍应在包含更新后的捆绑 JDK 的版本发布后尽快进行升级。

缓解方案 2

下载最新的 JDK，并让 Elasticsearch 使用自带 JDK 的模式来运行。请注意，此缓解措施不适用于 Docker。 

自管 Elastic Cloud Enterprise (ECE) 客户的缓解措施

对于运行在存在漏洞的 CPU 架构上的 ECE 客户，升级至 ECE 4.2.2 / 3.8.7（发布后），然后重启所有部署，即可修复所有托管 Elasticsearch 集群中的此漏洞。

在 ECE 4.2.2 / 3.8.7 发布之前，可以使用 API 或高级编辑器将缓解性 JVM 标志注入每个集群。详情请联系支持团队。  

Elastic Cloud on Kubernetes (ECK) 客户的缓解措施

ECK Operator 不使用 Java，因此不受影响。ECK 管理的 Kibana、Beats、Elastic Agent、APM Server 和 Elastic Maps Server 不使用 Java，目前不受影响。

ECK 管理的 Elasticsearch 集群与其他自管 Elasticsearch 集群一样受到影响。只有运行在支持 AVX512_VBMI 指令集的 x86-64 CPU Kubernetes 节点上的 Elasticsearch Pod 受到影响。

要检查 Elasticsearch Pod 所在的节点，请运行：

kubectl exec <pod-name> -c elasticsearch -- grep -c avx512vbmi /proc/cpuinfo

结果大于 0 表示该节点受影响。Kubernetes 可以将 Pod 移至其他节点。如果节点池混合使用多种 CPU 类型，请对所有 x86-64 nodeSets 应用缓解措施。

要应用此缓解措施，请在每个受影响 nodeSet 的 podTemplate 中，将 ES_JAVA_OPTS 环境变量添加 -XX:-UseBASE64Intrinsics。如果 ES_JAVA_OPTS 已有值，例如用于设置堆大小，请将该选项添加到现有值的末尾。不要添加第二个 ES_JAVA_OPTS 条目。

spec:
  nodeSets:
  - name: default
    podTemplate:
      spec:
        containers:
        - name: elasticsearch
          env:
          - name: ES_JAVA_OPTS
            value: "-XX:-UseBASE64Intrinsics" # keep your existing options

应用此更改后，ECK 会自动逐一重启 Elasticsearch Pod（即滚动重启）。您无需手动重启 Pod。

要确认缓解措施已生效，请确保在 GET _nodes/jvm 输出中，每个节点的 jvm.input_arguments 都包含 -XX:-UseBASE64Intrinsics。

更新版本的捆绑 JDK 一可用，请立即升级到包含该 JDK 的发行版本。要升级，请更改 Elasticsearch 资源的 spec.version。升级后，您可以移除该选项。

ECK 上的 Logstash

只有当 Logstash 对攻击者可控的 Base64 数据运行 elastic_integration 过滤器时，才会受到影响。其结果是崩溃，而不是代码执行。要应用缓解措施，请在 Logstash 资源的 podTemplate 中，将 -XX:-UseBASE64Intrinsics 添加到 LS_JAVA_OPTS 环境变量。如果 LS_JAVA_OPTS 已有值，请将该选项添加到现有值的末尾。

spec:
  podTemplate:
    spec:
      containers:
      - name: logstash
        env:
        - name: LS_JAVA_OPTS
          value: "-XX:-UseBASE64Intrinsics" # keep your existing options

自托管 Logstash 客户的缓解措施

自托管客户可以通过禁用受影响的 JVM 优化来缓解此漏洞。只有运行在支持 AVX512_VBMI 指令集的 x86-64 CPU 上的 Logstash 节点会受到影响（例如 Intel Xeon Ice Lake 及更新版本，以及 AMD Zen 4 及更新版本）。根据我们目前的分析，运行在 ARM CPU 和较旧 x86 CPU 上的节点不受影响。

要检查主机，请运行 grep -c avx512vbmi /proc/cpuinfo；结果大于 0 表示该主机受到影响。

要应用缓解措施，请将单行 -XX:-UseBASE64Intrinsics 添加到每个受影响节点的 config/jvm.options 文件中，然后重启 Logstash。Docker 和 ECK 用户可以将该选项添加到 LS_JAVA_OPTS 环境变量。要确认缓解措施已生效，请检查 Logstash 启动日志中的 JVM 引导标志行是否包含 -XX:-UseBASE64Intrinsics。

客户仍应在包含更新后的默认配置的发行版本一可用时立即升级。升级后，不再需要手动设置。客户不得设置 -XX:+UseBASE64Intrinsics，因为这会重新启用受影响的优化。
