中文原文

攻击者于周一在 Hex.pm 的六台生产服务器上运行了操作系统命令。Hex.pm 是软件包注册中心，Elixir 和 Erlang 开发者会从中获取依赖项。

此次攻击所用的漏洞自 2016 年 2 月起就一直存在于该注册中心的代码中；在首次恶意请求出现后约 15 分钟内，维护该服务的团队便让所有服务器都运行了已修补的构建版本。

此后的检查未发现任何软件包被更改的迹象。团队表示，无法排除攻击者读取了账户数据（如电子邮件地址、密码哈希和双因素身份验证密钥）的可能性。

Hex 用户现在应该做什么

由于维护人员替换了用于签署会话和访问令牌的密钥，所有拥有 hex.pm 账户的用户都已被注销登录。他们建议账户持有人采取以下步骤：

  • 更改你的 hex.pm 密码。
  • 重新设置双因素身份验证：添加新的身份验证器条目，并保存新的恢复代码。
  • 使用 mix hex.user auth 重新登录客户端；对于 Erlang 项目，则使用 rebar3 hex user auth。
  • 等待下一个版本发布后更新 Hex 客户端，该版本预计将在数日内推出，并将采用新的注册中心签名系统。
  • 警惕网络钓鱼。已暴露的电子邮件地址可能会被滥用，因此请检查所有有关 Hex 的电子邮件中的链接是否指向 hex.pm。

据该团队称，无需替换 API 密钥：这些密钥是随机的 128 位值，仅以 HMAC-SHA256 哈希形式存储，团队表示实际上无法通过暴力破解获得。密码则使用 bcrypt 进行哈希处理，这会减慢猜测速度，但无法阻止对弱密码的猜测，因此修改密码仍然很重要。

报告作者之一 Peter Ullrich 在 Elixir Forum 的维护者澄清中表示，从未创建 hex.pm 账户、仅获取公共软件包的开发者无需重置任何内容。通过 GitHub 注册的用户仍应重新登录客户端；如果启用了双因素身份验证，也应重新设置。

在新客户端发布之前，建议仅从 repo.hex.pm 获取软件包，并避免使用第三方镜像。注册中心签名密钥尚未被替换，而它也是攻击者可能读取到的凭据之一。

该漏洞追踪编号为 CVE-2026-129514，CVSS 最高评分为 10.0。它位于 hex.pm 用于读取以 Erlang 数据格式发送的请求正文的解析器中。该解析器在路由和身份验证之前运行，因此，向站点上的任意地址发送未经身份验证的 POST 请求都能到达该解析器。

解码函数原本应当是安全的，并且确实会阻止诸如函数等危险术语，但它接受包含 __struct__ 键的映射，从而允许请求正文伪装成应用程序已加载的任意 Elixir 结构体。

本可阻止此问题的安全检查于 2016 年 2 月 23 日从代码中移除，这正是该漏洞存在已久的原因。目前尚未证实此次攻击在周一之前就已被利用。

精心构造的结构体本身不会执行任何操作。它会引发错误，而错误报告代码随后会检查该结构体。通过 Ecto 和 DBConnection 数据库库进行的这种检查，最终使服务器调用了攻击者选择的函数，该函数随后以注册中心服务账户的权限运行了操作系统命令。

安全公告将 hex.pm 列为受影响组件，受影响时间从 2016 年 2 月 23 日持续至星期一。修复提交使解码器拒绝任何包含带有 __struct__ 键的映射的 term，并且截至星期一 18:31 UTC，所有 hex.pm 服务器都已运行该修复。

Hex.pm 团队昨日在事件报告中表示，负载均衡器日志记录了星期一 18:16 至 18:29 UTC 之间的 69 次漏洞利用请求，这些请求全部来自两个地址。漏洞利用创建的文件出现在六台 web 服务器上，其中一次请求后仅 3 毫秒就出现了文件。攻击期间有三台服务器加入，当时一次重启让仍运行易受攻击构建版本的机器重新上线。

为检查这些包，团队将每个数据库表与首次漏洞利用请求前两分钟获取的副本进行了比较，并逐一追踪每项差异，确认均属于正常活动。攻击期间发布的 23 个版本全部与审计日志一致，没有较早的版本被更改，当晚写入的包和注册表文件也与数据库记录一致。

数据库读取、shell 命令、环境变量以及从文件存储直接读取的操作均未被记录。因此，团队写道：“我们无法排除攻击者访问了存储在数据库中的数据的可能性。”该数据库保存着电子邮件地址、密码哈希、API 密钥哈希、双因素身份验证密钥和会话数据，私有包也可能被读取而不留下任何痕迹。

检查未发现遗留的 shell，审计日志中也没有新账户或新的云密钥。攻击者身份尚不清楚。团队表示，这两个地址从上周晚些时候开始的活动表明，攻击者构建了 hex.pm 的本地副本用于测试。

一份描述同一漏洞的独立安全报告于星期一 19:07 UTC 通过电子邮件送达，此时攻击已经结束。截至昨日上午，团队已替换攻击者可能读取过的所有凭据，但注册表签名密钥除外。星期一晚上，团队向瑞典数据保护局、美国 CISA 和欧盟 ENISA 报告了此次数据泄露。

相关库修复

与此次事件同时，三个广泛使用的 Elixir 库的维护者披露了各自存在的漏洞，涉及使用不受信任数据构建的结构体，并于昨日发布了修复版本。这些属于独立披露的事件，并非针对 Hex.pm 的进一步攻击。

库 CVE 受影响版本 修复版本
ash CVE-2026-124283 3.31.3 至 3.38.0 之前（不含 3.38.0） 3.38.0
db_connection CVE-2026-133555 1.1.0 至 2.10.3 之前（不含 2.10.3） 2.10.3
flop CVE-2026-130411 从 0.8.0 开始，各分支中修复版本之前的版本 0.26.7, 0.27.3, 0.28.1, 0.29.2

每个漏洞都需要特定条件才能利用。根据Ash 公告，Ash 漏洞要求使用客户端提供的游标进行键集分页、使用某些排序字段类型，并且签名密钥仍保留未设置的默认值。

DBConnection 公告称，db_connection 漏洞“单独在 db_connection 中无法利用”，因为必须先由另一个组件将不受信任的数据解码为结构体。根据Flop 公告，Flop 漏洞在其分页游标方面存在类似条件。

被利用的漏洞位于 hexpm 服务器代码中，而非 Hex 客户端，因此自行运行注册表副本的组织在部署补丁之前都会受到影响。
