执行摘要

CVE-2026-123633 是 NGINX HTTP/2 中的一个释放后重用漏洞，可能允许未经身份验证的攻击者造成拒绝服务。在该 CVE 记录中，F5 表示，当地址空间布局随机化（ASLR）被禁用或绕过时，可能实现代码执行。

CVE-2026-123633 会影响接受 HTTP/2 客户端连接、将请求代理到后端且可用工作进程连接数较低的 NGINX 服务器。分片请求可能使一个活跃连接仍被标记为可重用。在连接压力下，NGINX 可能关闭该连接，并释放活跃请求仍在使用的内存。

F5 的 CVE 记录依据 CVSS 4.0 将该问题评为 9.2 严重。NGINX 安全公告页面将该问题标为中等，并列出 1.19.7 至 1.30.6 以及 1.31.0 至 1.31.8 版本受到影响。F5 在报告者名单中列出了memN0ps（Palo Alto Networks Unit 42）。

稳定分支中的 NGINX 1.30.7 和主线分支中的 1.31.9 包含此修复。F5 还列出了受影响的 NGINX Plus 版本。

管理员应审查 HTTP/2 反向代理暴露情况，并升级到已修复的 NGINX 版本或包含 CVE-2026-123633 修复的供应商软件包。

Palo Alto Networks 客户可通过以下产品和服务获得更好的保护，以应对上述威胁：

  • Cortex XDR 和 XSIAM
  • Cortex Agentic Endpoint Security

组织可通过 Unit 42 Threat Intel Services及其 Deep and Dark Web Service获取定制的对手情报、分析师直接咨询以及专门的暴露面追踪。

背景

在研究 NGINX 时，我独立发现了现已登记为 CVE-2026-123633 的 HTTP/2 连接状态缺陷。

未经身份验证的客户端可以发送分片的 HTTP/2 请求，使一个活跃连接仍被标记为可重用。当服务器在请求期间解析主机名且可用连接槽位较少时，NGINX 可能在请求进行中回收该连接，并释放其 DNS 解析器仍在使用的内存。

我在未经修改的 NGINX 1.31.7 和 1.31.8 源代码构建版本上，使用AddressSanitizer (ASan)复现了释放后重用问题。NGINX 安全公告页面列出 1.19.7 至 1.30.6 以及 1.31.0 至 1.31.8 版本受到影响，并将 1.30.7 和 1.31.9 列为已修复版本。

我私下向 F5 报告了这个 HTTP/2 释放后重用问题。F5 的 CVE 记录依据 CVSS 4.0 将其评为 9.2 严重，依据 CVSS 3.1 将其评为 8.1 高危。NGINX 安全公告页面将其标为中等。

在 Debian 客户机上的 ASan 测试中，ASan 在首次读取已释放的 DNS 查询内存时停止了 NGINX。

测试中的解析器路径源自登记为 CVE-2026-123633 的 HTTP/2 连接漏洞。CVE-2026-123634是另一个 DNS 解析器漏洞，已在同一版本中修复。

我还发现了一个会泄露 libc 指针的内存泄露漏洞。我利用该地址计算 libc 基址，并在将泄露问题与 CVE-2026-123633 串联时绕过 ASLR。我将这个额外漏洞作为单独问题报告给了 F5。从攻击者虚拟机出发，我成功在目标虚拟机上以非 root NGINX 工作进程身份实现了预身份验证远程代码执行。该利用链需要使用非默认的 NGINX 配置，且部分尝试未能打开 shell。

F5 将该内存泄露评估为仅出现在非典型配置下的行为，并且截至撰写时未为其分配 CVE，因此我略去相关细节和利用步骤。

连接状态缺陷的工作原理

当 NGINX 可以在压力下关闭某个连接时，会将其标记为可复用。一旦请求开始，流的创建应当清除可复用标记，但在受影响的版本中，ngx_http_v2_create_stream() 会让该标记保持设置状态。

当客户端仅发送部分 HTTP/2 HEADERS 帧头时，ngx_http_v2_handle_connection() 会将连接标记为可复用并提前返回。下面的代码展示了这一判断：

可复用标记使 NGINX 能够回收因部分帧而停滞的连接，避免它们耗尽 worker 的槽位。

随后客户端发送剩余的帧头字节。ngx_http_v2_create_stream() 创建一个活动流并递增活动流计数器，但返回时该可复用标记仍处于设置状态：

现在，NGINX 在一个连接上拥有活动请求，但其清理逻辑仍将该连接视为可复用。

1.30.7 和 1.31.9 中的修复会在创建流时通过 ngx_reusable_connection(h2c->connection, 0) 清除可复用标记。图 1 展示了受影响版本中的执行顺序：

  • 部分帧头会将连接标记为可复用
  • NGINX 创建流时该标记仍处于设置状态
  • 后续进行套接字分配时会回收该活动连接

触发 Resolver 释放后重用

过期的可复用标记使 NGINX 在需要空闲槽位时能够回收活动连接。在我的测试中，请求期间的 DNS 查询打开了一个新套接字并触发了回收。

我的测试使用了一条带有可变上游的 HTTP/2 代理路由。该变量求值得到一个主机名，它既不是字面量 IP 地址，也不是已配置的上游组，因此 NGINX 会在请求期间查询该主机名。该查询还必须打开一个新的 resolver UDP 套接字。

只有在 worker 没有针对所选名称服务器的套接字时，才会打开新的 UDP 套接字。已缓存的答复和正在进行的查询也会跳过我所测试的套接字分配回收过程。

打开 DNS 套接字需要一个连接槽位，因此 ngx_get_connection() 会先执行一次连接排空检查。当可用槽位降至 worker_connections 的十六分之一或更低，且至少存在一个可复用连接时，ngx_drain_connections() 就会执行一次。随后，该排空函数从可复用队列尾部选取条目，设置每个连接的关闭标志，并调用其读取处理程序：

1

2

c->close = 1;

c->read->handler(c->read);

我的测试客户端在完成帧后以零 linger 关闭了套接字，使 NGINX 在已重置的连接上仍保留着一个活动请求。当连接压力触发排空时，HTTP/2 读取处理程序试图在该套接字上发送 GOAWAY。

写入成功本会使请求继续运行，但写入因 Connection reset by peer 而失败，因此 NGINX 结束了该连接和请求。ASan 的释放栈经过 ngx_http_upstream_check_broken_connection()。

请求清理流程到达 ngx_resolve_name_done()，它会释放解析器状态，而原始查询仍持有指向该状态的指针。

ASan reported that NGINX read memory from a freed DNS lookup context. The free path ran through ngx_drain_connections(), ngx_http_v2_finalize_connection(), ngx_http_upstream_finalize_request() and ngx_resolve_name_done(). Source review showed that, if execution continues past the reported read, ngx_resolver_set_timeout() can also write ctx->event and ctx->ident through that stale pointer.

In the run where ASan reported the read, I split the 9-byte HEADERS frame header after 5 bytes. For the control, I sent the full frame header first and then the HPACK block. NGINX sent a DNS query and kept running. Figure 2 follows the calls from socket allocation to the use-after-free.

Test Setup and Limits

I ran the ASan test in an isolated Debian 13 guest. NGINX was built from official 1.31.7 and 1.31.8 source with Clang 19.1.7, HTTP/2, ASan and UndefinedBehaviorSanitizer. I sent the HTTP/2 requests over the guest's loopback interface.

For the 1.31.8 run, I set worker_connections to 16 and opened 13 filler connections that NGINX had not marked reusable. Table 1 shows the sanitizer results alongside the released-source review.

Limits

A source build includes the HTTP/2 module only when configured with --with-http_v2_module. Distribution packages commonly enable it.

The ASan evidence in this article comes from builds of 1.31.7 and 1.31.8 over loopback. The 1.31.8 test configuration set worker_connections to 16 instead of the documented default of 512, and ran NGINX with master_process off. The sanitizer aborted that single process. The public fix commit also names upstream connection setup as a drain trigger.

暴露情况审查

CVE-2026-123633 描述了 HTTP/2 反向代理中的一种释放后使用漏洞，这些代理的 worker 连接数不足。我复现的路径使用了一个变量 proxy_pass 主机名、一个已配置的 resolver 以及一个新的 UDP socket。F5 的 CVE 描述涵盖了范围更广的 HTTP/2 反向代理。

检查正在运行的配置。master 进程可以通过 -c 选择其他文件，因此不要想当然地认为打包路径就是实际使用的路径。命令 nginx -T 会打印磁盘上的配置，但该配置仍可能与运行中的 worker 所加载的配置不同。

我只测试了 proxy_pass。运维人员还应审查以下指令中的变量目标：

  • grpc_pass
  • fastcgi_pass
  • uwsgi_pass
  • scgi_pass

对于匹配的路由，检查正在运行的构建版本，以及 worker 接近其连接限制的程度。我测试了一条 DNS socket 路由，但上游连接建立也会通过 ngx_get_connection(), 分配资源，因此静态上游路由仍需审查。

缓解措施

NGINX 1.30.7 和 1.31.9 修复了 HTTP/2 问题。CVE-2026-123633 记录中未列出任何变通方案。如果必须等待升级，以下更改可能降低暴露风险：

  • 在服务允许的情况下，在暴露的监听器上禁用 HTTP/2。检查每个相关的 listen ... http2 参数；对于 NGINX 1.25.1 或更高版本，还要检查 http 或 server 上下文中的任何 http2 on; 设置。这两个设置中的任何一个都可能导致 HTTP/2 保持启用。禁用 HTTP/2 可能会破坏 gRPC 客户端，并且如果其他流量回退到 HTTP/1.1，可能会增加连接使用量。如果其他监听器上的 HTTP/2 仍保持启用，额外的 HTTP/1.1 连接可能会使同一个 worker 更接近其 worker_connections 限制。
  • 提高 worker_connections 可以在相同流量下为 worker 提供更多余量，但攻击者仍可能耗尽新增的连接槽位，而且连接状态缺陷仍然存在。

部署前测试每一项更改。升级后，确认正在运行的 worker 所使用的二进制文件包含 CVE-2026-123633 修复。重新加载配置（nginx -s reload）会让旧的二进制文件继续在内存中运行，因此应执行完全重启或实时二进制文件升级。

结论

该缺陷始于 HTTP/2 连接在请求开始后仍被标记为可复用。在我的测试中，在连接压力下打开 DNS socket 会耗尽该活动连接，并释放请求仍在使用的解析器状态。ASan 报告 NGINX 在内存释放后仍对其进行读取。

防御人员应确定受影响的 HTTP/2 反向代理，留意连接压力下 worker 的退出情况，并安装已修复的 NGINX 版本或供应商回移补丁。我的解析器测试展示了触发释放后使用的一种方法。F5 的说明更广泛地涵盖了 HTTP/2 反向代理。

失陷指标

本研究未发现已确认的失陷指标。将以下项目视为调查 CVE-2026-123633 的线索，并结合运行中的构建版本和 HTTP/2 流量一并调查。

  • 调查疑似代码执行时，以 NGINX worker 账户运行的异常 shell 进程
  • 在 HTTP/2 流量和连接压力附近出现的 NGINX 进程异常终止
  • 包含“worker_connections are not enough, reusing connections”的连接耗尽警告；解读这些警告时，应检查正在运行的 worker_connections 值
