中文原文

我们为保护 PHP 应用所投入的大部分工作，对于这个应用来说都发生得太晚，已经无济于事。我们会加固控制器、清理输入、争论中间件，而在这一切发生期间，解释器早已读取请求正文，并代表我们运行了一整套功能代码。php2shell 就存在于这个间隙中，在任何一行用户态代码运行之前。它包含两个无需身份验证的 RCE：CVE-2026-109618 和 CVE-2026-109619，二者的 CVSS v4.0 评分均为 9.2，由 Wiz Research 报告，并向多名独立报告者及 PHP 核心团队共同致谢。两者都不算是单个函数中的 bug。它们都源于 PHP 如何处理异常终止请求的内存，因此我想逐一讲解，因为披露前流传的那份解释（我所相信的那份）并不准确。

有必要把这两个漏洞分开来看，因为几乎每篇早期文章——包括我写的——都将二者混为一谈。

CVE-2026-109618，“通过 OOM 破坏实现 RCE”，涉及 PHP 在构建某个结构的过程中内存耗尽时会发生什么。请求在写入中途被拆除，而关闭代码随后仍会信任遗留下来的任何内容。

CVE-2026-109619，“通过陈旧的全局状态实现 RCE”，是一个跨越两个请求的释放后重用。一个请求留下一个指向自身堆的 worker 级全局变量，该堆随后被释放，而同一 worker 上处理的下一个请求在任何内容重置该全局变量之前就读取了它。

会话上传进度功能在两个漏洞中都会出现，这正是它登上头条并出现在漏洞名称中的原因，但它只是一种投递机制，也是多个使用方之一，并非根本原因。

当一次分配使请求超过 memory_limit 时，Zend 内存管理器会触发致命错误，并直接通过 longjmp() 退出，将原本正在处理的内容遗弃在半途中。如果被跳出的代码留下的结构仍然完整，这没有问题。但如果失败的分配恰好发生在一块内存变得可访问与该内存完成初始化之间的间隙中，就会产生问题。

Datadog 的文章给出了最清晰的示例。当 PHP 将表单字段插入哈希表时，_zend_hash_str_add_or_update_i() 会在分配新键之前增加表中的元素计数器。如果恰好是键的分配失败，那么该表现在会认为存在一个从未被写入的桶。此时还不会发生崩溃。真正的触发出现在请求关闭时：PHP 销毁该表，并遍历它认为归其所有的每个桶，将未初始化的堆字节当作 zvals 读取。攻击者设法留在该槽位中的任何内容，都会被当作有效值交给析构逻辑处理。

显而易见的反对意见是，post_max_size 的存在正是为了阻止请求变得如此庞大，而安全公告也详细介绍了在多部分解析过程中绕过它的几种方法：

  • 一个没有可用的已声明内容长度的多部分请求，可以绕过最初的 post_max_size 检查，并继续传入已解码的正文数据。
  • 单个部分可以携带数量不受限制的标头，而 PHP 在内存中对这些标头的表示远比其在线路上的形式占用更多资源。
  • 空文件控件不计入 max_file_uploads，但仍会构建通常的文件元数据数组，而嵌套的字段名称会进一步增加工作量。

Datadog 的复现过程只使用了一个约 3.5 MB 的表单字段名称，便在复制键时超出了限制。所有这些都发生在 SAPI 仍在解析正文期间，因此任何应用代码都尚未运行。

损坏后的状态是否会被读取，取决于 SAPI 在启动失败后所执行的操作。Apache mod_php 无论如何都会运行请求关闭流程，即使请求启动已经失败，因此半构建的表始终会被遍历。正是这一点使 618 在 mod_php 上完全与应用程序无关，并且我们正是在默认输入和内存限制下验证了完整的 RCE。源码分析表明，FrankenPHP 也属于同样情况。

PHP-FPM 的行为有所不同。当 php_request_startup() 失败时，FPM 只会退出子进程，损坏的状态也会随进程一同消亡。FPM 仍被认为容易受到影响，因为在应用程序路径中，即使干净启动之后也可能触发 OOM，而该路径并未预期会提前退出，但目前没有人展示过完整的 FPM 利用。

CVE-2026-109619 需要先介绍一些概念。PHP 在工作进程全局变量中保存大量状态：错误状态、会话状态、解码器状态、扩展状态。持久工作进程（Apache prefork 子进程、FPM 子进程）会在多个请求之间保留这些全局变量，但它们所指向的大部分内容位于每请求堆内存中，而后者会在每个请求结束时被销毁。其不变式很简单：每个指向请求内存的全局变量都必须在该内存被释放之前重置。

公告将该漏洞描述为生产者与消费者。生产者是一项将请求自有状态暂存到全局变量中、随后在有机会重置之前被中断的操作，中断通常由致命错误引起：OOM、解析失败、Maximum execution time exceeded。在关闭流程后期发出的非致命诊断信息，也可能在错误状态已经被清除后重新填充它，从而导致同样的结果。无论哪种情况，请求堆都会在全局变量仍指向它的情况下被释放。消费者则是该工作进程处理下一个请求时，在正常的请求初始化来得及替换该全局变量之前，对它进行访问的某项操作。

两个具体案例。

最强的一个是 PHP 8.5 的致命错误回溯。启用 fatal_error_backtraces 后，致命错误会将请求自有的回溯存储在 EG(last_fatal_error_backtrace) 中，而关闭流程始终会遗漏对它的重置。消费者是在 PHP 应用 INI 设置期间、执行器初始化之前发出的任何警告、通知或弃用提示，而这类提示的列表很长：8.3+ 上的旧版 assert.* 设置、8.4+ 上的旧版会话设置、显式设置的 mbstring.* 或 iconv.* 编码、格式错误的数量、被 open_basedir 拒绝的路径等等。PHP 甚至还没决定是否报告该警告，就会读取这个全局变量，因此 error_reporting、@ 和 display_errors 都帮不上忙。在 mod_php 上，这些设置通过 .htaccess 和 Apache php_value 指令传入，并在 php_request_startup() 之前应用；在 FPM 上，它们通过前端传入的 PHP_VALUE 和 PHP_ADMIN_VALUE 应用。这就是已确认的 mod_php RCE 的基础。

第二个是会话上传进度生命周期。上传进度会在正文解析期间、普通会话初始化之前运行，而且完全不需要应用程序调用session_start()。因此，它可以提前充当生产者，发布会话和解码器状态；之后也可以充当消费者，在后续请求中读取这些全局变量，而此时尚未发生任何重置。在 mod_php 上，生产者、致命错误和下一个消费者都可能落在 multipart 启动阶段。在 FPM 上，经过验证的路径稍长一些：先在正常应用程序执行期间发布状态，然后发生致命错误，再在后续请求中由上传进度充当早期消费者。Wiz 描述了同一系列中的另一个内存泄露问题，其中过期的 PS(id) 被错误地信任为有效字符串，并被 URL 编码写入 PHPSESSID 响应 Cookie，泄露当时位于该堆内存中的任何数据，可能包括其他请求中的凭据和令牌。

无论采用哪种方式，攻击者都需要让生产者请求和消费者请求命中同一个工作进程。工作进程越多、回收越频繁，每次尝试成功的概率就越低，但这并不会堵住漏洞。

在安全公告发布之前，我们中有几个人构建了另一种模型，我也构建了一个。上传进度回调 php_session_rfc1867_callback 会将两个原始 zval * 指针缓存到它所创建数组的 arData 中，而 php_session_rfc1867_update 会在 session.upload_progress.min_freq 经过指定时间后重新初始化 $_SESSION。向 php-fpm 流式发送 multipart 正文，并在各数据块之间停顿超过一秒，就能在这些内部指针仍然有效时，让回调经历一次更新。我们的 PoC 正是这样做的，并通过从会话文件中读回 bytes_processed，证实了通过缓存指针进行的写入。

它从未崩溃，即使在启用 USE_ZEND_ALLOC=0 的 AddressSanitizer 下也没有崩溃，而 0x4148 的实验室在其 README 中也明确得出了同样的结论。我们曾认为，这是因为已释放的缓冲区在请求结束前没有再次被解引用，并猜测堆布局调整是缺失的关键因素。但这些安全公告给出了更直接的解释：这根本不是漏洞。两个真实的 CVE 都需要致命中断，而 619 还需要向同一个工作进程发起第二个请求；一次行为正常的停滞上传无法满足其中任何一个条件。回调中的内部指针模式从代码审查角度仍值得警惕，但 php2shell 并不会利用它。

发布前声称禁用上传进度只能阻止两个漏洞中的一个，这一说法碰巧是正确的，只不过原因并非我们原先设想。那个不受该设置控制的漏洞是 618，即正文解析中的 OOM 内存耗尽破坏，而不是隐藏在 main/rfc1867.c 中的第二个悬空指针。

由于 php2shell 工具包在漏洞披露前就已开始流传，我们在信任其中任何一行代码之前，先对其进行了静态分析。Python 部分足够干净：没有隐藏的 C2、没有数据外泄、没有混淆，而且每个目标默认都指向 localhost，或指向操作员传入的主机。那些大型 .zval.debug 文件并不是要运行的二进制文件，而是仅含调试符号的 ELF 对象（代码节被标记为 NOBITS），其唯一用途是恢复每个构建版本的符号偏移量，因此只会交给 readelf 处理，绝不会用于执行。

让这个值得写一写的，并不是上述任何一点。真正的原因在于，整套东西最终变成了一连串貌似合理的幻觉：一个看起来像完成版漏洞利用的东西，几乎完全由真实部件拼成，但能让它真正成立的那一块——实际的端到端代码执行——却悄无声息地缺失在中间。这些层次值得逐一拆解，因为它们的失败方式完全相同。

先从根因说起，而根因被自信地判断错了。这个合集找到了正确的回调函数，然后在它之上构建了一整套机制：孤立的 serialize 和 unserialize 上下文全局变量、初始化前的 bailout、下一次请求中连行号都原样保留的被释放上下文块。这些都不是修复所针对的漏洞。真正成对出现的是正文解析中的 OOM 破坏，以及范围更广的陈旧全局变量这一类问题；其中，致命错误回溯是最有力的已确认案例。它从所有人已经在谈论的功能出发，推导到一个听起来合理的机制，而这正是我自己也掉进去过的陷阱。

再来看那些“证据”，它们只能证明漏洞路径可以到达，仅此而已。诚实地读一遍阶段图，就会发现所有确定性证明都属于“请求返回 500”“worker 仍然存活”“关闭该功能后问题停止”这种形式。它们当然都属实，但没有一个是代码执行。真正本应是代码执行的阶段，挂着自己的“已调优演示 / 需要暴力破解 ASLR”标签，并且在自己的说明中承认失败次数多于成功次数。一个在作者自己的机器上八次才成功一次、且没有捕获到任何东西的证明，不是证明。

这种精确性最具诱惑力，却也最缺乏依据。字节偏移、喷洒大小、按发行版列出的两个符号之间的距离、会“随每次运行而漂移”的泄漏值，以及在指定 CMS 版本上植入 shell 的视频帧。真正的漏洞利用确实会包含这类细节，所以它才显得可信；但其中没有一个字节与任何可供重建和核验的构建版本绑定。那段视频是所有材料中最明显的例子：对某件事的录制并不是对它的复现。

而我第一次就应该察觉的破绽，是那次缺失的崩溃——它非但没有被认真对待，反而被敷衍解释掉了。这个合集自己的实验室从未触发 AddressSanitizer；它没有把这当作结果本身，反而将其包装进一套关于哪个堆 bin 被回收的理论。用真实的函数名称、真实且默认启用的功能，以及真实的用户态启动前窗口拼凑出一个整洁答案，这并不是胡言乱语；恰恰正因如此，它才显得可信，并赢得了与信任相反的评价。诚实的结论很有限：该工具能够可靠地到达漏洞路径，也能可靠地杀死 worker；它所声称的根因是错误的；它所声称的 RCE 在其自身材料中并未得到证明。它仍然是货真价实的攻击性代码，因此它仍然只会指向你所拥有的基础设施。

打补丁是唯一的完整修复方案，而两份公告都用粗体明确说明了这一点。修复版本为 8.2.35、8.3.36、8.4.27 和 8.5.12，PHP 还针对 7.4、8.0 和 8.1 发布了源码回移植，不过某些发行版可能在不更新版本字符串的情况下提供这些修复。618 号补丁彻底将 longjmp() 移出 OOM 处理流程，改为使用一个在下一个 VM 安全点提高的软限制，以及一个通过 _exit() 杀死 worker 的硬限制。619 号补丁则重置范围更广的 worker 全局变量，确保它们都不会存活到初始化前的代码中。

如果必须推迟打补丁，这些配置缓解措施只能按路径逐项实施，而且并不完整。最后这个词很重要：

  • 618 OOM corruption
    • 缓解措施：memory_limit=-1、frontend body size limits、降低 max_input_nesting_level、限制 parts、headers 和 uploads
    • 不覆盖：mmap() 失败仍可能命中存在漏洞的 longjmp() 路径
  • 619 fatal error backtraces (8.5)
    • 缓解措施：fatal_error_backtraces=0
    • 不覆盖：其他所有会产生陈旧状态的来源
  • 619 session lifecycle
    • 缓解措施：session.upload_progress.enabled=0
    • 不覆盖：618，以及所有非会话状态的产生来源
  • 619 in general
    • 缓解措施：移除会提高诊断级别的逐请求 INI 覆盖项、消除可触达的 fatal error，并在能承受的情况下设置 pm.max_requests=1
    • 不覆盖：未经任何审计的应用和扩展路径

所有这些都必须写入启动配置，并在其后重启所有 worker。session.upload_progress.enabled 是 INI_PERDIR，因此 ini_set() 对它无效；而 .user.ini 会在正常初始化之后才应用，对于这些路径来说已经太迟。也别指望用 RLIMIT_AS 或 RLIMIT_DATA 来限制内存；它们只会让 mmap() 失败，而这正是存在漏洞的路径，并非针对该漏洞的防御。而且，即使打了补丁，如果没有任何功能使用上传进度，也值得继续保持关闭，公告本身也建议这样做。

在检测方面，值得关注的信号包括记录为“Unknown on line 0”的 fatal “Allowed memory size … exhausted” 错误、名称异常巨大的表单字段、Apache AH00052 segfault、超大或格式错误的 PHPSESSID cookie，以及最重要的：Web worker 生成 shell。成功利用后可以返回 HTTP 200，同时让 worker 保持运行，因此崩溃日志干净并不能证明没有遭到利用。

这两个 CVE 均可由单个提交 31c0ea7 修复，其提交说明直截了当：“Replace bailout on OOM with UnwindExit”和“Properly reset various globals that may be accessed during startup”，每个漏洞对应一行。这是一项庞大的改动，涉及一百多个源文件，因为不安全模式遍布整个代码树，但其核心可以归结为两个思路。

第一个思路从根源上消除 618，方法是让内存耗尽时停止跳转。打补丁前，超过限制的分配会调用 longjmp()，直接脱离其正在构建的任何未完成结构。修复在 executor globals 上加入了延迟 OOM 状态机（EG(delayed_oom)、none/pending/handling/handled 状态的 zend_oom_state，以及用于测试该状态的 ZEND_HAS_OOM() 宏），同时加入了一整套平行的可失败分配器，即 _femalloc() 等；它们在失败时返回 NULL，而不是直接中止。位于危险的预初始化窗口中的分配点会切换到这些可失败变体，因此分配失败现在会通过常规错误返回进行栈展开，不会留下任何半构建结构供关闭过程遍历。对于确实无法处理 NULL 的调用代码，OOM 会被记录为 pending，并在下一个安全点处理，而不是在写入过程中处理：zend_call_function() 现在会在入口处以及再次执行中断检查时检查 ZEND_HAS_OOM()；如果存在 pending 状态，它会调用 zend_handle_delayed_oom()、抛出异常并返回 FAILURE，而不是任由调用方继续运行并进入损坏状态。

对此提供支持的是公告中提到的软/硬内存限制。main.c 新增了一个 memory_hard_limit_percent INI 配置项（当限制低于 1 GB 时，默认值为该限制的 200%；否则默认在限制之上额外提供 1 GB 的余量），以及一个 ZEND_MM_MAX_ALLOCS 上限。超过软限制时，你只会收到延迟处理的错误；超过硬限制时，进程会立即被终止，并返回明确的退出状态（ZEND_MM_MAX_ALLOCS_EXIT_STATUS，121），从而让运维人员能够区分内存终止与普通致命错误。PHP 仍然保留强制执行内存限制的能力，只是以后不再使用曾使这种强制执行方式变得危险的 longjmp()。

第二个想法通过重置下一个请求的消费者可能读取的全局变量来修复 619。最清晰的改动位于 zend_shutdown_executor_values() 中；该函数现在会在 init_executor 之前，明确清除公告中指明为可访问的确切状态：EG(last_fatal_error_backtrace) 被重置为 undef，EG(record_errors)、EG(num_errors)、EG(errors)、EG(error_handling) 和 EG(exception) 被清零，用户错误处理程序和异常处理程序也会被清除；每处都附有类似“可能会在 init_executor 之前被 zend_error_zstr_at 使用”的注释。这样，产生致命错误回溯的代码与提前进行 INI 诊断的消费者在源代码中相遇，并最终被彻底分开。php_request_shutdown() 也会对请求全局变量执行同样的处理：在析构函数之后将 PG(http_globals)[i] 重置为 undef（“可能会在 php_request_startup() 之前被访问”），并调用 clear_last_error()。此外，php_request_startup() 现在会运行新的 php_basic_early_rinit()，以便提前重新初始化基础扩展状态，以及位于上传进度路径核心位置的会话和序列化全局变量，而不是让它们继续保持陈旧状态。甚至 php_verror() 现在也会在即将发生 OOM 时立即返回，因此错误报告不会因为试图报告损坏状态而反被该状态绊倒。

我觉得这件事颇有启发意义：修复并没有去寻找我们在披露前都曾追逐的那个易受攻击的指针，而是针对的是这一类漏洞：不允许从只构建了一半的结构中执行不安全的跳转，也不允许请求所拥有的全局变量继续指向已释放内存，供下一个请求读取。涉及一百个文件的差异，正是按这一类而非某个具体实例进行修复所需的实际成本。

这件事留给我的主要启示，是关于跨越边界的生命周期。PHP 的持久工作进程是一个长期存活的进程，其中承载着生命周期短暂的请求堆；每个从一侧跨越到另一侧的指针，都是一份终将有人完成清理的承诺。致命错误和 longjmp() 正是破坏这些承诺的路径，因为它们会跳过普通控制流本应执行的清理。因此，如果要寻找下一个同类问题，不要只盯着单个回调，而要检查每个可能在致命错误之前被写入、并在下一次 php_request_startup() 完成之前被读取的全局变量。

这个漏洞也让我对自己的流程有了两点认识，而且它把这两点都教了两遍。我先称它是安全的，接着又称为无法复现，然后构建了一个整洁的单请求模型，碰巧契合了标题中的那个特性以及我已经打开的代码。它确实复现了某种东西，这让人感觉已经足够接近确认；而唯一与它相悖的事实——完全没有发生崩溃——我却用缺少堆预置来搪塞，而没有把它当作答案。当漏洞无法复现时，想要信任的本能恰恰是反过来的：应当怀疑模型，而不是报告。当模型只能复现一半时，就更应该怀疑它。
