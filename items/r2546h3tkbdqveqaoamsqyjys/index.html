Microsoft FORGE Lab 复盘 AI 扫描发现 59 个 Linux 内核漏洞

Lessons from 59 Linux Kernel Bug Reports

AI 导读

Microsoft FORGE Lab 使用代号 MDASH 的 AI 扫描系统研究 Linux 内核，3 个月产出 59 个公开上游报告和 33 个已分配 CVE，其中 8 个 CVE 已验证本地提权利用，38 个报告的修复已合并主线。

在Microsoft 的 FORGE Lab，我们使用代号 MDASH 扫描了 Linux 内核若干子系统的部分代码，时间从 2026 年 5 月下旬持续到 6 月中旬。这项为期三个月的工作由一名全职研究员和一名实习生主导，截至目前已产出59 份公开的上游报告和33 个已分配的 CVE。我们确认了其中 8 个 CVE 的有效 root 权限提升利用，并且我们 38 份报告的修复已合并到主线。

发现漏洞只是这项工作的一部分。初始扫描在约两周内产生了 26,502 条原始发现，但将这些结果转化为可复现漏洞、上游报告和补丁，需要专家投入数月时间进行调查，并与 Linux 维护者协作。

在这篇文章中，我们回顾了如何从数千个潜在发现推进到经验证的漏洞和上游修复，以及我们在使用 AI 扩展漏洞发现规模方面的经验。

从扫描到报告

我们重点关注了若干核心内核子系统，例如网络、文件系统和安全模块。我们的选择标准很直接：选取对安全敏感且不明显依赖专用硬件的组件，从而让基于 QEMU 的验证过程简单且统一。代码扫描主要使用 Sonnet 4.6（占代码扫描令牌的 71.1%）、GPT-5.4（20.1%）和 GPT-5.5（7.1%）。

代号 MDASH 的扫描在约两周内于两台服务器上产生了 26,502 条原始扫描发现（64 核/256 GB RAM 和 32 核/128 GB RAM），但将这些输出转化为补丁和报告需要专家数月的工作。我们利用代号 MDASH 的置信度级别，以及自行构建的独立快速筛查代理，过滤掉低置信度的主张，将候选数量缩减至 11,769 个。随后，PoC 生成代理尝试在 QEMU 中复现，主要使用 GPT-5.5（占复现令牌的 77.3%）、Opus 4.6（13.2%）和 GPT-5.5-cyber（9.4%）。接着，专家审查了 621 个具有 PoC 证据的案例，以确定根因、合并重复项并准备上游提交。

621 个案例的去向

平均每 10 个有 PoC 支持的案例最终产生约 1 份公开的上游报告：621 个案例产出 59 份报告（9.5%）。在这些案例中，未单独提交新报告的主要原因是：

  • 266 个（42.8%）与另一个案例存在相同的根因，因此可以通过一个补丁一并修复。
  • 163 个（26.2%）经审查后未予报告，主要是因为安全影响有限。
  • 133 个（21.4%）此前已被报告或已在上游修复。

提交时间可以解释这 133 个重叠案例中的许多情况。扫描完成时，621 个案例中的大多数都是新发现的（不过其中一些可能已由他人提交处理）。我们的首份公开报告于 2026 年 6 月 27 日发布，比扫描开始晚了五周多。截至 9 月 1 日，59 份报告中的 55 份已发布到公开邮件列表；其余 4 份在同一时间窗口内进行了私密报告，并已于 10 月中旬转交至公开邮件列表。

推动修复合并

上游 Linux 通常要求漏洞报告附带可用的补丁。智能代理帮助起草了初始修复方案，但人工验证、理解相关子系统，以及在审查期间与维护者反复协作仍然至关重要。到目前为止，我们报告中的 38 个修复已被合并到上游主线，其中一半在首次提交时即被合并，其余则经过一至四次修订。从首次公开补丁到进入主线发布版本，耗时中位数为 41 天（最长 108 天）；我们仍在与其余报告的维护者协作。

这些漏洞存在了多久

值得注意的是，我们报告的大多数漏洞都已在内核中存在多年。在 59 份报告中，我们首次公开报告时，这些漏洞的平均存续时间为 8.1 年。其中最久的一个是 cls_u32 移位越界漏洞（CVE-2026-74544），至少已经存在了 21 年。

深入了解 CVE-2026-64563

CVE-2026-64563 是 rhashtable（Linux 内核共享的可扩展哈希表）中的一行状态重置漏洞。由于调用方信任遍历表时返回的对象指针，这一小型的库缺陷使得在 Linux 上稳定实现本地权限提升成为可能；该漏洞也影响启用了 SELinux 强制模式的 Android，并且无需特殊的内核配置或用户命名空间。

许多内核子系统会将活动对象（例如套接字）存储在rhashtable中，并在用户空间要求列出这些对象时遍历该表。由于大型列表可能会拆分到多个响应中，一次遍历可以暂停并恢复。其迭代器会保存停止的位置，包括指向最后访问条目的指针（iter->p）。然而，在遍历暂停期间，该表仍可能发生变化：条目可以被移除并释放，调整大小也可能替换底层的桶表。

遗漏的重置

在 2018 年之前，rhashtable_walk_stop()总是在暂停时将 iter->p 清空为 NULL。为提高遍历在停止/启动周期之间的稳定性，一项2018 年提交（5d240a8936f6）在 walk_stop() 之后保留 iter->p，并将重置操作移入 rhashtable_walk_start_check()——但只在其两条恢复路径中的一条上执行：

调整大小释放旧表（iter->walker.tbl == NULL）：第 877–882 行切换到新表，重置槽位并跳过，然后提前返回 -EAGAIN，而未清除 iter->p：

旧表仍然存在（iter->walker.tbl != NULL）：第 884–919 行扫描 iter->p 所在的桶链；如果该条目已被移除，则重置 iter->p = NULL。

if (!iter->walker.tbl) {
	iter->walker.tbl = rht_dereference_rcu(ht->tbl, ht);
	iter->slot = 0;
	iter->skip = 0;
	return -EAGAIN;
}

此后再次启动时，下一次调用 rhashtable_walk_next()会发现 iter->p 仍被设置，并沿 iter->p->next 继续，而不是从 slot = 0 重新开始。如果该条目在遍历暂停期间已被释放，对 iter->p->next 的解引用就会读取已释放的内存。

为什么这个漏洞八年都未被发现？触发它需要在同一次遍历中同时满足三个条件：调用方必须跨 walk_stop() 和 walk_start() 暂停并恢复同一个迭代器；表必须在暂停期间调整大小并释放旧桶表；iter->p 处的条目也必须在遍历恢复前被移除并释放。大多数 rhashtable 遍历器会在单次遍历中完成，从不恢复已停止的迭代器；即使调用方确实会暂停并恢复，这三个事件在正常工作负载中也很少偶然同时发生。

上游修复只是在返回前清除失效指针：

+		iter->p = NULL;

从套接字列表到内核写入

由于 rhashtable 是一个共享库，其调用方既决定该漏洞是否可被触达，也决定其安全影响的严重程度。在整个内核中，大约有二十几个文件使用 rhashtable 遍历器 API，其中大多数会在单次遍历中遍历该表并立即退出。在这些调用方中，我们发现了两个会跨批次暂停并恢复迭代器、且至少能够导致崩溃的调用方：TIPC 的套接字转储（tipc_nl_sk_walk()）和 Netlink 的套接字诊断（__netlink_diag_dump()）。

两者之中，__netlink_diag_dump()是可利用的调用方。在标准内核上，非特权用户可以触达它，并且用户空间可以控制转储响应之间的暂停（通过 recvmsg()）。攻击者可以让转储保持暂停，同时调整表的大小并释放 iter->p 处的套接字，然后重新分配该内存以控制 iter->p->next，从而使 rhashtable_walk_next() 返回伪造的套接字指针 sk。

__netlink_diag_dump() 随后检查 net_eq(sock_net(sk), net)，并将 sk 传递给 sk_diag_fill() 和 sock_diag_save_cookie()；后者会在 sk->sk_cookie 为零时对其初始化。这会将伪造的 sk 指针转化为一次受约束的 64 位写入（当目标 8 字节为零且 sk->sk_net 与 &init_net 匹配时）。结合其他通用漏洞利用技术，这次写入足以实现本地权限提升。

我们感谢 NebuSec 的 Yuan Tan，他也独立发现了此漏洞。他迅速向我们和维护者分享了其真实严重程度，这有助于推动上游修复，之后还向我们提供了适用于 Linux 和 Android 的可用漏洞利用程序。我们也感谢 NebuSec 的 Frank Wu，他找到了一种可行的漏洞利用原语，并开发出了可用的权限提升漏洞利用程序。

结语

发现漏洞与修复漏洞之间的平衡严重失衡。通过代号 MDASH 扫描两周，我们获得了初步发现，并将其范围缩小到 621 个有 PoC 支持的案例。但报告其中 59 个案例耗费了四个多月，而五个月后已有 38 个修复被合并。对于 Linux 内核这类复杂基础设施而言，仍需让人类参与其中，因此人力成为了瓶颈。漏洞猎手和维护者都可能因大量真实发现而不堪重负，所以专注于真正的高严重性问题至关重要。

更多 token 可能带来更多漏洞，但并不意味着系统就会安全。我们只扫描了内核的一小部分，进一步调优和增加 token 可能发现多得多的漏洞。但即使修复了所有漏洞，系统就安全了吗？在 Microsoft FORGE Lab，我们正使用 AI 扩大漏洞研究的范围，但我们的经验表明，发现漏洞只是工作的一部分。更紧迫的问题是如何构建实用、可运营、可累积且经济上合理的安全解决方案。

这些经验也适用于我们的研究之外。通过与构建代号 MDASH 的工程团队密切协作，我们正将从现实世界漏洞发现与验证中学到的经验用于指导这些能力的演进。目标是让 AI 赋能的安全研究成果为安全团队所用，帮助他们更有效地识别并处理关键漏洞。
