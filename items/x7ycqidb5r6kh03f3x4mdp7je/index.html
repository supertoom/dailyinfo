Chrome 157.0.8103.38 修复 CVE-2026-121104 目录授权漏洞

cve-2026-121104 chrome路径拦截调用链分析

AI 导读

CVE-2026-121104 影响 Chrome 的 File System API 敏感路径拦截机制，旧版规则未覆盖多个平台上的 ~/.cache，恶意页面诱导用户通过 showDirectoryPicker() 授权目录后即可读写该路径并执行代码。

值得关注

文章沿目录选择调用链定位了 Chrome 路径拦截缺口，并对比修复前后的命中逻辑与拦截结果。

正文

cve-2026-121104

简单描述：chrome 拦截规则里，~/.cache 在多个平台上完全不在拦截范围内。攻击者诱导用户把目录授权给  showDirectoryPicker()，就能往 ~/.cache 里读写文件，导致执行代码

漏洞提及到的关键点，后文以 Chrome 157.0.8103.38 对这些关键点展开研究。
1、目录拦截列表由 GenerateBlockPaths() 生成、主目录规则为 kDontBlockChildren
2、base::DIR_CACHE 实际解析.
3、在 $XDG_CACHE_HOME 指向其他位置时同样无法命中 ~/.cache
4、攻击者通过恶意页面诱导用户将主目录（或包含 .cache 的目录）授权给 showDirectoryPicker

01 敏感路径拦截调用链

当用户选择目录，或网站调用 showDirectoryPicker() 访问时，Chrome 会在返回句柄之前，将所选路径与黑名单进行比对。调用链如下：

JS 调用 showDirectoryPicker(options)
  > GlobalFileSystemAccess::showDirectoryPicker
  > ShowFilePickerImpl(type=kDirectory)
  > FileSystemAccessManager::ChooseEntries
  > FileSystemAccessManagerImpl::ChooseEntries
  > ConfirmSensitiveEntryAccess()
  > CheckPathAgainstBlocklist()
  > CheckShouldBlockAccessToPathAndReply()
  > ShouldBlockAccessToPath()   //实际的匹配逻辑

window.showDirectoryPicker()

1、window.showDirectoryPicker() 属于 File System API 的一个控件，可使用 js 来调用。

File System API: 通过文件系统访问 API 提供的扩展功能，可以实现对设备文件系统的文件读取、写入和管理操作。该 API 的核心功能包括读取文件、写入或保存文件，以及访问目录结构。

<button onclick="showDirectoryPicker({mode:'readwrite'}).then(h=>o.textContent='OK '+h.name,e=>o.textContent=e.name)">click</button><pre id=o></pre>

2、用户通过 showDirectoryPicker() 选择常规目录，弹出 写权限授予框 （由 FileSystemAccessPermissionGrant 弹出）

3、选敏感目录，如果命中拦截规则，弹出的是 黑名单拦截判定弹窗 （由 ConfirmSensitiveEntryAccess() 触发），直接拦不让你 allow，让你另选目录

GlobalFileSystemAccess::showDirectoryPicker

把网页调用的 showDirectoryPicker() 转成 浏览器能选目录的请求

ShowFilePickerImpl、FileSystemAccessManager::ChooseEntries

把刚拼好的请求送到浏览器进程，由浏览器做后续操作

ConfirmSensitiveEntryAccess()

ConfirmSensitiveEntryAccess() 是所有黑名单策略入口。判断路径是否敏感目录，命中则弹出受限目录确认框，把(拦 / 重选 / 放弃)的结果回给调用方。
接收 url::Origin、content::PathInfo、HandleType、AccessTrigger、GlobalRenderFrameHostId，以及一个回调。但真正进入黑名单匹配的只有路径、handle_type 和 access_trigger 三项。得到回调回一个三态 SensitiveEntryResult

url::Origin  发起请求的站点
content::PathInfo  路径 + 显示名 + 路径类型（本机 / 外部卷）
HandleType , 文件或目录 (kFile / kDirectory)
AccessTrigger ,选择器、拖放、保存或程序化写入 (kOpen / kSave / kLoadFromStorage / kDragAndDrop / kProgrammaticRead / kProgrammaticWrite)
GlobalRenderFrameHostId  发起请求的 frame
SensitiveEntryResult 拦 / 重选 / 放弃,（kAllowed/kTryAgain/kAbort）

CheckPathAgainstBlocklist()

CheckPathAgainstBlocklist() 是查询层。把路径连同访问性质交给黑名单比对，返回命中与否。不弹框、不记录用户选择、不关心站点与 frame。相比上一层，无 origin 和 frame_id 
接收一个 content::PathInfo、 HandleType、 AccessTrigger，得到 bool 的回调。 

CheckShouldBlockAccessToPathAndReply()

CheckShouldBlockAccessToPathAndReply() 是汇总层。把常规规则表与额外规则交给 ShouldBlockAccessToPath() 逐条比对，取回最终结论后统一回复。规则表在此层只被消费，不再构造。
接收一个 base::FilePath、 HandleType、 AccessTrigger、std::vector<BlockPathRule> extra_rules、BlockPathRules block_path_rules ，得到 bool 的回调

base::FilePath  裸路径，PathInfo 已在此前被降级
std::vector<BlockPathRule> extra_rules —— 本次运行时临时追加的规则
BlockPathRules block_path_rules —— 已构造好的规则集，按值移入

ShouldBlockAccessToPath()

整条调用链上只有 ShouldBlockAccessToPath() 真正做判定拦不拦，前面都在准备参数。
1、路径规范化


2、Windows 上的 UNC 做特判
3、单条规则的判定（lambda)

02 修复的位置

从 chrome_file_system_access_permission_context.cc#470 看157.0.8103.38 版本的更新点
文件 chrome_file_system_access_permission_context.cc 中 BlockType 的 kBlockAllChildren 类型新增了 .cache

03 场景：用户选中 ~/.cache

旧版：readwrite 模式下写权限要单独授予一次，弹出 写权限授予框 ，点允许后句柄可写，攻击成立。


新版：在到达这一步之前就 reject 了，弹出的是 黑名单拦截判定弹窗，写权限框不会出现。

1、链路会在返回句柄之前终止，终止点是第 6 跳。
第一跳：window.showDirectoryPicker()，收到 {mode:'readwrite'}，结果为 Promise 挂起
第二跳：GlobalFileSystemAccess::showDirectoryPicker，收到 window、options，结果校验 user activation 通过，转成 mojom 选项
第三跳：ShowFilePickerImpl，收到 options、type=kDirectory ，结果发 IPC，绑定回调
第四跳：FileSystemAccessManager::ChooseEntries 收到 options、callback，结果 仅 Mojo 桩，序列化后送出
第五跳：FileSystemAccessManagerImpl::ChooseEntries 收到 options、frame 上下文，道检查通过，弹出原生框；用户选中后，PathInfo{C:\...\.cache, ".cache", kLocal} 
第六跳：ConfirmSensitiveEntryAccess，收到 origin、PathInfo、kDirectory、kOpen、frame_id，拦截发生。
第七跳：CheckPathAgainstBlocklist，收到 PathInfo、handle、trigger，结果 true
第八跳：CheckShouldBlockAccessToPathAndReply，收到 裸路径、extra_rules=[]、规则集，结果 true
第九跳：ShouldBlockAccessToPath ，收到 path、handle、trigger、规则表，结果 true ， path == block_path 命中黑名单

2、停在第 9 跳的哪一行
新增规则让 ~/.cache 进入了规则表。因此第 9 跳没有走到“记录最近祖先”那一步，而是在第一个判断处就立即返回：

if (path == block_path || path.IsParent(block_path)) { return true; }

path 是 ~/.cache，规则也是 ~/.cache，两者相等，因此直接返回 true。

3、之后
返回的 true 沿回调链向上传递，CheckShouldBlockAccessToPathAndReply 和 CheckPathAgainstBlocklist 都原样传递。
到第 6 跳时，ConfirmSensitiveEntryAccess 拿到 true，弹出受限目录确认框，只有两个按钮：Choose a different folder（kTryAgain）和 Cancel（kAbort）。没有 allow 的选项。
到第 5 跳时，函数收到 error，回执 (error, entries=[])；
到第 3 跳时，回调 reject；
到第 1 跳时，Promise reject。

4、新版的整条链在构造 FileSystemAccessEntry 之前就结束了，所以请求 readwrite 权限时写权限授予框 没有出现。

5、与旧版的差异：差别只在第 9 跳。
旧版没有 .cache 规则，落到 ~ 的 kDontBlockChildren，返回 false，kAllowed，静默放行。
新版精确命中，返回 true，kAbort
