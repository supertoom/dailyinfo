正文

深瞻情报实验室 2026-11-05 17:53 北京

近期，深瞻情报实验室发现位于 91.224.92.16 的 18128 端口存在未授权可列目录。目录内完整存放着一个用于入侵某国内第三方支付机构生产环境的整套工具链，共计 91 个文件，涵盖内存马、JVM 注入器、隧道组件、Metasploit 载荷与数据窃取脚本。截至本文撰写时，该目录已无法访问。

与常见的僵尸网络面板或矿机配置泄露不同，该目录是一套针对单一目标高度定制的作业工具包：所有部署脚本内置目标内网的主机名门禁、中间件路径、内部服务地址与业务组件标识。我们对全部文件进行了纯被动抓取与离线静态分析，以下为本次监测的详细分析与研判。

基础设施：单点 C2 与三个低级失误

全部证据指向单一攻击服务器 91.224.92.16，一台机器承担载荷分发、SSH 隧道端点、Meterpreter handler 与自写隧道回连等多类角色（脚本注释中自称"kali"，隧道注释中称"operator"）：

从整体看，攻击者在目标侧投入较多，但基础设施相对简陋：只有一台 C2，没有备用域名，载荷未做免杀，目录没有访问控制，甚至把 SSH 私钥也放在里面。我们判断，这处设施更像是为某次任务临时准备的落脚点，长期运营的专用 C2 的可能性较低。

定向攻击特征

从工具包可以看出三点。第一，攻击有明确的目标清单：部署脚本内置主机名白名单与排除名单，清单外主机直接跳过，其中一类节点被 20 余个脚本反复引用，是重点目标。第二，工具按目标环境定制：针对 Tomcat 7 与 JDK 1.8 编写，预置多套 JDK 路径和 Alpine 与常规 Linux 的计划任务回退。第三，攻击者熟悉业务：直接引用 Hessian 业务路径、订单查询接口与两台 Dubbo 节点的 telnet invoke，查询前还先反编译订单组件确认字段。结合“业务探针+异常回滚”的做法，其目的是长期驻留、按需取数。

综合判断，这是一次有目标清单、有前期情报、按环境定制的定向作业。

工具包分析

冰蝎内存马家族（I4127b.java 等 8 个文件）

核心组件 I4127b.java 为编译后植入 WEB-INF/classes/ 的 Servlet，协议与冰蝎 v3 兼容：硬编码 AES-128-ECB 密钥（按目标定制的口令派生），通过加密信道接收指令并在应用进程内直接执行，执行结果加密回传；非 POST 请求一律返回 200 空响应，无任何页面特征。配套变体包括 .jsp/.jspx 落盘版（jspx 为带调试日志的排障版）与 Valve 版——后者插在 Tomcat 管道最前，把特定 URI、特定 UA（Behinder）的流量、乃至 POST 到 /hessian/* 的流量全部劫持给冰蝎处理器，借正常业务路径作隐蔽入口。

蚁剑 Valve 家族（AsV2/V3/V4/As5180 等 14 个文件）

四个迭代版本均为 Valve 形态，协议为蚁剑 base64 类加载（特征串 yv66vg，即 base64 的 .class 魔数 cafebabe）。版本迭代可见攻击者对兼容性的持续改进：V3 起记录命中审计日志，V4 引入独立类加载器规避同名类冲突，均使用空 Servlet 伪造 JSP PageContext 提高 payload 兼容性。与冰蝎家族并列，构成"双客户端冗余"。

JVM Attach 无文件注入

当落盘文件可能被完整性巡检发现时，攻击者切换至纯内存注入：通过 JDK Attach API 向运行中的 Tomcat 进程动态加载 Agent，在内存中注册请求处理组件，实现不落盘驻留。磁盘仅残留 /tmp 临时文件，应用目录零改动；组件随进程重启失效，客观上降低了被巡检发现的概率。

隧道组件与持久化

Tun.java（43 行纯 JDK 实现）为反向端口转发器：向 C2 发起出站 TCP 连接，将 C2 指令流与受害机本地 8080 双向转发；默认并行 6 实例，后期配看门狗进程保活。与 SSH 反向隧道并用，构成至少三条相互独立的回连通道——单点封堵无法断联。

met.bin 为 Linux x64 Meterpreter（mettle 实现）：静态链接、未剥离、含调试信息，内嵌回连配置 tcp://91.224.92.16:18140 与会话 UUID。met.jar 为完整的 Java 版 Meterpreter 载荷（含 Payload.class，LPORT=18141，内部时间戳 2026-09-28 05:31:48），与原生 ELF 互为冗余。持久化终版脚本 i5180p.sh 的设计比较周密：载荷落地到隐蔽临时目录（/tmp 不可写时自动退到 /dev/shm），写入每分钟执行一次的计划任务，runner 通过进程探测保证双载荷至少一个存活，再叠加秒级轮询看门狗双层保活。计划任务路径为 Alpine/BusyBox 风格，说明目标或跳板中存在 Alpine 容器，攻击者针对不同系统环境做了适配。

web.xml 修改与回滚机制

落盘植入均伴随对应用配置的修改：向 web.xml 注入 servlet 映射，把命令入口藏在 Hessian 业务路径下。后期版本形成完整的"备份—校验—回滚"流程：修改前自动备份，修改后校验 XML 合法性，正常业务端点一旦异常即恢复备份。攻击者刻意维持业务外观正常的意图非常明确——避免业务异常引起运维人员注意。

数据窃取：目的不止于数据

接口侦察：反编译受害机自身的订单组件，枚举 DTO getter，筛选条件为 Card/Cvv/Cvn/Pan/Account/Bank/Payer 等字段族——先确认数据模型里有什么，再决定偷什么。随后利用 Dubbo telnet invoke 未授权调用个人订单查询接口：时间窗覆盖 2019 年初至 2026 年 9 月末的全部历史，固定对 3 个重点商户客户号执行，并细分"近 7 天 + 开户日当周"窗口持续追踪新交易。查询结果落盘后立即结构化提取订单号、付款人银行账号、户名、卡号、CVV、PAN 等敏感要素，并以 awk 过滤堆栈行、只保留数据行，说明攻击者是按真实接口的返回格式来做数据处理的。

作业特征与团队画像

综合全部部署脚本与源码（共 42 个 shell 脚本），我们发现其AI辅助编码痕迹明显，作业特征如下：

  • 波次化迭代：脚本编号 i4438→i5180 呈完整演进链（独立Context→配置修改→JSPX落盘→JVM注入→远控持久化），每版针对上一版失败修正；

  • 失败经验制度化：注释中以 fact# 编号记录教训（如某项配置残留导致正常业务端点失效、某文本处理工具损坏配置文件后被明令禁用），把失败教训写入了标准作业流程；

  • 业务存活优先：以正常业务端点为探针，异常即回滚备份——把"不被发现"放在"功能达成"同等地位；

  • 防并发与幂等：目录锁、旧进程清理、映射已存在即跳过；

  • 环境自适应：多 JDK 路径回退、多解释器探测、Alpine 与常规 Linux 计划任务路径差异处理。

文本取证层面存在多组 AI 辅助编码的指示性信号：注释中出现中文圈码序号（①）与英文"约束清单式"注释（如 "NO awk, NO ROOT.xml, NEVER touch web.xml"），在全部部署脚本中，错误处理、路径回退、语义化状态码等防御性写法高度统一——这更像是把任务需求与约束提交给代码生成模型后的产出。我们可以判断其模式为"人工主导、AI 辅助"。

总结

本次攻击综合了开放目录工具包反查所得的多项手法：针对目标环境定制的冰蝎与蚁剑双套内存马、JVM 无文件注入、Meterpreter 持久化，以及利用 Dubbo 未授权调用批量查询订单数据并尝试窃取商户私钥，各环节均以不影响业务为前提，整体呈现前期情报充分、目标明确的定向作业特征。
