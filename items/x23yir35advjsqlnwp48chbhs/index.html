正文 · AI 翻译
中文原文

当开发者让 AI 编码代理“设置 GitHub MCP”时，代理必须选择一个软件包。Glow Labs 的新研究记录了若干会话，其中代理选择了一个来自已归档仓库的软件包，而该仓库以后不会再获得安全更新。

来源：Glow Security

Glow Labs 在审查真实的 AI 编码会话记录时，发现已弃用的 MCP 服务器被安装到开发者的机器上，并将这种现象称为 MCPhantom。在其中 98% 的会话里，代理似乎是从模型的训练数据中补全了软件包名称。另外 2% 中，用户点名要求使用旧软件包。该研究仅查看了安装或推荐了已弃用服务器的会话。

GitHub 维护着自己的 MCP 服务器。在 Glow Labs 记录的 GitHub 示例中，代理绕过了它，转而从训练数据中选取了一个已弃用的 Anthropic 参考服务器。该仓库已被归档，并声明不会再提供安全更新，但代理不会阅读归档通知。

同样的模式出现在 Claude Code、Cursor、Codex CLI、Claude Cowork 和 Claude chat，以及 Anthropic、OpenAI 和 xAI 的模型中。

四个漏洞，无补丁

这些参考服务器中发现了四个高危漏洞。最严重的是 Puppeteer 服务器中的远程代码执行漏洞，该漏洞允许代理操控浏览器。只需进行一次 提示注入即可触发。代理会启动机器上的任意进程，而不是浏览器，并执行攻击者选择的任何命令。开发者批准了网页浏览，而这一项权限随后被扩展到涵盖其余操作，因此运行框架会将其放行。

Glow Labs 的报告因超出范围而被关闭，维护人员回复称，该服务器已于 2025 年 5 月归档且无人维护，因此不会从该仓库发布修复。他们确实表示会考虑将 npm 软件包标记为已弃用，以便用户收到警告，但已弃用的软件包仍可通过 npx 安装。目前尚未发现遭到利用的情况，而且也不会有补丁发布。

使用量并未随着弃用而下降。自 2025 年 7 月以来，Glow Labs 统计到的这些已弃用软件包已从 npm 下载超过 1730 万次，其中五个位列 npm 的 MCP 100 热门榜。

为何现有控制措施保持沉默

这些服务器属于永远不会出现在依赖文件中的依赖项。EDR 看到的是一个受信任的 Node 进程应代理请求安装一个公开的 npm 软件包，这看起来属于常规操作。SCA 没有清单可用，因为服务器通过 npx 运行，而且这些漏洞没有 CVE。软件清单工具从未登记过该应用，因此只有在端点上才能看到它。

让代理在安装前先进行查询也不是解决办法。“仅在安装前查询本身并不够，”Glow 的漏洞研究员 Nadav Claude Cohen告诉 Help Net Security。“在一次会话中，代理在 npm 上检查了该软件包，得到回复‘此软件包已弃用。’但它仍然安装了软件包，而且从未告知用户。”

谁可以解决这个问题

Cohen 认为修复方案可能来自四个方面：

  • 运行框架厂商可以拒绝使用已弃用的服务器，或至少警告操作人员；还应涵盖已经安装的服务器，而不只是新安装的。不过，“这只有在每个运行框架都这么做时才有效。如果只有一个运行框架修复了问题，其他框架仍然会敞开心门。”
  • 模型厂商可以更新模型所掌握的信息：“只要模型的知识中仍包含旧软件包名称，代理就会继续安装它们”，不过“更新模型权重的成本非常高，因此这种情况不太可能发生。”
  • 软件包所有者可以修复这些漏洞，“这是唯一能够保护继续使用这些服务器的人的措施。”
  • 安全公司可以利用许多测试框架已经支持的执行前钩子：“这在今天就能用，无需等待测试框架制造商、模型制造商或软件包所有者的行动。”

卸载这些软件包并不可行。只有当某个软件包在过去一周内的下载量少于 300 次、仅有一个所有者且没有公开依赖项时，npm 才允许其所有者将其下架。Cohen 表示：“server-github 上周有 185,239 次下载，并有 6 个所有者。”npm 会移除包含恶意软件的软件包，但他没有发现因漏洞而移除软件包的案例。

安全团队可以先查找引用了已弃用的 @modelcontextprotocol 服务器的 MCP 配置，并在存在相应服务时切换到服务所有者的服务器，为每项服务批准一个服务器，同时将 npm 弃用状态纳入审批标准。

“该模型的记忆如今就像一个没有弃用反馈机制的包管理器，”表示，Glow 研发副总裁 Ophir Arie认为，各团队必须将智能体的决策视为可疑对象，并加以管控。
