简介

nginx 是世界上部署最广泛的 Web 服务器之一。找到其中未经身份验证即可远程执行代码的漏洞，长期以来一直是安全研究人员追求的“圣杯”。Xint 研究团队最近发现了五个。这些漏洞每一个都能单独导致远程代码执行，但影响的配置各不相同。

Xint 还在 Linux 内核中发现了一个独立漏洞，可以与任意一个 nginx 漏洞串联，以在主机上获取 root 权限。我们将这六个漏洞统称为 nginx2root。

如果你运行 nginx，请在修复版本发布后尽快更新到 1.31.9。本文解释了每个 nginx2root 漏洞的根本原因，并总结了我们对可利用性的评估。有关暴露情况检查，请参阅第 2 节；有关补丁和临时缓解措施，请参阅第 3 节。

2. 受影响版本及暴露情况检查方法

第 2 节重点介绍 CVE-2026-123007，这是影响服务器数量最多的漏洞。利用它只需要启用 HTTP/2。对于另外四个 nginx 漏洞，请先查看第 1 节中的配置表。

2.1. 受影响版本

CVE-2026-123007 影响从 1.9.5 到 1.31.8 的每个 nginx 官方发行版。截至 2026 年 11 月 10 日，易受攻击的代码仍存在于开发分支（master）中。

2.1.1. 受影响的 Linux 发行版

仅凭版本号可能无法判断服务器是否已修补。

最常见的三个版本是主要 Linux 发行版附带的默认软件包版本。Ubuntu 24.04 附带 1.24.0，Ubuntu 22.04 提供 1.18.0，Debian 12 提供 1.22.1。这些发行版可能会将安全修复反向移植到现有版本，而不是用新的 nginx 发行版替换。

反向移植可以在不改变 nginx -v 报告版本的情况下修复漏洞。只有发行版的完整软件包版本会发生变化。例如，Ubuntu 22.04 最初附带 1.18.0-6ubuntu14。截至 2026 年 10 月 26 日，安全更新已将软件包升级至 1.18.0-6ubuntu14.22，而 nginx 版本仍为 1.18.0。

要确定是否包含特定修复，请将完整的已安装软件包版本与发行版的安全公告进行比较。

2.2. 互联网暴露情况

截至 2026 年 11 月 10 日，Shodan 对 product:nginx 返回了 5670 万个主机。其中，1194 万个主机（21.1%）报告了可识别的版本。在已识别版本的主机中，98.9% 处于 CVE-2026-123007 受影响的版本范围内：1.9.5 至 1.31.8。

这些数字基于报告的版本字符串，不能确认服务器存在漏洞。利用 CVE-2026-123007 还需要启用 HTTP/2，并且报告的版本可能已经包含反向移植的修复。

2.3. 检查暴露情况的命令

如果服务器运行未修补的版本、包含 HTTP/2 模块并启用了 HTTP/2，则会受到 CVE-2026-123007 的影响。以下前三项检查分别测试这些条件，第四项检查是否可通过互联网访问 HTTP/2。本节末尾的表格说明了如何解读综合结果。

2.3.1. 检查版本

首先，输出 nginx 版本。

nginx -v 2>&1

该命令会输出类似 nginx version: nginx/1.31.8 的版本字符串。

  • 1.9.5 至 1.31.8：官方发行版包含易受攻击的代码。请继续进行后续检查。

  • 1.9.4 或更早版本：在 HTTP/2 支持之前发布，因此不受影响。

  • 1.31.9 或更高版本：可能已修补，但请确认该版本包含 my.f5.com/manage/s/article/K000164058 中引用的变更。

  • 发行版或设备专用版本：不要仅依赖版本字符串。请确认是否已回移此修复。

2.3.2。检查 HTTP/2 模块

检查该二进制文件是否使用 HTTP/2 模块构建。

nginx -V 2>&1 | grep -q -- '--with-http_v2_module' \
  && echo 'HTTP2_MODULE=present' \
  || echo 'HTTP2_MODULE=absent'

  • HTTP2_MODULE=present：该二进制文件包含 HTTP/2 代码；如果未修补，则存在漏洞。请继续进行下一项检查。

  • HTTP2_MODULE=absent：该二进制文件不包含 HTTP/2 代码，因此不受此漏洞影响。

2.3.3。检查配置中是否启用了 HTTP/2

在配置中搜索启用 HTTP/2 的指令。

sudo nginx -T 2>&1 \
  | sed 's/#.*//' \
  | grep -nE 'listen[[:space:]].*http2|^[[:space:]]*http2[[:space:]]+on[[:space:]]*;'

输出（例如 listen 443 ssl http2; 或 http2 on;）表示已启用 HTTP/2；没有输出表示未启用。请注意，nginx -T读取的是磁盘上的配置。如果你修改配置后未重新加载 nginx，运行中的配置可能有所不同。

2.3.4。检查能否通过 Internet 访问 HTTP/2

在网络外部的机器上运行以下命令。该命令会在 TLS 握手期间向服务器请求 HTTP/2。请将两个 {HOST} 占位符都替换为你的域名；如果使用的不是 443 端口，还需更改端口。

openssl s_client -connect {HOST}:443 -servername {HOST} -alpn h2 </dev/null 2>&1 \
  | grep -E 'ALPN protocol:|No ALPN negotiated|Connection refused|connect:errno|handshake failure'

如果看到 ALPN protocol: h2，则表示服务器接受来自 Internet 的 HTTP/2；No ALPN negotiated 表示不接受。其他任何输出都表示连接失败，因此请检查服务器是否可访问并重试。

如果 nginx 前面部署了 CDN 或反向代理，该测试只能访问到代理，因此还要直接对 nginx 服务器运行此测试。

3. 响应与建议操作

3.1. 立即操作

修复版本发布后，将 nginx 更新至 1.31.9，并确认所安装的版本包含针对全部五个漏洞的修复。如果无法立即修补，请应用第 3.3 节中与你的配置相对应的缓解措施。请注意，禁用 HTTP/2 只能解决五个 nginx 漏洞中的两个。

安装更新后，请重启 nginx 或完成受支持的二进制文件实时升级。仅重新加载配置无法替换正在运行的可执行文件。

3.2. 调查可能的攻击

利用 CVE-2026-123007 发动的攻击可能不会在 nginx 访问日志中留下多少证据。用于触发漏洞的 WINDOW_UPDATE 和 RST_STREAM 控制帧不会作为请求被记录，而且 TLS 会在传输过程中对其加密。以下小节介绍另外四个需要检查的位置：连接统计（3.2.1）、每个连接的请求数（3.2.2）、工作进程启动的程序（3.2.3）以及工作进程崩溃（3.2.4）。第 3.2.5 节说明如何综合评估这些结果。

3.2.1. 检查连接统计

在目标服务器上，检查端口 443 的 TCP 统计信息。

sudo ss -tinp state established '( sport = :443 )'

将命令运行两次，间隔一小段时间，并比较 bytes_received 和 bytes_sent 的变化。优先关注同时表现出以下多种情况的连接：

  • 来自同一个外部 IP 的连接持续开放数分钟

  • bytes_received 继续非常快速地增长

  • 服务器的 bytes_sent 远小于接收到的流量

  • 同一个外部 IP 还创建了许多短生命周期的 TLS 连接

这些模式与我们测试的攻击相符。它通过一个长连接发送大量 WINDOW_UPDATE 帧，因此 nginx 几乎不返回任何内容，而 bytes_received 会持续攀升。它还会从同一个 IP 打开许多短 TLS 连接。如果连续数分钟同时观察到这两种情况，且不存在合理的解释（例如大型上传），则应封禁该来源并展开调查。

3.2.2. 按连接审查请求

默认访问日志不会显示每个请求所属的连接。下面的日志格式增加了连接 ID（conn）、该连接上的请求数量以及每个请求的大小。将其添加到 nginx 的 http 块中。无需使用调试构建。

log_format h2_hunt '$time_iso8601 src=$remote_addr conn=$connection '
                   'requests=$connection_requests proto=$server_protocol '
                   'status=$status request_length=$request_length '
                   'bytes_sent=$bytes_sent request_time=$request_time';

access_log /var/log/nginx/h2-hunt.log h2_hunt;

验证并重新加载配置，然后仅显示 HTTP/2 请求。

sudo nginx -t && sudo nginx -s reload
sudo grep 'proto=HTTP/2.0' /var/log/nginx/h2-hunt.log | tail -n 200

从第 3.2.1 节获取一个可疑 IP，按 conn 汇总其日志条目中的 request_length。将该总和与 ss 针对同一 IP 显示的 bytes_received 进行比较。如果 bytes_received 持续快速增长，而记录的请求长度仍然很小，则说明客户端正在发送大量从未体现为请求的数据。这符合 HTTP/2 控制帧洪泛攻击的特征，与此次攻击相同。同一时间段内较长的 request_time 值也是另一项迹象。

3.2.3. 监控工作进程执行的命令

我们的漏洞利用使用 execve() 启动 shell 或其他程序。正常的 nginx 工作进程没有理由运行外部程序，因此它启动的任何程序都值得立即调查。首先，确定工作进程账户的 UID。

ps -eo uid,user,pid,ppid,args | grep '[n]ginx: worker process'

在使用 Linux audit 子系统 auditd 的系统上，将 NGINX_UID 替换为上一个输出中的数字 UID，并添加以下规则。

sudo auditctl -a always,exit -F arch=b64 -S execve,execveat \
  -F euid=NGINX_UID -k nginx_worker_exec

该规则只会记录安装后发生的执行行为。空结果不能排除此前已经遭到入侵。它还会匹配使用相同 UID 的其他进程，因此应检查进程和父进程 ID，以确定事件是否来自 nginx。

使用以下命令审查记录：

sudo ausearch -k nginx_worker_exec -ts recent -i

查找 /bin/sh、/bin/bash 或由 nginx 工作进程启动的任何其他程序。如果其他应用程序以同一账户运行，则应根据服务配置检查每个事件的父进程，以确定哪些事件来自 nginx。

3.2.4. 检查工作进程异常退出

漏洞利用尝试失败可能导致 nginx 工作进程崩溃，因此应使用以下命令查找异常退出和核心转储。

sudo grep -Ei 'worker process.*exited|signal 11|segfault' /var/log/nginx/error.log
sudo coredumpctl list nginx

工作进程可能因与攻击无关的原因崩溃。在得出结论前，应将这些记录与其他信号进行关联分析。

3.2.5. 评估证据

由 nginx 工作进程启动的程序（第 3.2.3 节）是攻击成功的最明确迹象。应立即进行调查。下面的迹象较弱，而且每一种单独出现都可能有正常原因。如果多种迹象同时出现且无法解释，则应封禁该来源并展开调查：

  • 持续的高入站流量（第 3.2.1 节）。

  • 来自同一来源的大量连接（第 3.2.1 节）。

  • 实际接收字节数与记录的请求长度之间存在巨大差异（第 3.2.2 节）。

  • 工作进程反复异常退出（第 3.2.4 节）。

3.3. 打补丁前的紧急缓解措施

在补丁发布之前，禁用受影响功能可以阻断已知的攻击路径。这些措施只是临时性的。修复版本发布后应立即安装。

3.3.1. 禁用 HTTP/2（CVE-2026-123007 和 CVE-2026-123633）

这两个漏洞都源于 nginx 处理 HTTP/2 连接的过程。在安装补丁之前，应在受影响的端口上禁用 HTTP/2。支持 HTTP/1.1 的客户端仍可继续使用该服务，但需要 HTTP/2 的服务（例如原生 gRPC）将受到影响。

对于 nginx 1.25.1 及更高版本，在每个受影响的 server 块中设置 http2 off;，并从其 listen 指令中移除所有旧版 http2 参数。检查所有共享同一监听地址和端口的 server 块。

listen 443 ssl;
http2 off;

对于 nginx 1.9.5 至 1.25.0，从 listen 443 ssl http2; 中移除 http2。

listen 443 ssl;

验证并重新加载配置。然后重复第 2.3.4 节中的 HTTP/2 检查，以确认更改已生效。

sudo nginx -t
sudo nginx -s reload
openssl s_client -connect HOST:443 -servername HOST -alpn h2 </dev/null 2>&1 | grep -F 'ALPN protocol: h2'

禁用 HTTP/2 后，最后一条命令不会输出任何内容。如果连接失败，它也不会输出任何内容，因此请确保站点仍可通过 HTTPS 正常加载。

3.3.2. 移除请求时 DNS 查找（CVE-2026-123634）

此缓解措施适用于按请求选择上游（后端）且还使用 mirror 的服务器。当 proxy_pass 中包含变量（例如 proxy_pass http://$host;），并且 nginx 在处理请求时使用其 resolver 通过 DNS 查找该名称时，就会出现这种情况。

该缺陷会在主请求及其镜像等待同一 DNS 响应时触发。在安装补丁之前，应将 proxy_pass 指向固定的上游组。这样可以移除请求期间的 DNS 查找，并阻断我们测试到的攻击路径。

设置 mirror_request_body on 也阻止了我们的利用，但这并不能修复解析器缺陷。不要仅依赖此设置。

如果不需要镜像，请在受影响的 location 中将其关闭，并将 proxy_pass 指向固定的上游。将 {BACKEND_IP} 替换为后端的 IP 地址，并根据需要调整端口：

upstream backend_hotfix {
    server {BACKEND_IP}:8080;
}
location / {
    mirror off;
    proxy_pass http://backend_hotfix;
}

如果需要镜像，请为主请求和镜像都使用固定的上游组。下面的示例将主请求和镜像发送到不同的后端；如果两者使用同一后端，请将它们指向同一个固定组：

upstream backend_main_hotfix {
    server [MAIN_SERVER_IP]:8080;
}
upstream backend_mirror_hotfix {
    server [MIRROR_SERVER_IP]:8080;
}
location / {
    mirror /mirror;
    proxy_pass http://backend_hotfix;
}
location = /mirror {
    internal;
    proxy_pass http://backend_mirror_hotfix;
}

验证并重新加载配置：

sudo nginx -t
sudo nginx -s reload

3.3.3. 禁用 HTTP/3（QUIC）（CVE-2026-121810）

该漏洞源于 nginx 在 QUIC 连接上处理 HTTP/3 请求流的方式，因此在安装补丁之前，应从受影响的服务中移除 QUIC 监听器。

在每个受影响的 server 块中，移除包含 quic 的 listen 指令，设置 http3 off，并将任何用于通告 HTTP/3 的 Alt-Svc 标头替换为 Alt-Svc 'clear'。基于 TCP 的常规 TLS 监听器会保留，因此结果应如下所示：

listen 443 ssl;
# listen 443 quic reuseport;
# listen [::]:443 quic reuseport;
http3 off;
add_header Alt-Svc 'clear' always;

验证并重新加载配置。然后检查是否仍有任何服务在端口 443 上接受 UDP 流量（根据需要调整端口）：

sudo nginx -t && sudo nginx -s reload
sudo ss -lunp 'sport = :443'

如果输出中仍显示 nginx，则说明 QUIC 监听器仍处于活动状态。为了增加防御，还应使用防火墙阻止该端口上的 UDP 流量。

3.3.4. 限制对邮件代理的访问（CVE-2026-113425）

此缓解措施仅适用于将 nginx 作为邮件代理置于 IMAP、POP3 或 SMTP 服务器之前的场景。如果 mail 块同时使用 proxy on 和 auth_http，则会受到影响。使用 auth_http 时，nginx 会向 HTTP 服务询问每次登录是否有效。该缺陷会在登录期间触发，攻击者无需有效凭据。在安装补丁之前，应确保不受信任的客户端无法访问邮件代理。

如果代理不需要外部访问，请将每个 IMAP、POP3 和 SMTP 监听器绑定到环回地址。这样只有同一台计算机上的程序才能连接。远程客户端（例如用户的邮件应用）将无法再访问该代理。例如：

listen 127.0.0.1:143;

验证并重新加载配置，然后确认邮件端口不再监听外部地址：

sudo nginx -t && sudo nginx -s reload
sudo ss -ltnp | grep -E ':(25|110|143|465|587|993|995)([[:space:]]|$)'

该命令会检查标准邮件端口。如果你的端口不同，请添加你的端口。如果外部客户端确实需要访问该代理，请使用防火墙仅允许你信任的 IP 地址。

3.3.5. 关闭现有连接

重新加载只会将新配置应用于新连接。已经打开的连接（例如 HTTP/2 或邮件会话）会继续使用旧工作进程，并继续采用旧配置。在 ps 中，这些工作进程显示为 nginx: worker process is shutting down。

如果重新加载后这些工作进程仍在运行，请通过服务管理器重启 nginx（例如 systemctl restart nginx）。重启会强制断开所有客户端连接，并中断正在进行的下载、上传和邮件会话，因此预计服务会短暂中断。

5. nginx 漏洞的技术分析

本节 examines 五个 nginx 漏洞。CVE-2026-123007 源于窗口计算错误，该错误会导致越界写入。另外四个是释放后重用漏洞。对于每个漏洞，我们将解释相关的 nginx 功能与行为，追踪漏洞背后的代码，并概述其如何导致远程代码执行。我们会说明如何实现地址泄露和可控内存破坏，但有意省略了复现完整漏洞利用所需的最后步骤。

5.1. CVE-2026-123007

CVE-2026-123007 是 HTTP/2 流控中的整数溢出漏洞。发送窗口超过允许的最大值，最终产生无效的内存复制长度，进而导致堆上的越界读取和写入。

5.1.1. nginx 如何管理 HTTP/2 发送窗口

HTTP/2 通过单个连接处理多个请求和响应。每个请求与响应对应使用一个流。客户端创建的流会获得称为 Stream ID 的不同标识符，例如 1、3 和 5。在每个流内，HEADERS 帧承载标头，DATA 帧承载正文。

HTTP/2 使用流控机制，防止服务器发送的数据超过客户端准备好接收的数据量。服务器通过发送窗口跟踪这一状态，每个流各有一个窗口，整个连接还有一个窗口，称为 h2c 窗口。每个窗口记录服务器仍可发送的 DATA 数量。只有当该流的窗口和 h2c 窗口都有足够额度时，服务器才能在该流上发送 DATA。当客户端准备好接收更多数据时，它会发送一个 WINDOW_UPDATE 帧，服务器相应增加对应窗口的额度。

WINDOW_UPDATE 中的 Stream ID 决定增加哪个窗口的额度。Stream ID 0 会更新 h2c 窗口，而非零 Stream ID 只更新该流的窗口。

nginx 的默认窗口为 65,535（0xffff），最大值为 0x7fffffff（(1U << 31) - 1）。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.h#L50-L51
#define NGX_HTTP_V2_MAX_WINDOW      ((1U << 31) - 1)
#define NGX_HTTP_V2_DEFAULT_WINDOW  65535

nginx 在通过套接字发送帧之前，会将其保存在内存中的输出队列里。当它将响应 DATA 加入队列时，ngx_http_v2_send_chain() 会从连接级发送窗口 h2c->send_window 和流的发送窗口 stream->send_window 中扣除 DATA 的长度。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1232-L1244
ngx_http_v2_queue_frame(h2c, frame);
h2c->send_window -= frame_size;
stream->send_window -= frame_size;
stream->queued++;

如果流在 DATA 发送之前被取消，ngx_http_v2_filter_cleanup() 会从队列中移除该流剩余的 DATA 帧，并把已扣除的长度返还给连接级发送窗口。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1719-L1767
h2c->send_window += window;

nginx 在将 DATA 加入队列时扣除额度，并在流于 DATA 发送前被取消时返还该额度。这两个步骤本身都是有效的。问题在于两者之间可能发生的情况。当 DATA 仍在队列中时，客户端可以发送一个 WINDOW_UPDATE，再次提高窗口额度。如果随后取消该流，清理过程会在已提高的窗口额度之上再加上返还的额度。清理过程从不根据 HTTP/2 最大值检查结果，因此 h2c->send_window 最终可能超过允许的上限。

5.1.2. 漏洞详情

从窗口记账错误到命令执行的序列概括如下。小节 (1) 涵盖步骤 1–2，小节 (2) 涵盖步骤 3，小节 (3) 从较高层面涵盖步骤 4–6。

步骤

说明

  1. 将 DATA 保留在队列中

将响应正文加入队列，并从发送窗口中扣除其长度，同时防止 DATA 到达客户端。

  1. 提高窗口额度，返还队列中的额度

通过 WINDOW_UPDATE 提高发送窗口，然后取消这些流，使清理过程加上为队列中 DATA 扣除的额度。

  1. 绕过上限检查

一旦共享连接窗口超过其最大值，剩余容量计算就会失效，后续的 WINDOW_UPDATE 帧仍会被接受。

  1. 创建异常复制长度

代码将相同的位分别解释为有符号值和无符号值，从而把一个较小的负距离转换为非常大的复制长度。

  1. 泄露地址并破坏内存

将复制的两端定位到响应中返回的内存指针处，从而破坏 TLS 分配元数据。

  1. 控制清理回调

利用泄露的地址和被破坏的内存覆写清理函数指针，然后在清理调用该函数时执行任意命令。

(1) 返还队列额度时超过 31 位限制

第一个目标是在 nginx 的输出队列中累积 DATA，使其已消耗窗口额度但尚未发送。

客户端首先将连接发送窗口提高到最大值（Wmax），并在 Stream ID 0 上发送一个带有 WINDOW_UPDATE 的帧。客户端通过 SETTINGS 帧中的 SETTINGS_INITIAL_WINDOW_SIZE 设置新流的初始发送窗口。将其设为 0 可以让 nginx 创建响应 HEADERS，但会阻止其发送 DATA。这会使响应正文保持挂起状态，直至客户端选择释放它们。

接下来，客户端停止读取并突发发送 PING 帧。nginx 会将控制帧响应（包括 PING 确认）放在待处理的 DATA 之前，因此这些确认会填满 TLS 和 TCP 发送缓冲区。随后，客户端为每个流发送足够覆盖其整个响应正文的 WINDOW_UPDATE 信用额度，导致 nginx 将 DATA 排队并从连接发送窗口中扣除其长度。由于 TLS 和 TCP 缓冲区已经填满，这些 DATA 会无限期保持排队状态。

设 Q 为这些已排队 DATA 的总量。客户端现在两次将 Q 加回 h2c 窗口。首先，它在 Stream ID 0 上发送一个授予 Q 信用额度的 WINDOW_UPDATE。其次，它发送 RST_STREAM 以取消这些流。取消操作会触发清理，丢弃未发送的 DATA 并返还其信用额度，从而再次将 Q 加入 h2c 窗口。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1723-L1767
if (frame->stream == stream && !frame->blocked) {
    *fn = frame->next;
    window += frame->length;
}
h2c->send_window += window;

这第二次增加（显示在上面的最后一行）没有上限检查。因此，h2c 窗口会依次经过四个值：

  • Wmax：客户端将窗口提高到最大值。

  • Wmax - Q：将 DATA 排队会扣除 Q。

  • Wmax：Stream ID 0 上的 WINDOW_UPDATE 返还 Q。

  • Wmax + Q：清理第二次返还 Q，使窗口超过 31 位限制。

确切的响应大小和流数量并不重要。关键在于，同一个已知数量 Q 被加了两次，一次由 WINDOW_UPDATE 完成，另一次由清理操作完成。

(2) 窗口检查中的无符号下溢

ngx_http_v2_state_window_update() 在应用增量之前计算剩余容量。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.c#L2564-L2575
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window) {
    return ngx_http_v2_connection_error(h2c, NGX_HTTP_V2_FLOW_CTRL_ERROR);
}
h2c->send_window += window;

此检查仅在共享连接窗口等于或低于 Wmax 时有效。h2c->send_window 的无符号类型为 size_t，而上一步已将其改为 Wmax + Q。因此，剩余容量表达式的值为 Wmax - (Wmax + Q)；如果按有符号值解释，它将为负数，但无符号算术会将其回绕为一个非常大的正值。

nginx 将此值视为可用容量，并继续接受 h2c 的连接级 WINDOW_UPDATE 帧。每次增量仍符合 HTTP/2 规范，但该检查未能检测到当前窗口已经超出有效范围。重复此过程可以将发送窗口提高到任意 64 位值。

(3) 从超大窗口到越界复制

h2c->send_window 的无符号类型为 size_t。在 64 位目标平台上，将其增大到比如 2^64 - d 后，按无符号值看会显得非常大，但转换为有符号类型 off_t 后会得到一个较小的负值 -d。

ngx_http_v2_send_chain() 将此值移入 DATA 帧大小。它首先将发送窗口与 limit 比较，后者即当前调用可以发送的最大数量。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1144-L1146
if (limit == 0 || limit > (off_t) h2c->send_window) {
    limit = h2c->send_window;
}

正数 limit 大于 -d，因此条件成立，limit 也会变为 -d。

下一次比较使用 frame_size（当前 DATA 帧大小）和 limit。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1163-L1166
if ((off_t) frame_size > limit) {
    frame_size = (size_t) limit;
}

正数 frame_size 大于 -d，因此此条件也成立。将 -d 转换回 size_t 会得到 2^64 - d，用一个非常大的值取代正常的 DATA 大小。

nginx 将该值存储在 rest 中，该字段跟踪尚未附加到缓冲区的长度。随后，它将此值传递给 ngx_http_v2_filter_get_shadow()，以设置缓冲区的起始和结束指针。

// Call site: https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1169-L1207
// Implementation: https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2_filter_module.c#L1287-L1308
rest = frame_size;
cl = ngx_http_v2_filter_get_shadow(stream, in->buf, offset, rest);
static ngx_chain_t *
ngx_http_v2_filter_get_shadow(ngx_http_v2_stream_t *stream, ngx_buf_t *buf,
    off_t offset, off_t size)
{
    chunk->last = chunk->pos + size;
}

作为 off_t，size 保存 -d，因此 chunk->last 指向 chunk->pos 之前 d 个字节的位置。TLS 输出路径随后会将这两个指针之间的差值用作复制长度。

// Declaration: https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/event/ngx_event_openssl.c#L3054-L3057
// Copy path: https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/event/ngx_event_openssl.c#L3137-L3150
ssize_t size;
size = in->buf->last - in->buf->pos;
ngx_memcpy(buf->last, in->buf->pos, size);

last - pos 是 -d，但传给 memcpy() 的长度参数是 size_t。最终转换会将其变回 2^64 - d，同时传入一个非常大的复制长度。

复制将近 2^64 字节通常会越过堆末尾并使 worker 崩溃。但在这里不会，这是因为 glibc 对大型复制的处理方式。我们实验所用的 x86-64 glibc memcpy() 路径不会从前向后复制。它先加载源地址的起始位置和结束位置，然后通过一个循环复制中间部分，该循环从目标地址末尾向后遍历至 dest。

目标地址的末尾是 dest + size。加上 size = 2^64 - d 后，该求和会溢出 64 位地址空间并回绕至 dest - d，后者比 dest 低 d 字节。由于现在末尾位于起始位置下方，向后循环执行一轮后便停止，因此大块中间区域从未被触及。这种每次移动四个 32 字节向量的向后复制结构，自 2016 年发布的 2.24 版本起就已存在于 glibc 的 x86-64 实现中。

下面展示的是 glibc 2.41 AVX2 路径的简化版本。

# Introduced in: https://github.com/bminor/glibc/blob/glibc-2.24/sysdeps/x86_64/multiarch/memmove-vec-unaligned-erms.S#L413-L462
# https://github.com/bminor/glibc/blob/glibc-2.41/sysdeps/x86_64/multiarch/memmove-vec-unaligned-erms.S#L513-L554
head = load128(src)
tail = load32(src + size - 32)
end = (dest + size) mod 2^64
cursor = align_down(end - 129, 32)
do {
    copy128(dst=cursor, src=src + (cursor - dest))
    cursor -= 128
} while (cursor > dest)
store128(dst=dest, data=head)
store32(dst=end - 32, data=tail)

align_down(x, 32) 将 x 向下取整至 32 字节边界。当 end 按 32 字节对齐时，如下方示例所示，cursor = align_down(end - 129, 32) 会变为 end - 160。glibc 从此位置复制 128 字节，并单独复制最后 32 字节。

end - 160                         end - 32             end
    |---------- 128 bytes ----------|------ 32 bytes -----|
              loop copy                    fixed copy

由于 cursor 已经低于 dest，循环仅运行一次。长中间区域被跳过，仅需复制最前面的 128 字节和最后的 160 字节。

src ~ src + 127                    -> dest ~ dest + 127
src - d - 160 ~ src - d - 1       -> dest - d - 160 ~ dest - d - 1

dest 是 TLS 明文缓冲区中的下一个写入位置，因此它恰好位于 nginx 已写入内容之后。在响应正文之前，nginx 会写入客户端控制帧的确认响应，而客户端可以控制发送多少个此类帧。在 nginx 源码中，HTTP/2 帧头为 9 字节，PING 数据为 8 字节，SETTINGS ACK 数据为 0 字节。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.h#L27
#define NGX_HTTP_V2_FRAME_HEADER_SIZE    9
// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.c#L30-L34
#define NGX_HTTP_V2_SETTINGS_ACK_SIZE    0
#define NGX_HTTP_V2_PING_SIZE            8

因此，不带 ACK 标志的 PING 会产生 17 字节的 PING ACK，而 SETTINGS 会产生 9 字节的 SETTINGS ACK。如果客户端发送 p 个 PING 帧和 s 个 SETTINGS 帧，nginx 首先生成 17p + 9s 字节的响应。加上随后 9 字节的 DATA 帧头，便得到了下一个响应正文的起始位置。

P = 17p + 9s + 9
dest = TLS + P

客户端使用 WINDOW_UPDATE 调整发送窗口，使其变为 d = P - 64。此时复制末尾 dest - d 变为 TLS + 64。160 字节区域随后横跨 TLS 缓冲区正前方的 96 字节，以及该缓冲区内部最前面的 64 字节。

第二次移动会将 src - d 正下方的 160 字节复制到 TLS 缓冲区的边缘。攻击者希望这些字节中包含两项内容：一个用于覆盖 TLS 缓冲区之前堆元数据的选定值，以及位于缓冲区内部并在响应中回传的指针。请求池中同时具备这两者。它保存请求的标头，以及描述这些标头并指向 nginx 映像和堆的 nginx 数据结构。为了将 src 移到那里，攻击者发送一个请求多个字节范围的 Range 标头。nginx 随后构建一个 multipart 响应，其开头是一个在请求池中分配的边界字符串，因此 src 指向该处。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/modules/ngx_http_range_filter_module.c#L484-L505
ctx->boundary_header.data = ngx_pnalloc(r->pool, size);
// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/modules/ngx_http_range_filter_module.c#L867-L882
b->pos = ctx->boundary_header.data;

b->pos 在经过输出路径时变为 in->buf->pos，因此它就是最终 memcpy() 所使用的 src。

借助请求池中的 src，攻击者使用 Cookie 字段填充 src - d 下方的 160 字节。当同一请求包含多个 Cookie 字段时，nginx 会为每个分隔符增加两个字节以计算总长度，然后使用 "; " 连接这些值。它将长度和合并后缓冲区的地址存储在请求标头结构中。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.c#L3725-L3769
len += vals[i].len + 2;
len -= 2;
h->key.data = cookie.data;
h->value.len = len;
h->value.data = buf;

h->key.data指向nginx映像中的一个静态字符串，而h->value.data指向堆上的Cookie缓冲区。因此，该结构包含一个由攻击者控制的长度，以及指向nginx映像和堆的指针。

如果当前请求池块有足够的空间，nginx会将新的小分配紧接在上一个分配之后放置。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/core/ngx_palloc.c#L157-L166
m = p->d.last;
if ((size_t) (p->d.end - m) >= size) {
    p->d.last = m + size;
    return m;
}

Cookie数量和长度控制数据及其位置，而Range和URI长度则确定用作src的multipart缓冲区的位置。这允许将紧邻src - d之前的160字节布置如下。

Source:      [96 bytes containing the value for the size field][64 bytes of code and heap pointers]
Destination: [96 bytes before the TLS buffer, containing heap metadata][first 64 bytes of the TLS plaintext buffer]

前96字节会覆盖TLS明文缓冲区之前堆区域中的size字段。剩余的64字节会在TLS响应中发送，从而泄露nginx映像地址和堆地址。因此，一次格式错误的复制同时造成越界写入和地址泄露。这些漏洞可用于覆盖清理函数指针，并以nginx工作进程权限执行命令。我们省略了详细的函数指针覆写过程。

5.2. CVE-2026-123634

CVE-2026-123634是nginx DNS解析器逻辑中的一个释放后重用漏洞。请求的处理程序可以释放等待列表循环尚未处理的另一个解析器上下文，而该循环随后继续使用已释放的内存。

5.2.1. nginx在请求时如何解析上游名称

nginx可以充当地反向代理，将客户端请求转发到后端服务器（称为上游）进行处理。proxy_pass配置指令指定上游的位置。

上游可以在配置中固定，也可以从请求中选择。例如，proxy_pass http://$host;使用$host中的请求主机名作为目标地址。该值通常来自客户端的Host标头。如果nginx需要通过DNS查询获取服务器的IP地址，它会向resolver指令指定的DNS服务器发起查询。

由于DNS解析需要时间，nginx在等待DNS应答期间会继续处理其他请求。每次查询都有一个解析器上下文（ngx_resolver_ctx_t），用于保存其状态、结果，以及查询完成后要调用的handler。

解析器在一个节点中跟踪每个域名。如果同一名称的查询已在进行中，nginx不会发送第二次查询，而是倾向于将新上下文推入该节点等待列表的头部。

当应答最终到达时，解析器通过将rn->waiting设置为NULL，将等待列表从节点中分离出来。然后，它遍历该列表并调用每个上下文的handler，在每次调用前将下一个上下文保存到next中。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/core/ngx_resolver.c#L2131-L2147
next = rn->waiting;
rn->waiting = NULL;
...
while (next) {
    ctx = next;
    ctx->state = code;
    ctx->valid = ngx_time() + (r->valid ? r->valid : 10);
    next = ctx->next;
    ctx->handler(ctx);
}

因此，释放列表中较后上下文的处理程序会使 next 变成悬空指针。不过，不同的请求不会导致此问题，因为终止一个请求只会释放它自己的上下文。因此，只有当两个上下文来自同一请求时，这才构成漏洞。

在我们的测试中，只发现一个配置选项会创建两个附加到同一请求的上下文。mirror 配置指令会将请求复制到第二个位置，作为后台子请求。它通常用于将实时流量的副本发送到测试系统。如果主请求及其镜像使用相同的上游名称，它们的上下文可能会在同一节点上等待 DNS 应答。

5.2.2. 漏洞详情

(1) 终止主请求会释放镜像的上下文

如果 DNS 查找失败，主请求的 ngx_http_upstream_resolve_handler() 会尝试发送 502 响应。如果客户端已重置 TCP 连接，该写入操作可能会失败，导致 ngx_http_terminate_request() 终止主请求。

主请求的 cleanup 列表包含镜像的上游清理项，因此以下清理代码也会为镜像运行，即使其 DNS 结果尚未被处理。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/ngx_http_upstream.c#L4802-L4805
if (u->resolved && u->resolved->ctx) {
    ngx_resolve_name_done(u->resolved->ctx);
    u->resolved->ctx = NULL;
}

随后，ngx_resolve_name_done() 释放镜像的上下文，而解析器循环仍在 next 中持有该上下文。

(2) 解析器使用已释放的上下文

在解析器循环到达镜像上下文之前，该上下文仍处于状态 NGX_AGAIN。在释放处于此状态的上下文之前，ngx_resolve_name_done() 会尝试将其从节点的等待列表中取消链接。但循环已经分离该列表并将 rn->waiting 设置为 NULL。搜索找不到任何内容，而上下文仍然被释放。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/core/ngx_resolver.c#L554-L595
if (ctx->state == NGX_AGAIN || ctx->state == NGX_RESOLVE_TIMEDOUT) {
    rn = ctx->node;
    if (rn) {
        p = &rn->waiting;
        w = rn->waiting;
        while (w) {
            ...
        }
        ngx_log_error(NGX_LOG_ALERT, r->log, 0,
                      "could not cancel %V resolving", &ctx->name);
    }
}
done:
    ...
    ngx_resolver_free_locked(r, ctx);

随后控制权返回解析器循环，该循环前进到保存在 next 中的上下文，即镜像的已释放上下文。循环现在通过写入 ctx->state 和 ctx->valid、读取 ctx->next 并调用 ctx->handler(ctx) 来触发释放后使用。如果另一次分配重新占用了已释放上下文的内存，则 next 和 handler 都可由攻击者控制。因此，攻击者可以重定向列表遍历和最终的间接调用，从而控制程序执行。

要执行任意代码，我们首先需要获取一个地址泄露。有趣的是，这个漏洞本身就可用于泄露信息。glibc 的空闲链表指针会覆盖上下文的 next 字段，因此循环的 next“上下文”是一个已释放的 DNS 记录数组，其内容由我们选择。随后我们采用一种技巧：将受控处理程序指向 vsyscall gettimeofday() 地址（在 amd64 系统上是固定的），伪造堆块大小，并将 glibc 和堆指针放入 nginx 向我们控制的服务器发送的 DNS 查询中。

在完成信息泄露后，我们可以让循环通过该数组指向待处理请求体中的伪造 context，并将其处理程序设置为 system()，从而在主机上获得任意命令执行能力。

5.3. CVE-2026-123633

CVE-2026-123633 是一处释放后重用漏洞，源于仍符合条件的活动 HTTP/2 连接保留在可排空状态。当请求打开上游连接时，nginx 可能关闭该请求自身的 HTTP/2 连接并释放其内存，而上游代码仍在继续访问它。此漏洞要求 nginx 打开上游连接，这在 nginx 的生产环境中很常见。

5.3.1. nginx 在压力下如何重用连接

每个 nginx worker 都有固定数量的连接槽位，由 worker_connections 设置。客户端连接和上游连接共用这些槽位。当槽位即将耗尽时，nginx 会关闭空闲连接，以回收槽位供其他用途使用。为了跟踪哪些连接可以被回收，nginx 会在连接满足某些特定于协议的条件时将其标记为 reusable，例如空闲的 HTTP/1.1 keep-alive 连接或没有活动流的 HTTP/2 连接。这些 reusable 连接会被跟踪在一个专用队列中。

在分配槽位之前，ngx_get_connection() 会调用 ngx_drain_connections()。如果空闲槽位不超过 1/16，且可重用队列非空，nginx 会从最旧的条目开始关闭连接，这一过程称为“排空”。

排空过程会设置 c->close，并直接调用每个选定连接的读取处理程序。这些调用是同步的，只有在处理程序返回后，才会继续分配槽位。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/core/ngx_connection.c#L1411-L1442
if (cycle->free_connection_n > cycle->connection_n / 16
    || cycle->reusable_connections_n == 0)
{
    return;
}
...
n = ngx_max(ngx_min(32, cycle->reusable_connections_n / 8), 1);
for (i = 0; i < n; i++) {
    ...
    q = ngx_queue_last(&cycle->reusable_connections_queue);
    c = ngx_queue_data(q, ngx_connection_t, queue);
    ...
    c->close = 1;
    c->read->handler(c->read);
}

5.3.2. 漏洞详情

(1) 活动 HTTP/2 连接仍留在可重用队列中

当 HTTP/2 连接没有活动流或待发送的输出帧时，ngx_http_v2_handle_connection() 会将其作为可重用连接加入队列。如果最后一次读取停止在某个帧的中间，h2c->state.incomplete 会被设置，但该标志仅在连接加入队列之后才会被检查：

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.c#L628-L674
if (h2c->last_out || h2c->processing) {
    return;
}
...
ngx_reusable_connection(c, 1);
if (h2c->state.incomplete) {
    return;
}

通常，空闲连接的读取处理程序会被更新为 ngx_http_v2_idle_handler()，从而在数据到达时将其移出队列。然而，当 ngx_http_v2_handle_connection 因帧不完整而提前返回时，连接仍保留正常的 ngx_http_v2_read_handler()，而它永远不会将连接移出可重用队列。

因此，该缺陷的触发方式如下：

  1. 客户端发送 HEADERS 帧的第一部分，使连接进入可重用队列。

  2. 随后客户端发送剩余部分，从而打开一个流。

  3. 如果该请求打开上游连接并触发排空，排空过程可能会回收新打开的流所使用的连接。

(2) 上游连接释放了其自身请求

为了连接到上游，请求需要另一个连接槽位。ngx_event_connect_peer() 调用 ngx_get_connection()，在槽位不足时运行排空过程。此时，留在可重用队列中的 HTTP/2 连接可能会被选中关闭。

HTTP/2 读取处理程序看到 c->close 后会尝试发送 GOAWAY，但如果客户端已经重置了 TCP 连接，发送就会失败，随后 ngx_http_v2_finalize_connection() 会关闭该连接及其流。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/v2/ngx_http_v2.c#L356-L382
if (c->close) {
    c->close = 0;
    ...
    if (!h2c->goaway) {
        h2c->goaway = 1;
        if (ngx_http_v2_send_goaway(h2c, NGX_HTTP_V2_NO_ERROR)
            == NGX_ERROR)
        {
            ngx_http_v2_finalize_connection(h2c, 0);
            return;
        }
        if (ngx_http_v2_send_output_queue(h2c) == NGX_ERROR) {
            ngx_http_v2_finalize_connection(h2c, 0);
            return;
        }
    }

关闭该流会调用 ngx_http_free_request()，从而销毁包含请求 r 及其上游结构 u 的请求池。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/http/ngx_http_request.c#L4062-L4071
/*
 * Setting r->pool to NULL will increase probability to catch double close
 * of request since the request object is allocated from its own pool.
 */
pool = r->pool;
r->pool = NULL;
ngx_destroy_pool(pool);

排空过程返回后，nginx 会继续运行已被释放请求的上游代码。它会连接到上游、发送代理请求，并处理该连接上的事件，而这一切都通过已释放的 r 和 u 进行。

利用某些堆布局整理技术，我们可以让一个 glibc largebin 头部恰好位于 u 上方，并让该头部的 bk_nextsize 字段位于 u->peer.sockaddr 上。此时，它会指向我们控制的字节（对于我们自己的服务器而言是一个 sockaddr_in），导致上游连接实际连接到我们自己的服务器。

为了绕过 ASLR，我们只需接受连接，随后 nginx 会发送已释放的请求缓冲区，而该缓冲区此时包含各种指针值。worker 随后崩溃，但其替代 worker 具有相同的地址布局。

为了执行命令，我们使用另一种堆整理技术，回收已释放的请求，并将其替换为一个伪造请求，其上游读取处理程序为 execv()。当我们拒绝连接时，epoll 会报告错误，随后 nginx 会调用该处理程序。

5.4. CVE-2026-121810

CVE-2026-121810 是一个释放后重用漏洞，其成因是在某个 HTTP/3 请求仍在运行时关闭 QUIC 连接。在流创建期间，父 QUIC 连接被错误地设为可进入排空状态。随后，该请求连接上游时，便会释放其自身的请求内存。

该漏洞与 CVE-2026-123633 类似，但触发机制略有不同，因此我们的文章将省略之前已经介绍过的一些定义和背景信息。因此，我们建议在阅读本节前先阅读第 5.3 节。

5.4.1. nginx 如何将 HTTP/3 流作为连接处理

HTTP/3 通过一个 QUIC 连接承载多个请求流，但 nginx 在内部会为该 QUIC 连接分配一个 ngx_connection_t，并为每个流额外分配一个。所有这些对象都来自同一 worker 的连接槽位，因此创建请求流也需要一个空闲槽位。我们将这些流所属的 QUIC 连接称为父连接。QUIC 连接和等待标头的 HTTP/3 请求流都可能进入可排空状态。

当单个流关闭时，nginx 会检查父连接是否也可以被排空。ngx_quic_can_shutdown() 遍历父连接的流树，如果所有剩余流都可取消，nginx 便会将父连接放入可重用队列。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/event/quic/ngx_event_quic_streams.c#L1168-L1170
if (!pc->reusable && ngx_quic_can_shutdown(pc) == NGX_OK) {
    ngx_reusable_connection(pc, 1);
}

5.4.2. 漏洞详情

(1) 在流创建期间重新将 QUIC 连接入队

在为新流分配连接槽位之前，ngx_quic_create_stream() 会将父连接从可重用队列中取出，其目的是防止 ngx_get_connection() 在分配槽位期间排空父连接。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/event/quic/ngx_event_quic_streams.c#L734-L743
reusable = c->reusable;
ngx_reusable_connection(c, 0);
sc = ngx_get_connection(c->fd, log);
if (sc == NULL) {
    ngx_destroy_pool(pool);
    ngx_queue_insert_tail(&qc->streams.free, &qs->queue);
    ngx_reusable_connection(c, reusable);
    return NULL;
}

然而，新流只有在连接槽位分配完成后才会进入父连接的流树。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/event/quic/ngx_event_quic_streams.c#L814
ngx_rbtree_insert(&qc->streams.tree, &qs->node);

假设排空操作关闭了同一父连接上的一个现有空闲流。如果该流的两个方向均已完成，它就可能触发决定父连接是否可排空的检查，但该检查无法看到仍在创建的流。如果树中没有其他不可取消的流，nginx 便会将父连接重新放入可重用队列，即使新流之后已创建，它仍会留在该队列中。

(2) 上游连接释放请求

当新流的请求连接上游时，它需要另一个槽位，这可能再次触发排空操作，并选中刚刚入队的父 QUIC 连接。ngx_quic_close_connection() 调用 ngx_quic_close_streams() 来关闭父连接的各个流，从而终止上游连接仍在进行中的请求。

ngx_http_free_request() 销毁请求池，其中包括上游结构 u。随后控制流返回 ngx_event_connect_peer()，后者继续使用已释放的 u->peer，从而导致释放后重用。

从这里开始，ASLR 绕过和控制流劫持路径与第 5.3.2 节中的路径相同，因此为简洁起见在此省略。

5.5. CVE-2026-113425

CVE-2026-113425 是邮件代理的 auth_http 身份验证路径中的释放后重用漏洞。关闭客户端连接会释放其会话，但与身份验证服务的连接仍保持打开。该连接上随后发生的事件会使用已释放的会话。

5.5.1. 邮件代理如何对客户端进行身份验证

nginx 可以在客户端与邮件服务器之间代理 IMAP、POP3 和 SMTP。客户端登录时，nginx 会询问一个通过 auth_http 配置的 HTTP 服务，以确定凭据是否有效以及应使用哪个后端邮件服务器。

在此查询期间，nginx 会维护两个连接：一个连接客户端，另一个连接 HTTP 身份验证服务；后者称为 auth 连接。

ngx_mail_auth_http_init() 创建一个带有独立内存池的查询上下文。然而，auth 连接的 data 和 pool 字段分别指向客户端会话 s 和客户端连接的内存池。在 auth 连接使用该会话期间，该内存池必须保持已分配状态。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/mail/ngx_mail_auth_http_module.c#L216-L221
ctx->peer.connection->data = s;
ctx->peer.connection->pool = s->connection->pool;
s->connection->read->handler = ngx_mail_auth_http_block_read;
ctx->peer.connection->read->handler = ngx_mail_auth_http_read_handler;
ctx->peer.connection->write->handler = ngx_mail_auth_http_write_handler;

5.5.2. 漏洞详情

查询开始时，客户端的读处理程序会被替换为 ngx_mail_auth_http_block_read()。如果重新设置读事件失败，该处理函数会关闭 auth 连接并释放查询池。然而，客户端的写处理程序仍为 ngx_mail_send()，其错误路径不会清理 auth 连接。该缺陷在于，这个写处理程序可以在 auth 连接仍指向客户端连接时关闭客户端连接。

(1) 查询期间释放客户端会话

此路径要求事先注册客户端的写事件。例如，如果客户端停止读取响应并填满套接字的发送缓冲区，send 会返回 EAGAIN。随后 ngx_mail_send() 会注册写事件，以便重试。

如果登录命令和 TCP 重置在同一轮事件循环迭代中得到处理，nginx 会通过运行当前活动的读处理程序、随后运行写处理程序，来处理 epoll 报告的套接字错误。读处理程序解析登录命令，然后启动身份验证查询，此时 s->out 中仍有回复处于排队状态。

随后 ngx_mail_send() 会尝试发送排队的回复。写入在已重置的套接字上失败，因此它会关闭客户端连接并销毁其内存池。

// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/mail/ngx_mail_handler.c#L812-L815
if (n == NGX_ERROR) {
    ngx_mail_close_connection(c);
    return;
}
// https://github.com/nginx/nginx/blob/140aa942711868a8daeb95810bc9a81f272ada72/src/mail/ngx_mail_handler.c#L966-L972
c->destroyed = 1;
pool = c->pool;
ngx_close_connection(c);
ngx_destroy_pool(pool);

会话 s 及其模块上下文数组均分配自现已释放的内存池。重要的是，auth 连接仍保持打开，其 data 字段仍指向 s。

(2) Auth 连接使用已释放的会话

下一个事件（例如连接完成、响应或超时）会在 auth 连接上运行处理程序。读处理程序和写处理程序都会从连接的 data 字段获取会话指针，并使用它来获取查询上下文，从而访问已释放会话中的 s->ctx。如果攻击者控制的数据重新占用了该内存，s->ctx 就可能指向伪造的上下文。身份验证响应路径随后会调用 ctx->handler，从而为攻击者提供控制流劫持。

为了绕过 ASLR，我们利用过期认证连接的超时机制。通过进行一些堆内存整理，超时机制会释放一块内存，而该内存此时保存着来自另一个连接的部分接收到的 IMAP 命令。后续分配操作会重新占用该内存并写入堆指针，当 nginx 回复该 IMAP 命令时，又将这些指针回显给我们。

为了执行命令，我们在一个全新的 worker 上再次运行触发器。会话被释放后不久，一个带有受控密码的 IMAP LOGIN 会通过伪造会话重新占用该内存。它的 s->ctx 指向一个伪造的查找上下文，而该上下文的 handler 是 system()。当认证服务回复时，ngx_mail_auth_http_read_handler() 会跟随这个过期会话并调用 system(s)。

6. Linux 内核分析LPE漏洞分析

nginx 漏洞可使攻击者以 worker 权限执行代码。worker 通常在受限权限下运行，因此要完全控制主机，还需要一个权限提升漏洞。我们研究了 Linux 内核，并发现了其 SCTP 子系统中的零日漏洞。将该漏洞与其中一个 nginx 漏洞串联起来，可使我们在主机上获得 root 权限。当 nginx 运行在 Docker 容器中时，这种方法同样有效。

本节介绍该 SCTP 漏洞的成因以及我们的验证结果。在内核补丁发布之前，我们暂不公开复现或利用该漏洞所需的大部分细节。

6.1. SCTP 关联的工作方式

SCTP（流控制传输协议）是一种传输层协议，与 TCP 和 UDP 类似。

与 TCP 类似，SCTP 面向连接。它将连接称为 关联。一个关联在每个端点都可以使用多个 IP 地址，因此如果某条路径失败，它可以通过另一条路径继续传输。

6.2. 漏洞详情

该漏洞位于 SCTP 发送路径中。在等待发送操作期间，其关联可以转移到另一个 socket。等待中的操作随后可能释放已转移的关联。根据另一个 socket 的行为，这会导致释放后使用或双重释放。

在使用 KASAN（内核的内存错误检测器）构建的内核上，双重释放表现为如下形式：

BUG: KASAN: double-free in sctp_[...]
Free of addr ffff8880021b0880 by task t306/838
Call Trace:
 kfree+0x170/0x490
 sctp_[...]
 sctp_[...]
 sctp_[...]
Freed by task 836:
 kfree+0x23c/0x490
 sctp_[...]
 sctp_[...]
 sctp_[...]
 sctp_[...]

该漏洞于 2018 年引入 Linux v4.15，并已在内核中存在超过八年。

6.3. 可利用性验证

释放后使用提供了两种原语：一种可泄露内核内存并绕过内核地址空间布局随机化（KASLR），另一种可在内核中调用任意函数。二者结合，使我们能够控制内核执行并提升权限。在我们的测试中，已经以 nginx worker 权限运行代码的攻击者可以可靠地获得 root 权限。

我们还在 nginx 运行于 Docker 容器中的环境下，在主机上获取了 root shell。在许多 Linux 发行版中，SCTP 模块默认已安装，并且当某个程序首次打开 SCTP 套接字时，内核会自动加载该模块。某台主机上能否访问 SCTP，仍取决于内核、可用模块以及容器的限制。在可以访问的情况下，攻击者可以接管主机内核。由于主机上的所有容器共享同一个内核，这使攻击者能够控制该主机及其上的每个容器。

在内核补丁发布之前，不使用 SCTP 的主机可以通过在 install sctp /bin/false 下的 .conf 文件中放置 /etc/modprobe.d/ 来阻止模块加载。这只能阻止通过 modprobe 加载模块。它不会卸载已经加载的模块，也不会禁用编译进 内核 的 SCTP。

感谢你读到这里。总结一下：如果你运行 nginx，请在 1.31.9 发布后尽快更新。如果无法立即更新，请应用第 3.3 节所述的缓解措施。它们可以阻止我们已知的攻击路径，但不能替代补丁。在内核修复可用之前，还应按照第 6.3 节的说明，在不需要 SCTP 的主机上阻止加载 SCTP 模块。

检查服务器是否已打补丁时请务必谨慎。Linux 发行版经常在不对 nginx -v 显示的版本号进行更改的情况下回移植修复。请根据发行版的安全公告检查完整的软件包版本。
