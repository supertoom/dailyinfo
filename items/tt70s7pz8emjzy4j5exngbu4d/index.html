Swati Khandelwal2026年11月09日云安全 / 数据泄露

云安全公司 Wiz 今天表示，攻击者在 10 月 14 日至 10 月 26 日之间入侵了多个 Qubole 客户所属的 AWS 账户，并窃取了存储的机密和数据。

攻击者使用了 Qubole 平台用于访问这些客户的某个 AWS 账户的凭据。攻击者是如何获得这些凭据的，尚未披露。

Qubole 是 Idera 旗下拥有的数据湖平台，运行在客户的 AWS 账户内。为了允许其访问，客户会创建一个 IAM 角色，这是一种具有自己权限集的 AWS 身份。

该角色的信任策略允许 Qubole 的 AWS 账户承担此角色，从而授予这些权限。每个此类请求都称为 AssumeRole，并且必须包含 Qubole 称为 External ID 的匹配代码。

据 Wiz 的研究人员称，除此次攻击外，攻击者承担的大多数角色均未被使用。但每个角色仍然信任 Qubole 的账户，因此攻击者的请求得以成功。

任何已将 Qubole 连接到 AWS 的组织，即使是不再使用 Qubole 的组织，都应检查其自 10 月 1 日起的 CloudTrail 日志。需要查找的迹象是，来自 Qubole 平台所使用的账户 805246085872 且来自 AWS 外部地址的 AssumeRole 请求。

研究人员没有说明这些凭据此后是否已被禁用，也没有说明相关活动是否已经停止。The Hacker News 今天查看时，Qubole 和 Idera 均未在其网站上发布关于此次攻击的声明。

这些角色为何让攻击者得以进入

研究人员表示，在其技术分析中，攻击者发起的每个 AssumeRole 请求都带有 External ID，并且均被接受。

AWS 会在此类角色的 AssumeRole 请求来自受信任账户且包含正确 External ID 时接受该请求。根据 AWS 的External ID 指南，该代码不会被视为机密，任何有权访问该角色的人都可以查看。

Sentra 在其若干客户环境中发现了这些活动，并提醒了研究人员。

在研究人员检查的账户中，攻击者寻找存储的凭据。它读取了 Lambda 函数的环境变量，从 Secrets Manager 中提取了机密，并读取了 SSM Parameter Store 中的值。

随后，它将找到的凭据输入 TruffleHog，以测试这些凭据是否有效。这些是受害者自己的 AWS 访问密钥、Entra ID 客户端密钥和 Okta 客户端凭据。

攻击者还从 S3 复制了数据。它会从角色能够访问的任何存储桶中检索数据，而不是搜索特定数据，有时还会在一次会话中下载整个存储桶。

研究人员尚未将此次攻击活动与其他任何公开报告的活动联系起来，并表示其目标锁定方式与国家支持组织通常所针对的目标不符。

Qubole 还允许客户使用 AWS 访问密钥而非角色进行连接。10 月 8 日至 10 月 11 日，攻击者使用了客户自己的 AWS 访问密钥，研究人员认为这些密钥是为 Qubole 设置的。

该攻击者随后入侵了若干受害者的云环境。这些活动尚未与 AssumeRole 的滥用行为联系起来。

如何检查你的账户

Wiz 的威胁狩猎指南涵盖每个持有 Qubole 角色的 AWS 账户自 10 月 1 日起的 CloudTrail 日志。查找：

  • 账户： AssumeRole 请求中 userIdentity.accountId 为 805246085872，且 sourceIPAddress 不是 AWS 地址。研究人员发现，Qubole 的真实流量仅来自 AWS。
  • IAM principal ID： AIDA3W7DIFLYOLTK63SFS。此 IAM 用户的任何活动都应进行调查，因为在研究人员检查过的账户中，只有攻击者使用过它。
  • IAM principal ID： AIDAJYRRH5Y3A7AAJM2HW，且源地址位于 AWS 之外。攻击者从 10 月 18 日起使用此 IAM 用户，但 Qubole 的正常流量也使用它。
  • IP： 57.129.54[.]120 和 2001:41d0:70d[:]7800::，攻击者使用的 OVH 托管地址。
  • IP： 45.83.220[.]211、 185.209.199[.]73 和 89.37.63[.]175，这些是 Mullvad VPN 地址。其他 VPN 用户也会共享这些地址，因此仅凭匹配不能作为证据。
  • 会话名称： 以 quiam- 开头的角色会话，例如 quiam-enum。
  • 用户代理： 从上述某个 IP 地址发起的 GetCallerIdentity 调用使用了 TruffleHog 。请在你的身份提供商登录日志中查找相同的用户代理。

对于每个可疑会话，审查其之后执行的所有操作，尤其是在 Secrets Manager、SSM Parameter Store、Lambda 和 S3 中。

CloudTrail 管理事件会记录每个 AssumeRole 请求和存储桶列表操作，但不会记录读取了哪些 S3 对象。这需要 S3 数据事件或 S3 服务器访问日志。多名受害者缺少所需日志，因此响应人员无法确定攻击者读取了哪些对象。

如何封堵该路径

研究人员建议采取以下步骤：

  1. 如果攻击者承担了你们的某个 Qubole 角色，请轮换该角色有权访问的所有机密、参数和 Lambda 环境变量，并撤销该角色的活动会话。轮换凭据不会终止已经签发的会话。
  2. 移除任何不再需要的 Qubole 角色，或将 Qubole 的账户从其信任策略中移除。
  3. 在 Qubole 支持的情况下，将信任策略中适用于整个账户的 :root 主体替换为 Qubole 使用的特定 IAM 主体。
  4. 添加 aws:SourceIp 或 aws:SourceVpce 条件，将 AssumeRole 请求限制在供应商文档所述的网络范围内。研究人员表示，在此次攻击中，“仅设置源 IP 条件本就可以阻止我们观察到的每一次角色承担。”
  5. 假定他人可以看到 External ID。它会以明文形式记录在 CloudTrail 中，供应商和基础设施即代码文件也经常存储它，因此不要将其作为唯一控制手段。发生此类事件后，请将其更改为 Qubole，并在可能的情况下为每个角色使用不同的值。
  6. 审查每个供应商角色可以访问的范围。研究人员称，Qubole 的设置指南包含一个示例 S3 策略，该策略允许该角色读取账户中的每个存储桶。供应商角色为便于使用，通常会被授予访问 Lambda 设置、Secrets Manager、SSM 参数以及广泛 S3 读取权限的权限。
  7. 针对来自供应商账户、通过 VPN 或此前未曾使用的托管公司发起的 AssumeRole 请求设置警报。
  8. 使用组织跟踪记录每个账户和区域，并为存储敏感数据的存储桶启用 S3 数据事件或服务器访问日志。
