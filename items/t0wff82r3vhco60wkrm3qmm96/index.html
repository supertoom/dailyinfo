攻击者伪装 Microsoft Teams IT 支持，利用不安全 AD CS 窃取企业数据

Attackers Pose as IT Support on Microsoft Teams, Abuse AD CS to Steal Company Data

AI 导读

Microsoft 调查了两起攻击者伪装 IT 支持并诱导员工通过 Microsoft Teams 使用 Quick Assist 授予远程控制的入侵，攻击者随后利用不安全配置的 AD CS 获取高权限账户及域控制器证书，其中一起将企业数据复制到外部服务器。

值得关注

两起入侵展示了社会工程、Quick Assist 与不安全 AD CS 配置如何串联成数据窃取，并暴露自动响应遗漏高权限账户的处置风险。

正文 · AI 翻译
中文原文

攻击者冒充 Microsoft Teams 上的 IT 支持人员，诱使员工将 PC 的远程控制权交给他们。随后，他们利用不安全配置的 Active Directory Certificate Services（AD CS）设置，获取特权账户（包括一个域控制器账户）的登录证书。

Microsoft 在一份报告中表示，它调查了两起此类入侵事件，其中一起导致公司数据被复制到外部服务器。

攻击者并未利用 Teams 本身的任何漏洞。他们依靠社会工程，以及配置不安全的 AD CS；Microsoft 未将该活动与任何已知组织关联起来。

攻击是如何开始的

Microsoft 表示，两起入侵事件的起始方式相同。攻击者在 Teams 上向员工发送消息和拨打电话，冒充该公司自己的 IT 或服务台人员，并使用带有支持主题名称的外部租户，使该联系方式看起来很熟悉。

他们说服每位用户打开 Quick Assist——一款内置于 Windows 的远程协助工具——并将连接代码读给他们。这使攻击者能够直接实际操作该工作站。

随后，攻击者将一个压缩包放入 Downloads 文件夹，将其解压到一个名称仿似 Windows 更新的新文件夹中，并使用便携版 Python、Bun 或 Java 运行时运行其中的内容。仅凭文件名是较弱的判断依据，因为其中一个副本虽然被重命名，却仍保留真实运行时的版本信息。

证书能为攻击者带来什么

AD CS 是 Windows 中负责签发用户和计算机登录时所持证书的角色。来自配置不当模板的证书，会让持有者以证书所指定的账户身份登录。

Microsoft 表示，即使账户密码被重置或第一台计算机被清空，此类证书仍可继续使用，因此这两项操作都无法终止攻击者的访问。

案例 1：特权证书，以及遏制措施中的缺口

在第一起入侵事件中，攻击者发现一个存在名为 ESC1 的弱点的证书模板。使用此类模板时，请求者可以指定证书所代表的账户，因此低权限用户可以申请一张代表特权账户的证书。

第一轮通话针对了三名用户和一台工作站，为三个高权限账户生成了证书。Microsoft Defender 的自动攻击中断功能切断了这些身份，并终止了它们的活动会话。然而，有一个特权账户未被纳入自动响应，因此仍可使用。

约 90 分钟后，更大的一波攻击波及 16 名用户和第二台工作站，又为另外 8 个特权账户生成了证书。Microsoft 表示，之后超过 1,000 次试图通过 SMB 访问文件或登录的尝试均被阻止。

在获取证书后的数秒内，攻击者登录了一台域控制器，并运行 DCSync——一款用于从 Active Directory 复制密码数据的工具。在遏制措施生效时，该操作已经开始，因此可复制的数据量受到限制。Microsoft 未说明攻击者获取了多少凭据数据。

被排除在自动响应之外的账户成为了突破口。攻击者持续使用该账户，接入一台文件服务器，并运行经过重命名的文件复制工具 Rclone，将数据从共享目录移至外部 SFTP 服务器。Microsoft 未说明有多少数据被窃取。

此案例以 Microsoft 的原话表明，“部分身份遏制措施可以减少攻击活动，但同时仍会留下一条可行的特权访问路径。”

案例 2：域控制器的证书

第二次入侵起初以相同方式展开，但由于不存在该模板弱点，发展方向有所不同。攻击者转而使用一种称为 PetitPotam 的技术，迫使域控制器向攻击者控制的一台计算机进行身份验证。

该 NTLM 登录被中继到 AD CS Web 注册页面，这种滥用方式称为 ESC8，不需要密码。攻击者利用中继后的登录，为域控制器自身申请证书。凭借该证书和 Kerberos（PKINIT），攻击者获得了域控制器的票据授予票据，将一次性的中继登录变成了持久的身份。

此次响应取得了成功。Defender 触发了 ESC8 警报，客户隔离了工作站，而 Microsoft 表示之后没有发现进一步活动。

两次事件之间的差异归根结底是遏制措施。在第一次事件中，自动中断阻止了攻击的大部分进程，但被排除的账户仍保持开放。在第二次事件中，隔离单台工作站阻止了攻击。

Defender 可以采取的措施

没有补丁可用，因为这并非软件漏洞。Microsoft 的建议涉及配置和响应。

  • 让员工在共享屏幕或交出远程控制权限之前，通过已知的内部渠道确认任何意外的支持请求。限制哪些外部 Teams 租户可以访问员工，并且只允许使用获批的远程支持工具。
  • 审查证书登录模板，查找允许请求者指定账户，或允许过多用户注册的模板，并移除不需要的注册权限。
  • 在 Web 注册终结点上要求使用 HTTPS，并启用身份验证扩展保护（EPA）；在可行的情况下，关闭这些终结点上的 NTLM。Microsoft 的 KB5005413 介绍了这一点，其 Defender for Identity 基线检查 会标记暴露于 ESC1 和 ESC8 的模板和终结点。
  • 启用证书审核。如果颁发了不良证书，应将其吊销，但请记住，吊销不会取消已经签发的 Kerberos 票据；应单独审查活动票据。
  • 将任何被排除在自动遏制范围之外的账户视为一项有意决定，并为其指派手动处置措施。

已知与未知事项

Microsoft 未将此次入侵归因于任何已命名团体，也未提供事件发生日期。

这些方法并不新颖。研究人员早在 2021 年就指出了 ESC1 和 ESC8 证书弱点 ，而 PetitPotam 强制认证技巧 也在同年被披露。Microsoft 自身早在 2026 年就记录了通过 Teams 帮助台转移到远程访问的入侵方式 。

这份报告增加的新信息是，这两种技术会在真实入侵事件中汇合，同时还带来了有关被排除账户的教训。

较新的 Windows 对 ESC8 步骤的暴露程度较低。Microsoft 在 Windows Server 2025 中默认为 AD CS 启用 EPA ，而 Server 2022 和 2019 则需要手动启用。

指标与检测

Microsoft 的报告列出了 Teams、终结点和身份信号方面的 Defender 警报，以及四条高级搜寻查询，并称它们是“调查起点”，而非单独的证据。Microsoft 还发布了与初始访问脚本关联的三个文件哈希：

  • SHA-256 85b6c424117494d3056e88689dbc94c75e9afdb187a339714043aec0da109f17（JavaScript 初始访问脚本）
  • SHA-256 f326201269f1ee2f803ae435317507263bb6e0dbfdeb70bd1bb5446e2e46f001（Python 初始访问脚本）
  • SHA-256 06c5c14f043aee3bcc5843b5f50909623d5c9a6239a7c1fba9cddad4111469e7（Python 初始访问脚本）
