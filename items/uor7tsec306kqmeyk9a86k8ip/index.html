自部署 Ollama 流式响应包长侧信道攻击实测与缓解方案评估

AI 导读

研究者在 qwen2.5-0.5b、TLS 1.3 和 1Mbps 链路上实测自部署 Ollama 的流式响应侧信道：被动监听仅凭 TLS 记录长度即可推断 10 类中文对话主题，基线交叉验证准确率为 33.0%，高于 10% 随机水平。

值得关注

通过真实抓包与五类缓解对照，量化了自部署 Ollama 流式响应的包长泄露及部署层取舍。

正文

导读：TLS加密只保护内容，藏不住流量的形状。本文把公开研究针对商业API的包长侧信道攻击搬到自部署Ollama场景：10类中文主题、真实抓包与随机森林分类实测主题推断准确率，再对关流式、反代缓冲、随机填充、定长填充、时序抖动五类缓解逐项实测准确率衰减与延迟代价，并给出可落地的部署层结论。

1 加密救不了隐私：问题从哪来

1.1 两年半研究脉络，一条没有合上的口子

这条攻击线不是新故事，但它一直在进化：

2024年3月，Ben-Gurion大学的Weiss等人在USENIX Security '24论文《What Was Your Prompt? A Remote Keylogging Attack on AI Assistants》（arXiv:2403.09751）里把流式响应的token长度侧信道做成了远程键盘记录攻击——从加密流量逐token恢复对话文本。该问题经微软安全响应中心（MSRC）流转至各厂商，Cloudflare于同月公开了自己的缓解方案：对token响应做填充与聚合。此后主流厂商陆续把token合并引入为默认缓解。同期，Carlini等人在arXiv:2403.06565（Stealing Part of a Production Language Model）里证明了推理服务的时序信号还能反推模型内部属性。

2025年11月，微软Defender安全研究团队发布Whisper Leak（arXiv:2511.03675，11月7日安全博客同步）：不解密任何流量，仅凭包长与时序训练分类器，就能推断用户与LLM对话的主题，实验覆盖多家主流厂商，并事先向约30家厂商做了责任披露。

2026年，USENIX Security '26收录的PromptEcho（From Length to Content: Token-Length Side-Channel Attacks on LLM API Merged Outputs，Sijia Li等）给出结论：token合并没有关上这扇门——合并后的传输仍存在可利用的长度侧信道。

也就是说，两年半过去，厂商侧的缓解（合并、padding）一直在被证明不够。

1.2 本文要补的三个空白

第一是部署形态。公开研究有一个共同前提：目标是商业API。商业服务前置了CDN、API网关和厂商侧缓解层，攻击者与模型之间隔着整条优化过的链路。但另一类部署形态被系统性忽略了：把Ollama直接架在公网VPS上，Nginx一层反代加自签证书就对外提供服务。这条路径上没有任何厂商侧缓解，TLS记录的形状原样暴露。本文实测的就是这个场景：自部署小模型服务，攻击者能看到什么。

第二是语言。公开实验以英文提示词为主，中文的分词密度、UTF-8字节宽度都不同，泄露特征是否同样成立需要数据说话。

第三是缓解的实测对照。论文给出的缓解方案（如TokenPadding）偏学术，而自部署运维真正会动的层是Nginx反代和自写网关。关流式、反代缓冲、SSE填充、时序抖动这四类"运维可操作"的手段，各自能换来多少准确率下降、付出多少延迟代价，公开资料里没有对照数据。本文逐项实测。

2 威胁模型与泄露原理

2.1 流式响应为什么逐chunk下发

OpenAI兼容API在请求体里带 "stream": true 时，服务端以SSE（Server-Sent Events）返回：每个生成步产生一个 data: {...}\n\n 事件，JSON里包着增量token。Ollama的 /v1/chat/completions 兼容此行为。逐chunk下发是流式体验的来源，也是泄露的来源：SSE事件的字节数等于固定的JSON包装加上该token的UTF-8字节宽度——包装恒定不变，波动部分只来自token本身。

2.2 TLS不隐藏长度

TLS（1.2与1.3均如此）对记录载荷加密，但记录头中的length字段是明文的。tshark里 tls.record.length 直接可读。TCP层的到达时间同样明晃晃地暴露。加密链路上，攻击者拿不到内容，但拿到一个完整的"形状序列"：每次响应的TLS记录长度序列与到达时间序列。

2.3 主题如何从形状里浮出来

以qwen2.5的分词器为例，一个汉字通常对应1个token（UTF-8占3字节），英文单词、标点、代码符号各有自己的字节宽度。10类主题（菜谱、代码、诗歌、运维……）的用词分布差异，会体现在"每个SSE事件的字节数"这个序列的统计分布上。分类器要做的，就是把形状序列映射回主题。注意这里必须排除一个混淆变量：答案的长短。如果某类主题的回答天然更长，分类器学到的可能只是长度而非主题。实验协议里用固定 max_tokens=64 控制了这一点。

威胁模型：被动监听者（同WiFi、企业出口、ISP链路上的任意位置），只读包元数据，不解密、不注入、不干扰。任务是10类闭集主题判定。

3 服务端搭建

3.1 目标环境与模型

实验目标机是一台阿里云ECS：2vCPU、2GB内存、1Mbps公网带宽，Alibaba Cloud Linux 3（内核5.10.134）。这个配置是个人开发者自部署LLM的典型下限档，也正因为带宽只有1Mbps，后续延迟代价的测量才会被放大到值得讨论的程度。

内存约束下选qwen2.5-0.5b-instruct（GGUF q4_k_m，491MB）。Ollama已预装，模型权重从ModelScope拉取后经Modelfile导入。这里有个国内VPS的现实困难值得记录：直连Ollama Registry与hf-mirror的下载吞吐都只有几十KB/s，最终走ModelScope源并用 curl -C - 断点续传才稳定拉完（491,400,032字节分三次续传）——1Mbps带宽的机器拉491MB模型本身就是一次运维体验：

3.2 Nginx TLS反代：一行配置决定泄露强度

用openssl自签证书（生产环境换成ACME证书不影响本文结论，TLS层对包长的处理一致）：

openssl req -x509 -newkey rsa:2048 -keyout side.key -out side.pem \
  -days 30 -nodes -subj "/CN=llm-side-lab"

反代配置里有一行值得单独说：

server {
    listen 8443 ssl;
    ssl_certificate     /etc/nginx/ssl/side.pem;
    ssl_certificate_key /etc/nginx/ssl/side.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    gzip off;                          # 压缩会改写包长特征，SSE 也不应压缩
​
    location / {
        proxy_pass http://127.0.0.1:11434;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;           # 关键行：SSE 逐 chunk 即时转发
        proxy_read_timeout 300s;
    }
}

proxy_buffering off 是所有流式部署教程都会教的一行：不关它，Nginx会把上游chunk攒进8KB缓冲区，用户就看不到"逐字吐出"的效果。但换个视角——这行配置同时是把每个SSE事件即时推到网络上的开关。缓冲关闭时，TLS记录与token一一对应，泄露信号最强；缓冲开启时，响应被攒成整块下发。它是本文最重要的缓解实验变量（第6.2节）。

4 攻击端实现

4.1 抓包与流量切分

攻击端在Kali上。抓包用dumpcap（免root，capabilities已配）：

dumpcap -i eth0 -w cap_base.pcap -f "host 118.31.227.72 and port 8443"

图6是基线配置下tcpdump的实时输出：服务端8443发往客户端的每一行 Flags [P.] 就是一个token包，length 字段逐包变化，肉眼即可分辨。

图6 基线阶段tcpdump实时输出

一个关键设计：每次请求使用独立TCP连接（请求头带 Connection: close）。这样pcap里每条TCP流恰好对应一次请求-响应，不需要从长连接里切分响应边界。真实攻击里攻击者面对的多是keep-alive长连接，按SSE事件边界切分是额外工程；本文选择独立连接以简化归因，不改变泄露本质。

TLS记录提取用tshark，只取服务端到客户端方向的记录。这里有一个公开资料很少提到的坑：实验链路协商的是TLS 1.3，tls.record.content_type（解密后的内容类型）在没有密钥时为空，外层类型要改用 tls.record.opaque_type——TLS 1.3的所有记录外层统一为23：

tshark -r cap_base.pcap -Y "tcp.srcport == 8443 && tls.record.opaque_type == 23" \
  -T fields -e tcp.stream -e frame.time_epoch -e tls.record.length

这里还有第二个更隐蔽的坑：一个TCP段可能携带多条TLS记录（SSE事件小、服务端写入密时会被合并发送），此时tshark把同一帧内多条记录的长度用逗号拼进同一个字段输出。解析脚本若按整数直接转换，这类帧会被整帧丢弃——基线流量里它只占约4%，流式场景下仅造成轻微失真；但换到关流式或缓冲开启场景，响应被高度聚合，几乎所有帧都是多记录帧，逐帧丢弃会让特征矩阵直接蒸发成空集。稳健做法是按逗号拆分逐条展开，同帧记录共享帧时间戳。

本文第一版解析脚本恰好踩中此坑。事后核查被丢弃的602个帧，内容几乎全是 122,1,38,817,281,69 这样的响应开场簇与 443,22,19 这样的收尾簇——即响应头、TLS控制记录与[DONE]尾事件等常数结构。丢弃它们等价于一次无意的"去常数记录"预处理，基线准确率因此虚高了8个百分点（41.5%对修正后的33.0%）。本文所有阶段数据均以修正解析后的结果为准。

4.2 特征工程

每条响应构造23维特征：

  • 包长分桶直方图（11桶，边界0/64/128/192/256/320/384/512/768/1024/1536/+inf）；

  • 记录数、总字节、均值、标准差、中位数、P90、首记录长、末记录长；

  • 时序4项：平均到达间隔、间隔标准差、最大间隔、响应总时长。

时序4项可以整体关闭（消融实验用）。特征构造的核心实现如下（节选自分析脚本，与后文所有数字一一对应）：

SIZE_BINS = [0, 64, 128, 192, 256, 320, 384, 512, 768, 1024, 1536, 10**9]
​
def features(recs, use_time=True):
    # recs: [(到达时间, 记录长度), ...] 单次响应的全部记录
    ts = [t for t, l in recs]; ls = [l for t, l in recs]
    hist = [0] * (len(SIZE_BINS) - 1)
    for l in ls:
        for i in range(len(SIZE_BINS) - 1):
            if SIZE_BINS[i] <= l < SIZE_BINS[i + 1]:
                hist[i] += 1; break
    n = len(ls); arr = np.array(ls, dtype=float)
    f = hist + [n, arr.sum(), arr.mean(), arr.std(),
                np.median(arr), np.percentile(arr, 90), ls[0], ls[-1]]
    if use_time and n >= 2:
        d = np.diff(np.array(ts))
        f += [d.mean(), d.std(), d.max(), ts[-1] - ts[0]]
    else:
        f += [0.0, 0.0, 0.0, 0.0]   # 仅包长消融：时序 4 维置零
    return f

这样设计的动机：目标服务器上同时跑着一个第三方算力共享agent，周期性外连下载文件，构成真实生产环境里的背景噪声。时序信道对这类噪声最敏感，消融对照能回答"在真实噪声下，包长信道和时序信道各自贡献多少"。

  • 10类主题（cooking/code/science/fitness/poem/game/business/ops/myth/movie），每类3条中文问法轮换，避免同一句提示重复造成的过拟合假象；

  • 固定 max_tokens=64、temperature=0.7；

  • 分类器与评测代码：

clf = RandomForestClassifier(n_estimators=300, random_state=42)
cv = StratifiedKFold(5, shuffle=True, random_state=42)

​
Xtr, Xte, ytr, yte = train_test_split(
    X, y, test_size=0.25, stratify=y, random_state=42)

  • 每阶段独立抓包、独立训练评测。

4.4 缓解措施实现

M3/M4/M5共用一个Python填充代理（127.0.0.1:9445，Nginx 8443切换上游到它）。填充利用了SSE规范允许的注释行：以冒号开头的行会被所有合规客户端解析器忽略，却能撑大事件体积——

def pad_event(ev):
    if PAD_MODE in ("random", "fixed"):
        target = random.randint(256, 1024) if PAD_MODE == "random" else PAD_SIZE
        body = ev[:-2] if ev.endswith(b"\n\n") else ev
        need = target - len(body) - 4      # "\n: " + pad + "\n\n" 的位置
        if need > 0:
            ev = body + b"\n: " + b"a" * need + b"\n\n"
    return ev

M5时序抖动在代理层对每个事件 time.sleep(random.uniform(0.05, 0.2)) 后再转发。

五组缓解全部走同一个8443端口：M1关流式（客户端侧 "stream": false）、M2反代缓冲开（切换Nginx location的 proxy_buffering on + 8k缓冲）、M3随机填充、M4定长512B填充、M5时序抖动。切换只需改一处Nginx配置reload，这也是给运维的启示：缓解不需要动业务代码。

5 基线攻击结果

5.1 主题推断准确率：随机10%，被动监听33%

先交代信号规模。基线200次请求全部成功，pcap中共解析出14675条服务端方向的TLS应用数据记录，平均每次响应73.4条——比请求端逐请求统计到的约65个 data: 事件多出约8条，差额是响应头记录、TLS控制记录与[DONE]尾事件等固定结构，这部分不含主题信息。平均总延迟13.62秒、首字节0.535秒——这是1Mbps公网带宽加0.5B模型的真实服务节奏，也是后文衡量缓解延迟代价的参照。

随机森林（300棵树，random_state=42）5折分层交叉验证的结果：23维全特征（包长19维+时序4维）准确率33.0%，标准差8.1%；仅用包长特征32.5%，标准差4.7%。随机猜是10%，被动监听的攻击收益是3.3倍。

两组特征再次同分（相差0.5个百分点，落在方差范围内），4.2节埋下的背景噪声消融结论成立：目标服务器上的第三方算力agent周期性外连，对时序特征干扰最大，实测时序信道没有可测增益——1Mbps链路上包间隔被发送队列与TCP发包节奏抹平，时序信号本身已弱，叠加噪声后不再携带可用的主题信息。这个消融结论直接支撑第7章的部署建议——防住包长信道就切断了主要泄露面，不必再上时序混淆这类高成本手段。

留出集（每类5个样本，共50个）准确率40%，混淆矩阵见图8。值得注意的不是对错本身，而是错误的分布：错判高度聚集而非在10类间随机撒开——game一类就吸引了9个误判样本（ops 3个、myth 2个、code/fitness/movie/science各1个），poem有2个被判成myth。这说明分类器学到的是真实的用词分布差异，但差异在部分文体之间互相重叠。强类是cooking（4/5）与fitness（3/5），食材与动作词汇的字节模式稳定；弱类movie、code、ops、business各只有1/5正确。

与公开研究对照要诚实：Whisper Leak在商业API的英文场景上报告的准确率显著高于本文（多数主题90%以上），本文33%低了不少。三个候选解释，按可信度排序：其一，本文每类仅20个样本，公开工作用数百个样本训练，分类器的学习充分度不在一个量级；其二，中文以汉字为主，一个汉字3字节、通常对应1个token，字节数的离散度天然低于英文子词（2~4字节不等，词长方差更大）；其三，固定max_tokens=64掐掉了回答长度的长尾，压缩了主题间的长度差异。三者哪个占主导，以本文的实验规模不下结论。但即便只有33%，结论已经成立：不解密、不注入，只靠旁路听包长，就能以3倍于随机的精度判断对话主题。

6 缓解措施逐项实测

五组缓解全部复用第4章的实验协议（10类中文主题、每类12个样本、同一分类器与5折交叉验证），每阶段独立抓包、独立训练评测，另加一项"迁移击溃测试"：攻击模型只在基线（无缓解）流量上训练，直接去测各缓解阶段的流量——模拟真实世界里攻击者先积累了大量未防护流量、防御方事后才上缓解的时间线。每组缓解的评价维度有三个：准确率衰减多少、延迟付出多少、能否击垮已训练的攻击模型。

切换实现只需改一处Nginx上游或重启填充代理（4.4节），业务代码零改动——这也是实测选择的五个缓解全部位于部署层的原因。

6.1 M1关流式（stream=false）

关流式直接切掉了泄露的根源：不再逐token下发，响应整体生成完毕后一次性返回。120次请求全部成功，抓包结果印证了形态变化——每次响应固定为10条记录，其中9条的长度完全恒定（1、38、69、122、281、817、266、266、19字节，对应响应头、TLS控制记录与事件框架），唯一的变量是JSON主体那条记录：602~865字节，随答案长短浮动，120条响应里只有77种取值。逐token的波动消失，包长直方图从"每次响应一张独特的形状"坍缩成"大家共用一张形状"，主题信息只剩答案长短一个弱维度。

分类结果随之崩塌：5折交叉验证准确率15.8%±4.9%，仅包长14.2%±7.7%，留出集16.7%——全部贴近10%的随机线。基线阶段3.3倍于随机的攻击收益，被 "stream": false 一个参数抹掉。

代价同样极端：平均总延迟14.41秒，首字节延迟从基线的0.535秒变为14.41秒——用户盯着空白屏幕等完整答案生成，27倍的首字节延迟让流式体验完全丧失。结论：关流式把准确率压回了随机线，但也是体验代价最大的缓解，适合内部工具、API后端这类"无人盯着进度条"的调用场景，不适合面向用户的服务。

6.2 M2反代缓冲开启（proxy_buffering on）

缓冲开启后，Nginx把上游响应攒进8KB缓冲区，凑满或响应结束才下发。抓包形态随之改变：每次响应平均只有9.9条记录（中位数10条），记录长度中位数仅122字节，最大单条14.3KB，大于1400字节的记录占9.8%——大量小记录与少数8KB级大块并存，单token粒度消失，响应变成少数几个大块的搬运。

聚合压掉了大部分信号，但没压干净：5折交叉验证准确率30.3%±7.5%，只比基线33.0%低不到3个百分点；仅包长特征23.9%±5.0%。对照M1的15.8%，M2残留的信号略多——关流式的记录形态是"9条恒定+1条主体"，而缓冲聚合的记录边界受缓冲时机影响，每条响应残留的变化维度更多。结论：M2单独使用不能视为有效缓解。

延迟与稳定性才是M2的真正问题。首字节延迟16.71秒，与总延迟几乎相等——缓冲把"逐字吐出"变成了"最后一次性吐出"，流式体验与M1一样完全丧失，总延迟还比基线多23%。更糟的是稳定性：120次请求中有11次（9.2%）以连接重置告终，客户端未收到任何字节、等待19~26秒后被重置，失败散布在整个阶段；同样的120连发在基线与M1配置下零失败。M2的综合评价：牺牲全部流式体验、引入9%请求失败率，只换来3个百分点的准确率下降——所有维度上都不划算。

6.3 M3随机填充与M4定长填充

两个填充变体走同一个代理（4.4节），重跑后各120/120成功、每类恰好12个样本，协议完整。先说体积与延迟的账：实测每响应总字节中位数从基线的17.1KB涨到45.1KB（随机填充，2.6倍）与37.2KB（定长填充，2.2倍）；但平均总延迟14.36/14.34秒，只比基线多5%，首字节延迟0.61/0.62秒，比基线的0.535秒仅多0.07秒——填充的字节在1Mbps链路上的排空时间相对14秒的生成时间可以忽略，流式体验完整保留。这也是填充区别于关流式的关键：它不消灭逐token下发，只是让每个token的"体积"失去信息。

准确率的结果把这条逻辑验证到了底。M3随机填充：交叉验证10.8%±3.3%（全特征）、11.7%±3.1%（仅包长）、留出集6.7%（30个样本仅对2个，小样本下略低于随机线属正常波动）——三个口径全部贴着10%的随机线，攻击收益从基线的3.3倍归零。M4定长512B填充：仅包长特征10.0%±4.2%，同样精确归零——所有事件被撑到同一尺寸后，包长序列变成常数，这是设计目标的直接兑现；全特征18.3%±8.6%略高于随机，残余来自未被填充触碰的时序4维特征，但落在标准差范围内，不足以构成可用信号。

单从矩阵看，随机填充是六种配置里唯一同时做到"压到随机线"和"流式无损"的缓解——M1也压到了随机线，但首字节延迟27倍。

不过M3的实测过程里有一个必须记录的插曲。首跑随机填充阶段52/120失败：推理进程llama-server在21:17（服务器时间）于一次响应的中途冻结，客户端收到104个事件后读超时，随后39个连续请求在等了约20秒后被以0字节重置，持续29分钟；21:46，Ollama的调度器重启llama-server后立即恢复，21:51-22:21又出现一段13/36的散布失败。定长填充首跑也有30%失败。两轮失败都无OOM、无内核段错误记录，Ollama主进程全程存活。重启推理服务后重跑，两个填充阶段各120/120零失败。按日志证据能下的结论只有一条：响应体积放大约2.2~2.6倍的填充负载，在2GB内存、长时间运行的推理机上与两次服务停滞时间上吻合，重启后消失；机制未定。给运维的提示是明确的：上填充之前把推理服务的监控和定期重启排上，别让"隐私缓解"变成"可用性事故"。首跑的残缺数据已整体弃用，本文所有填充数字以重跑为准。

6.4 M5时序抖动

时序抖动在代理层对每个事件随机延迟50~200ms再转发。结果：全特征25.0%±7.0%、仅包长25.0%±2.6%，对基线的33.0%/32.5%下降在运行间噪声范围内（表中留出集43.3%偏高是30个样本、每类仅3个的方差所致，不改变结论）。这个结果其实注定：抖动只扰动到达间隔，不改变包长，而5.1节的消融已经证明本场景里时序信道本就无可测信号、包长信道是唯一活着的信道——M5没有打中要害。作为单独缓解，在本环境无效。

它的延迟账反而有个反直觉的细节。理论代价是65个事件×平均125ms≈+8.1秒，实测总延迟只多了1.5秒（15.09秒），首字节+0.34秒。原因：这台机器的生成节奏约208ms/token，慢于平均抖动间隔，代理的睡眠时间被生成等待吸收了——慢推理链路上时序抖动几乎免费。可惜免费的东西在这里没有目标可打。

7 讨论与结论

7.1 自部署为什么是重灾区

商业API与自部署服务在链路结构上有本质区别：前者前置了CDN、API网关与厂商侧缓解层，token合并、padding都在流量到达公网之前完成；后者的典型链路只有一层Nginx反代，TLS记录的形状原样出网——第3章那条"人人都在抄"的 proxy_buffering off，就是这条链路上唯一的形状处理配置，而它的作用方向恰好相反（6.2节实测验证）。

部署面本身也远比想象中暴露。Censys 2025年9月的单日快照显示：约10,600个高置信度公开Ollama实例分布在1,229个自治系统，其中约1,500个无需认证即可直接调用推理API。对这类服务，侧信道攻击者连"入口"都不必找——链路本身就是公开的，被动监听者与模型之间的全部设备只有一台带宽个位数Mbps的VPS。

本文实验场景（2GB内存VPS+0.5B模型+Nginx+自签证书）就是这条链路的最小典型实现，33%的主题推断准确率是在"真实带宽、真实噪声、真实自签TLS"下取得的，不是实验室理想链路。

7.2 部署层缓解的选型建议

把第6章的矩阵和迁移测试压成可执行的部署建议：

首选：网关层随机填充。 它是唯一同时满足"准确率压到随机线（10.8%）、流式体验无损（首字节+0.07秒）、业务代码零改动"的缓解。实现就一层：在Nginx反代与推理服务之间放一个填充代理（本文4.4节的实现，整个代理99行Python，核心是利用SSE规范允许的注释行），或用等价的网关脚本完成。代价是响应体积放大2.6倍——在1Mbps出口上实测可忽略，但出口带宽更小的环境应先算这笔账。

无交互场景用关流式。 纯API调用、定时任务、批处理这类"调用方本来就要等全量"的链路，"stream": false 一行配置同样把准确率压到随机线（15.8%），且没有任何代理成本。代价只有首字节延迟等于总延迟，而这类场景不在乎。

两个不要。 不要把反代缓冲开启当隐私缓解——它只降3个百分点，却附带9%的请求失败率与流式体验死亡，所有维度都是负收益。不要单独依赖时序抖动——它不触碰包长信道，而包长才是主信道；迁移测试里它对已有攻击模型也只有24.2%的削弱。

位置与叠加。 自部署链路没有厂商侧缓解层，网关就是唯一防线，这与商业API的缓解（token合并）作用于不同维度：合并减少记录数量，填充抹平记录大小，理论上可叠加——叠加后的效果本文未实测，不在此下结论。

两条运维前提。 其一，上填充前先做容量预算：响应体积2.6倍放大对带宽、缓冲区和推理服务写出路径都有影响，本文的停滞事故（6.3节）就是前车之鉴，推理服务要有监控与重启预案。其二，缓解要一次性到位：迁移测试表明攻击者无法复用旧模型，但防御方如果只上一半措施（比如只开缓冲），留着的信道仍然完整可用。

7.3 局限与未覆盖面

把不测什么说明白，结论才可信。本文结论的边界如下：

  • 闭集任务：10类主题是攻击者预定义并采集了同分布训练样本的设定。真实场景中用户提示词分布未知、随时间漂移，开放集与漂移下的攻击效果未测；

  • 样本规模：基线每类20个样本、缓解阶段每类12个，5折交叉验证标准差±8.1%。本文证明的是"信号存在且可利用"，33%不是攻击成功率的精确刻画；

  • 单一模型与链路：全部数据来自qwen2.5-0.5b（q4_k_m）+1Mbps+TLS 1.3+无CDN的组合。更大模型的输出分布、HTTP/2多路复用与CDN终止都会改变记录形状，结论不能直接外推到商业API；

  • 连接形态：实验用独立TCP连接简化流归因，keep-alive长连接下多轮对话的响应切分是攻击端的额外工程，未在本文实现；

  • 模态：音频流式输出与端侧推理不在范围；

  • 压缩：SSE场景gzip实际上总是关闭（压缩破坏流式语义），本文沿用此常态，未测压缩开启时的特征变化。
