nginx 披露五项内存破坏漏洞 CVE-2026-123007 等，Cloudflare 分析代理防护边界

nginx2root: Five new nginx vulnerabilities, and how Cloudflare protects origins from the worst of them

AI 导读

F5 与 nginx.org 披露五项 nginx 内存破坏漏洞，未认证攻击者在特定配置下可导致 worker 崩溃，并在禁用或绕过 ASLR 时执行服务器命令；Xint 还发现可由 Docker 容器内提权至宿主机 root 的 Linux SCTP use-after-free。

值得关注

文章结合源码、AddressSanitizer 测试和流量量级还原五项 nginx 内存破坏漏洞，并厘清 Cloudflare 代理的防护边界与例外。

正文 · AI 翻译
中文原文

2026 年 11 月 18 日，F5 和 nginx.org 披露了 nginx 中的十个漏洞。其中五个漏洞由 Xint 研究团队详细说明，并以 nginx2root 为名发布；它们属于内存破坏缺陷，未经身份验证的攻击者可利用这些缺陷使 nginx worker 崩溃，或者据 Xint 的研究，在服务器上运行命令。Xint 还发现了一个 Linux 内核漏洞，可将该立足点提升为宿主机的 root，包括从 Docker 容器内部提权。其他团队则独立发现了这两个 HTTP/2 漏洞：对于 CVE-2026-123007，F5 同样致谢 Rapid7、Wiz Research 和 Ikotas Labs；对于 CVE-2026-123633，则致谢 Metnir、Wiz Research 和 Palo Alto Networks Unit 42。

nginx 是一款 HTTP web 服务器，同时也可作为反向代理、内容缓存、负载均衡器、TCP/UDP 代理服务器和邮件代理服务器。全球有大量 web 服务器运行 nginx，因此这是必须立即打补丁的事件。但如果你的 nginx 服务器只能通过 Cloudflare 的代理访问，攻击者便无法触及其中最严重漏洞的易受攻击代码路径；你在更新服务器期间将受到保护。

下面介绍 Cloudflare 的立场、这种保护覆盖的范围及其边界，以及这些漏洞的工作原理。

简而言之

  • Cloudflare 的边缘节点不受影响。 目前，我们边缘节点上处理客户流量的代理大多运行在用 Rust 编写的 FL2 上。在漏洞披露前，我们针对全部五个漏洞审查了仍基于我们经过深度修改的 nginx 分支构建的部分，而修复相关代码路径的更新已在漏洞发布前完成全球推送。同批发布版本还修复了其他五个 nginx CVE，其中包括 CVE-2026-118899，即通过 TLS 1.3 读取请求正文时出现无限循环。
  • Cloudflare HTTP 代理后方的源站可免受 HTTP/2 和 HTTP/3 攻击。 对于经过代理的主机名，Cloudflare 会在边缘节点终止所有客户端 HTTP/2 和 HTTP/3 连接，并另行建立一条通向源站的连接。攻击者发送的帧永远不会到达你的 nginx。
  • 解析器和邮件代理漏洞是否可利用取决于具体配置。 许多 nginx 配置不会受到影响，但确保安全的最佳方式是更新安装版本或禁用相关功能。
  • 你仍应打补丁。 请更新至 nginx 1.30.7 或 1.31.9（或供应商提供的修复版本）并重启。下面涵盖的部分配置不受代理保护。

nginx2root 包含五个彼此独立的漏洞。每个漏洞都可单独利用，而且各自需要不同的配置。

F5 将每个漏洞均评为 High（CVSS 3.1: 8.1）和 Critical（CVSS 4.0: 9.2），并指出代码执行需要禁用或绕过 ASLR （地址空间布局随机化）。对于 CVE-2026-123007，Xint 的文章展示了如何泄露内存地址以实现上述操作。

CVE-2026-123007 是最令人担忧的一个。它只需要启用 HTTP/2，而 TLS 部署中通常已启用 HTTP/2；自 HTTP/2 支持随 1.9.5 发布以来，它已存在于每个 nginx 版本中。Xint 通过公共互联网对 AWS、GCP 和 Azure 上的服务器运行了利用程序。Xint 在披露前的 11 月 10 日搜索了 Shodan，发现有 5670 万台主机与 product:nginx 匹配。在报告了版本的 1194 万台主机中，98.9% 落在受影响范围内。截至 11 月 19 日，Censys 的 nginx2root 暴露情况跟踪器 记录了约 880 万个运行可能受影响版本且启用 HTTP/2 的服务。版本字符串并不能证明主机存在漏洞，因为各发行版会回移植修复，但暴露范围非常庞大。

同一批 nginx 版本还修复了另外五个漏洞。其中最严重的是 CVE-2026-118899：在通过 TLS 1.3 读取请求正文时出现无限循环，可使未经身份验证的攻击者阻塞工作进程，影响 nginx 1.13.0 及更高版本。

Linux 内核漏洞是 nginx2root 的第六部分。Xint 在内核的 SCTP 发送路径中发现了一个释放后重用漏洞，该漏洞自 Linux 4.15（2018）起就已存在：在发送操作等待期间，其 SCTP 关联可能被移动到另一个套接字，随后等待中的发送操作便可将其释放。已能以 nginx 工作进程身份运行代码的攻击者可以利用它在主机上获得 root 权限；Xint 已在一个运行于 Docker 容器内的 nginx 上完成了这一操作。许多发行版会在程序首次打开 SCTP 套接字时自动加载 SCTP 模块，因此即使从不使用 SCTP 的主机也可能受到影响。截至 11 月 18 日，尚无内核修复可用，Xint 表示在修复发布前暂不披露细节。

截至 11 月 19 日，五个 nginx2root CVE 均未被列入 CISA 的已知被利用漏洞目录，我们也未看到在野利用的报告。Xint 和 Wiz Research 尚未发布其利用程序。Rapid7 发布了一个概念验证，并称其仅适用于演示针对刚启动的本地容器的攻击。GitHub 上还在流传虚假的“利用程序”。

为什么 Cloudflare 的代理会保护你的源站

nginx2root 最危险的漏洞存在于 nginx 解析和管理 HTTP/2 与 HTTP/3 连接的方式中。要触发这些漏洞，攻击者必须直接向 nginx 进程发送经过精心排序的协议帧序列：数十亿个 WINDOW_UPDATE 帧、一个暂缓响应数据的 SETTINGS 帧、填满发送缓冲区的 PING 帧、不完整的 HEADERS 帧，以及在恰当时机发送的 RST_STREAM 。

当你的 DNS 记录通过 Cloudflare 代理时，该连接终止于我们的边缘节点。

Cloudflare 读取客户端的 HTTP 请求，应用你的安全与缓存规则，然后通过由 Cloudflare 控制的连接向源站发起自己的请求。攻击者发送的流控帧、PING 帧、SETTINGS 帧和流重置帧都会被我们的边缘节点消耗，不会被转发。你的 nginx 只会看到 Cloudflare 选择发送的请求，其封装方式也由 Cloudflare 决定。Cloudflare 通过 HTTP/2 连接源站时同样如此：Cloudflare 会在该连接上运行自己的流控机制，仅根据自身流量需求发送 WINDOW_UPDATE 和 RST_STREAM 帧，因此客户端无法迫使它中继攻击所需的数十亿个 WINDOW_UPDATE 帧。

Rapid7 在分析 CVE-2026-123007 时也指出了同样的问题：如果 HTTP/2 连接经过代理，攻击者的帧“很可能不会被重新传输”到可利用的程度。这会阻断 HTTP/2 和 HTTP/3 攻击中的每一种。

未受到保护。Cloudflare 的 HTTP 代理不承载邮件流量。

要在这里受到 Cloudflare 的保护，有一个条件：你的源站必须无法被直接访问。 如果攻击者能找到你的源站 IP 并直接连接（HTTP/2 使用 TCP 443 或 80，HTTP/3 使用 UDP 443，或使用邮件端口），Cloudflare 就不在通信路径中，保护也不会生效。你应确保源站服务器只能通过 Cloudflare 的代理访问，方式如下：

  • Cloudflare Tunnel。 你的源站仅向外连接 Cloudflare，不开放任何入站端口。
  • 指向 Cloudflare IP 范围的防火墙。 仅接受来自 Cloudflare 公布的 IP 范围 的入站 HTTP/HTTPS 请求。这必须通过 IP 防火墙实现，而不能依赖 nginx 服务器中的配置。
  • Authenticated Origin Pulls （mTLS）。 你的源站会拒绝任何未提供 Cloudflare 客户端证书的 TLS 连接。

Xint 自有的暴露面检查也指出了同样的问题：“如果 CDN 或反向代理位于 nginx 前面，该测试只能到达代理，因此还要 直接针对 nginx 服务器运行该测试。”

保护不适用的情形

有多种情况会导致 Cloudflare 的 HTTP 代理无法提供保护。

  • Spectrum TCP/UDP 应用。 对于这类配置，来自互联网的流量会原样转发到你的源站。如果你的源站正在运行 nginx，请打补丁或禁用受影响的功能。
  • nginx 邮件代理。 Cloudflare 的 HTTP 代理不承载 IMAP、POP3 或 SMTP。在打补丁之前，请将邮件监听器限制为仅可信网络可访问。
  • CVE-2026-123634（解析器）。 这取决于你的配置如何根据请求构建 proxy_pass 目标，以及能否精确把握 HTTP 请求的取消时机。将流量通过 Cloudflare 的代理转发会使其更难被利用，但不能提供完整保护。无论如何都应进行更新。
  • 仅 DNS（灰色云）、内部或未经过代理的 nginx。 任何攻击者无需经过 Cloudflare 即可访问的 nginx 服务器，包括已失陷主机之后的内部服务，都需要打补丁。

Cloudflare 的 WAF 规则与这些漏洞无关。 这些是协议层漏洞。由于 Cloudflare 的代理会解析 HTTP 协议消息，并创建新的消息以从源站获取信息，因此位于 Cloudflare HTTP 代理之后的源站无需配置规则，即可免受 HTTP/2 和 HTTP/3 漏洞影响。因此，我们没有发布托管规则。这种保护源于连接终止，而非模式匹配。

现在该怎么做

  1. 找出每一台 nginx 服务器。 包括 nginx Plus、发行版软件包、容器镜像和设备。对每台服务器运行 nginx -V 和 nginx -T ，并记下 HTTP/2、HTTP/3/QUIC 监听器、带有变量的 proxy_pass 以及 SSI 或 mirror，以及任何 mail 块。
  2. 打补丁。 将 nginx Open Source 更新至 1.30.7 或 1.31.9，将 nginx Plus 更新至 37.0.8.1 或 37.3.0.1，或者安装发行版提供的修复软件包。F5 将 nginx Plus R34 至 R36 列为受影响版本，且没有修复构建，因此应将其迁移至已修复的 37.x 版本。随后重启 nginx 或完成二进制升级。重新加载配置不会替换正在运行的二进制文件。
  3. 仔细检查回移植版本。 发行版通常会在不改变 nginx -v 所报告版本号的情况下打补丁。请将完整的软件包版本与所在发行版的安全公告进行比较。
  4. 确保源站只能通过 Cloudflare 访问。 使用 Tunnel、IP 允许列表或 Authenticated Origin Pulls。
  5. 如果暂时无法打补丁，请禁用不需要的功能。 http2 off; （nginx 1.25.1 及更高版本；在旧版本上，从 listen 指令中移除 http2） 块可阻止 CVE-2026-123007 和 CVE-2026-123633。移除 QUIC 监听器并设置 http3 off; 可阻止 CVE-2026-121810。将 proxy_pass 指向已修复的上游组可阻止 CVE-2026-123634。不要仅依赖 mirror_request_body：Xint 测试的配置将其设为 off，默认的 on 也阻止了此次利用，但 SSI 和其他子请求仍可能触发该漏洞。将邮件监听器绑定到可信网络可阻止 CVE-2026-113425。重启以关闭旧连接。
  6. 如果不使用 SCTP，请将其阻止。 在 /etc/modprobe.d/ 中的一个文件里添加 install sctp /bin/false，以阻止内核模块加载。这不会卸载已经加载的模块，也不会禁用内核内置的 SCTP。当所在发行版提供针对该 SCTP 漏洞的内核更新时，请安装更新并重启。在那之前，阻止该模块只是一种临时措施。

Cloudflare Radar 的 nginx2root 的 Zero Wire 条目 包含完整检查清单、可交给智能体以对您的服务器集群进行只读评估的提示词，以及指向每个供应商安全公告的链接。

技术深入解析

让我们通过查看代码来深入了解这五个漏洞。我们查看的是修复前发布的最新代码 nginx 1.31.8（提交 140aa94），并将其与 1.31.9 中的修复进行对比（这些修复也已包含在稳定分支的 1.30.7 版本中）。

方法说明：我们的分析基于公开的安全公告；为验证我们对代码的理解，我们使用 AddressSanitizer 构建了公开的 1.31.8 和 1.31.9 版本，并针对五个漏洞中的四个运行了测试（流控制、HTTP/2 释放后使用、解析器和邮件代理）。这些漏洞中的每一个在 1.31.8 上都会触发故障，在 1.31.9 上则运行正常。我们未能复现 HTTP/3 漏洞；该章节基于修复提交和已发布的分析。

一种模式，出现在四处

五个漏洞中的四个是释放后使用漏洞。这是在缺少语言支持的情况下手动管理内存的程序中常见的问题：一部分代码释放了一个对象，而另一部分代码仍在使用该对象。

nginx 是事件驱动的。处理程序运行后调用其他代码，而该代码返回到处理程序。其中三个漏洞发生在被调用的代码拆除处理程序正在处理的连接或请求时。第四个漏洞中，第二个连接仍持有指向该对象的指针。

  • CVE-2026-123633 和 CVE-2026-121810。 请求需要一个连接槽位才能访问其上游。nginx 的槽位不足，因此会关闭一个空闲连接以释放槽位。它选择的连接恰好是请求所属的连接。
  • CVE-2026-123634。 解析器回调结束了请求。对该请求的清理过程释放了第二个解析器上下文，而解析器接下来正要调用该上下文。
  • CVE-2026-113425。 向邮件客户端写入失败时，客户端连接会被关闭，而指向认证服务的连接仍指向其会话。

F5 将这四个漏洞全部评为：在禁用或绕过地址空间布局随机化（ASLR）的情况下，可能导致代码执行；在其测试中，Xint 报告代码以 nginx 工作进程的权限执行。

第五个漏洞 CVE-2026-123007 属于另一种类型：一个原本是计数错误的问题最终演变为长度错误。

CVE-2026-123007：两个看似正确的流控部分

HTTP/2 流控制限制了服务器可以发送的响应数据量。nginx 为每个流维护一个发送窗口，并为连接维护一个发送窗口，h2c->send_window。客户端通过 WINDOW_UPDATE 帧扩大窗口，而该协议将每个窗口限制在 2^31 − 1。

nginx 在收到 WINDOW_UPDATE 时强制执行这一上限（ngx_http_v2_state_window_update()）：

if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window) {
   /* logs "client violated connection flow control" */
   return ngx_http_v2_connection_error(h2c, NGX_HTTP_V2_FLOW_CTRL_ERROR);
}

单独来看，此检查是正确的。但连接窗口还会在第二个位置增大。当 nginx 为一个流排入 DATA 帧时，它会从窗口中减去这些帧的长度。如果在那些帧发出之前取消该流，ngx_http_v2_filter_cleanup() 会将它们从队列中移除并返还相应的额度：

h2c->send_window += window;

这一行没有任何上限限制。正如修复提交所描述的，如果客户端在这些帧排入队列之后、流终止之前扩大连接窗口，那么返还的额度会使窗口超过 2^31 − 1。

从那一刻起，第一个检查便不再有效。h2c->send_window 是一个无符号 size_t，因此 NGX_HTTP_V2_MAX_WINDOW - h2c->send_window 会回绕成一个非常大的数，之后每个 WINDOW_UPDATE 都会被接受。客户端随后便能将窗口扩大到任意大小。

该窗口是无符号的，但用于确定 DATA 帧大小的代码却将其作为有符号值进行比较（ngx_http_v2_send_chain()）：

if (limit == 0 || limit > (off_t) h2c->send_window) {
   limit = h2c->send_window;
}
...
if ((off_t) frame_size > limit) {
   frame_size = (size_t) limit;
}

窗口超过 2^63 后，作为 off_t 它就变成了负数。帧大小会变成窗口值本身，即一个介于 2^63 和 2^64 之间的数，而 nginx 构建的缓冲区其 last 指针位于 pos 指针之前。

通过 TLS 时，该缓冲区会带着该长度到达 memcpy() 在 ngx_ssl_send_chain() 中。在那个位置，我们的 TLS 测试在 AddressSanitizer 下停止。Xint 的文章解释了，当窗口被推近 2^64 时，这如何变成一次可控的越界写入和地址泄露；Xint、Rapid7 和 Wiz 均报告称可由此实现代码执行。本文不会进一步讨论该故障。

通过明文 HTTP/2，同一个无效缓冲区会走另一条输出路径。我们的明文测试在 1.31.8 上同样在 AddressSanitizer 下发生故障，而在 1.31.9 上运行正常。公开文章讨论的是 TLS 情形。

已知攻击需要多少流量

WINDOW_UPDATE 能够推进的最大幅度是 2^31 − 1，而一个 WINDOW_UPDATE 帧为 13 字节。因此，要将一个 64 位窗口推近其上限，大约需要 2^33 帧：约 86 亿帧，也就是约 112 GB（104 GiB）。

Rapid7 发布了概念验证，并给出了相同的数字。它还补充指出，nginx 会相对于同一连接上的其他流量限制控制帧流量，因此其运行过程中还会发送约 15 GiB 的其他请求流量。总计约为 128 GB 的 HTTP/2 数据：在 10 Gbit/s 链路上约需两分钟，在 1 Gbit/s 链路上约需十七分钟。Rapid7 估算，要让 WINDOW_UPDATE 流量达到 2^63，约需 2^32 帧，也就是 52 GiB，是 104 GiB 这一数字的一半。它还指出，这些数字描述的是其测试路径，并非已证实的最小值。

对防御者而言，这是有关该漏洞最有用的信息。在这种流量规模下，已知攻击很难隐藏：nginx 会通过一个长连接从单个客户端接收数十 GB 数据，而返回的数据很少，远超访问日志中的请求所能解释的量。

为什么很难发现

自 nginx 在 2015 年随 1.9.5 引入 HTTP/2 支持以来，退款逻辑就一直存在。有两点使它很难被注意到。

首先，每个部分单独看起来都是正确的。对 WINDOW_UPDATE 的检查是正确的检查。退款也是正确的退款。问题在于，该检查依赖了一个退款未能保持的假设。

其次，等待崩溃的测试几乎不可能触发它，因为崩溃需要数十 GB 的输入。而进入错误状态本身只需要很少的流量：Censys 发布了一个明文测试，通过 5.69 MB 的抓包即可达到其所谓的损坏流控状态。如果测试在每个帧之后都断言“发送窗口绝不超其协议最大值”，那么一旦测试序列到达该状态，就会立即标记出错误状态。等待内存损坏的测试则不会。

修复

该修复（新增 6 行）引入了一个计数器 h2c->send_queued，用于记录已排队但尚未发送的 DATA。WINDOW_UPDATE 检查现在会将这些字节计入窗口：

if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window - h2c->send_queued) {

从客户端的角度来看，已排队的帧仍然计入窗口，因此客户端无法再补充 nginx 即将退款的信用额度。在修复后的版本中，此类尝试会因流控错误而被拒绝。

CVE-2026-123633：两种防护机制之间的相互作用

nginx worker 拥有固定数量的连接槽位（worker_connections），由客户端连接和上游连接共享。自 1.19.2 起，当空闲槽位较少时（总数的 1/16 或更少），ngx_get_connection() 会调用 ngx_drain_connections()，从而关闭被标记为“可复用”的连接：例如没有任务正在进行中的空闲 keep-alive 连接。

这只有在可复用连接确实没有任务正在进行时才有效。对于 HTTP/2 而言，情况并非总是如此。2021 年 2 月同一天合入的两个提交一同发布于 1.19.7：

  • “HTTP/2: fixed reusing connections with active requests”修复了一种情况：明文 HTTP/2 连接在仍有请求时可能仍保持可复用状态。
  • “HTTP/2: reuse of connections with incomplete frames”修复了这样一种情况：连接会等待部分接收帧的剩余部分，却在此期间被注册为可复用状态，因此客户端无法通过部分帧占用连接槽位。

第二项更改与此处相关。正如修复提交所说明的，如果该帧的剩余部分是 HEADERS 帧，就会创建一个流，但在连接下次进入空闲状态之前，可复用状态都不会被重置。随后，该连接已有请求，并仍留在可复用队列中。

如果该请求被代理，nginx 会为上游连接申请一个槽位。如果槽位不足，排空操作会在该调用内运行，并可能选中同一个连接。排空操作指示连接关闭，而 nginx 会尝试发送 GOAWAY。如果发送失败，nginx 会释放该连接及其上的每个流。随后控制权返回上游代码，后者继续使用调用时对应的请求。

每项更改单独来看都有其合理性。它们之间的交互十分微妙，直到今年才被发现。F5 的公告致谢了 Metnir 的 Albert Ebb、Wiz Research 的 Nir Ohfeld、Xint.io，以及 Palo Alto Networks Unit 42 的 memN0ps；nginx.org 的变更日志致谢了 Vexera AI 的 Albert。

修复

新增两行：ngx_http_v2_create_stream() 现在会调用 ngx_reusable_connection(h2c->connection, 0)。拥有流的连接绝不会被标记为可复用，无论它之前处于何种状态。

CVE-2026-121810：QUIC 中的同一思路

根据修复提交和 Xint 的分析，HTTP/3 漏洞通过另一条路径达到了相同结果。

在 nginx 的 QUIC 代码中，每个 QUIC 连接使用一个连接槽位，每个流使用另一个槽位。只有当连接树中剩余的每个流都可以被取消时，QUIC 连接才可能被排空；nginx 通过遍历连接的流树来判断这一点。

ngx_quic_create_stream() 将 QUIC 连接从可复用队列中移除，然后为新流申请槽位。修复前，新流要到此之后才会被加入树中。如果槽位申请触发排空操作，并关闭同一 QUIC 连接上的另一个空闲流，处理已关闭流的代码会遍历树，却没有找到正在创建的流，于是得出该连接处于空闲状态的结论，并再次将其设为可复用。之后的一次排空操作，例如新请求连接到其上游时，就可能在该请求运行期间关闭 QUIC 连接。

F5 的公告指出，利用过程“还取决于攻击者无法控制的其他条件”。Xint 表示，该漏洞的“触发机制与 HTTP/2 漏洞略有不同”。

修复

新增四行：流会在申请槽位之前加入树中，并在错误路径上再次被移除。

CVE-2026-123634：遍历列表期间释放下一个列表项

当 proxy_pass 包含变量时，nginx 会在处理请求期间解析主机名。如果针对同一名称的查询已在进行中，新请求会在同一个解析器节点上等待。答案到达时，nginx 会分离等待上下文列表，并依次调用每个上下文：

next = rn->waiting;
rn->waiting = NULL;

while (next) {
   ctx = next;
   ...
   next = ctx->next;

   ctx->handler(ctx);
}

循环会在调用处理程序之前存储 next ，因此处理程序可以释放其自己的上下文。问题始于处理程序释放同一列表中的另一个上下文时。当两个上下文属于同一个请求时就会发生这种情况，例如请求及其 mirror 子请求解析同一个名称（Xint 测试的情况；F5 也列出了 SSI 子请求）。如果第一个处理程序结束请求，请求的清理过程会为第二个上下文调用 ngx_resolve_name_done() 。该函数在节点的等待列表中查找该上下文，但由于该列表已被分离而找不到它，随后仍会释放该上下文。循环接着会前进到已释放的上下文。

nginx 通常会记录这一点。在存在漏洞的版本中，当查找失败时，它会写入

could not cancel <name> resolving

到错误日志，级别为 alert。这行日志值得搜索。它无论如何都不能作为证据：修复提交指出，其中一个变体在跟随 CNAME 时不会产生 alert。

该修复

当一个上下文位于已分离的列表中时被取消，不再立即释放。其处理程序会被替换为一个在循环到达它时释放它的处理程序（新增 31 行）。该修复还将 alert 降级为 debug 消息，因此上述日志行只会出现在未打补丁的版本中，级别为 alert。

CVE-2026-113425：两个连接，一个会话

使用 auth_http 时，邮件代理会要求 HTTP 服务验证每次登录。在等待期间，它会为单个会话持有两个连接：客户端连接，以及指向认证服务的连接。第二个连接指向该会话，并使用客户端连接的内存池。

修复之前，协议处理程序为客户端准备的回复在认证请求进行期间仍留在队列中，并且客户端的写处理程序仍为 ngx_mail_send()。如果该处理程序运行，且由于客户端重置连接而导致写入失败，它就会关闭客户端连接并销毁会话。认证连接仍指向该会话，而该连接上的下一个事件会使用已释放的内存。

Xint 描述了出现此问题的两个条件：客户端的写事件必须已经注册（例如，因为客户端停止了读取回复），并且登录命令与连接重置必须在事件循环的同一轮处理中被处理。并不需要有效的凭据，因为这发生在检查登录之前。

该修复

新增的两行会在认证请求开始时丢弃排队的回复。同一版本还包含另外三个提交，分别在代理等待认证响应时、连接上游并读取其问候语时，以及解析 SMTP 客户端的地址和名称时阻止客户端写入。

这些修复的共同点

这五个修复都涉及对代码的小幅修正。每个修复分别新增 2 到 31 行，邮件代理修复还附带另外三个提交。无需进行设计变更。每个修复都恢复了一个其余代码已经依赖的不变量：

  • 发送窗口永远不会超过协议规定的最大值
  • 有请求正在进行的连接绝不会被重复使用
  • 其他代码即将使用的对象不会被提前释放

在每种情况下，都是某条代码路径未能维持其余代码所依赖的规则，而修复会让该路径遵守这些规则。随着代码不断修改，这类规则很容易被破坏。

需要关注的内容

尝试利用此漏洞通常会触发一些具有特定特征的日志消息。其中三条消息（info和warn处的两条，以及另一条）低于 nginx 默认的error_log级别error，只有将级别设置得更低时才会出现。alert消息默认会被记录。

缺陷

日志消息或其他信号

CVE-2026-123007

一条长时间保持的 HTTP/2 连接，nginx 从客户端接收数十 GB 数据，却只向客户端返回很少的数据，远超其已记录请求所对应的数据量。在已修复的版本中，被拒绝的尝试会记录client violated connection flow control: received WINDOW_UPDATE frame with window increment ... not allowed for window ...（级别info；旧版本对普通违规行为也会记录同一条消息）。在这样的连接上，http2 flood detected（级别info）可能表示一次失败的尝试，但 nginx 也会因触发其他多项限制而记录该消息。

CVE-2026-123633、CVE-2026-121810

在接受 HTTP/2 或 HTTP/3 并代理到上游服务器的服务器上，会记录worker process <pid> exited on signal 11（级别alert），同时还会记录worker_connections are not enough, reusing connections（级别warn）。释放后使用并不一定会导致崩溃。

CVE-2026-123634

could not cancel <name> resolving（级别alert，仅限未打补丁的版本）。没有出现此消息并不能排除该缺陷。

CVE-2026-113425

使用auth_http的邮件代理中的工作进程崩溃，客户端连接在登录过程中被重置。

全部五个

由 nginx 工作进程启动的异常程序，例如针对工作进程用户执行auditd规则中的execve。Xint 建议进行此项检查，这是攻击成功最明确的迹象。

这些缺陷还会不断出现

CVE-2026-123007 在 nginx 中存在了十多年。SCTP 缺陷自 2018 年起就已存在于 Linux 内核中。Xint 表示，其一名研究人员手动发现了 CVE-2026-123007，而一次 Xint 自动化扫描发现了另外四个 nginx 缺陷。还有其他几个团队独立发现了这两个 HTTP/2 缺陷。与此同时，nginx 的公告列表已从 2025 年的两条增加到今年迄今的 36 条。借助 AI 的研究正在以前所未有的速度发现经过大量审查的代码中的缺陷，未来还会公布更多类似漏洞。

这也是为什么值得在源站前方部署 Cloudflare 的重要原因之一。当攻击者无法直接与您的服务器通信时，Web 服务器中的协议缺陷所造成的风险就会大幅降低。我们的边缘节点不受影响，针对您的 nginx 发起的 HTTP/2 和 HTTP/3 攻击会在我们的网络处终止。无论如何都应打补丁，锁定源站以确保 Cloudflare 是唯一入口，并使用Radar Zero Wire 页面 检查您的资产范围。
