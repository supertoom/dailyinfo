NGINX HTTP/2 漏洞 CVE-2026-123007 可实现未认证代码执行

10-Year-Old NGINX HTTP/2 Flaw Lets Unauthenticated Attackers Execute Code on Servers

AI 导读

F5 披露 NGINX HTTP/2 漏洞 CVE-2026-123007，自 1.9.5 起存在，未认证攻击者在启用 HTTP/2 且可绕过或关闭 ASLR 的情况下可执行代码，获得 NGINX worker 进程权限；公开 PoC 已验证利用，研究人员称目前尚无真实攻击报告，CISA KEV 也尚未收录。

同一件事，精选收录的是《F5 与 Rapid7 披露 NGINX HTTP/2 整数下溢漏洞 CVE-2026-123007，可导致 RCE》

正文 · AI 翻译
中文原文

NGINX 的 HTTP/2 支持存在一个缺陷，攻击者无需登录即可在启用了 HTTP/2 的服务器上运行代码。

这个已有十年历史的缺陷 CVE-2026-123007 被称为“nginx2root”，自 2015 年 9 月 22 日发布的 1.9.5 版本起就存在于 NGINX 的开源代码中。修复版本 1.31.9 和 1.30.7 已于今天发布。

F5（NGINX 背后的公司）表示，在关闭 ASLR 或可以绕过 ASLR 的情况下，攻击者可以运行代码。Wiz 的安全研究人员表示，他们在测试中绕过了 ASLR，并通过该缺陷运行了代码。Xint 的研究人员表示，他们只需一个可访问的 HTTP/2 端口，就能通过该缺陷运行代码。

以这种方式运行的代码将获得 NGINX 工作进程的权限。据卢森堡计算机事件响应中心 CIRCL 介绍，要获得主机 root 权限，还需要第二种提权方式。

在 Xint 的测试中，即使 NGINX 运行在 Docker 容器内，以工作进程身份运行的代码也可通过 Linux 内核 SCTP 代码中的另一个漏洞获得主机 root 权限。

截至目前，供应商以及 Wiz 和 Rapid7 的研究人员均未报告任何利用该缺陷的攻击。CISA 的已知被利用漏洞目录中也尚未将其列入。

该缺陷的概念验证代码已在 GitHub 上公开，但其说明指出，该代码仅适用于演示对同一台机器上刚启动的 Docker 容器的攻击。

根据 NGINX 的安全公告，从 1.9.5 到 1.31.8 的每个开源版本都存在该漏洞。其中包括 10 月 21 日发布的 1.31.8，以及 10 月 14 日发布的安全版本 1.31.7 和 1.30.6。

Wiz PoC

根据供应商公告，NGINX Plus 也受到影响，包括修复版本之前的 37.x 版本以及 R34 至 R36。

今天的发布版本还修复了另外四个缺陷，供应商称在相同的 ASLR 条件下，这些缺陷可能导致代码执行。五个漏洞在 CVSS 4.0 中的评分均为 10 分中的 9.2 分。

每个缺陷只能在特定配置下利用：

缺陷 所需条件
CVE-2026-123007 启用 HTTP/2
CVE-2026-123633 HTTP/2，当 worker 的 worker_connections 资源不足时，将请求传递给后端服务器
CVE-2026-123634 由变量构建的代理服务器名称，加上服务器端包含（SSI），或向查询同一名称的位置发起 mirror 子请求
CVE-2026-121810 启用 HTTP/3
CVE-2026-113425 将 NGINX 用作邮件代理

在启用了 HTTP/2 的情况下，listen 指令包含 http2，或者设置了 http2 on。使用 openssl s_client 搭配 -alpn h2 针对服务器运行；如果服务器接受 HTTP/2，输出会显示 ALPN protocol: h2。如果位于 CDN 之后，应测试 NGINX 源站本身，因为仅接受 HTTP/1.1 的源站无法通过 HTTP/2 发起攻击。

修复、变通方案与攻击迹象

据 F5 表示，这些发布版本修复了 CVE-2026-123007：

  • NGINX Open Source 1.31.0 至 1.31.8（主线）：已在 1.31.9 中修复
  • NGINX Open Source 1.9.5 至 1.30.6，包括 1.28 等较旧分支：已在 1.30.7 中修复
  • NGINX Plus 37.1.0 至 37.2.0.1：已在 37.3.0.1 中修复
  • NGINX Plus 37.0.0 至 37.0.7.1：已在 37.0.8.1 中修复
  • NGINX Plus R34 至 R36：未列出修复版本

根据 NGINX 的发布说明，1.31.9 和 1.30.7 版本修复了全部五个缺陷。在 NGINX Plus 中，37.3.0.1 和 37.0.8.1 修复了其中四个缺陷，而 CVE-2026-123633 的修复已包含在更早的 37.2.0.1 和 37.0.7.1 版本中。

升级后，请完全重启 NGINX，或使用其实时二进制升级功能。仅重新加载会使旧可执行文件继续运行，现有连接也可能继续由旧的 worker 进程处理。

截至今天，NGINX 的官方 Docker 镜像有 1.31.9 和 1.30.7 标签，包括 Alpine 变体。

截至今天，Ubuntu 和 Debian 尚未发布修复软件包。Ubuntu 的CVE 状态页面将 nginx 列为从 16.04 到 26.10 各发行版均存在漏洞，Debian 的安全跟踪器则将其列为在 bookworm、trixie、forky 和 sid 中存在漏洞。发行版软件包可能包含修复，而 nginx -v 报告的版本号不会改变，因此请将完整的软件包版本与该发行版自己的公告进行比较。

Xint PoC

供应商仅为五个漏洞中的两个列出了变通方案。对于解析器漏洞 CVE-2026-123634，请避免使用 SSI 和 mirror 指令，也不要使用变量构建代理服务器名称。对于邮件代理漏洞 CVE-2026-113425，请将监听器限制在受信任的网络中。

CIRCL 的响应指南建议，在能够升级之前，暂时关闭 HTTP/2 作为缓解措施。这样可以阻止 CVE-2026-123007 和 CVE-2026-123633，但不能阻止另外三个漏洞。在使用 HTTP/3 的地方将其关闭，可消除 CVE-2026-121810 所需的配置。

在 NGINX 1.25.1 及更高版本中，请在每个受影响的 server 块中设置 http2 off;，并从其 listen 指令中移除 http2。在 1.9.5 至 1.25.0 中，请从 listen 指令中移除 http2，使 listen 443 ssl http2; 变为 listen 443 ssl;。然后在需要的地方重启 NGINX，并重新运行 openssl 检查，以确认服务器不再接受 HTTP/2。

在 Linux 内核的 SCTP 缺陷得到修复之前，同一份指南建议，不使用 SCTP（一种类似 TCP 的网络传输协议）的主机应阻止加载其内核模块。一种方法是在 /etc/modprobe.d/ 中的 .conf 文件中添加 install sctp /bin/false 这一行。这不会卸载已经加载的模块，也不会关闭内核中内置的 SCTP。

要识别攻击迹象，CIRCL 建议查找以下情况：启动了意外程序的 NGINX worker、异常退出或留下 core dump 的 worker、长时间保持且入站流量很大但记录的请求很少的 HTTP/2 连接，以及异常的出站连接或 DNS 查询。干净的访问日志并不能排除攻击的可能性，因为 HTTP/2 控制帧通常不会作为请求出现在其中。这些迹象中的任何一项都不能单独作为证据。

据 Rapid7 的技术分析称，其攻击版本需要大约 128 GB 的 HTTP/2 流量。在演示中，攻击耗时两分半钟。在速度低于约 300 Mbit/s 的链路上，传输时间将超过 NGINX 默认的一小时连接限制，攻击将会失败。

该方法还依赖一个 glibc 内存复制例程；在具有 avx512f 和 avx512vl 功能的 x86-64 CPU 上会选择该例程。

据 Wiz 的披露文章称，Wiz 在 64 位系统上使用基于 TLS 的 HTTP/2，对官方 NGINX 1.31.7 和 1.31.8 构建版本进行了测试。

据 Xint 的研究报告称，Xint 的攻击对其在 AWS、GCP 和 Azure 上的测试服务器有效，包括通过公共 IP 地址发起的攻击。
