Rapid7 发现暴露的 Ollama 服务器已被第三方租用和控制

Open by Default, Already Occupied: Threat Actors are Renting your Compute

AI 导读

Rapid7 对 20,354 个预选 IPv4 地址的快照分析显示，过滤疑似诱捕基础设施后，仍有 7,627 台主机在未认证状态下响应 AI 或 Notebook API，其中 7,675 个 Ollama 发现项经校正后成立，54.8% 的 Ollama 主机带有第三方活动痕迹。

值得关注

文章用单次扫描和模型清单还原第三方占用计算资源的手法，并区分暴露面与真实活动，为排查 AI 服务失陷提供了可操作线索。

正文 · AI 翻译
中文原文

在此次扫描发现的暴露 Ollama 服务器中，超过一半已经被所有者之外的人接触过。我说的不是理论上存在漏洞，而是实际可见的使用痕迹：作为回调地址的模型名称、盖有服务器自身 IP 的标签，以及解码后为 /etc/shadow 的 Base64 字符串。

暴露统计数据通常描述的是风险。这些模型列表描述的却是实际活动。未经身份验证的 /api/tags 调用是一个只读请求，而在数千台机器上，它会返回一份接近访客日志的内容。

下面是数据所呈现的情况、我认为它指向何处，以及我会在周一早上采取什么措施。我将各项主张标注为 [观察到]、[解读]或 [假设]，以便你看出证据在哪里戛然而止。

首先，有一个我并不信任的数字

扫描器报告了 11,891 个 IP 地址上的 14,064 项发现，并将其中 14,060 项标记为易受攻击，387 项为严重。如果把它写进标题会很吸引眼球，但那也会是错误的。

[观察到] 有 148 个 IP 地址返回完全相同的指纹：3000 端口上的 Grafana、8888 端口上的 Jupyter，以及三个端口上的 Ollama，每个都提供一个模型，llama3.1:8b。它们分布在五个国家的五家不同托管服务商处。另有 281 个地址在同一端口上以两到五种不同产品作出响应。真实服务器很少会这样，传感器和兜底响应器却天天如此。

[解读] 这些极有可能是欺骗基础设施，由研究人员、厂商或威胁行为者运营，用来观察谁会上门。排除这 429 个地址后，严重发现数从 387 项降至 39 项。MLflow 从 126 项降至 4 项。蜜罐看起来极度易受攻击，这正是它们的全部工作内容。

在继续之前，再作两点更正。Streamlit 健康检查返回 ok 只能说明某个应用已暴露在互联网上，并不能说明它可被利用。而且，目标列表是预先选定的：20,354 台主机中有 58% 产生了发现项，这一比例远高于任何全互联网基准比率。因此，应将这些总数视为规模大得多总体中的一个样本，而不是普查结果。

仍然令人不安的情况是：在 7,627 台主机上发现 7,714 个问题，其中 AI 或 Notebook API 在无需身份验证的情况下即可响应，而且几乎全部与 Ollama 有关。在所有发现项中，只有 0.3% 通过 HTTPS 提供服务。

对于任何统计暴露数量的人，包括我们自己，这条经验教训是：如果你统计的是横幅信息和健康检查，你测量的只是互联网如何呈现自己，而不是它如何运行。

这是租用的计算资源，而非企业数据中心

[观察] 大约 65% 的主机位于托管或云网络中，且六家提供商（OVHcloud、Hetzner、Contabo、Oracle Cloud、Tencent Cloud 和 DigitalOcean）占全部目标的 42%。这些目标分布在 1,656 个网络中，但集中在那些五分钟内就能租到一台高配服务器的地方。

[解读] 在暴露的 Ollama 中，德国居首（1,306 台主机），领先于中国和美国。我不认为这意味着德国人粗心大意。Hetzner 和 Contabo 来自德国，OVH 在欧洲拥有广泛布局，而这三家都是那些想在这个下午就试用某个模型、无需走采购流程的人的首选。地理位置取决于价格表。

[解读] 此类机器很少出现在 CMDB 中。通常是某个团队需要快速进行计算，便用信用卡租用，之后再连接到公司数据。现在，你的攻击面还包括了开发人员的费用报销单。

实际运行的内容

[观察] 已暴露的 Ollama 服务器列出了 106,938 个模型条目、18,733 个不同标签，平均每台主机约 14 个。在本地模型中，Qwen 占据主导，其次是 Llama 和 Gemma。但更重要的区分在于运行在机器上的模型与机器仅负责路由的模型。

这台机器正在成为网关

[观察] 79% 的已暴露 Ollama 主机至少列出一个 :cloud 模型，主要是 GLM、DeepSeek、MiniMax 和 Kimi 的各个变种。当主机已使用 ollama signin 登录时，Ollama 的混合模式会将这些请求通过本地守护进程路由至 ollama.com，从而将 ~/.ollama/id_ed25519 中的本地 ed25519 密钥与用户账户关联起来。

[解读] 一台已暴露且处于登录状态的服务器，可以让他人访问你的付费订阅，而账单则由订阅所有者承担。这是自托管版本的 LLMjacking，完全不需要任何漏洞利用。

[假设] 列出的云标签并不能证明主机已登录，而且我们没有测试推理。不过，同样的七种云模型共同出现在 1,295 台互不相关的主机上。这一模式看起来更像是第三方自动拉取模型，以检查哪些服务器会为其提供服务，而不像数千次独立选择。

护栏是可选的，前门也是

[观察] 28% 的已暴露 Ollama 主机至少搭载了一个“abliterated”、“heretic”或“uncensored”模型，即刻意移除了拒绝行为的版本，其中包括一个以进攻性安全工作命名的微调模型。运行这些模型是合法的，而且通常有充分的研究理由。但若在互联网上未经认证地运行，任何人都能使用你的硬件上未经日志记录、未经筛选的模型。

[已观察到] 另有 28% 会运行嵌入模型，例如 nomic-embed-text 或 bge-m3。[解读] 嵌入模型是检索增强生成的基础设施。这些服务器很可能接入了读取内部文档的流水线，因此暴露的主机是一座桥，而不是一座孤岛。

访客日志

我认为最值得关注的发现如下。Ollama 的 API 允许任何调用者从任意注册表拉取模型、复制或创建模型，并将其推送到其他位置。在没有身份验证的情况下，模型列表就成了一份记录， 显示陌生人都曾要求服务器执行什么。

[已观察到] 24% 的主机列出了从原始 IP 地址和端口拉取的模型。22% 列出了通过免费隧道或一次性注册表服务拉取的模型：Cloudflare quick tunnels、ttl.sh、bore.pub、Pinggy。当服务器从你控制的地址拉取模型时，它就会回调你。这是一种干净且可靠的方法，可确认目标可达、可写并且能够建立出站连接：典型的服务器端请求伪造，却被作为一项功能提供。

[已观察到] 有 712 个模型名称嵌入了其所在服务器的 IP 地址。[解读] 这是在进行资产盘点。有人正在给目标添加标签，以便其工具稍后能够识别它们。同样适用于反复出现的标记，例如 zzvitals-beacon、verif_sys 和 ops-verify，每个都出现在数百台主机上；也适用于以 -copy-test 结尾的名称，这些名称表明有人正在检查复制端点是否正常工作。

[假设] gpt-4o、gpt-4 和 claude-3-opus 这组三元标记同时出现在 1,190 台主机上，而且几乎总是紧挨着 tinyllama，看起来像是以高级名称复制的小型本地模型。这要么是一次写入测试，要么是一种让服务器在下一个发现它的人看来像是提供了前沿模型的方法。我不敢断言是哪一种。

他们试图获取什么

[观察到的]在 55 台主机上，模型名称包含可解码为文件路径的 Base64 或十六进制字符串。目标读起来像一份漏洞利用后的检查清单：/etc/shadow、/etc/passwd、/proc/self/environ、Ollama 自身的 systemd 单元及其 override.conf（人们往往会在那里放置环境变量和 API 密钥）、SSH authorized_keys、AWS 配置、Oracle Cloud 元数据端点；在 10 台主机上，还包括 Ollama 私钥本身。有几个目标指向 /etc/ld.so.preload 和新的 systemd 服务文件，这些是持久化位置，而非读取材料。

[解释]这与 Wiz 于 2024 年发布的 Probllama（CVE-2024-37032）技术相似：在模型清单的摘要字段中利用路径遍历载荷，通过 /api/pull 实现任意文件写入，通过 /api/push 实现文件读取，并通过破坏 /etc/ld.so.preload 实现代码执行。Ollama 于 2024 年 5 月在 0.1.34 版本中修复了该漏洞。我们无法从这些列表中判断任何目标是否仍运行易受攻击的构建版本，因此这些尝试只能证明意图，而不能证明成功。两年半后仍有人认为值得尝试，这表明该技术依然足够有用，值得继续测试。

其经济账不容忽视。攻击者使用免费隧道、免费的临时注册表，最终还会利用你的计算机和你的云订阅。每个目标的成本算下来接近于零。

没有人查看模型列表

[观察到的]其中一些标记于 6 月创建，并且截至 11 月 10 日仍然存在。[解释]当陌生人的模型在你的服务器上停留五个月时，主要问题并不是漏洞本身。主要问题在于，这台服务器没有任何人负责。

看到这些数据后，我会做哪些改变

暴露面研究需要提出第二个问题。

“它是否开放？”这是容易回答的部分。“它是否已被触碰？”才是有用的部分；对于 AI 运行时而言，答案通常就藏在只读 API 响应中。防御者应根据痕迹进行分流，而不是根据横幅信息。

模型运行时正在成为凭据代理。

一旦本地守护进程能够使用磁盘上的密钥路由到付费云模型，攻破它就意味着获取访问权限和资金，而不只是消耗 CPU 周期。这与大多数团队键入 OLLAMA_HOST=0.0.0.0 时所设想的是不同的威胁模型。

这里的攻击者并不需要 AI。

我们耗费大量精力争论 AI 是否会让攻击者更快。在这些服务器上，现成的套路依然老套：未经身份验证的服务、路径遍历、服务器端请求伪造、对外回调。熟悉的原语，新的落脚点。我们早已知道哪些控制措施有效，只是它们还没有跟上工作负载。

互联网测量数据受到污染，我们应当明确指出这一点。

所谓“关键 AI 暴露”中，有相当一部分实际上是其他人的传感器在相互观察。任何发布暴露数据的机构，包括厂商在内，都应说明其筛选方式。

企业应采取的措施

这里涉及的控制措施并不陌生：归属管理、身份验证、出口控制、日志记录、补丁管理和暴露管理。实际步骤也很直接：

本周：找出它们，并检查是否有访客

  • 扫描你们自己的公网地址范围，以及公司付费的每一个云端和 VPS 账户，包括通过个人信用卡支付并报销的账户。不要只看默认端口：这里有 6% 的发现结果位于非标准端口上。
  • 在每个 Ollama 实例上，读取模型列表。任何以 IP 地址、隧道域名或 ttl.sh 为前缀的东西，任何名为 beacon、verify、probe 或 pwn 的东西，以及任何包含你自己 IP 地址的东西，都是陌生人留下的产物。
  • 如果发现其中一个，应将主机视为已被攻陷，而不只是配置不当。轮换其环境和服务文件中的所有凭据，撤销关联 ollama.com 账户上的 Ollama 密钥，检查云端用量中是否有无法识别的支出，并进行重建，而不是清理。

30 天内：先关上门，再关上窗

  • 将模型运行时绑定到 localhost 或私有网络。如需远程访问，应在前面部署带身份验证的反向代理或零信任访问层。Ollama 没有内置身份验证，因此这不是可选项。
  • 将模型服务器的出站流量限制到你批准的注册表。出口控制能够将基于拉取的回调或 SSRF 尝试转化为连接失败。
  • 保持运行时为最新版本；除非共享服务器位于身份验证和支出告警之后，否则不要将其登录到个人或企业云端模型账户。
  • 记录会改变状态的 API 调用（pull、create、copy、push、delete），并针对这些调用发出告警。在稳定的生产服务器上，这些调用应当很少出现。

本季度：让归属管理成为默认要求

  • 将登记纳入 AI 基础设施支出的前提条件：每台模型服务器都要有指定的负责人、数据分类和到期日期。如果无人负责，就将其关闭。
  • 以书面形式确定允许在哪些位置运行未经审查或经过审查移除限制的模型，以及这些模型可以接触哪些资源。研究沙箱可以，面向互联网且接入文档处理流水线的机器不可以。
  • 将 AI 运行时、笔记本和实验跟踪器纳入暴露管理和红队测试范围。测试的不只是引擎，还要测试制动系统：你能否在一小时内找到、隔离并关闭其中一台服务器？

方法与局限性

于 2026 年 11 月 10 日进行单次快照采集，针对预先选定的七个端口上的 20,354 个 IPv4 地址（3000、5000、8000、8080、8501、8888、11434）。产品检测针对每项服务发出一个未经身份验证的 HTTP 请求：Ollama /api/tags、Jupyter /api/kernels、MLflow experiment search、JupyterHub /hub/api/、Streamlit 和 Grafana health endpoint。未发送任何推理、写入或漏洞利用请求。

可能通过两种启发式方法移除了疑似欺骗基础设施：148 台主机共享相同的五服务指纹，以及以多种产品身份响应的 IP:port 对（281 台主机）。这在 429 台主机上移除了 1,513 项发现。有些真实服务器可能已被移除，但肯定仍有部分传感器留存。

第三方活动指标仅根据模型名称推断。干净的清单并不能证明主机干净，因为名称可以被删除。编码字符串已从 Base64 和十六进制片段中解码。模型家族按名称模式归类。地理位置和网络数据来自 DB-IP Lite（CC BY 4.0）、MaxMind GeoLite2 和 iptoasn。本文不会列出单独暴露的主机。

本文反映了作者对上述扫描数据的分析。Ollama、Jupyter、MLflow、Streamlit 和 Grafana 分别是其各自所有者的商标。本文包含由 MaxMind 制作的 GeoLite2 数据。
