MongoDB Server 预认证 use-after-free 漏洞 CVE-2026-118383 可在故障转移时崩溃

Critical Pre-Auth MongoDB Flaw (CVE-2026-118383) Can Crash Lagging Servers on Failover

AI 导读

MongoDB Server 的 CVE-2026-118383 允许未认证攻击者发送两个带 readConcern.afterOpTime 的 ping 请求，在受影响节点落后且随后赢得选举时触发 use-after-free 并使数据库崩溃；CVSS 4.0 评分为 9.5。

值得关注

原文通过复制集实验还原了崩溃触发链，并给出版本、补丁、日志特征和临时网络限制，便于评估暴露风险与排查节点。

中文原文

MongoDB Server 中的一个严重漏洞允许未经身份验证的攻击者发送两个请求，从而导致数据库服务器崩溃。只有在该服务器之后被选为接管主服务器、且仍缺少某些近期更改时，才会发生崩溃。

制作该数据库的 MongoDB 公司于本周早些时候发布了修复版本。

受影响的服务器是副本集的成员。副本集是一组保存相同数据副本的 MongoDB 服务器。其中一个成员（主服务器）充当主服务器并处理所有新写入操作，其他成员则复制这些写入。如果主服务器不可用，其他成员会举行选举以选出新的主服务器。

Datadog Security Labs 的研究人员在实验室中复现了该崩溃，并于昨日公布了研究结果。研究人员称，在易受攻击的版本上，启用身份验证也无法阻止这两个请求。攻击者无法使目标成员落后或在选举中获胜，也无法获知任何一种情况何时发生。

该漏洞的跟踪编号为 CVE-2026-118383，属于释放后重用：服务器最终使用了已经释放的内存。MongoDB 在 CVSS 4.0 严重性评分标准上将其评为 10 分中的 9.5 分。该公司表示，是公司自行发现了此漏洞，并且“并未发现任何试图利用此漏洞的行为”。

受影响的成员包括分片集群中的分片服务器和配置服务器成员。独立的 mongod（即不隶属于任何副本集的单一服务器）不受影响。

每个受影响的分支都有一个修复版本，列表如下并列于 CVE 记录中。分支中早于该版本的每一个版本都受到影响，可一直追溯到该分支的首个版本。

MongoDB 表示，MongoDB Atlas 集群会在维护期间自动获得修复版本，详情见其安全公告。推迟维护的客户应尽快应用升级。

自托管部署需要让每个副本集成员都使用修复版本。升级后，应检查每个成员正在运行的版本，包括容器中的成员以及维护期间处于离线状态的任何成员。

8.2 分支不在列出的受影响版本之中，其最新版本为 8.2.12。但 GitHub 上发布的一份概念验证报告称，在使用仅限测试的设置进行实验室测试时，8.2.12 仍表现出该漏洞。

根据该公司的生命周期计划，8.2 分支已于 7 月 31 日结束生命周期。此后，版本不再获得修复，包括安全修复。

在成员能够升级之前，研究人员建议将数据库的网络访问限制为仅允许需要访问的系统。这样可以限制谁能发送这两个请求，但无法修复该漏洞。

据 Datadog 研究人员的技术分析，首先赢得选举的成员会先应用其错过的写入操作以完成追赶，然后再接受新的写入操作。该漏洞存在于这一步追赶操作结束时所执行的清理过程中。

这两个请求都是携带 readConcern.afterOpTime 值的 ping 命令。每个命令都要求服务器等待复制达到某个特定时点，服务器会为其记录一个待处理通知，称为 waiter。

植入这些 waiter 并不会使服务器崩溃。它们不会过期，而是一直保留到该成员重启、回滚或从主服务器角色退下为止。

崩溃需要接收请求的成员在之后的选举中获胜，即使该成员落后于另一名成员。追赶结束时，清理流程会运行两次，重复使用已经释放的内存，而新的主节点在接受任何写入之前就会崩溃。研究人员表示，一旦满足这些条件，崩溃并不取决于赢得计时竞争。

在实验室中，研究人员使用管理员权限暂停和停止 mongod 进程，迫使该成员落后并自行触发故障转移。只有这两个请求来自一个没有凭据的客户端，并且该客户端无法向数据库写入。

在 8.0.34 版本中，该成员因段错误而崩溃，导致实验室集群失去主节点。其他部署可能会选出一台新的主节点并继续运行。

在已修复的 8.0.37 版本中，服务器立即将两个请求都判定为未授权并予以拒绝，该成员继续运行。修复的一部分只允许系统用户使用 readConcern.afterOpTime。

MongoDB 表示，在某些条件下，该缺陷还可能导致服务器进程中的任意代码执行。不过，研究人员表示，他们在实验室中“未能实现代码执行”。他们的结果也未表明该攻击在其他配置中成功的频率。

据其作者称，概念验证代码在实验室副本集中重现了该漏洞。其可靠模式需要一个仅供测试使用的设置，远程攻击者无法启用该设置。它所声明的影响是崩溃或内存损坏，并未声称能够实现代码执行。

研究人员表示，修复的第二部分可以防止清理流程即使已有等待者存在也运行两次。他们没有亲自测试这一部分。

在关闭身份验证的概念验证实验室测试中，修复后的 8.0.37 接受了植入的等待者，但仅运行了一次清理流程。

要检查是否存在植入行为或崩溃，请查看服务器的结构化日志，寻找研究人员在存在漏洞的运行中发现的以下迹象：

  • 日志事件：一条 COMMAND "Slow query" 条目（ID 51803），对应一个未通过身份验证且携带 readConcern.afterOpTime 的 ping 请求，并以 MaxTimeMSExpired 结束。
  • 日志事件：一个成员进入主节点追赶状态（ID 21359），随后在一次状态转换中两次退出该状态（ID 21363）。
  • 日志事件：在上述两次退出之后，出现涉及 CatchupState::abort_inlock() 的致命信号或回溯。

正常的选举或单次追赶退出并不能指向该缺陷。这些请求也可能在故障转移之前到达，因此还应检查同一成员更早的日志。

请求字段是否会被记录取决于日志设置，attr.remote 字段可能显示环回地址，而不是客户端的真实 IP。
