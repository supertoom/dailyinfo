中文原文

印度计算机应急响应团队（CERT-In）披露，其跟踪的一个名为 Crafty Falcon 的人工智能（AI）辅助型威胁行为体正在针对该国银行、金融服务和保险（BFSI）行业的组织发起攻击。

CERT-In 将该威胁描述为活跃且持续进行中，相关活动使用了 公开可用的 AI 驱动型进攻性安全工具，例如 ARTEX、PentAGI、Cairn 和 CyberStrikeAI。

“这些工具能够以机器速度自主执行完整攻击链，快速生成并优化大量定制攻击脚本，并根据目标响应调整其载荷，”CERT-In 表示。“其配套攻击基础设施会在数小时至数天之间轮换 IP 地址。”

该机构称，这些攻击还针对了加密货币交易所和数字资产服务提供商，导致密钥和资金被盗。

此次更新紧随 CERT-In 于 2026 年 10 月发布的警报，该警报曾警告有多个网络攻击活动针对非银行金融公司（NBFC）、数字借贷平台、金融科技实体、支付服务提供商和加密货币钱包运营方。

据观察，威胁行为体利用面向互联网的应用、暴露的 API 和特权端点窃取支付聚合器/网关及合作银行 API 凭据，随后直接从这些实体自身的允许列表基础设施内调用资金转账 API。

其他一些值得注意的初始访问途径如下——

  • 使用被盗的长期有效静态硬编码 API 令牌
  • 通过伪造提交对源代码存储库实施供应链入侵
  • 利用配置文件、源代码或数据库中的明文凭据
  • 访问缺少多因素认证（MFA）的应用程序和远程服务

CERT-In 补充称，这种做法可绕过应用层控制，例如贷款创建、KYC、制裁、收款人验证、余额充足性和单笔交易限额。

这些快速执行的欺诈交易旨在将资金转移至攻击者控制的多家银行中的骡账户。此外，攻击还涉及运营方采取措施删除日志并篡改端点安全工具，以试图增加检测和事件响应的难度。

CERT-In 还警告称，攻击者正在针对云基础设施执行命令和部署恶意载荷，以及针对可公开访问的非生产环境获取共享凭据、令牌或网络路径，然后利用这些信息横向渗透至生产系统。

该对手采取的其他值得注意的后渗透操作如下——

  • 对应用程序代码库进行逆向工程，以开发定制漏洞利用程序
  • 使用经过修改的应用程序包发起未经授权的 API 调用，从而破坏那些“假定只有合法客户端应用才会调用这些 API”的控制措施
  • 执行微额测试交易（例如 1 卢比），在执行大额转账前验证未经授权的资金流
  • 滥用支付聚合器的商户结算 API 转移资金
  • 利用新披露的漏洞，包括在 PHP 和 Node.js 应用程序中导致 Web shell 的文件上传和反序列化漏洞利用链
  • 即时创建大量自定义脚本，并在短时间内反复迭代改进，这一模式符合 AI 辅助开发的特征

这一进展正值 CERT-In 发布《人工智能安全审计指南》之际，该指南提出了具体要求，以确保“人工智能系统的治理、安全、隐私、公平性、透明度、韧性和可审计性”。

该框架要求对人工智能代理的已记录身份、授权目标、经批准的工具使用、权限边界及其对最小权限原则（PoLP）的遵守情况进行测试。它还要求人工智能代理在执行后果性操作时必须获得人工批准，同时确保高风险人工智能系统具备紧急中断、凭据吊销以及防止自动重启的控制措施。

该机构表示：“有效的保障需要组织问责、技术测试、数据与模型治理、持续监测、人工监督、事件响应和第三方保障。”“因此，该框架提供了与每个人工智能系统的性质、规模、自主性和潜在影响相称的可审计要求。”

仿冒版 ARTEX 派发 root shell

在现实入侵中滥用 ARTEX 等开源渗透测试工具，促使其开发者从 GitHub 下架了相关代码仓库。但多个副本已在微软旗下的代码托管平台上出现，以填补这一空缺——

  • github[.]com/trhhubsd/ARTEXX
  • github[.]com/mhtsec/ARTEX（Docker Hub 上的“mianhuatang11/artex”）
  • github[.]com/RuoJi6/ARTEX

前两个 GitHub 仓库已无法下载。据一位使用网名 Badbyte 的独立网络安全研究人员称，“trhhubsd/ARTEX”仓库获得了 2,449 次星标和超过 600 次复刻。

GitHub 副本的显著之处在于，它修改了“docker-compose.yml”中的一行，改为从 Docker Hub 拉取“tomicdd/artex”镜像。修改后的版本隐藏了一个例程，只要向登录端点发送未经身份验证的请求，就会授予 root shell。根据 Docker Hub 分享的数据，该镜像已被下载 9,000 次。

研究人员在一份通过电子邮件提供给 The Hacker News 的声明中表示：“它在登录处理程序中添加了一个隐藏的 verifyCaptcha() 函数：如果 CAPTCHA 字段以一个秘密标记开头，其余代码就会以 root 身份通过 sh -c 运行，并在进行任何凭据检查之前返回输出。”“这意味着每次安装都有一个未经身份验证的 root shell，而且它永远不会出现在代码审查中。”

“被攻陷的 ARTEX 实例掌握着其目标的未修补漏洞发现、有效凭据、已捕获会话和网络位置。掌握该后门的人还可以悄无声息地改变代理在下一次运行时的行为。”

2026 年 11 月 2 日至 4 日期间，最多发现 62 个 ARTEX 控制台在互联网上提供带有后门的构建版本，其中第一个实例于 2026 年 10 月 20 日上线，比 Docker 镜像推送晚了十二天。其中，26 个控制台位于美国，其次是香港的 17 个和中国的 7 个。

截至 2026 年 11 月 4 日，总共发现 1,645 台主机在提供 ARTEX 控制台服务。除“tomicdd/artex”外，还发现了多个 Docker Hub 命名空间在发布名为“artex”的镜像。其中一些如下——

  • congdonglinux/artex（同样被植入后门，与“tomicdd/artex”完全相同）
  • mianhuatang11/artex
  • autumn26/artex
  • andy1099zz/artex
  • dgddw/artex
  • trhhubsd/ARTEX
  • ylh440104/artex

“这个后门程序的作者不需要再做更多事情。他们所针对的人早已选择把一个未经审查的攻击工具以 root 权限运行在开放端口上，”Badbyte 说道。“我们知道 ARTEX 已被恶意用于实际攻击中，而且这种使用方式还会持续。我们也知道，许多出于正当好奇心的用户安装了它，只是想看看究竟有什么动静。他们并没有自愿在自己的服务器上获得一个 root shell。”
