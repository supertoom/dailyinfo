CyberStrikeAI 入侵 AWS：16 天内跨 4 个账户调用 78 次 API

56 AWS API calls in 141 milliseconds: Inside an AI-run intrusion

AI 导读

一台 CyberStrikeAI 服务器在 2026 年 9 月 30 日至 10 月 16 日间，利用 8 个 AWS 身份凭据侵入 4 个账户并触发 78 条告警；其中一次在 141 毫秒内批量读取 56 个 EC2 user data，另一身份解密 SSM 参数后 29 秒发起 SendCommand。

值得关注

文章通过 CloudTrail 时间线还原了低严重度告警如何经长期关联构成同一次入侵，并提供了可迁移的行为检测与 IAM 处置思路。

正文 · AI 翻译
中文原文

一台服务器在 141 毫秒内读取了 56 个 EC2 用户数据脚本。随后它沉寂了 14 天，再次出现。这一间隔造成的破坏比那次爆发更大，因为固定的相关性分析窗口无法跨越两周。

2026 年 9 月 30 日至 10 月 16 日期间，一台 CyberStrikeAI 服务器以熟悉的顺序利用被盗的 AWS 凭据执行操作：验证身份、从 Secrets Manager 收集机密、提取 EC2 用户数据、解密 SSM 参数以及发送远程命令。这些操作中的每一步都是合法角色每天都会调用的。当时，CloudTrail 中没有任何迹象显得紧迫。

CyberStrikeAI 是一个将 LLM 智能体与进攻性安全工具相结合的开源平台。Team Cymru 的 Thomas 统计了 2026 年初运行该平台的 21 个 IP，它们全部以 Fortinet 边缘设备为目标。这是我们首次看到同一套工具被用于攻击 AWS。

基于工具归因以及日志中的机器速度行为，我们将其称为 AI 辅助攻击。我们无法证明是由 LLM 智能体作出决策，也不知道攻击者是如何获得这些凭据的。

CyberStrikeAI AWS 入侵事件的主要发现

  • 2026 年 9 月 30 日至 10 月 16 日，一台 CyberStrikeAI 服务器（43[.]240[.]29[.]11）使用了来自四个账户中八个 AWS 身份（五个 IAM 用户和三个 EC2 实例角色）的凭据，并产生了 78 条警报。

  • app-role 在 141 毫秒内发送了 56 个用户数据请求，占 58 条用户数据检索警报的一部分（总数的 74%），这表明使用了自动化工具。

  • 10 月 2 日，container-role 读取了一个加密的 SSM 参数，并在 29 秒后发出了 SSM SendCommand。审计日志未显示该命令的内容，也未显示其是否执行成功。

  • 43[.]240[.]29[.]28 和 43[.]240[.]29[.]33 在端口 8080 上提供 CyberStrikeAI 页面，使用的自签名证书与 43[.]240[.]29[.]11 相同，从而将这三台服务器关联在一起。截至 11 月，这三个 IP 均已不再提供该界面，因此应将其视为回溯性狩猎的指标。 

  • 全部 78 条警报的严重程度均为中等或低，只有按源 IP 进行关联后才能看出其意义。

该活动分四个阶段持续四个活跃日，随后在最终回访前间隔了 14 天。所示时间均为相对于每个阶段首个事件的偏移量。

使用 Elastic Workflows 实现 IAM 遏制

AI 辅助的攻击往往零散且迅速，尤其是在身份凭据被攻破时。Elastic Workflows 可以通过调用 AWS 服务（如 IAM）的 API 自动封禁该身份，从而为响应人员提供支持。

Elastic Workflows 随技术栈（9.4+）一同提供，允许检测规则在每次告警时调用自定义工作流，该工作流使用以 YAML 定义的步骤流水线。作为概念验证，我们创建了一个自定义工作流，在下文共享的检测项触发时执行，以模拟与建议的响应操作一致的行为。

在每次告警时，该工作流会执行以下操作，并在数秒内完成，以帮助遏制该身份：

  1. 基于 AWS EC2 Bulk User Data Enumeration 检测规则触发

  2. 遍历与告警关联的每个用户名

  3. 通过 Elastic 的 AWS Lambda 连接器调用 AWS Lambda 函数

  4. 使用 iam:UpdateAccessKey 停用已失陷的访问密钥。

  5. 通过 iam:PutUserPolicy 添加带有 aws:TokenIssueTime 截止条件的内联拒绝策略，阻止与 IAM 用户关联的较早临时会话

  6. 通过附加内联全量拒绝策略来隔离 IAM 用户

可在此处找到此工作流的一个示例。

可在 CloudTrail 中搜寻的行为指标：

  • 在某一角色会话中，每秒发出大量请求 userData 的 DescribeInstanceAttribute 调用。

  • 同一分钟内，来自同一外部 IP 的多个账户或用户首次调用 GetCallerIdentity。

  • 由实例角色会话发出的 GetSessionToken 或 GetSecretValue，而其源 IP 并非该实例或你的 NAT。

  • 同一角色执行带解密的 GetParameter，随后一分钟内发出 SSM SendCommand。

我们新增了两项高严重度、低误报的 ES|QL 检测规则，用于识别这种突发枚举行为：当一个主体和源 IP 在 10 分钟内从 20 个以上不同实例读取 userData 时，AWS EC2 Bulk User Data Enumeration 会触发告警；当三个或以上不同的非角色身份在 10 分钟内从同一外部 IP 和 ASN 调用 GetCallerIdentity 时，AWS STS GetCallerIdentity Bulk Account Enumeration 会触发告警。

如果你的 AWS 身份凭据已泄露，应如何响应

假定受影响角色能够读取的任何内容均已泄露，并以这些凭据为起点向外排查。

  1. 轮换所有曾访问该指标 IP 的身份的凭据，并撤销活动会话，包括使用临时凭据创建的会话。

  2. 对于实例角色，应通过替换实例配置文件或实例来轮换凭据，因为被盗的角色凭据虽然会过期，但只要主机仍处于失陷状态，就可能被重新签发。

  3. 将 EC2 user data 中的所有机密都视为已泄露，并将其迁移到 Secrets Manager 或 Parameter Store。

  4. 审查 SSM 命令历史中任何异常 SendCommand 调用发生前后的时间段，以确定运行了什么。检查是否滥用了 AWS 托管文档、AWS-RunShellScript、AWS-RunPowerShellScript 或自定义文档。

  5. 检查非生产环境角色和机密与生产环境是否存在重叠。

  6. 在 WAF、VPC、NaCL 和安全组级别封禁该指标 IP，但同时应依赖行为检测规则，因为基础设施可能发生变化，而且网络封锁无法阻止被盗凭据调用 API。

  7. 使用 IAM 策略或服务控制策略，将 ec2:DescribeInstanceAttribute 对 userData 的访问权限限制为确有需要的角色。

  8. 如果尚未启用 GuardDuty，请予以启用，并对凭据从预期 IP 范围之外被使用的情况发出告警。

  9. 调查实例凭据是如何被获取的，首先检查暴露的 Web 应用程序、SSRF、代码存储库和 IMDS。

结论：此次入侵对告警关联意味着什么

AI 辅助攻击由目标驱动，因此会产生大量告警。一台 CyberStrikeAI 服务器在 16 天内基于六条规则产生了 78 条告警，其中 65 条出现在第一天。每条告警单独看都属于中低严重度，而且看起来都很常规：首次调用 GetCallerIdentity、调用 GetSessionToken、由少见用户发出的 SSM SendCommand。只有共同的源 IP 表明它们属于同一次入侵。

防御人员需要高信号检测规则，以便尽早阻止破坏；上述两条批量枚举规则等低误报行为规则，能够为立即采取行动提供依据。中低严重度告警很适合进行关联，但只能依据源 IP 进行关联，而且关联时间窗口需要保持灵活，因为 AI 辅助活动并不规律。这里，56 个请求集中在 141 毫秒内，后续步骤相隔数小时至数天，操作者则在 14 天后再次返回。若采用固定的短时间窗口，这次入侵就会被拆分成彼此无关的告警。

高信号检测还可以推动修复工作。将规则附加到工作流（例如 Elastic Workflows 库中的工作流）后，此类规则可以自动阻断攻击，例如通过阻止来源 IP，同时让分析人员展开调查。
