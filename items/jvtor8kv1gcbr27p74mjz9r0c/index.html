SentinelLabs 开源 VerifiedIDA，规范 LLM 驱动的二进制逆向分析

VerifiedIDA | Making LLM-Driven Reverse Engineering Inspectable, Continuable and Reusable

AI 导读

SentinelLabs 开源 VerifiedIDA，用于在 IDA Pro 中规范 LLM 驱动的逆向分析。研究基于 Anthropic、OpenAI 及开源模型对恶意与合法二进制的评估，指出模型虽较少编造，却会产生失真标签、遗漏已确认发现、因上下文压缩丢失未完成任务，并可能在相关代码尚未全部检查时提前停止。

值得关注

研究把模型逆向中的标签失真、发现遗漏和任务中断归因于机制缺失，并给出可复用的工程约束。

执行摘要

  • SentinelLABS 评估了前沿模型逆向工程二进制文件并为反汇编器数据库添加注释的能力，发现反复出现的问题，包括标签不准确和分析不完整。
  • 为提高性能，我们制定并测试了一套由 LLM 驱动的逆向工程标准，该标准确保注释与证据保持关联、验证数据库更改、保留项目状态，并要求对模型的工作进行审查。
  • 我们开源了 VerifiedIDA，这是一个参考实现，将该标准应用于 IDA Pro 中的自主逆向工程。
  • 尽管新模型的能力不断提升，但我们的研究表明，扩大逆向工程的规模需要确保模型产出的分析结果可供人类、其他模型以及下游安全工作流检查、继续使用和复用。

概述

将大型语言模型（LLM）用于逆向工程，使得以超越手动分析的规模和速度检查二进制文件成为可能。这也让不具备该领域专业知识的人员能够使用逆向工程。规模、速度与可访问性的结合在多个领域带来了重大转变。例如在网络安全领域，防御者可以在更短时间内分析更大批量的恶意软件，而攻击者也可能滥用同样的能力，大幅加速并扩大漏洞研究与漏洞利用开发规模，缩短从漏洞出现到被利用的时间，并增加入侵数量。

作为我们更广泛创新计划的一部分，该计划旨在应用 AI将防御工作流自动化并扩大规模，以跟上日益快速且广泛蔓延的威胁格局，这项工作有助于使LLM 驱动的逆向工程可检查、可延续且可复用。当逆向工程输出被用于网络防御行动时，这些属性非常重要，例如事件响应、检测开发或威胁狩猎；在这些场景中，分析师会依据这些输出采取行动，与其他利益相关者分享，并将其作为其他工具和工作流的输入。这要求能够检查 LLM 结论背后的证据以进行验证，让另一名分析师或模型从 LLM 停止的位置继续工作，并复用与其所描述的代码和数据相关联的结果。

为此，我们专注于输出为带注释的反汇编器数据库的 LLM 驱动逆向工程，例如 IDA Pro、Ghidra 或 Binary Ninja 数据库。与文本报告不同，文本报告会将分析简化为模型结论的散文式快照，并脱离支持这些结论的代码；而带注释的数据库则将发现直接记录在反汇编后的代码和数据上，形式包括标签、类型、数据结构和注释。 

因此，分析师可以针对每个结论对照其所描述的代码和数据进行验证。当数据库与其他利益相关者共享时，接收者会获得所有注释，而不仅仅是报告所包含的发现，并且可以验证和使用自己需要的部分。此外，另一名分析师或 LLM 可以从数据库中现有的注释继续分析，必要时还可对其修正，而不必解读散文式报告并逐一查找每个结论所指向的代码和数据。其他工具和工作流也可以直接处理这些发现及其所适用的代码，例如生成以被识别为实现特定能力的函数为目标的 YARA 规则，或使用已恢复的数据结构解析配置数据。 

然而，带注释的数据库只有在注释准确且完整的情况下才能提供这些好处，而 LLM 并不能保证这一点。为了在实践中了解这些局限，我们开展了评估研究，让 LLM 分析二进制文件并注释 IDA 数据库，且未对其工作的准确性或完整性采取任何保障措施。

我们首先介绍这些研究的结果。结果显示，模型生成了不准确的标签、遗漏了一些发现、失去了对未完成工作的追踪，并提前停止了分析。完整的模型信息见下节。

基于这些发现，我们提出了一项由 LLM 驱动的逆向工程标准，该标准要求对反汇编器数据库进行注释。按照该标准，每条注释都必须确认已记录在数据库中，并可追溯至有文档记录的证据，以便核验其准确性；未完成的工作会持续受到跟踪，直至得到解决；独立审查会评估注释的准确性并识别未完成的工作，然后将其审查结果返回给负责逆向工程该二进制文件的 LLM 以供修正。

最后，我们介绍 VerifiedIDA，这是一个测试框架，作为该标准的初步实现，负责调节 LLM 对 IDA 数据库的访问。VerifiedIDA 已发布为开源项目，并同时提供了该标准的规范和用户指南。

评估研究 | 无保障措施的 LLM 驱动逆向工程 

我们的评估研究旨在识别由模型主导的逆向工程中常见的挑战，其中模型必须使用基础工具对反汇编器数据库进行注释。我们并未重点详细比较各个模型单独、按厂商或按层级划分时的表现。

除开源模型外，我们还使用了 Anthropic 和 OpenAI 的专有模型，对不同大小、既恶意又合法的二进制文件进行逆向工程。本文介绍的大部分测试使用了 GPT-5.6 Sol。这些模型通过一个简单的测试框架开展工作：LLM 自主分析二进制文件，不接收任何人工或自动化反馈，并且只能使用基础逆向工程能力。该框架仅提供一般性说明和一组固定工具，用于查看反汇编和反编译后的代码、跟踪交叉引用、搜索二进制文件，以及将标签、类型和注释（例如函数的自由文本描述）写入 IDA 数据库。

Anthropic 和 OpenAI 模型的完整推理过程无法通过其 API 获取，因此在对二进制文件进行逆向工程时，我们无法直接观察它们如何作出决策。作为替代，我们逐步记录了每个分析步骤，并将我们称为 LLM 日志的内容记录下来，包括模型调用的工具、检索到的代码、其中间笔记与计划执行的下一步，以及它对数据库所做的编辑。例如，LLM 日志可能显示模型检索某个函数的伪代码、跟踪其交叉引用，随后在数据库中为该函数添加标签。这使我们能够重建模型检索了什么、每条注释依据什么，以及它如何依据这些信息采取行动。

为了说明接下来讨论的一些观察结果，我们在“案例研究”部分介绍两个案例研究，每个案例都详细考察 GPT-5.6 Sol 如何完成一项常规逆向工程任务。在这两个案例中，模型都对一个 ComRAT 样本进行了逆向工程（SHA-1 哈希：0139818441431c72a1935e7f740a1cc458a63452）；该后门被归因于俄罗斯 APT 组织 Turla。案例研究 #1 涵盖恢复作为参数传递给两个 ComRAT 函数的一种数据结构，而案例研究 #2 涵盖分析单个 ComRAT 函数的行为。

以证据为基础的结构化工作

我们观察到，LLM 对逆向工程任务采取了合理而系统化的方法。例如，在标注变量或函数时，它们通常先对伪代码或反汇编进行广泛分析，然后转向有针对性的探索，分析该变量或函数在整个二进制文件中的使用方式，以确定变量的作用或函数的主要操作，而标签应当描述的正是这一点。

这些模型在很大程度上也避免了编造。例如，当模型无法确定变量的作用或类型时，通常会使用通用标签，如 unknown，或使用通用数据类型，如 void，而不是凭空发明代码并不支持的内容。

此外，LLM 还有效利用了与分析相关的权威信息，例如 Windows API 函数的公开文档，而这些文档极有可能存在于其训练数据中。例如，当变量被传递给某个 Windows API 函数时，它们会根据该函数文档中记载的参数类型来确定变量类型；当某个函数调用 Windows API 函数时，它们会在确定调用方函数的主要操作时，参考这些 API 函数的文档行为。

不准确且不完整的反汇编数据库

除了上述优势之外，我们还发现了四个主要且反复出现的问题。这些问题削弱了带注释数据库作为 LLM 驱动逆向工程主要输出的作用；该输出本应成为供任何下游用途使用的、准确且完整且以二进制文件为依据的基础。

标签的准确性 

LLM 应用于变量和函数的某些标签并未准确描述变量的角色或函数的主要操作。这一点很重要，因为分析人员经常依赖标签在带注释的反汇编数据库中导航。因此，无论使用带注释的反汇编数据库的是人还是模型，不准确的标签都会给继续分析或从中得出结论的人带来后果。例如，含糊的标签可能导致分析人员重做已经完成的工作，而不精确的标签则可能使注意力偏离重要的二进制行为。 

不准确的标签还会错误呈现正在分析的二进制文件，而从数据库中得出的任何结论都会延续这种错误呈现。此外，从数据库本身无法看出标签的不准确性，因为标签并未说明其依据有多充分。因此，不准确的标签要么被直接采信并承担可能由此产生的后果，要么只能在付出重新分析——而该标签本应记录这一分析的结论——的代价后才发现。

发现捕获 

模型在分析过程中反复确立发现，却未将其记录为数据库中的注释，也就是说，它们无法可靠地将逆向工程发现转化为数据库注释。这些发现未能延续到后续分析会话中，其背后的努力实际上就此丢失，导致数据库不完整。

工作连续性

随着分析推进，模型经常丢失未完成工作的踪迹，我们怀疑这主要源于上下文压缩，即将模型先前的输出和工具结果压缩，以适应其上下文窗口。它们原计划执行的步骤被丢弃，导致其所针对的二进制文件部分未得到分析，数据库中也没有相应的注释。

分析的完整性

LLM 经常在检查完与其分析目标相关的所有代码之前就停止探索。例如，在确定某个函数的主要操作后，LLM 便为该函数添加标签，却没有探索该函数的所有被调用方，而其中一些被调用方实现了额外功能。这些功能仍未被识别，该函数的标签也未体现出它们。

逆向工程标准

我们观察到的四个问题并非单一故障的不同表现形式。每一个都指向一项不能仅交由模型承担的责任。

模型并非 infallible，因此任何系统都无法保证它们所应用的每个标签都准确无误。然而，系统可以保留每条注释背后的证据，从而在不重做该项分析——而该分析本应记录这一结论——的情况下，发现并纠正不准确的标签。系统可以确认哪些发现进入了数据库，将未完成的工作保留在模型上下文之外，并检查支撑某项结论的代码是否已被检查。

这些检查分为两类。机械检查无需解释代码即可进行：某项请求的更改是否已保留，或如案例研究 #2 所示，在为函数添加标签之前是否已检查该函数的被调用方。语义检查则需要复核标签是否描述了函数的主要操作，或分析是否确立了两项功能之间的关联。

这就是我们标准所强调的分工：模型负责做出分析判断，而围绕模型的系统负责保存证据、维护项目状态并确保后续落实。我们将其正式化为四项要求。

可归因的证据。 每个标注都必须能够追溯到模型为支持该标注而检索的证据，并标明二进制文件及其来源数据库的状态。不再反映当前数据库状态的证据不得用于支持新的标注。

经验证的变更。 系统必须检查每项请求的变更在数据库中记录了什么，以及是否已保留。如果变更失败，已接受的数据库必须保持完整，并且模型必须收到可供其采取行动的反馈。这对于类型变更尤其重要。无法干净应用的恢复结构，或会改动模型无意更改的数据库部分的结构，都可以在影响其他代码的反编译结果之前，通过机械化方式检测并拒绝。

保留的项目状态。 已接受的标注、变更历史、二进制的当前工作摘要以及待处理任务列表，必须存储在模型上下文之外。这样，在上下文压缩、中断或切换到另一个二进制文件后，可以由同一模型、不同模型或人类分析人员继续分析。

可强制执行的范围与审查。 独立审查者必须能够质疑标注的准确性，并识别未完成的工作。其发现必须反馈给调查模型，并持续跟踪，直到每项发现得到修正、被证据否决，或被记录为未解决事项以供人工接手。

我们提议的标准是 LLM 驱动逆向工程的最低要求。它不会让模型的分析变得正确，也不规定模型应如何对二进制文件进行逆向工程。许多工具已经以各自的方式使用模型进行逆向工程，未来也会有更多工具采用这种方式。验证必不可少，但它只能确立记录了什么，而不能证明记录是否正确；由另一个模型或人类专家进行审查，仍可能遗漏错误。该标准所确保的是，模型的结论始终与可供重新审视的证据相联系，其错误能够被识别，而不是被隐藏。该标准也不依赖于特定的反汇编器。我们将其作为接口规范发布，并同时提供针对 IDA Pro 的参考实现，下文将对此进行介绍。

VerifiedIDA Harness

VerifiedIDA 是我们对该标准的参考实现。我们首先为 IDA Pro 构建它，因为这是我们团队最常用的反汇编器。模型选择调查对象、检查代码并提出标注。VerifiedIDA 充当宿主，调解对 IDA 数据库的每次访问：它识别每个请求的目标，要求提供当前证据，将编辑应用到数据库的候选副本，检查结果，并记录每项操作。它维护三份记录：

  • IDA 数据库，其中保存已接受的标签、注释、类型、接口和关系，每个二进制文件对应一份，包括嵌入式二进制文件。
  • 一个 SQLite 台账，其中保存检查、操作、验证结果、数据库修订和跟踪的工作项。
  • 一个项目笔记本，其中保存模型当前的理解、不确定之处和后续行动，以及这些内容如何变化的日志。

可归因的证据。每次编辑都必须引用主机针对当前目标和数据库修订所记录的证据。证据通过二进制文件和修订来标识，而不是仅通过地址来标识，因为一个二进制文件及其嵌入的二进制文件可能会使用相同的地址。如果自模型检查代码以来数据库已发生变化，主机会拒绝此次编辑，并说明如何获取当前证据。模型的推断和历史证据都会相应地加以标注。审查人员可以从任意注释出发，在台账中找到引入该注释的操作，并检查模型在作出该注释时看到的代码。

经验证的更改。主机会将每项编辑应用到一个隔离的候选数据库中，通过独立路径读回结果，并在候选数据库成为已接受的数据库之前对其进行检查。类型和原型的编辑还会收到受影响 IDA 状态的比较，出现无关更改时则会被拒绝。如果编辑失败，已接受的数据库将保持不变，模型会收到目标、失败阶段、请求状态和观察到的状态，以及恢复方向。检查点会在全新的 IDA 进程中重新打开数据库，以确认已接受的更改已持久保存。

反馈还直接针对捕获问题。编辑完成后，主机会标记不完整的注释，例如已重命名但没有行为注释的函数，或仍保留生成名称的参数，并报告新创建的类型尚未应用的位置。在我们的示例中，该示例基于案例研究 #1 中的 ComRAT 结构，反馈报告称模型创建的结构已声明但尚未在任何位置使用，随后模型继续将其应用到该函数的参数。

保留的项目状态。笔记本记录调查当前所处的阶段，其当前状态部分会随着模型理解的变化而重写。在压缩上下文后，模型会收到当前指令和已记录的项目状态，任何后续编辑仍需要来自 IDA 的最新证据。当模型跟踪一个嵌入式二进制文件时，主机会记录其子进程的字节、提取方式及其与父进程的关系，并为其打开一个单独的数据库。在切换之前，我们要求模型记录其已在父进程中确定的内容，以及父进程如何使用该子进程，以便模型知道之后应返回何处。

可执行的范围与审查。独立审查从主机建立注释和潜在缺口的清单开始。随后，审查模型会检查各项具体声明以及对程序的整体解释，并可只读访问数据库的临时副本。主机会验证其发现，并冻结必须 更正的范围。调查模型随后恢复工作，一次处理一项发现：它可以应用更正、修改更正、以证据拒绝更正、推迟处理，或请求具体的跟进工作。然后，它会检查已接受的审查结论是否与注释一致，任何剩余分歧都会阻止任务完成。最终报告会说明已验证的内容、仍未解决的内容，以及是否满足完成策略。

覆盖模式。 我们在启用实验性调用流模式的情况下，重新运行了案例研究 #2 的功能。在此前六次 GPT-5.6 Sol 运行中，没有一次打开过 sub_180081450；为父函数添加注释的四次运行也都遗漏了转发导出处理。 

在新的运行中，Sol 从干净的数据库开始，且未被告知哪个被调用函数至关重要。一旦它对 sub_180077C10 提出了一项声明，该模式便列出该函数的 20 个直接内部被调用函数，并将该声明保持为未解决状态，直到每个函数都有记录在案的结果。Sol 打开了 sub_180081450，将其确定为转发导出的递归解析器，并确认了一条父级注释，该注释将本地导出表解析与其委托的递归操作区分开来。 

根据修订后的策略再次运行时，在全部 20 个被调用函数上都得到了相同结果，并且每次编辑都成功保留在全新进程的重新加载之后。该模式仅跟踪直接调用。早期曾尝试将其应用于整个项目，结果八项编辑生成了 265 个必需节点，因此我们仅将其用于选定的声明。

结论

过去一年里，我们看到信息安全社区一直在应对 AI 工具的快速普及和自动化程度不断提升。显而易见，AI 模型如今能够以分析师团队无法企及的规模对二进制文件进行逆向工程。随着模型产出的分析量不断增长，我们理解其决策如何得出以及这些决策基于何种证据的能力，正面临日益扩大的鸿沟。归根结底，模型的标签、类型和描述是否有用，取决于分析师确认、纠正并在此基础上继续构建的能力。 

数据库以一种报告无法做到的方式实现了这种程度的审查，因为每项结论都可以关联到其所描述的代码。这使人（或另一个模型）能够轻松地继续工作，或将研究发现纳入下游检测和威胁狩猎工作流。 

LLM 为我们提供了自动化更多安全分析的机会，但前提是它们产出的工作成果仍能被理解。 如果扩大分析规模时没有同步提升我们审查分析的能力，就只是用一个瓶颈取代另一个瓶颈。

我们的评估研究表明，仅靠模型无法可靠地生成可验证的数据库。标签会偏离代码的实际行为，发现会滞留在日志中，计划好的工作会消失，分析也会在读取相关代码之前停止。标准和 VerifiedIDA 的做法是将分析判断留给模型，同时让周围的系统负责确保这些判断可被核查。我们对案例研究 #2 的重新运行展示了这种差异：此前六次运行都跳过的辅助函数，成为模型无法搁置未完成的工作。

我们将两者都作为起点发布。这些要求描述了模型驱动工作流应提供的最低能力，而我们的实现仅覆盖一个反汇编器。我们邀请社区使用自己的工具对该规范进行测试，为 Ghidra 和 Binary Ninja 构建适配器，并对经不起实践检验的要求提出异议。在允许共享的情况下，我们也鼓励研究人员随报告发布带有注释的项目，以便其他人能够扩展分析，而不是重复分析。

本文补充了我们在 LABScon 2026 上展示的研究。

案例研究

#1 | 恢复数据结构

恢复数据结构是常规的逆向工程工作。在内存层面，结构是一个基地址，各个字段位于距该基地址固定的偏移处，其中某个字段本身还可能是复杂的数据类型。如果二进制文件不携带调试符号，就不会声明字段偏移、类型和名称，而这些信息必须通过分析来恢复。

两个 ComRAT 函数使用 IDA 默认名称 sub_18002C770 和 sub_18002CDA0，它们接收一个指向数据结构的指针作为参数。IDA 将这些参数类型化为整数。

LLM 将这些参数类型化为指向数据结构的指针，并声明如下。

LLM 分两个阶段进行结构恢复。首先，根据 sub_18002C770、sub_18002CDA0 及其调用函数的伪代码，它观察到对函数参数值（结构基地址）的特定偏移的引用，从而得出该参数是指向结构的指针。随后，它将分析范围扩大到 ComRAT 的其余代码，寻找结构字段在所有位置的引用。对于它识别出的每个字段，它都会分析该字段的使用上下文，以提出标签、类型和大小。 

这使 LLM 能够恢复完整的结构字段集合，并根据这些字段的大小确定结构本身的正确总大小。

LLM 判断字段类型的最有力证据，是该字段被用作某个 Windows API 函数的参数。许多 Windows API 函数都有公开文档，其参数集合相对稳定，因此这些参数的类型极有可能出现在模型的训练数据中。IDA 也可能会在提供给 LLM 的伪代码中公开这些类型，因为它会自动为许多此类函数定义参数类型。因此，模型可以根据权威来源确定字段类型。

例如，LLM 观察到，指向偏移 0x30 处结构字段的指针被作为 CreateProcessW 的第十个参数传入。Microsoft 文档将该参数的类型说明为指向 PROCESS_INFORMATION 结构的指针，IDA 的伪代码也显示了相同类型。LLM 利用这些信息，正确地将该字段类型化为 PROCESS_INFORMATION。

LLM 没有生成其分析无法支持的注释。例如，它在受分析函数中未发现偏移 0x28 处字段的用途，因此没有根据臆造的角色为该字段添加标签。相反，它标记了这一发现，并决定进一步探索 ComRAT 的代码，以确定该字段的角色。它在 ComRAT 的任何位置都未发现该字段的用途，并将其标记为 unresolved_28。我们自己的分析证实，该字段确实从未被使用。

然而，LLM 生成的一些结构字段标签和函数标签并不准确，因为它们没有描述应当描述的内容：字段在代码中发挥的作用，或函数执行的主要操作。例如，LLM 将偏移 0x28 处的字段标记为 unresolved_28，这是以自身的分析状态命名，而不是描述该字段的角色或缺乏角色的状态。该标签还存在歧义，因为它没有区分尚未检查的字段与已经检查并确认未使用的字段。就此字段而言，unused 之类的名称会更合适。

该 LLM 还为函数命名为 sub_18002C770 PrepareSuspendedSurrogateProcess，尽管该函数的主要操作是以挂起状态创建浏览器进程。LLM 的名称完全没有体现进程创建，而 Prepare 暗示的是后续步骤之前进行准备工作，并非该函数的主要操作。LLM 对该函数的自由文本描述（“Create the configured surrogate process before proxy injection”）表明，模型已经识别出其主要操作。该描述以进程创建为主，并将后续的注入作为上下文；而名称 PrepareSuspendedSurrogateProcess 仅保留了上下文，却省略了进程创建。人工逆向工程师更可能采用 CreateSuspendedBrowserProcess 之类的名称，这在任务背景下更具描述性，也更加准确。

除了标签不准确之外，LLM 也没有将其所有发现记录到 IDA 数据库中，偏移量 0x0 处结构体字段的标注便证明了这一点。该字段是一个结构体指针，其中保存与日志写入机制相关的数据，而 LLM 日志显示，模型已将此字段识别为上述用途。

然而，在 IDA 数据库中，LLM 将该字段录入为通用的 void 指针，并将其标注为 owner_context，而不是更贴近其实际用途的名称，例如 LogWriter。LLM 已经确定了该字段的类型和作用，但并未将这些发现转化为 IDA 数据库标注。

#2 | 分析函数的行为

一个 ComRAT 函数在 IDA 中的默认名称为 sub_180077C10，它按名称获取远程进程中所加载 动态链接库（DLL）导出的函数地址。如果该导出被转发到另一个 DLL，该函数会递归解析被转发导出的地址。

LLM 将该函数标注为 ResolveRemoteExportAddress，准确表达了其主要操作。与案例研究 #1 相同，LLM 所依赖的最有力证据是该函数调用的 Windows API。ResolveRemoteExportAddress 还会将数值与公开记录的常量进行比较，这为 LLM 判断该函数的行为提供了进一步的权威依据。

例如，LLM 从 ReadProcessMemory 调用中确定，该函数会读取远程进程的地址空间中的内存。通过与 MZ（0x5A4D）和 PE（0x4550）签名常量的比较，模型判断该函数会查找 Windows PE（Portable Executable）头。由于PE 格式已公开记录且极有可能存在于模型的训练数据中，伪代码中可见的这些标头偏移量使模型能够识别该函数读取了 DLL 的哪些 PE 结构，例如导出目录及其导出函数名称数组。

LLM 的自由文本描述“Resolve an exported function address in a remote module from its PE export directory”准确但不完整，因为它没有涵盖对转发导出的解析。

如果导出被转发到另一个 DLL，sub_180077C10（ResolveRemoteExportAddress）会调用 sub_180081450，后者解析被转发导出的地址。LLM 将其对 sub_180077C10 的理解视为完整，未探索其所有被调用函数，其中包括 sub_180081450。因此，sub_180081450 实现的功能始终未被识别。
