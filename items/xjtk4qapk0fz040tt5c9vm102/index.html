WordPress CVE-2026-119977 已在野利用，安装修复时仍可能再次被攻破

Installing the Fix for an Exploited WordPress Flaw Can Expose Some Sites One Last Time

WordPress CVE-2026-119977 已被确认在野利用，但安装 7.1.4 修复版本时，部分站点仍会因旧版更新器使用可预测的 wp-content/upgrade 目录名而再次暴露安装器。

中文原文

据发现该漏洞的 Picus Security 研究员 Umut Bayram 表示，一些 WordPress 网站在安装正在被积极利用的漏洞修复程序期间，仍可能遭到攻击。

安装修复程序的更新仍会使用网站旧的、未打补丁的代码来解包其文件，因此攻击者若选对时机，便可在服务器上运行代码。该研究员建议，在更新前阻止网站访问 wp-content/upgrade 文件夹。

该漏洞的跟踪编号为 CVE-2026-119977，影响 WordPress 4.7 至 7.1.3。在使用完整软件包进行核心更新时，WordPress 会将新版本的副本解包到 wp-content/upgrade 内的临时文件夹中。该副本包含 WordPress 安装程序，通常可通过 Web 服务器访问。

没有账户的攻击者只要能够确定该文件夹的名称，并在 WordPress 删除该副本之前访问安装程序，就可能最终在服务器上运行代码。美国网络安全和基础设施安全局（CISA）于本周早些时候将该漏洞加入其已知遭利用漏洞目录。

WordPress 上周在 7.1.4 版本中发布了修复程序，同时也为可追溯至 4.7 的较旧分支发布了相应的更新，全部列于其 安全公告中。

修复程序会为临时文件夹指定随机名称。但正如 WordPress 的更新程序代码所示，安装该修复程序的更新仍会使用网站上已有的旧代码来解包其文件。在运行 5.9 或更高版本的网站上，该旧代码会根据下载文件的名称为文件夹命名，因此最后一次仍有可能预测出该名称。

在修复之前，攻击者可以利用安装程序在临时副本中写入新的配置文件 wp-config.php。随后，更新会用该文件覆盖网站真正的配置文件。修复程序中阻止此操作的部分，在安装修复程序的那次更新期间就已生效，因为 WordPress 会使用新代码将文件复制到位。

Bayram 在其技术报告中表示，攻击者若能抓住该次更新期间的时机，仍可使用自己的数据库配置临时副本中的 WordPress、登录该副本，并在副本被删除之前以 Web 服务器的权限运行 PHP 代码。此后，攻击者便能读取或写入在线 WordPress 网站中的文件。

更新期间谁会受到暴露

该研究员表示，并非每次更新都会暴露安装程序。完整软件包始终包含安装程序文件。专为某一个特定起始版本构建的小型部分软件包，只有在恰好包含这些安装程序文件时才会暴露网站。

在允许自动后台更新的网站上，WordPress 会通过同一个更新程序并按照相同的步骤自动安装修复程序。

The Hacker News 今日检查了 WordPress.org 的更新服务，涉及多个版本。对于同一分支内的更新，例如从 7.1.3 更新至 7.1.4，该服务会提供部分软件包，自动更新也不例外。对于从较旧分支升级，例如从 7.0.7 更新至 7.1.4，则只会提供完整软件包。

在 4.4 至 5.8 版本中，旧代码会在文件夹名称中添加随机字符。除非网站通过其他方式泄露该名称，例如出现在错误消息中，否则该名称会被隐藏，该研究员表示。

安装 7.1.4 或相应分支修复程序后，后续更新将使用随机文件夹名称，且临时副本中的 wp-config.php 文件绝不会被复制到真实文件上。

更新前应采取的措施

研究人员的第一项建议是彻底阻止 Web 服务器提供 wp-content/upgrade 目录。他说，WordPress 直接在磁盘上使用该文件夹，因此阻止 Web 访问不会影响更新。

  1. 在 Web 服务器配置中屏蔽该文件夹。在 Nginx 上，添加 location ^~ /wp-content/upgrade/ { deny all; }。在 Apache 上，在虚拟主机配置中针对该文件夹的 <Directory> 块内添加 Require all denied 。
  2. 如果你只能编辑 .htaccess，请在 WordPress 根目录的 .htaccess 文件中、位于 WordPress 重写规则之上，添加 RedirectMatch 403 ^/wp-content/upgrade/ 。
  3. 不要在 wp-content/upgrade 目录本身内放置 .htaccess 文件。旧的更新程序会在解压更新之前删除该文件夹中的所有内容，因此需要该文件时它已经不存在了。
  4. 确认对 /wp-content/upgrade/ 的请求返回 403 错误。
  5. 更新到 7.1.4 或你所在分支的修复版本。

他说，另一条安全的途径是在 Web 根目录（即 Web 服务器提供的文件夹）之外手动更新。备份站点文件和数据库，将新版本解压到 Web 服务器不提供的文件夹中，把核心文件复制到相应位置，同时不要改动 wp-config.php 或 wp-content，然后运行 WordPress 数据库更新。这样一来，Web 可访问的文件夹中就绝不会生成临时安装程序。

WP-CLI 的 wp core update 命令不能替代这一做法，因为它运行的是同一个更新程序，并将软件包解压到同一个文件夹中。

WordPress 4.6 及更早版本不再接收安全更新，因此没有针对它们的修复。研究人员称，该缺陷可追溯到 2008 年发布的 WordPress 2.7，这些站点应迁移到受支持的版本。

攻击及检查事项

CISA 本周早些时候新增该条目时，依据的是存在主动利用活动的证据，但该机构没有描述这些攻击。

分配该 CVE 标识符的 WordPress 安全公司 Wordfence 称，在发布当天部署针对该缺陷的防火墙规则后九分钟，就发现了 攻击尝试。两个最为活跃的攻击来源持续对小型网站群进行检查约 14.5 小时；该公司在其 攻击分析中表示，这与试图捕捉网站更新时机的尝试相符。

它在该漏洞的 CVE 记录中给出的评分为 CVSS 量表上的 10 分制 8.1 分。在其实验室测试中，该时间窗口仅持续数秒。WordPress 自己的公告将该缺陷评为低危。

自本周早些时候以来，其作者称为该漏洞利用程序的代码已出现在公开的 GitHub 仓库中。其中一个称，其代码也可在完整软件包更新期间仍使用可预测文件夹的网站上运行。该代码是否有效尚未得到确认。

对于发布后仍留在受影响版本上的网站，Wordfence 建议检查：

  • 对 wp-content/upgrade 下 PHP 文件的异常请求
  • 无人认识的管理员账户
  • 无人安装的插件
  • 位于 wp-content/upgrade 中且并非由任何人放入的 PHP 文件

更新

Bayram 于 11 月 6 日告诉 The Hacker News，部分更新是否会暴露取决于该特定软件包包含哪些内容。部分软件包只包含两个版本之间发生变化的文件。如果其中不包含安装程序文件，那么临时副本就无法作为 WordPress 安装运行，安装程序也就永远不会被访问到。

当存在部分更新包时，网站也不一定会获得部分更新包。如果网站的核心文件与官方校验和不匹配，或者此次更新属于重新安装，WordPress 会回退到完整更新包。

研究人员表示，决定性因素“并不是部分更新还是完整更新，而是该网站已经安装的更新程序是否已被修复。”
