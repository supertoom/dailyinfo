正文 · AI 翻译
中文原文

在某些运行标准 openssh-server 包的 Alpine Linux 服务器上，攻击者可以登录没有密码的账户，例如仅使用 SSH 密钥的账户。他们需要具备对服务器的网络访问权限、知道账户名称，并提供长度在 257 到 1,024 字节之间的密码。

将该漏洞评为严重级别的 OpenSSH 今天发布了 10.6p2 版本以阻止该问题。Alpine 已为从 3.16 起的每个版本发布修复后的软件包。

当 OpenSSH 服务器（sshd）在不使用可插拔认证模块（PAM）接口的情况下检查密码、启用了密码登录，并且机器上至少还有一个其他账户设有密码时，该攻击就会奏效。Alpine 的 openssh-server 包构建时不带 PAM，并且默认启用密码登录。

该漏洞源于 sshd 与 musl（Alpine 所基于的 C 库）协作的方式。OpenSSH 项目的 Damien Miller 表示，非 Linux 系统、基于 glibc 构建的 Linux 系统，以及通过 PAM 检查密码的系统均不受影响。

他建议任何运行受影响系统的人“立即为这些系统设置 PasswordAuthentication=no 或禁用 SSH。”目前尚未报告使用该漏洞实施的攻击。

谁会受到影响

Alpine 的安全公告列出了四项条件。当以下四项条件全部成立时，服务器即暴露于风险之中：

  • 运行 openssh-server 包（该包构建时不带 PAM），或者运行 openssh-server-pam 并附带 UsePAM no。
  • PasswordAuthentication 是 yes，这也是 OpenSSH 的默认设置。
  • 某个账户的密码字段为 *，这意味着未设置密码。
  • 至少还有一个其他本地账户的密码哈希以 $5$ 或 $6$ 开头。

攻击者还需要知道某个未设置密码的账户名称。只要有一个设有密码的账户，就足以暴露每一个未设置密码的账户。根据该公告，攻击者只需单次连接，每次尝试都能成功。

在 Alpine 上，未设置密码的账户包括：

  • 使用 adduser 创建且未设置密码的仅限密钥用户，或者使用 usermod -p '*' 创建的用户
  • 通过 musl-nscd 来自目录服务的用户，因为他们没有 shadow 条目
  • root，自大约 Alpine 3.16 起一直作为 root:* 随基础镜像发布
  • 使用 tiny-cloud 构建的官方云镜像中的 alpine 用户

root 受默认的 PermitRootLogin prohibit-password 设置保护，只有将 PermitRootLogin yes 设置为特定值后才能直接访问。如果暴露风险的账户能够成为 root，例如通过 doas，那么这种保护就无济于事。

从 3.18.11 到 3.24.3 的 tiny-cloud 镜像为 alpine 用户提供了免密码的 doas。它们在首次启动时是安全的，但一旦机器上存在任何 $6$ 哈希，例如管理员设置控制台密码后，就会暴露于攻击之下。届时攻击者可以 alpine 登录，并使用 doas 成为 root。

未运行 sshd 的容器、带有 PasswordAuthentication no 的系统，以及通过 cloud-init 设置的云镜像均不受影响，因为 cloud-init 会写入该设置。在 /etc/shadow 中通过 ! 锁定的账户也不受影响，任何账户都不具有 $ 样式密码哈希的机器同样不受影响。

该漏洞并不仅限于 Alpine。报告该漏洞的 Wakefield 公司的 Özgün Kültekin 在他的技术说明中列出了 OpenWrt、Buildroot 和 Yocto 等其他基于 musl、值得检查的系统。

正如其Dropbear 文档所示，OpenWrt 默认使用 Dropbear 处理 SSH，Kültekin 表示 Dropbear 不受影响。在 OpenWrt 上，只有管理员安装了 OpenSSH 服务器的情况下，该漏洞才可能产生影响。

如何修复

在 Alpine 上，修复方式是更新软件包后重启，因为升级软件包不会重启正在运行的 sshd：

  1. 更新软件包：apk upgrade -U -a
  2. 重启服务器：rc-service sshd restart

Point 版本 3.21.10、3.22.8、3.23.8 和 3.24.4 已包含修复后的软件包。3.16 到 3.21 分支虽然已停止支持，但也获得了修复后的软件包。

从早于上述 Point 版本的 tiny-cloud 镜像启动的云实例仍需更新，或应用下面的设置。

如果你自行构建 OpenSSH，10.6p2 版本已包含此更改，正如其发布说明所描述的。

如果目前还无法更新，关闭密码登录也能阻止此次攻击。首先确保你的 SSH 密钥登录可用，并在新一次登录成功之前保持当前会话开启。然后设置 PasswordAuthentication no，使用 sshd -t 检查配置，并重启 sshd。

公告提供了相关命令，会在一个 drop-in 文件中添加该设置，文件位于 /etc/ssh/sshd_config.d；从 3.19 开始，Alpine 的默认配置会从该位置读取。命令还会将 /etc/ssh/sshd_config 中的每一行 PasswordAuthentication 从 yes 更改为 no，包括 Match 块内的行。之后，sshd -T | grep -i passwordauthentication 应输出 passwordauthentication no。

公告建议在 /var/log/messages 中查找内容为 Accepted password for 的 sshd 配置行，即没有密码的账户，例如 alpine、root 或仅使用密钥的用户。在暴露于网络的机器上，还应检查 doas 的使用情况、近期创建的用户、文件以及授权密钥。

“如果无法排除有人登录的可能性，就应将这台机器视为已被攻陷，”公告称。

长密码为何有效

未使用 PAM 时，sshd 会自行检查密码。它使用 crypt() 对尝试登录的密码进行哈希处理；这是 C 标准库中的一个函数，用于将密码转换为存储形式，然后将结果与存储字段进行比较。

没有密码的账户在该字段中只有 *。这个值太短，无法容纳盐值（哈希值的随机前缀），因此 sshd 会借用另一个拥有真实哈希值的账户的盐值。

对于 $5$ 和 $6$ 哈希类型，musl 的 crypt() 会拒绝长度超过 256 字节的密码，并返回 * 以表示错误。该 * 与存储的 * 相匹配，因此 sshd 会接受登录。该范围的上限是 sshd 自身对每个密码 1,024 字节的限制。

这一行为源自 musl 在 2012 年 8 月 9 日进行的一项更改：失败的 crypt() 调用将返回“无法匹配的哈希值，而不是 NULL”，因为许多程序不会检查调用失败。随后在 2012 年 8 月 29 日加入了 256 字节限制，以保护服务器免受拒绝服务攻击。

借用盐值的机制来自 2016 年 7 月 15 日的一项OpenSSH 更改，用于修复 CVE-2016-6210。该漏洞会让攻击者得知哪些用户名存在。Kültekin 表示，此问题自那时起就一直存在。

10.6p2 的代码更改让 sshd 在存储字段少于四个字符时拒绝匹配。OpenSSH 称这是一种变通方案，并表示根本原因位于 sshd 之外。Alpine 的稳定软件包也包含针对同一问题的补丁。

修复为何在第二天发布

Miller 的团队于本周早些时候得知该漏洞，并尽快发布了修复。在发布公告中，他表示团队现在认为，长时间保密既危险，又主要对攻击者有利，因为团队最近发现 AI 代理会在数小时内再次找到相同的漏洞，有时甚至更快。

截至今天，该漏洞尚未分配 CVE 标识符。
