990 个自定义脚本、两项 Zammad 漏洞，再加上针对数据库通信的数据包注入，构成了这起事件的主要技术轮廓。真正值得复盘的，是攻击者如何借助 Agentic 工具，把一台互联网工单服务器变成集执行、持久化、数据搜集和外传于一体的操作中枢。

2026 年 11 月 24 日，Merlon Security 发布 DIVD 内部网络入侵事件的最终取证报告。DIVD 是荷兰漏洞披露机构，日常工作包括扫描互联网上的脆弱系统、通知资产所有者，以及协调漏洞披露。入侵者最终攻破的 Zammad 系统，承担其 CSIRT 工单通信。

攻击发生在 2026 年 9 月 21 日至 22 日。Merlon Security 与 DIVD 成员共同开展主机和网络取证，NVISO 负责 Google Workspace 等部分的调查。将这些调查结果拼合起来，可以还原出以下核心链路：

WebSocket 会话信息泄露 → 劫持 Zammad 管理员会话 → 恶意邮件模板触发 RCE → 本地提权至 root → 建立多层持久化 → ARP 欺骗与 PostgreSQL 数据包注入 → 获取 Confluence、Jira 管理访问 → 批量搜集并外传数据。

01 没有钓鱼邮件，突破始于一段泄露的会话

攻击者最早于 9 月 21 日 07:40:38 探测 DIVD 外部边界，来源地址为 98[.]98[.]124[.]175。当天傍晚，攻击者借助两个当时尚未公开修复的 Zammad 漏洞完成突破：CVE-2026-102489 与 CVE-2026-102490。

1. 从 WebSocket 错误信息中拿到管理员 Cookie

CVE-2026-102489涉及 Zammad 的 WebSocket 端点。攻击者触发端点异常后，错误信息会泄露其他在线用户请求上下文中的 HTTP 头，会话 Cookie 也包含其中。

Horizon3.ai 后续公布的根因分析揭示了异常如何发生：向 WebSocket 事件分发逻辑提交特定事件名，会错误调用 Sessions::Event::Base。随之而来的 NoMethodError将包含 @clients的对象状态返回给调用方，在线客户端的请求信息和 Cookie 正好保存在这里。成功利用还有一个前提：当时必须有已认证用户保持 WebSocket 连接。

DIVD 事件中的时间线，清楚展示了这一条件如何被利用：

  • 18:53:50，一名具有 Zammad 管理权限的 DIVD 成员登录系统；
  • 约 1.3 秒后，攻击者通过信息泄露获得该用户的会话 Cookie；
  • 19:01:00，攻击者开始复用该 Cookie，以管理员身份操作系统。

整个过程中，攻击者没有破解密码，也没有攻击 MFA 机制本身；被窃取并重放使用的，是用户完成认证后的会话。

2. 包管理写入文件，邮件模板完成执行

接管应用管理员会话后，攻击者利用 Zammad 的包管理功能向服务器写入文件。19:06:31，一次指向 /api/v1/packages的 POST 请求后，服务器出现用于验证写入能力的文件：

/opt/zammad/public/zzproof12517_13b45db9.txt

19:27:53，攻击者进一步写入恶意 Ruby 邮件模板：

/opt/zammad/app/views/mailer/admin_password_auth/nl.html.erb.custom

5 秒后，攻击者通过 POST /api/v1/users/触发相关邮件流程，服务器渲染该 .erb.custom模板，最终以低权限的 zammad操作系统用户实现远程代码执行。至此，攻击者获得 DIVD 内网立足点。

这里需要把功能与利用链分开看：Zammad 自定义包写文件本身属于既有功能，攻击者则将会话窃取、管理员包写入和邮件模板渲染组合起来，形成完整的代码执行链。

3. 第二项漏洞把 zammad 用户提升为 root

随后使用的 CVE-2026-102490，是针对 Zammad Debian/RPM 软件包部署方式的本地提权问题。Merlon Security 将成功利用所需条件概括为以下三项：

  1. /etc/zammad 目录错误地归 zammad 用户所有，低权限进程可以写入其中；
  2. Zammad 服务启动流程先以 root 身份加载 /etc/zammad/conf.d/ 中的配置，再降权运行；
  3. zammad 进程能够终止自身 Web Worker，从而触发 systemd 重新启动服务。

攻击者先上传 payload 和 stager，再终止 Zammad Web Worker。服务重启时，写入配置目录的脚本被 root 执行，随后将 /bin/bash复制到以下路径并设置 setuid 位：

/var/tmp/i95/i95rootsh

这个 setuid Shell 将一次性的提权成果固化下来，攻击者此后可随时调用 root 执行能力。时间线上，19:27:58 首次 RCE，约 19:46 已完成 root 提权，间隔约 19 分钟。

02 一台工单服务器，如何变成攻击操作中枢

一个反向 Shell 远不足以支撑后续行动。失陷主机无法直接任意外联，攻击者于是将 Zammad 自身的 API、公开 Web 目录和 DIVD 代理链路组合起来，承担任务下发、结果读取与数据外传。

其中，GET /api/v1/text_modules被用于命令与控制；脚本和输出文件被放进 /opt/zammad/public/，再由攻击者通过 HTTP 请求读取。从网络侧看，大量恶意流量因此呈现为对既有 Web 应用的访问，没有表现出失陷服务器突然连接陌生 C2 地址的典型特征。

为了保住入口，持久化被布置在应用、认证和操作系统等多个层面：

  • 应用账户与令牌：创建带有 artex-i13033标识的管理 API 令牌，并创建、赋权 artex.ops@divd.nl管理账户；
  • 认证逻辑后门：修改 /opt/zammad/config/initializers/omniauth.rb，将 Google OAuth 的 access_type从 online改为 offline，并增加 https://mail.google.com/权限范围；
  • 系统服务与计划任务：安装 /etc/systemd/system/zzr.service，并创建 /etc/cron.d/zz9cron、/etc/cron.d/zz17cron；
  • root 命令循环：循环扫描 Web 目录中的任务文件，再通过 setuid Shell 以 root 身份执行，把结果写回公开目录。

OmniAuth 后门的运作思路是：后续登录用户授权时生成可离线访问 Gmail 的 OAuth 令牌，轮询脚本再从 Zammad 的 authorizations表中读取。这一设计有一个必要条件：后续用户必须登录并同意扩权。实际取证显示，后门运行期间没有捕获到新的用户令牌，也没有通过它成功侵入个人 Google Workspace 账户。

03 横向突破的关键，藏在数据库通信里

两项 Zammad 漏洞只解释了最初的立足点。后续 Jira 和 Confluence 的失陷走的是另一条链路，若归结为“同一组漏洞被再次利用”，就会误读整个横向移动过程。

1. 从被动监听到 ARP 缓存投毒

9 月 21 日 21:19:53，攻击者开始在失陷的 Zammad 主机上进行被动数据包嗅探。9 月 22 日 01:37:48，攻击者使用自行编写的 Python 脚本发起 ARP 欺骗，污染网关与 Jira、Confluence 主机的 ARP 缓存，从而获得中间人位置。

02:27:43，Confluence 服务器请求网关 MAC 地址时，攻击者脚本返回了伪造应答，成功进入 Confluence 与后端 PostgreSQL 数据库之间的通信路径。

图 4｜重构网络流量中的 ARP 欺骗与重复地址告警

图源：Merlon Security《Project Fazant》，PDF 第 51 页（报告页码 49）图 2；直接提取报告内嵌原图。

Merlon Security 重建的部分流量显示，Confluence 与 PostgreSQL 之间未启用 SSL/TLS。攻击者因此能够观察 SQL 请求和响应，也获得了向现有 TCP 会话注入数据包的机会。

图 5｜Confluence 与 PostgreSQL 之间的明文通信抓包

2. SQL 通过 PostgreSQL 会话注入，与 Web SQL 注入无关

进入中间人位置后的约六小时里，攻击者持续下载并分析数据库通信，同时开始尝试向现有会话注入简单查询，确认当前数据库用户、数据库名和版本。03:34:25，首次成功注入出现。

08:46:35，攻击者把一条构造好的 SQL 语句注入 Confluence 数据库通信，向 remembermetoken表写入自定义 remember-me 令牌。该令牌对应三个处于管理员组中的有效账户，攻击者随后使用它访问 Confluence。

08:49:00，一次 GET /dashboard.action请求获得成功响应，并返回 X-Seraph-LoginReason: OK，证明伪造会话已被应用接受。攻击者由此获得 Confluence 管理访问，并开始批量下载页面和附件。

图 6｜伪造 remember-me 令牌被 Confluence 接受

图源：Merlon Security《Project Fazant》。

准确地说，攻击者先通过 ARP 欺骗取得中间人位置，再对 PostgreSQL 明文通信实施 TCP 数据包注入，最终修改数据库记录。Confluence Web 应用并未被利用为 SQL 注入入口。

3. Jira 也以同样方式失陷，但攻击止于应用层

攻击者也对 Jira 与共享 PostgreSQL 数据库之间的链路实施了类似中间人攻击。10:43:43，首次观察到针对 Jira 数据库流量的成功 SQL 注入。

14:04:10，第一次 remember-me 令牌重放因 Jira 清理旧令牌而失败。攻击者重新读取令牌数据，14:08:58 再次尝试并成功进入 Jira，继而批量抓取信息，还尝试生成和获取支持 ZIP 包，以继续搜集配置和敏感数据。

Zammad 与两台 Atlassian 服务器的失陷程度并不相同：

  • divd-p-zammad104：主机完全失陷，攻击者获得 root；
  • Jira、Confluence：攻击者获得 Web 应用管理访问，但未获得底层操作系统访问；
  • DIVD 另一套 Zammad Helpdesk：未发现失陷；
  • GitLab、VMware vSphere、Proxmox 等目标遭到探测，但未发现进一步成功横向移动。

网络分段确实限制了影响范围，但迁移遗留的一条防火墙规则仍允许 Zammad 服务器访问内部代理，攻击者由此保留了探测其他系统的通道。

04 搜集凭据、扩展目标、打包数据

root 权限和应用管理访问到手后，高强度搜集随即开始，行动主要围绕“凭据搜集—目标扩展—数据打包”展开。

在 Zammad 中，攻击者同时通过 API、PostgreSQL 命令行和本地 Elasticsearch 接口搜索数据，关键词包括：

DEPLOY_KEY

PRIVATE KEY

其中 wachtwoord是荷兰语“密码”。搜索范围从工单正文延伸到用户表、认证记录、邮件通道配置、外部凭据表及附件内容。攻击者由此获得或接触了数据库口令、Google OAuth/XOAUTH2 令牌、BIT IMAP 明文口令、Jira/Confluence 会话和重置令牌，以及部分私钥与应用密钥。

攻击者用一组脚本下载 Confluence 的全部页面和 208 个附件，并反复执行敏感信息匹配。对 Jira 的数据搜集则结合批量抓取、支持包生成与本地二次扫描展开。

已有证据确认两类数据被外传：

  • 2806 个文件经 DIVD 代理链路被攻击者请求并传出；
  • 约 4.1 万个 Zammad CSIRT 工单标题经 Zammad API 被批量获取。

Merlon Security 对外传文件中的个人信息进行了清洗和人工复核，结果如下：

云端与 CNA 数据：实际触及范围

  • Google Workspace：未发现攻击者进入个人用户账户或更广泛 Workspace 环境。csirt@divd.nl 与 report-abuse@divd.nl两个共享邮箱的 OAuth 令牌被窃取，并被用于发送测试邮件；NVISO 未观察到邮箱数据本身被攻破。
  • BIT 邮箱：BIT IMAP 账户的明文口令被窃取并成功登录，攻击者检索了 abuse、csirt 邮箱内容；未发现 BIT Web 门户被成功登录。
  • Slack：一个 bot API 密钥泄露，但该密钥只有发送消息权限，没有读取消息权限。由于缺少可用 Slack 日志，Merlon Security 无法用日志完全验证其未被滥用。
  • CNA 数据：NVISO 未发现 Google Workspace 中的 CNA 数据被访问。Merlon Security 另确认两个从 Zammad 外传的文件包含较早的 CNA 相关邮件链，所涉内容均已超过 90 天披露期限。
  • 内部项目资料：外传的 Confluence 数据包括 3 个 TLP:RED 页面或附件，以及 33 个 TLP:AMBER/TLP:AMBER+STRICT 页面或附件。

从搜索行为看，Merlon Security 未发现针对特定个人的定向搜集。除系统管理员等特权账户外，攻击者主要寻找密码、密钥以及后续横向移动所需的信息。

05 Agentic 框架的判断依据

攻击速度固然醒目，Merlon Security 的判断依据却落在更具体的四类痕迹上。

1. 产出规模与人工操作不匹配

攻击期间，按不含子目录的统计口径，调查人员从 /tmp 与 /opt/zammad/public/中恢复了 990 个自定义 Python、Ruby 和 Bash 脚本，并发现 3259 个输出文件和228 个输出目录。这些脚本往往围绕单一任务被快速生成、执行和修改，随后再派生出下一批脚本。

2. 脚本注释记录了任务意图和决策过程

许多脚本用完整注释说明当前动作、目标和执行条件。例如，有脚本专门安排 MITM 任务在荷兰工作时段运行，也有注释声称某个测试“无害”。对取证人员而言，这些文本在提高可读性的同时，也保留了攻击者的任务上下文。

3. 文件命名与 ARTEX 的任务编号机制吻合

以 i加数字开头的文件大量出现，例如 i13245mitm.py。Merlon Security 对 ARTEX 框架副本进行分析后认为，这类编号与其用于区分任务的 intents机制一致：任务编号同时进入输入和输出文件名，框架由此可以追踪每项作业。

4. 现场直接出现了 ARTEX 标识

现场痕迹中还包括 artex-i13033 和 artex.ops@divd.nl，两者分别对应攻击者创建的管理 API 令牌标识与 Zammad 管理账户。结合任务编号和框架行为，Merlon Security 判断攻击者很可能使用了开源 Agentic 渗透测试框架 ARTEX。

另一条公开调查线也出现了 ARTEX。CrowdStrike 在针对韩国金融机构的攻击调查中发现 ARTEX 配置、Claude Code 会话历史和模型记忆文件，相关活动集中在 2026 年 9 月底至 10 月初。Merlon Security 则记录，ARTEX 的 GitHub 仓库在本次调查期间因涉及韩国金融机构入侵而被下架。不过，工具相同并不足以将两起事件归为同一操作者；公开材料同样没有指明 DIVD 事件背后的具体个人或组织。

NVISO 加入调查

比起讨论“AI 攻击有多快”，这条时间线提出了更现实的问题：高保真告警生成之后，谁有权、也有能力立即执行隔离？

告警若只进入队列，缺少明确的升级条件和预授权处置动作，攻击者的自动化速度与防守方的人工接力之间就会拉开时间差。事件仍在进行时，DIVD 完成了磁盘和内存快照，这些证据后来帮助调查人员恢复 990 个脚本，并重建 ARP 与数据包注入过程。

07 防守方可以立即着手的五件事

1. 升级 Zammad，并按已失陷标准回溯排查

DIVD 当前事件页确认，CVE-2026-102489的相关代码修改已进入 Zammad 7.2.0，CVE-2026-102490已在 7.2.2 修复。自建实例应升级至 7.2.2 或更高版本；无法及时升级时，应限制访问或暂时下线。

2026 年 10 月 2 日，CISA 已将两项漏洞加入 KEV 目录。对于曾运行受影响版本的实例，升级不能替代事件排查：还应使既有会话失效，轮换主机存储或能够访问的邮箱、数据库、OAuth、API、SSH 等凭据，并检查异常账户、模板、服务与计划任务。

2. 内部数据库通信也要加密和验证对端

Confluence 与 PostgreSQL 之间的明文通信，是攻击者得以利用这条横向链路的重要条件。传输加密不应在内部网络缺席。数据库连接至少应启用 TLS 1.2，并正确验证证书；具备条件时采用 mTLS，避免攻击者在取得中间人位置后直接读取或修改 SQL 流量。

3. 从“大 VLAN”走向按业务流划分的微分段

应复核工单系统是否确实需要访问 Jira、Confluence、数据库、域控和内部代理。采用默认拒绝的微分段策略，只开放必要端口与方向，并清理迁移后遗留的防火墙规则。对同网段主机，还可结合私有 VLAN、客户端隔离和 ARP 防护，降低单点失陷后直接发动二层攻击的机会。

4. 把检测重点放在高危行为上

检测无需先证明背后存在 AI Agent，以下行为本身就值得高优先级告警：

  • Zammad/Rails/Puma 进程派生 Shell、Python 或异常子进程；
  • zammad 用户向 /etc/zammad/conf.d/、systemd、cron 或应用模板目录写入文件；
  • 应用进程树中出现 UID 0 进程，或出现新的 setuid Shell；
  • 同一会话 Cookie 在短时间内从新的来源地址使用；
  • 对工单 API、PostgreSQL、Elasticsearch 的批量搜索与导出；
  • ARP 应答异常、网关 MAC 地址突变，以及应用服务器之间出现非预期转发；
  • 大量结果文件突然出现在 Web 公开目录，并随即被外部 GET 请求读取；
  • OAuth scope、离线访问配置或认证初始化文件被非预期修改。

5. 让响应与取证跟上机器速度

针对高置信度告警，事先定义主机隔离、会话吊销和密钥禁用动作，并定期演练。取证侧应提前准备磁盘与内存采集能力，保留 /var/log/zammad、/var/log/nginx、代理日志和数据库日志；响应过程中，避免继续依赖尚未排除失陷的协作平台传递敏感信息。

08 结语

DIVD 事件中的“AI”并没有掩盖攻击链的技术本质。会话劫持、模板执行、本地提权、持久化、ARP 欺骗、数据包注入、凭据搜集和数据外传，仍然是能够逐项观察和重建的传统技术。

Agentic 框架改变的是执行方式：这些动作被高速拆解、生成和并行执行。攻击最终仍要落到进程、文件、账户、网络连接和数据库操作上。防守重点也应落在这些具体行为上——更早发现它们，阻止单台互联网应用的失陷继续演变为身份、数据和内网链路的连续失守。
