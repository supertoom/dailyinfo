Microsoft 披露攻击者利用 ARTEX 批量搜寻 GitHub 密钥并入侵 Azure

Threat actors use agentic AI tooling to find and abuse exposed secrets

AI 导读

Microsoft 观察到攻击者使用 ARTEX 等 Agentic AI 框架批量查询 GitHub 公开仓库，寻找应用凭据、AI 推理 API 密钥等敏感信息，并自动分析结果发动后续攻击。

值得关注

文章展示了 AI Agent 从 GitHub 密钥扫描到云端数据外泄的完整链路，并给出可迁移的检测与凭据轮换方法。

Microsoft Threat Intelligence 发现，威胁行为者正在使用智能体 AI 攻击框架搜索公开 GitHub 仓库中的暴露密钥，包括多个应用程序和云服务中的凭据、应用程序凭据以及与 AI 推理相关的 API 密钥。随后，威胁行为者可以利用这些密钥针对已失陷的组织发起进一步恶意活动。

搜索开放代码仓库中的暴露凭据、密钥及其他认证材料是一项已有充分记录的技术。长期以来，这项技术受限于人工操作员查找代码仓库、审查仓库数据以及利用认证材料采取进一步行动所需的时间。然而，ARTEX 等智能体工具使威胁行为者不仅能够更快地扫描多个仓库中的密钥，还能利用智能体分析输出并发动后续攻击，从而减少威胁行为者在整个攻击链中进行手动键盘操作的需要。在至少一个案例中，Microsoft 观察到 AI 智能体从扫描 GitHub 中的密钥到从 Azure Key Vault 窃取数据仅用了五分钟。

Microsoft 还调查了涉及有效应用程序凭据误用的后续活动。早在 2026 年 10 月 28 日，Microsoft 就开始观察到来自 IP 地址 199.19.77[.]84 的成功服务主体登录，涉及部分受影响客户的多个应用程序 ID，其中包括多租户应用程序凭据在源头（供应商拥有的应用程序）被盗用，并被用于访问多个下游租户的案例。威胁行为者使用被盗凭据进行云资源发现以及凭据和数据窃取，其中包括从 Azure Key Vault 和 Storage Accounts 窃取数据，以及滥用 Azure AI 服务，这与上述活动一致。此外，Microsoft 还观察到来自两个可能与此次活动有关的 IP 地址的恶意活动。我们发现了来自 65.87.223[.]26 的恶意操作，包括有迹象表明攻击者通过嵌入在 User-Agent 中的 shell 命令利用漏洞，并尝试获取 App Service 身份验证令牌。Todyl 也报告了一场涉及相同 IP 地址的类似活动。另外，Microsoft 还观察到来自 157.22.126[.]128 的侦察活动，目标是在 Azure AI 服务上部署 AI 工作负载的受害者。

Microsoft 鼓励组织扫描其 GitHub 中的代码，并确定其中是否存在任何机密。除了从代码库中移除机密之外，受影响的组织还应立即轮换任何已暴露的密钥或凭据。GitHub 通过自动扫描机密来监控公共仓库。除了扫描自己的仓库外，组织还可以通过 GitHub 启用公共监控，检测整个 GitHub 平台上的次级公共仓库中泄露的机密。这将机密扫描扩展到企业拥有的仓库之外，以跟踪整个平台上的潜在机密暴露。GitHub Advanced Security for Azure DevOps 会扫描源代码中的凭据和其他敏感内容。推送保护还可以在受支持的机密被推送前将其阻止。组织需要启用 GitHub Advanced Security for Azure DevOps；对于使用独立体验的组织，则需要启用 GitHub Secret Protection for Azure DevOps。

当包含机密的代码被提交到 GitHub 时，机密就会暴露在公共仓库中。开发者可能会将机密存储在配置文件、脚本或其他代码中，以便快速启用 OAuth 应用，或避免配置更现代的身份验证流程。组织可以通过保护工作负载身份和机密、强制执行最小权限、保护恢复资源以及启用相关的 Microsoft Defender for Cloud 防护措施来减少暴露风险。公开暴露的凭据在撤销或轮换之前仍可使用；仅移除最初的披露内容无法消除暴露风险。Microsoft 建议开发者将 OAuth 应用迁移 away from secret-based authentication。虽然在代码中存储长期有效的应用客户端密钥是一种常见做法，但使用托管身份进行应用身份验证可以消除代码中机密暴露的可能性、与机密管理相关的手动流程，以及安全扩展应用时面临的障碍。

这一活动 illustrates an ongoing trend of threat actors accelerating all stages of the attack chain with agentic AI penetration testing frameworks, including ARTEX. As these capabilities evolve, defenders must similarly use AI to investigate and respond across large environments.

从暴露的机密到云端入侵

自 2026 年 8 月起，Microsoft 观察到威胁行为者使用智能体 AI 攻击框架向 GitHub 提交大量查询以寻找机密。该 AI 框架提交的查询通常包含目标组织的名称、机密相关关键词、与云服务关联的关键词，或与其他 AI 服务提供商关联的关键词。发现机密暴露在公共仓库中的组织必须假定，这些已暴露的机密及相关应用均已遭到入侵。

后续操作

通过 Entra ID 滥用凭据

在一次后续攻击中，攻击活动最早可追溯至 2026 年 10 月 28 日，一个智能体框架使用有效但泄露或被盗的应用凭据，访问了某些组织的 Microsoft Entra ID 租户，以及已连接的 Azure 和 Microsoft 365 资源。登录主要来自两个 IP 地址：199.19.77[.]84 和 199.19.77[.]18。后一个 IP 地址是 Tor 出口节点，可能与包括无关来源在内的无关恶意活动有关。该智能体成功对多个租户中数十个关联应用执行了服务主体登录。服务主体是应用用于进行身份验证的身份，并授予对应用获授权访问的任何资源的直接程序化访问权限。

威胁行为者 targeting 了会返回凭据的操作，包括存储帐户密钥、App Service 设置、连接字符串和发布凭据、AI 和机器学习 (ML) 连接及数据存储，以及 Azure Kubernetes Service (AKS) 用户凭据。受损应用随后访问了目标组织租户中的 SharePoint 和 OneDrive，包括下载文件和访问邮箱项目。在某些租户中，威胁行为者发送了 Microsoft Graph API 请求，其中大多数是用于查找感兴趣内容的搜索。威胁行为者枚举了 Azure 中的订阅、资源组、权限、AI 模型部署和服务配置，以绘制环境架构。

此外，威胁行为者尝试验证被盗的 Azure 资源，包括通过 Defender for Cloud 的 AI 威胁防护识别出的受损 Azure AI 服务。观察到的活动表明，威胁行为者可能尝试滥用其中一些受损的 AI 资源，以协助其更广泛的攻击活动。

表明存在自适应行为的云 API 调整

此外，在此攻击中，该智能体从 199.19.77[.]84 发往受害者 Azure Resource Manager (ARM) 实例的操作表现出与自适应故障排除一致的一系列行为：失败的云 API 请求之后，会更改 HTTP 方法或 API 版本，随后收到 HTTP 200 响应：

  • 一批尝试枚举多个 Azure Key Vault 资源中机密元数据的 ARM 请求返回了 HTTP 400（错误请求）。这些请求针对 ARM（控制平面）API 指定了与 Key Vault 数据平面 API 关联的版本。首次失败响应约 28 秒后，一批请求使用 ARM API 版本 2023-07-01 针对相同的保管库资源路径重新运行，并返回 HTTP 200。
  • 一个用于枚举 Azure SQL 服务器防火墙规则的 GET 请求指定了过时的 API 版本，并返回 HTTP 400。约 60 秒后，一个匹配的 GET 请求开始使用受支持的版本，并随后返回 HTTP 200。该 URL 仅在 api-version 参数中发生变化。
  • 向 Application Insights 查询端点发出的 ARM POST 请求因指定了过时的 API 版本而返回 HTTP 400。失败请求约 80 秒后，另一个 POST 请求开始针对同一端点发送，指定了受支持的 API 版本，并随后返回 HTTP 200。

OAuth 应用滥用

在多种情况下，Microsoft 发现同一批智能体 AI 工具随后获取了同一目标组织中单租户 OAuth 应用程序的令牌，然后利用已失陷的 OAuth 应用程序枚举该组织内的其他云资源。在某些情况下，这些智能体从该组织的 Azure Key Vault 中外泄了机密。这些智能体在完成一次身份验证后，还曾在 Azure DevOps 中搜索机密。在机密被吊销或轮换之前，它们可能使威胁行为者得以在组织中维持持久化、攻陷更多身份或劫持资源。在观察到的一个案例中，一个 AI 智能体在五分钟内从搜索 GitHub 中的客户端机密发展到从 Azure Key Vault 中外泄数据。

这些智能体还利用已失陷的 OAuth 应用程序使用Run Command，该功能可在 Azure VM 中运行脚本。一旦在 VM 上获得此功能的访问权限，威胁行为者便能访问未受保护的凭据和其他存储数据、攻陷关联的工作负载标识，或运行能够提供持久化或横向移动能力的代码。

在此类活动中，AI 智能体反复表现出对可访问 AI 服务的凭据的关注，例如主要 AI 服务提供商的 API 密钥，以及可访问 Foundry Tools（以前称为 Azure Cognitive Services）的 OAuth 应用程序。多份公开报告记录了威胁行为者使用智能体 AI 工具攻陷 AI 服务凭据的情况，有时是为了运行相同的智能体 AI 工作流。

缓解应用程序凭据滥用活动

Microsoft 建议采取以下缓解措施，以遏制、检测和调查此威胁。

遏制

  • 在针对工作负载标识（直接分配给服务主体）的条件访问策略中，将 199.19.77[.]84/32 作为一个命名位置加以阻止，并在用户范围的阻止策略中加以阻止，以涵盖重放的会话。请注意，工作负载标识策略需要 Workload ID Premium 许可，且仅涵盖在你的租户中注册的单租户应用程序。应阻止该确切 IP，而不是整个 ASN。
  • 对于受影响的用户，吊销 Entra 会话、Azure DevOps PAT 和 SSH 密钥。
  • 对于任何受影响的应用程序，移除所有客户端机密、证书和联合凭据，包括威胁行为者添加的凭据，并根据需要禁用服务主体。已签发的令牌在到期前仍然有效。
  • 轮换受影响应用程序可读取的任何 Key Vault 中存储的所有内容，以及在被访问文档中发现的所有凭据。
  • MSP：审查合作伙伴中心访问权限、GDAP 关系和客户租户，并按照你的协议通知受影响的客户。

检测与搜寻

  • 审查 Entra 服务主体和非交互式登录日志中涉及 199.19.77[.]84 和 199.19.77[.]18 的记录，包括失败尝试。登录错误 AADSTS7000215（机密无效）或 AADSTS7000222（机密已过期）表明有人持有你的应用程序凭据；失败后紧接着成功，情况十分紧急。
  • 审查 Azure Activity、Key Vault 和 Storage 诊断日志、Entra 审计日志、Azure DevOps 审计日志以及 Microsoft 365 统一审计日志中涉及该地址的记录，包括机密读取、blob 和文件下载，以及对应用程序、权限或管道的更改。
  • 在 Azure DevOps 审计中，检查 PAT 的创建和首次使用、联合服务连接、管道运行与编辑，以及不熟悉的用户代理。如果审计未启用，请将其启用。
  • 既要查找 IP，也要查找行为：一个地址以混合的成功结果认证到三个或更多服务主体，或一个应用在短时间内跨 Azure Resource Manager、Key Vault、Storage 和 Graph 请求令牌。尽可能在保留期允许的范围内向前搜索。

防御智能体式 AI 攻击

威胁行为者能够且确实会更改其所使用的智能体式 AI 渗透测试工具留下的源 IP 地址、用户代理字符串及其他指纹。这可能使防御人员难以在早期识别和阻止恶意网络流量。

多种行为信号可以帮助组织确定其正遭到使用智能体式 AI 的威胁行为者攻击。扫描目标的智能体式 AI 框架会在短时间内发送种类繁多的请求，并对同一技术进行重试变体，或以机器速度进入下一阶段行动。智能体式 AI 框架使用现有的渗透测试工具。例如，ARTEX 默认使用 Nmap、curl、wget、Python HTTP 客户端、Norma SDK WebFetch，以及通过 Playwright 驱动的无头 Chromium 等工具。这些工具发送的网络流量可能具有显著特征，例如默认用户代理字符串。虽然阻止具有这些特征的网络流量无法阻止 AI 智能体发起的攻击，因为后者会迅速更改这些特征，但识别这些特征可以提醒防御人员注意相关活动。

防御性蜜罐、诱饵、拖拽池和虚假胜利可以将自主 AI 攻击从合法目标引开。蜜罐以及 Microsoft Sentinel Deception 等诱骗表面可为智能体提供具有吸引力但毫无价值的目标。拖拽池会消耗智能体的时间和预算。虚假胜利会呈现令人信服的证据，表明智能体的目标已经完成，从而可能使其因虚假成功而停止。在 Microsoft 的测试中，这些控制措施有助于减少到达真实资产的攻击流量，并产生高置信度、达到归因质量的信号。

Microsoft 建议采取以下缓解措施，以降低此威胁造成的影响。

  • 保护应用程序凭据和密钥，并持续对其进行检查。避免将服务主体凭据、存储密钥、连接字符串及其他密钥存储在源代码、配置文件、公共存储库、问题或其他可能被意外暴露的位置。要查找源代码中的凭据，可考虑使用 GitHub Advanced Security 或其他 OWASP 源代码分析工具。
  • 立即轮换已泄露或暴露的凭据，并建立凭据生命周期管理实践。将已公开暴露的凭据视为已泄露，即使原始位置后来已编辑或删除。删除内容并不会使凭据失效，也无法消除保留在编辑历史记录、缓存、归档、日志或其他系统中的副本。立即撤销或轮换受影响的凭据，并调查其历史使用情况。在支持的情况下，组织应优先采用减少对长期有效凭据依赖的机制。详细了解如何使用 Defender for Cloud 保护密钥。
  • 为关键的 Azure 工作负载启用相应的 Microsoft Defender for Cloud 计划。考虑启用与环境中资源相关的工作负载保护，包括 Defender for Resource Manager、Defender for Storage、Defender for Key Vault、Defender for App Service 和 Defender for Databases。在Microsoft Defender for Cloud 概述中了解更多信息。
  • 对服务主体和其他工作负载标识应用最小权限。审查分配给服务主体的 Azure 基于角色的访问控制 (RBAC) 权限，并将其权限限制在应用程序所需的资源和操作范围内。在Azure RBAC 最佳实践中了解更多信息。
  • 将备份和恢复基础设施作为韧性的一部分进行保护。限制对备份和恢复资源的访问，并密切监控试图修改或移除其保护控制的尝试。在Azure Backup 安全最佳实践中了解更多信息。

加固 OAuth 应用程序以防失陷，包括管理组织中应用程序的权限并保护应用程序机密。要对环境中的应用程序进行分类排查，请在创建新应用程序时强制实施安全策略，并随着时间推移处理现有应用程序，先从最近的应用程序开始。

  • 识别并登记在云环境中运行的应用程序。Defender for Cloud Apps 中的云应用目录页面是一项可帮助完成此工作的服务。
  • 使用 Microsoft Defender for Cloud Apps 的Cloud Discovery工具来识别非托管应用，并确定最常用应用的优先次序，以便进行迁移和集成。
  • 使用适用于工作负载标识的条件访问策略。考虑使用工作负载标识风险防护来增强标识信号。
  • 设置权限限制，以限制谁可以在租户中创建应用程序。可以将用户注册应用的权限设置为“无”，并将应用程序开发人员角色限制为特权用户来实现。查看按任务划分的最小权限角色列表，以帮助确定环境中基于角色的访问控制范围。
  • 将企业应用程序与 Microsoft Entra ID 集成。

Microsoft 检测

Microsoft Defender 和 Microsoft Sentinel客户可以参考下面适用检测的列表。Microsoft Defender 协调跨终结点、标识、电子邮件和应用程序的检测、预防、调查和响应，以提供针对此类攻击的集成保护，就像此博客中讨论的威胁。

高级搜寻查询

以下搜寻查询与 10 月 28 日的 Entra ID 服务主体登录活动有关。

查找来自可疑 IP 地址的成功和失败应用程序登录

let startTime = datetime(2026-10-28T00:00:00Z);
let endTime = now();
EntraIdSpnSignInEvents
| where Timestamp between (startTime .. endTime)
| where IPAddress in ("199.19.77.84")
| project Timestamp, TenantId, Application, ApplicationId, ServicePrincipalName, ServicePrincipalId, ResourceDisplayName, ResourceId, ResourceTenantId, IPAddress, ErrorCode, UserAgent, CorrelationId, RequestId
| order by Timestamp asc

查找来自这两个 IP 地址的 Microsoft Graph API 请求，包括搜索和响应状态

let startTime = datetime(2026-10-28T00:00:00Z);
let endTime = now();
GraphAPIAuditEvents
| where Timestamp between (startTime .. endTime)
| where IpAddress in ("199.19.77.84")
| project Timestamp, TenantId, ApplicationId, ServicePrincipalId, AccountObjectId, IpAddress,
          RequestMethod, RequestUri, ResponseStatusCode, ResponseSize, Scopes, EntityType,
          TargetWorkload, UniqueTokenIdentifier, ClientRequestId, OperationId, RequestId
| order by Timestamp asc

查找来自可疑 IP 地址的可用 Microsoft 365 和 Microsoft Azure 云活动详细信息

let startTime = datetime(2026-10-28T00:00:00Z);
let endTime = now();
CloudAppEvents
| where Timestamp between (startTime .. endTime)
| where IPAddress in ("199.19.77.84")
| project Timestamp, Application, CloudAppId = ApplicationId, ActionType, ActivityType,
          AccountType, AccountDisplayName, AccountId, AccountObjectId, IPAddress, UserAgent,
          ObjectName, ObjectType, ObjectId, ActivityObjects, ReportId, RawEventData
| order by Timestamp asc

使用 CloudAuditEvents 表识别可疑的控制平面操作

Microsoft Security Copilot

Microsoft Security Copilot 嵌入在 Microsoft Defender 中，为安全团队提供 AI 驱动的能力，用于汇总事件、分析文件和脚本、汇总身份信息、使用引导式响应，以及生成设备摘要、 hunting 查询和事件报告。

客户还可以部署 AI 代理，包括以下 Microsoft Security Copilot 代理，以高效执行安全任务：

  • 威胁情报简报代理
  • 网络钓鱼分诊代理
  • 威胁狩猎代理
  • 动态威胁检测代理

Security Copilot 还可作为独立体验提供，客户可在其中执行特定的安全相关任务，例如事件调查、用户分析和漏洞影响评估。此外，Security Copilot 提供 开发者场景，允许客户构建、测试、发布和集成 AI 代理与插件，以满足独特的安全需求。

威胁情报报告

Microsoft Defender XDR 客户可以使用 Defender 门户中的 威胁分析报告（至少需要一种 Defender XDR 产品的许可证），获取有关本博客中讨论的活动和技术的最新信息。这些报告提供情报、保护信息和推荐操作，以防止、缓解或响应在客户环境中发现的相关威胁。

  • 活动配置文件：被盗用的应用程序凭据被用于以 Entra ID 工作负载身份登录并访问 Azure、Microsoft 365 资源

Microsoft Security Copilot 客户还可以在 Microsoft Defender Threat Intelligence 中使用 Microsoft Security Copilot 集成，无论是在 Security Copilot 独立门户中，还是在 Microsoft Defender 门户的 嵌入式体验中，以获取有关此威胁的更多信息。
