Claude Code's “Don't Ask Again” File Exposes Passwords and Keys in 1,122 Public Copies on GitHub

AI 导读

Claude Code 在用户选择“Yes, and don't ask again”后，会将批准的命令原样写入 .claude/settings.local.json，若命令含密码或令牌也会以明文保存。

值得关注

材料量化了 Claude Code 持久化命令泄露凭据的范围，并给出轮换凭据、清理历史和调整命令审批方式等可迁移处置方法。

正文 · AI 翻译
中文原文

开发者输入到 Claude Code 所批准命令中的密码和 API 密钥，正存放在公开的 GitHub 仓库中，任何人都可以读取。

当用户选择“是，并且不要再询问”时，Anthropic 的 AI 编程助手可以将该命令逐字保存（包括其中的机密信息）到项目设置文件中。

软件安全公司 Apiiro 昨天表示，有 1,122 份该文件的公开副本至少包含一个机密信息，但它没有测试其中是否仍有效。研究人员本周早些时候通知的一家公司确认，其密钥一直处于有效状态。

该文件是 .claude/settings.local.json。从项目中移除它也无法挽回泄露，因为旧版本仍保留在 git 历史记录和仓库的分支副本中。研究人员的建议是首先轮换：更改该文件曾经保存过的每一个密码、令牌和密钥，然后再进行清理。

机密信息如何进入文件

默认情况下，Claude Code 在运行大多数 shell 命令前都会询问。根据其 权限文档，如果用户选择“是，并且不要再询问”，它就会在项目内的 .claude/settings.local.json 中保存一条允许规则。此后，符合匹配条件的命令在后续会话中运行时将不再询问。

该规则仅涵盖提示中提供的范围。有时是一个模式，例如 npm test *，有时则是一条完全准确的命令。如果是完全准确的命令，输入其中的任何密码或令牌也会被保存，而且是以明文形式保存。

研究人员发现了内容中仍含机密信息的已保存命令，并使用最新模型 Opus 5.5 和 Fable 5.1 复现了这一行为。

Claude Code 会尝试防止该文件被纳入 git。据其 设置文档说明，第一次在 git 仓库中写入该文件时，它会将该文件添加到用户的全局 git 排除列表中。此后，那台计算机上的 git 会在每个仓库中忽略该文件。

研究人员表示，这种保护仅存在于某一台计算机上某个用户的 git 设置中，对于已经提交过的文件毫无作用。Claude Code 绝不会将该文件添加到项目自身的 .gitignore 中，因此这种保护不会随项目一同生效。

在研究人员追踪的 1,105 个仓库中，有 539 个仓库的某次提交将 Claude 列为共同作者。他们据此认为，Claude 经常会自行提交该文件。

Apiiro 的发现

Apiiro 对公开 GitHub 的搜索发现了 104,185 份该文件的副本，分布在 103,617 个仓库中，其 研究论文显示。其中约 1.1%，即 1,122 份副本，至少包含一个机密信息。这些副本合计包含 1,379 个不同的机密信息。

当某个值与已知密钥格式匹配，或某个密码或令牌位于公共服务器地址旁边时，该值即被计为机密信息。此外还需要一名 AI 审核员同意。研究人员没有说明是否有人使用过这些机密信息。

超过三分之一的机密信息可直接用于打开数据库，其中包括 379 个数据库密码。其他机密信息包括 43 组公共服务器的 SSH 登录凭据、42 个用于 GitHub、GitLab 和 npm 的令牌，以及 23 个 AWS 密钥。

这些文件的所属者包括 63 个组织，其中大多是各种规模的软件公司。研究人员表示，最严重的案例包括某数据库厂商自己的管理员级云密钥，以及某医疗记录数据库的所有者密码。

截至周一，每个包含机密信息的文件仍位于其所在仓库的默认分支上，而在这些仓库中，有一半至少在 217 天前就已存在该文件。

该文件的旧版本在 509 个仓库中包含另外 734 个未出现在任何当前副本中的密钥，通常是因为文件已被删除。Fork 会进一步传播这些文件：74 个仓库的 211 个 fork 携带了与原始文件相同的密钥。

在共享的 .claude/settings.json 文件的 76,011 个副本中，也有 298 个包含密钥；团队通常是故意将其提交到仓库中的，而且大多位于允许规则里。包括这些文件、旧版本以及保存的代理聊天日志，总计在 1,994 个仓库中发现了 2,539 个密钥。

研究人员比较了 16 个编程代理的文档，Claude Code 是唯一一个经确认默认会将完整的已批准命令保存到项目文件中的代理。

建议措施

研究人员建议开发人员采取以下步骤：

  1. 在 GitHub 组织中搜索 .claude/settings.local.json 和 .claude/settings.json，并检查每个仓库的 git 历史中是否存在这些文件，即使这些文件已消失。
  2. 在清理之前，轮换这些文件曾经保存过的每个密码、令牌和密钥。
  3. 使用 git rm --cached .claude/settings.local.json 停止跟踪本地文件，并将其添加到仓库自己的 .gitignore 中。
  4. 在自己的计算机上打开该文件，即使它从未被提交过，并删除其中每条包含密钥的规则。
  5. 不要在命令中直接使用密钥。应通过变量引用它们，例如使用来自密钥管理器的 $DB_URL，这样保存的规则中只会包含变量名，而不会包含密钥。
  6. 批准模式，例如 Bash(npm run:*)，而不是单条命令。

研究人员表示，即使副本从未到达 GitHub，也仍然值得关注。该文件是项目文件夹中的纯 JSON，也可能被留在 npm 包、Docker 镜像、zip 压缩包或同步文件夹中。

此前，恶意软件曾寻找开发者计算机上的密钥。2025 年 9 月，Shai-Hulud worm 在受感染计算机上运行了 TruffleHog 密钥扫描器，该扫描器将一半以上的文件标记为含有密钥。

常见的密钥扫描器会漏掉许多此类文件。研究人员对每个副本运行了 gitleaks 和 TruffleHog，且未启用这些工具的验证步骤。在包含密钥的 1,122 个文件中，gitleaks 标记了 564 个，TruffleHog 标记了 643 个，两者都未标记的有 215 个。

大多数漏报是直接在命令中输入的密码。扫描器会查找已知的密钥格式，而位于 PGPASSWORD=、 sshpass -p 或 mysql -p 之后的密码看起来就像普通命令行中的普通单词。

研究人员建议安全团队采取以下措施：

  • 将代理文件夹，例如 .claude/、 .cursor/、 .gemini/ 和 .specstory/，以及代理记忆文件，视为保存有密钥，就像 .env 文件一样，在笔记本电脑和仓库中都要加以防范。
  • 将这些文件加入提交前和 CI 密钥扫描范围，包括 git 历史，并确保扫描器能够检测命令内部的密码，而不只是已知的密钥格式。
  • 将 .claude/settings.local.json 添加到组织的 .gitignore 模板中。
  • 优先检查与公共服务器配对的凭据，因为这些凭据最容易被利用来获得访问权限。

此前报告

Claude Code 用户此前已报告过这种行为。一份于 2025 年 8 月 11 日提交的早期漏洞报告称，包含 API 密钥和令牌的已批准命令会逐字保存在 settings.local.json 中。

一个自动机器人于 1 月 3 日将该报告以“不计划处理”为由关闭，此前该报告已 60 天没有活动。

截至今天，研究人员引用的四份相关报告均已由同一个机器人关闭，最近一份是在昨天关闭的。他们表示，这些报告都没有得到 Anthropic 的回复。
