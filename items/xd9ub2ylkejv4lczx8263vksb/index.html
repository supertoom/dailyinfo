Microsoft Defender 与许多其他 EDR 和 AV 一样，都是漏洞研究的理想目标，因为它以最高权限运行，并包含许多内核级组件。另一个扩大其攻击面的关键属性是它是跨平台的：它运行在 Windows、macOS 和 Linux 上，而每个平台都有各自的一套操作系统 API 和安全控制机制。

2026年初，Microsoft Defender for Windows 中有两个本地权限提升漏洞被公开披露，并在真实环境中遭到利用。CVE-2026-33825（“BlueHammer”）利用了竞态条件，而 CVE-2026-41091 利用了 Defender 检测和修复流程中缺少符号链接验证的问题。尽管这些漏洞已得到修补，但我进一步查看了它们的根本原因，发现虽然这些漏洞可能已在 Windows 中修复，但 macOS 中安全 API 和文件系统 API 工作方式的细微差异，使这些漏洞的变体仍可被利用。

Microsoft 此后已修补了这两个漏洞，分别分配了 CVE-2026-50657（任意文件读取／信息泄露）和 CVE-2026-50658（TOCTOU 竞态条件／权限提升）。我在 BlueHat Asia 2026 上介绍了这项研究，而本文是这项研究的长篇详述。

虽然一旦获得最初的利用原语，这些漏洞本身相当简单，但我认为这是一个深入研究 macOS 特有安全机制及其与 Windows 对应机制差异的好机会。跨平台变体分析经常被忽视，但它可能揭示严重的回归问题，即某个漏洞可能已在一个操作系统中修补，却仍能在另一个操作系统中利用。

macOS IPC 安全机制 🔗

这里的漏洞是 macOS 特有的，这既是因为 Defender for macOS 的架构不同于 Defender for Windows，也是因为操作系统本身对身份验证、授权和链接的处理方式有所不同。

特权进程间通信（IPC）处处暗藏陷阱。其模式始终相同：一个非特权用户应用程序通过某种通道向特权监听器发送请求，由后者代其执行特权操作。当监听器缺少或存在错误的身份验证／授权检查、对特权操作的输入验证不足，或操作系统授权 API 配置不正确时，问题就会发生。我此前曾写过一篇专门讨论这种类型漏洞的文章：Zscaler Client Connector (CVE-2023-41973)。操作系统提供了机制来帮助开发者避开这些陷阱，因此值得了解 macOS 在这方面提供了哪些机制。

代码签名、Developer ID 和公证 🔗

macOS 上运行的每个可执行文件都经过代码签名。在 App Store 之外分发的第三方软件使用 Apple 向开发者 Team ID 签发的 Developer ID 证书进行签名（Microsoft 的是 UBF8T346G9），并且通常会经过公证。

代码签名服务 API（SecStaticCodeCreateWithPath、SecCodeCopyGuestWithAttributes、SecStaticCodeCheckValidity）允许用户态程序使用一种小型谓词语言验证另一个文件或运行中的进程是否满足代码签名要求。例如，anchor apple（由 Apple 签名）、anchor apple generic（链接到 Apple 根证书，包括 Developer ID）或 identifier "com.microsoft.wdav" and certificate leaf[subject.OU] = "UBF8T346G9"。这类似于 Windows 的 WinVerifyTrust API 和 Authenticode 策略。

代码签名机制使特权 macOS 守护进程能够验证 IPC 对端是否确实是供应商签名的二进制文件。也正因如此，如后文所见，把这个问题判断错误是致命的。

系统完整性保护与强化运行时 🔗

系统完整性保护（SIP）是一种默认启用、由内核强制执行的强制访问控制机制：它禁止修改受保护的位置，也禁止附加到受保护进程或向其中注入代码。SIP 是攻击者无法直接注入 Defender 的某个已签名辅助进程以借用其身份进行 IPC 的原因。启用 SIP 后，针对 Apple 已签名或经过强化二进制文件的 task_for_pid（进程注入）会失败，而 DYLD_* 注入（大致相当于 Windows 上的 DLL 注入）也会被阻止。因此，要冒充可信进程进行 IPC，漏洞利用必须找到目标中的其他缺陷。

Defender 的 IPC 构建在 macOS 授权服务之上，以执行特权操作。由于这个 API 经常被误解，因此有必要准确说明它的用途。

程序获取 AuthorizationRef，然后调用：

OSStatus AuthorizationCopyRights(AuthorizationRef authorization,
                                 const AuthorizationRights *rights,
                                 const AuthorizationEnvironment *environment,
                                 AuthorizationFlags flags,
                                 AuthorizationRights **authorizedRights);

使用字符串键（例如 com.microsoft.mdatp.controllogging）指定一个或多个权限。该调用会查询系统的授权策略数据库，其中将每项权限映射到一条规则。内置规则包括 allow、deny、is-root、authenticate-admin 和 authenticate-session-owner。如果规则得到满足，该调用会返回 errAuthorizationSuccess。Csaba Fitzl（theevilbit）对 macOS 授权机制进行了深入剖析。

在我分析的版本中，Defender 在策略数据库中注册了十三项自定义权限。读取一条实际生效的规则可以了解其要求。例如：

security authorizationdb read com.microsoft.mdatp.readlogs

返回一条规则，其中 rule 数组为 is-root 或 authenticate-admin-30。换言之，如果该授权所属进程已经是 root，或者任何管理员在弹出对话框中完成身份验证（凭据缓存为 30 秒），则授予该权限。

关键在于，用 Apple 自己的术语来说，此功能是选择性启用的，也就是“自我限制”。AuthorizationCopyRights提供的保护只有在代码选择调用它并根据结果采取行动时才有意义。它不是操作系统维护的强制执行边界。

对端身份与审计令牌 🔗

macOS 提供多种 IPC 机制：Mach 消息、XPC 和 NSXPC（现代且推荐的抽象），以及包括 AF_UNIX 在内的传统 BSD 套接字。Defender 的 wdavdaemon 使用 AF_UNIX 流式套接字。

任何特权监听程序面临的核心问题都是对端身份：另一端是哪个进程，它是否有权执行此操作？判断错误通常都是本地权限提升（LPE）的前兆。在 macOS 上，程序可以通过几种方式回答这个问题：

  • getsockopt(client, SOL_LOCAL, LOCAL_PEERPID, …)获取对端的进程 ID（pid），该值是在 connect() 时获取的。XNU（macOS 内核）会记录一次，之后永不更新。
  • proc_pidpath(pid, …)获取指定 pid 对应可执行文件的当前绝对文件系统路径。它回答的是“pid N 此刻运行的是什么映像？”如果进程使用 execve() 重新执行自身，该值就会发生变化。
  • getsockopt(client, SOL_LOCAL, LOCAL_PEERTOKEN, …)，或用于 XPC 的 xpc_connection_get_audit_token，获取对端的 审计令牌，这是一个不透明的结构体，除其他字段外还携带 pid 和 pidversion 代计数器，该计数器会在每次 execve 时递增。审计令牌还携带用于查找权限的 signing_id。它是唯一既与特定进程绑定、又会在该进程重新执行时失效的对端凭据。（Scott Knight 有一篇很好的审计令牌文章。）

一种常见且存在漏洞的模式是只依赖前两项：获取对端的 pid，然后根据该 pid 检查可执行文件路径是否在允许列表中。这会在捕获 pid 与检查路径之间产生竞态窗口。这种“PID 复用”技术由 Samuel Groß（5aelo）在其 《不要信任 PID！》 WarCon 2018 演讲中提出。

Defender 的攻击面 🔗

进程模型 🔗

在正在运行的 Defender for macOS 安装中，相关进程包括：

进程 权限 角色
wdavdaemon root 特权代理。拥有两个 IPC 套接字、引擎、隔离区和诊断功能。
wdavdaemon_enterprise root EDR 工作进程（企业功能）。
wdavdaemon_unprivileged _mdatp 扫描工作进程；与 root 守护进程通信。
Microsoft Defender Helper user GUI/托盘辅助进程。

具有 root 权限的 wdavdaemon 由 Microsoft 签名（Team ID UBF8T346G9），并作为 LaunchDaemon 运行。

IPC 套接字 🔗

wdavdaemon 暴露两个 AF_UNIX 流套接字：

  • /var/run/wdavdaemon.sock：公共套接字。
  • /var/run/priv_wdavdaemon.sock：私有套接字。

两者均以模式 0666（srw-rw-rw-）创建，归 root 所有，因此任何本地进程都可以连接它们。“私有”套接字仅在意图上属于私有：它处理更敏感的操作码（威胁处理、配置），但同样可以访问。

两个套接字都通过 SOCK_STREAM 共享一种数据包结构：

frame_header (16 bytes, big-endian)
  u32  seq            ; sequence, echoed in the reply
  u8   reserved[8]    ; always zero
  u32  body_len       ; length of body that follows
body (body_len bytes)
  u32  opcode  (little-endian)
  ...  payload        ; opcode-specific

本文关注两个操作码：

操作码 名称 操作
0x05 handle_threat 隔离/还原文件
0x0f get_diagnostic_files 生成一个全局可读的 ZIP

大多数特权操作码最终都会调用 AuthorizationCopyRights（重新检查 com.microsoft.mdatp.* 权限），该调用位于 libwdavdaemon_core.dylib 内。如果正文载荷中没有有效的 32 字节 AuthorizationExternalForm 结构，受限制的操作码会返回统一的“auth-failed”响应，并且处理程序不会运行。这是一个合理的同意门控，但它只能证明管理员已同意，不能证明调用方是真正的 Defender 客户端。调用方身份完全委托给单独执行的逐连接对端检查。

对端验证 🔗

在任何处理程序运行之前，守护进程会验证连接的对端：

  1. getsockopt(SOL_LOCAL, LOCAL_PEERPID)，用于获取对端连接时的 pid。
  2. proc_pidpath(pid, …)，用于获取该 pid 当前的可执行文件路径。
  3. 将该路径与运行时构建的允许列表进行严格前缀匹配，允许列表以 "/Applications/Microsoft Defender.app" 开头。匹配会强制执行目录边界，因此 /Applications/Microsoft Defender.appEVIL 不会通过。
  4. 路径匹配后，执行代码签名服务要求检查（anchor apple / anchor apple generic）。对于非捆绑应用的对端，永远不会执行到这一步，因为前缀检查会先将其拒绝。
  5. 失败时，返回 shutdown(SHUT_RDWR) + close()。从客户端来看，这表现为握手过程中出现 EOF。

对于普通的 uid-501 进程，第 3 步会无条件拒绝。但请注意，第 1 步和第 2 步使用了同一对端的两种不同表示：冻结的 pid 和实时的路径。这容易受到 PID 复用竞态攻击。

对端验证绕过 🔗

该竞态的利用方式很直接：

  • 在对端连接时捕获 LOCAL_PEERPID，此后它不可变。
  • proc_pidpath 返回 pid 当前的可执行文件路径，我们可以使用 execve() 修改该路径。

严格来说，我在这里使用的 PID 复用变体并不是回收的 pid 号落到另一个不同进程上，而是同一个进程重新 execve-ing，以改变其 pid 所解析到的路径；这属于同一 pid-trust 家族。

关于 execve 的关键事实是，内核会在返回用户态之前、在新映像的第一条指令运行之前更新进程记录的映像路径。被 exec 的二进制文件不必可用，不必执行任何 IPC，甚至不必存活。它只需要在守护进程调用 proc_pidpath 之前导致 pid 路径更新即可。

因此，该漏洞利用会 fork 许多子进程，每个子进程都像这样竞争：

  1. s = socket(AF_UNIX, SOCK_STREAM)
  2. connect("/var/run/wdavdaemon.sock")：LOCAL_PEERPID 现在已冻结到该子进程的 pid。
  3. send([16B header][u32 LE 0x0f])：请求已排队。
  4. execve("/Applications/Microsoft Defender.app/Contents/MacOS/wdavdaemon_unprivileged.app/Contents/MacOS/wdavdaemon_unprivileged", argv=["wdavdaemon"], …)：内核将 pid 路径更新为一个列入允许列表、由 Microsoft 签名的二进制文件（该文件随后会立即因其单例检查而退出，但这没关系）。

与此同时，在 accept() 之后，守护进程：

  1. getsockopt(LOCAL_PEERPID, &pid)：pid 是该子进程的 pid。
  2. proc_pidpath(pid, path)：此时记录的路径。
  3. prefix-match(path, "/Applications/Microsoft Defender.app")。
  4. 匹配 → 运行处理程序；不匹配 → shutdown(fd)。

如果守护进程的步骤 2 在子进程的步骤 4 之后运行，proc_pidpath 将返回 bundle 路径，检查便会通过，尽管实际连接的进程是攻击者自己的程序（在我的 PoC 中是一个 Perl 脚本）。当守护进程读取该路径时，该子进程已经重新 exec 成列入允许列表、由 Microsoft 签名的二进制文件，而这正是同时满足前缀匹配和代码签名检查的条件。攻击者控制的子进程现在可以向 wdavdaemon 发起任意 IPC 调用。

本地权限提升 🔗

绕过对端检查后，我们可以在任一 socket 上调用任何 opcode，并将 Defender 自身的特权处理程序变成漏洞利用原语。有两个 opcode 可以实现这一点：0x0f get_diagnostic_files 可实现以 root 身份进行任意文件读取，0x05 handle_threat::restore 可实现以 root 身份进行任意文件写入。

任意文件读取（CVE-2026-50657） 🔗

一个未设门的 opcode 🔗

与权限更高的 opcode 不同，0x0f get_diagnostic_files 完全不会通过 AuthorizationCopyRights 这道门。仅发送正文 [u32 LE 0x0f]、不带任何授权 blob，就会返回一个格式完整的回复：

result<optional<boost::filesystem::path>>  OK
path = "/Library/Application Support/Microsoft/Defender/wdavdiag/<UUID>.zip"

每次调用都会让 root 守护进程在 /Library/Application Support/Microsoft/Defender/wdavdiag/ 下以 UUID 命名路径构建一个全新的诊断归档，该目录可被全局读取和搜索（0755 root:wheel）。

检查生成的 ZIP 可以发现，归档器除其他内容外，还会收集$HOME/Library/Logs/Microsoft/Defender/ 下的所有常规文件。这是用户自己的日志目录，会在首次启动时自动创建。归档器使用守护进程正常的打开例程打开每个文件。守护进程是 root，因此 open(O_RDONLY) 会对该路径解析到的任何目标成功。

使用硬链接重定向 🔗

$HOME/Library/Logs/Microsoft/Defender/ 归用户所有（uid 501，0755），因此用户可以在其中创建目录项，包括硬链接。使其成为任意读取的微妙之处在于 POSIX link(2) 的一项性质：它不要求对源文件具有读取权限。它只要求源路径的各组成部分可搜索，并且目标目录可由调用者写入。

因此，以 uid 501 的身份执行：

link("/etc/kcpassword",
     "/Users/eugenelim/Library/Logs/Microsoft/Defender/microsoft_defender_app_logs.log");

是合法的，即使目标是仅限 root 访问的。现在，植入的目录项虽然位于用户拥有的目录中，却指向 root 拥有的 inode。

为什么使用硬链接而不是符号链接？当归档程序遍历目录时，它会检查每个条目，并使用 boost filesystem 库函数 boost::filesystem::status() 仅归档常规文件；该函数返回一个带有 file_type 枚举成员的 file_status。被拒绝的类型包括 directory_file、symlink_file、block_file、character_file、fifo_file、socket_file、reparse_file 和 type_unknown，因此植入的符号链接会被过滤掉，永远不会到达 open()。

另一方面，硬链接并不是一种独立的文件类型：它会报告为普通的常规文件（S_IFREG、uid=0），并通过常规文件过滤器。以 root 权限运行的守护进程打开该 inode，并将其字节流式写入可被全球读取的 ZIP，随后用户读取该 ZIP。

这是 CVE-2026-41091 在 macOS 上的对应问题，但仅针对符号链接的修复无法阻止它。与 Windows 硬链接不同，自 2015 年起，Windows 硬链接就需要对目标拥有 FILE_WRITE_ATTRIBUTES 访问权限，正如 James Forshaw 在 Between a Rock and a Hard Link 中所记录的那样；而 macOS 硬链接完全不需要访问目标。这是 macOS 与 Windows 在安全假设上的一个关键差异。

以 root 权限读取文件后，进一步提升权限十分容易。 juicy 目标包括 /var/db/dslocal/nodes/Default/users/*.plist（ShadowHashData 本地账户密码哈希，相当于 macOS 的 SAM）、/etc/kcpassword（经过 XOR 混淆的自动登录密码）、TCC.db、其他用户的 ~/Library 机密、SSH 密钥和浏览器 Cookie 存储。

任意文件写入（CVE-2026-50658） 🔗

第二个漏洞针对 私有套接字和 handle_threat::restore 操作（操作码 0x05，子操作 restore），它允许已授权管理员将隔离文件释放到选定目的地。

跳过授权的可选参数 🔗

恢复请求将其 AuthorizationExternalForm 编码为 std::optional<array<u8,32>>。这是一个存在字节；仅当该字节存在时，后面才会跟长度和对应字节：

body (opcode 0x05 restore):
  u32 LE opcode      = 5
  u32 LE pad         = 0
  u64 LE tid_len     + threat_id            ; ASCII UUID, 36 bytes
  u32 LE sub_action  = 1                     ; restore
  u8  has_dest_path  = 1
  u64 LE dest_len    + dest_path             ; daemon writes here, as root
  u8  has_auth_blob  = 0   <-- THE BYPASS    ; no bytes follow

当 has_auth_blob = 0 时，反序列化器会读取一个缺失的可选参数，而处理程序会完全跳过授权。它从不调用 AuthorizationCreateFromExternalForm 或 AuthorizationCopyRights。

这是一条不同于提供无效授权数据块的代码路径：32 字节全零数据块（has_auth_blob = 1，内容为零）会在 AuthorizationCreateFromExternalForm 处被正确地拒绝。恰恰是缺失的可选参数会绕过检查。

唯一剩下的关卡是私有套接字的对端验证，它采用相同的 getsockopt(LOCAL_PEERPID) → proc_pidpath → SecStaticCodeCreateWithPath 模式，因此同样容易受到 PID 重用竞态条件的影响。因此，非 root 用户可以将任意隔离文件恢复到任意目的地。

暂存隔离文件 🔗

恢复处理程序会恢复一个先前已被隔离的文件，因此攻击者首先让 Defender 隔离攻击者控制的字节：将 EICAR 字符串写入 /tmp/<name>，实时保护会将其隔离，并在隔离元数据中保留原始基本文件名。

隔离文件会落入 /Library/Application Support/Microsoft/Defender/quarantine/，成为用户拥有的文件，其内容仅经过 XOR(0x25) 编码。因此，攻击者可以轻易将隔离的 EICAR 替换为任意内容，并将其暂存以供恢复。攻击接着触发 restore，并提供可控的 dest_path；Defender 会解码该内容，并将攻击者控制的内容写入 <DEST_PATH>/<ORIGINAL_BASE_NAME>。这实际上相当于以 root 权限进行任意文件写入。

有一个重要限制：恢复流程只能写入尚不存在的路径。

处理程序会检查目标路径的状态；如果该路径已存在，原则上可以使用覆盖并备份模式，但对于恢复子操作，相关标志被硬编码为不覆盖路径，并以 EEXIST 拒绝请求。因此，我们获得的是任意文件创建原语，而不是覆盖原语。

命令执行 🔗

这一部分有点尴尬，但“仅创建”约束让我困扰了很久，因为我所知道的多数将文件写入权限提升为代码执行的方法，都依赖于覆盖现有文件或向其追加内容。我尝试了三次。

尝试 1：LaunchDaemons 🔗

LaunchDaemons（位于 /Library/LaunchDaemons/）是 macOS 中与 Windows 计划任务或服务相对应的机制，而投放一个 LaunchDaemon 不需要覆盖任何文件，所以看起来非常合适。然而，具有 root 权限的 LaunchDaemon 脚本必须归 root 所有，而恢复过程会使用 chown 恢复原始所有者：

1. open(<dest>/<basename>.tmp, O_CREAT|O_EXCL)        ; created as root
2. write(decoded original bytes)
3. rename(<dest>/<basename>.tmp, <dest>/<basename>)
4. chown(<dest>/<basename>, source_uid, source_gid)   ; BY PATH, not fchown

步骤 4 chowns 按路径执行，而不是按打开的 fd 执行。在步骤 3 和步骤 4 之间，最终文件已经存在且归 root 所有，因此如果 <dest> 是一个符号链接，且其目标在该时间窗口内被替换，那么步骤 4 的 chown 将落到另一个文件（诱饵文件）上，而真正的目标文件仍归 root 所有。这比 PID 复用的竞态窗口小得多，但理论上仍有可能成功。

遗憾的是，非特权用户无法 launchctl bootstrap 系统域的 plist，因此，即使一个完全归 root 所有的 LaunchDaemon，在系统重启之前也不会有任何攻击者可控制的触发器。

尝试 2：利用 Defender 自身的安装监控 LaunchDaemons 🔗

如果我自己无法引导启动 LaunchDaemon，或许 Defender 可以。该产品为其 tracer 和 DLP 子系统提供了安装监控 LaunchDaemons，当受监控的文件出现在 /Library/Application Support/Microsoft/{DLP, Defender/dlp_processor, Defender/tracer}/install/ 下时，会运行一个 root 脚本。该脚本（install_helper）会将一个 daemon plist 复制到 /Library/LaunchDaemons/ 并引导启动：

cp  "<app-bundle>/.../com.microsoft.wdav.tracedaemon.plist"  /Library/LaunchDaemons/
launchctl bootstrap system  /Library/LaunchDaemons/com.microsoft.wdav.tracedaemon.plist

乍看之下，这是一条确定性且无需重启的路径。但它因同样的原因而失败：写入原语只能创建。cp 源是应用包内一个预先存在、归 root 所有的 plist，恢复处理程序拒绝覆盖它，因此该脚本始终会部署 Defender 自己的 plist，而不是我的 plist。另一方面，在 cp目标位置植入文件也会失败，因为 root 的 cp 会在 bootstrap 之前将其覆盖；我同样无法锁定目标位置，因为将文件设为不可变需要拥有该文件，而 launchd 又要求该 plist 归 root 所有。这条路线的每种变体都依赖于重写一个已经存在的文件，而这恰恰是该原语无法做到的。

尝试 3：用 cron 保持简单 🔗

macOS 仍然内置了大量旧式 Unix 构件，其中之一就是 cron。

macOS 上的 cron 本身就是一个 launchd 作业，即 com.vix.cron，在标准安装中它虽然已弃用，但仍处于休眠状态。不存在 /etc/crontab，并且该作业的 KeepAlive 是一个监视该确切路径的 PathState 条件：

<key>KeepAlive</key>
<dict>
    <key>PathState</key>
    <dict>
        <key>/etc/crontab</key>
        <true/>
    </dict>
</dict>

因此，创建 /etc/crontab 会立即启动 cron，无需重启。由于该文件通常不存在，这属于创建而非覆盖，非常适合该写入原语。讽刺的是，正是由于弃用了 cron，macOS 才使这条链成为一个完美的候选项。

更好的是，它绕过了让 LaunchDaemon 路线失败的所有权问题。LaunchDaemon 必须归 root 所有，否则 launchd 会拒绝它，这正是上面迫不得已要利用 chown-TOCTOU 竞态的原因。cron 对 /etc/crontab 并无此类规则：它会读取文件，并以每行第六个字段中指定的用户身份运行该行的命令。以 * * * * * root … 开头的行即使在文件本身归 uid 501 所有时，也会以 root 身份运行。

载荷是单行 system-crontab 内容：

* * * * * root /bin/sh -c 'cp /bin/zsh /tmp/lpe_root_shell; chown root:wheel /tmp/lpe_root_shell; chmod 4755 /tmp/lpe_root_shell'

至此，端到端的提权链就完成了：准备一个名为 crontab 的 EICAR 文件，把它的隔离区 blob 替换为上面那一行，然后用 dest = /etc 执行跳过认证的恢复操作。对等竞态赢得 /etc/crontab（uid 501，0644）；launchd 启动 cron；/tmp/lpe_root_shell -p 在写入后大约一分钟内触发一个交互式 root shell。只需赢下这一个对等竞态，可靠性就高得多。

结论 🔗

这两个漏洞都已报告给微软安全响应中心（MSRC），并已在 2026 年 7 月的补丁星期二修复：

CVE-2026-50657 CVE-2026-50658
类别 向未授权行为主体暴露私人个人信息 TOCTOU 竞态条件
影响 本地信息泄露（任意文件读取） 本地权限提升（任意文件写入 → root）

这些 macOS 本地权限提升漏洞是独立于 Windows 那些漏洞发现的，但它们与 2026 年 Windows Defender 的提权链如出一辙并非巧合。真正有意思的是，同两类漏洞在 macOS 的 IPC 与安全原语中被处理的方式截然不同。

Windows macOS
进程身份 依赖进程句柄；内核在内存中锁定进程对象。 必须显式检查审计令牌，以缓解 PID 复用。
授权 由内核依据访问令牌与完整性级别，针对目标的 ACL 进行求值。 对 Authorization Services API 的“自限制”（opt-in）使用。

由于这些差异，该漏洞利用在 macOS 上的运作方式也不同：

  • 身份。 Windows 上的 TOCTOU 通常是在检查与使用之间移动一个文件。macOS 提供了更强的原语：execve 在连接与检查之间改变一个进程的路径。这就是 PID 复用攻击如此可靠的原因；攻击者可以在自己的进程内部精确控制主体替换的时刻。
  • 链接。 在 Windows 上，链接创建受到相对较多的限制：符号链接需要 SeCreateSymbolicLinkPrivilege（默认由管理员组持有），硬链接需要对其目标的写权限，而目录联接（junction）不需要任何权限，但只能重定向目录，如今可通过 RedirectionGuard 加以缓解。macOS 使用类 Unix 风格的链接，而 link(2) 不需要对目标有任何读或写权限，只需要一个可搜索的路径和一个可写的目标目录。这正是非 root 用户得以实现特权读取的原因。
  • 授权。 在 Windows 上，授权由令牌、完整性级别和 ACL 中介。在 macOS 上，Authorization Services 是自限制的，因此实现不当很容易埋下陷阱。macOS 特有的问题在于，同意（AuthorizationCopyRights）与调用者身份认证（审计令牌的代码签名校验）是不同的问题，不应混为一谈。

由于这些差异，在 Windows 上修补同样的原语并不足以在 macOS 上保障安全。持久有效的修复方案是使用 macOS 原生的 IPC，例如 XPC，它支持 xpc_connection_get_audit_token 和 xpc_connection_set_peer_code_signing_requirement 这类不受 PID 复用影响的操作系统原生 API，并阻止硬链接，而不是仅依赖符号链接检查。

构建跨平台很难；保护跨平台则更难。跨平台框架使用便利，但 IPC、文件处理和权限管理中细微的操作系统级别差异，仍在为漏洞研究人员源源不断地提供丰富的 hunting ground。
