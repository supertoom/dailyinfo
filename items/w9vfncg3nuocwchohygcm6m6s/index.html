Swati Khandelwal2026年11月13日漏洞 / 数据库安全

PostgreSQL 中的类型混淆漏洞允许有权创建对象的数据库用户在服务器上运行代码。昨天发布的更新修复了该漏洞以及其他 51 个安全漏洞。要全面防范此漏洞，还必须重新构建服务器上安装的任何 C 语言扩展。

该漏洞的跟踪编号为 CVE-2026-6460，CVSS 分数为 8.8。以此方式运行的代码拥有运行 PostgreSQL 的操作系统用户所具有的权限。18.7、17.12、16.16、15.20 和 14.25 之前的所有版本均受影响。

发布该数据库版本的 PostgreSQL 全球开发组尚未报告任何利用此漏洞的攻击。CISA 在 CVE 记录中的评估也将利用情况列为“none”。

该漏洞涉及复合类型，即由多个命名字段构建而成的类型，每个字段都有各自的数据类型。当该类型的旧值仍存储在服务器的其他位置时，可以更改某个字段的类型。

随后，服务器可能会将旧值当作新类型读取。该项目发布说明中描述的修复措施增加了版本检查，使服务器能够检测到不再与其类型匹配的值。

安全研究人员 Mehmet Ince 描述了一个针对该漏洞的有效利用方法，并在 PostgreSQL 18.6 上进行了演示。该方法详见本周发布的技术文章。

他的方法是准备一个保存值的查询，更改该值某个字段的类型，然后运行该查询。文章包含以此方式使未打补丁服务器崩溃的 SQL，以及泄露内存地址的第二步。它没有包含使服务器运行命令的最后一步所需的 SQL。

他写道，自己能够“以最低权限登录角色触发此崩溃”。该项目的安全公告仅将攻击者描述为有权创建对象的人，但没有说明这需要哪些权限。

提供 PostgreSQL 软件包的 Red Hat 在其CVE 评估中表示，攻击者需要拥有能够创建或修改对象的数据库登录权限。这些来源均未说明，仅具有默认权限的账户能否越过崩溃步骤进而运行代码。

Ince 将该漏洞的根源追溯至 2004 年 5 月 5 日，当时 PostgreSQL 获得了更改列类型的能力。他用于运行代码的技术依赖于 2015 年 5 月 14 日进行的后续更改。

他还针对托管 PostgreSQL 服务调整了利用方法，并于 8 月私下向这些服务的安全团队分享了概念验证。他合作过的服务提供商包括 AWS（Aurora 和 RDS）、Microsoft（Azure PostgreSQL）、Google（AlloyDB）、Supabase、Databricks 和 Ubicloud。文章没有说明每项服务当前的补丁状态。

该项目在 CVE-2026-6460中向十余名报告者致谢，其中包括该研究人员；还就同一版本发布中的另外五个漏洞向他致谢。

该项目将 52 个漏洞中的 32 个评为 8.8 分，这是本次发布中的最高分。根据其漏洞索引中的评分，服务器中只有一个漏洞既不需要登录，也不需要任何用户操作。该漏洞 CVE-2026-116322允许未经身份验证的客户端触发 PostgreSQL 18 服务器重启。

客户端工具中还有其他几项修复。精心构造的归档文件可能使 pg_restore 以运行该命令的用户身份执行代码。遭入侵的源服务器可能使 psql 通过 pg_dump 的 tar 输出中的恢复脚本执行代码。

管理员应采取的措施

  1. 将服务器更新至 18.7、17.12、16.16、15.20 或 14.25，与您的主版本相对应。
  2. 在更新服务器的同时，重新构建或更新每个 C 语言扩展。根据该项目 RPM 包维护者发布的仓库公告，针对较旧版本构建的扩展仍可加载，但“可能无法防范此版本中已修复的漏洞”。部分扩展还需要进行源代码更改。
  3. 针对新版本重新构建的扩展可能无法在较旧的服务器上加载。该项目 RPM 仓库中的扩展包现在要求使用新的次要版本。
  4. 如果 PostgreSQL 在其软件包自带的服务单元之外运行，例如在 Patroni 下运行，请在更新后立即重启它。RPM 包的维护者在一篇打包博客文章中这样表示。
  5. 在每台运行 pg_dump、pg_restore、reindexdb 和 vacuumdb 等客户端工具的计算机上更新这些工具。
  6. 不要使用新的 composite_type_mismatch 设置来关闭这些检查。该项目表示，这样做会带来安全风险。
  7. 对于尚无法更新的服务器，该项目的安全公告和发布说明未提供任何替代方案。
  8. PostgreSQL 14 现在已停止生命周期支持，14.25 是其最后一个版本。更早的主版本也受到影响，并且未收到更新。
  9. 更新后，按照发布公告中的步骤执行重建索引。如果您使用增量备份，请先进行一次新的完整备份，并以该备份作为后续增量备份的基础。
