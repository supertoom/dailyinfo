概述

今天，Rapid7 和 F5 都在披露 CVE-2026-123007，这是一个影响 nginx HTTP/2 的严重整数下溢漏洞。在特定条件下，它可能导致针对受影响服务器进行未经身份验证的远程代码执行（RCE）。

nginx 可能会错误计算 HTTP/2 客户端允许其发送多少响应数据。远程且未经身份验证的客户端可以利用此错误：先取消排队的响应数据，随后使 nginx 在复制后续响应时使用无效长度。由此导致的内存破坏可能泄露数据、中断服务，并以 nginx 工作进程的权限执行代码。

影响

Rapid7 开发了一个 概念验证，用于演示如何利用 CVE-2026-123007 对运行 nginx 版本 1.31.8 的易受攻击 linux/amd64 Docker 映像实施未经身份验证的 RCE，如下方图 1 所示。目标 nginx 服务器的配置启用了 http2 on 和 TLS。请注意，为简洁起见，视频播放速度为 8 倍。

图 1：通过 CVE-2026-123007 对 NGINX 1.31.8 实施未经身份验证的 RCE 的演示视频

利用 CVE-2026-123007 实施 RCE 需要传输大量网络流量，约为 128 GB 的 HTTP/2 数据。可用的网络带宽和连接超时都会对 Internet 上的利用构成实际限制。在图 1 所示的上述示例中，利用过程耗时两分半钟。在 10 Gbit/s 网络上传输所需网络数据大约需要两分钟，而在 1 Gbit/s 网络上则需要十七分钟。由于 nginx 的默认连接生存期为一小时，网络速度低于约 300 Mbit/s 时，所需时间将超过一小时连接上限阈值，因而无法成功。此外，如果 HTTP/2 连接通过代理转发，攻击者精确控制并传输的 HTTP/2 帧很可能不会以满足漏洞利用要求的方式进行重传。

最后，所开发的利用策略依赖于运行时依据 avx512f 和 avx512vl CPU 特性选择的特定 x86-64 glibc EVEX/YMM memcpy 实现。其他 RCE 利用策略可能可行，但目前尚未发现此类策略。

致谢

此漏洞由 Rapid7 高级首席安全研究员 Stephen Fewer 发现，并依据 Rapid7 的Rapid7漏洞披露政策进行披露。漏洞披露政策。

技术分析

测试的 nginx 版本是 nginx 版本 1.31.8 的 linux/amd64 Docker 映像（nginx@sha256:5ab5b0b01097420873a3f3330f44248e34a3c2a3e8d5ee30658aeae8cb7435da），运行时暴露了 HTTPS 服务并启用了 http2。

客户端如何控制 HTTP/2 响应数据

HTTP/2 通过称为帧的消息在单个连接上传输。每个请求和响应都属于一个编号的流，因此一个连接可以同时承载多个交换。响应体的字节在 DATA 帧中传输。

对于本漏洞，nginx 是发送方，远程客户端是接收方。客户端授予 nginx 发送一定数量 DATA 字节的权限，或者说流控信用。nginx 用两个计数器跟踪剩余信用：每个流一个，另有一个由连接共享。发送 DATA 必须同时得到这两个计数器的许可。这些 HTTP/2 计数器与 TCP 的接收窗口相互独立。

客户端还可以通过发送包含正增量的 WINDOW_UPDATE 帧来授予更多信用。流标识符为零时增加连接的发送信用。非零流标识符则增加具有该特定非零标识符的流的发送信用。HTTP/2 将增量以及由此得到的窗口限制在 2^31-1 字节，即 2,147,483,647 (0x7FFFFFFF)。本报告将该最大值称为 MAX。

客户端还可以发送包含 SETTINGS_INITIAL_WINDOW_SIZE 参数的 SETTINGS 帧。这会改变新流的起始信用。nginx 还必须按旧设置值与新设置值之差调整每个活动流的剩余信用。它不会改变连接的信用。因此，减少设置值可能使活动流出现负信用，直到客户端授予更多信用为止。连接窗口没有相应的减少机制：它必须保持在零与 MAX 之间。RFC 9113, section 6.9 定义了这些限制以及所需的错误。

nginx 将连接计数器存储在 h2c->send_window 中，其中 h2c 是 HTTP/2 连接记录。其 size_t 类型是无符号整数：在已验证的 64 位构建上，它可以容纳从零到 2^64-1 的值。因此，size_t 类型可以容纳高于 HTTP/2 最大连接窗口 2^31-1 字节（MAX）的值。nginx 必须在自己的逻辑中强制执行该协议限制。

// src/http/v2/ngx_http_v2.h
#define NGX_HTTP_V2_MAX_WINDOW ((1U << 31) - 1) // <--- [1]
struct ngx_http_v2_connection_s {
    // ...
    size_t send_window;                         // <--- [2]
    // ...
};
struct ngx_http_v2_stream_s {
    // ...
    ssize_t send_window;
    // ...
};

要求位于 [2] 的连接计数器在任何时候都不得超过位于 [1] 的 MAX 这一规则，就是连接窗口不变式。独立的流计数器 stream->send_window 被显式声明为 ssize_t，在已验证的构建中是有符号 64 位整数。这使得 SETTINGS_INITIAL_WINDOW_SIZE 能够让某个流的信用暂时变为负值。连接计数器仍保持无符号。之后发生的不安全转换，是在输出过滤器把过大的连接信用当作有符号 64 位 off_t 响应长度处理时出现的。

利用该漏洞有四个主要阶段：

  1. 通过放慢其对服务器输出的读取，客户端会让选定的 DATA 帧保持在队列中且尚未开始处理。它将连接的信用值提高到 MAX，并将选定流的信用值提高到略低于 MAX。当 SETTINGS 帧将 SETTINGS_INITIAL_WINDOW_SIZE 增加到超过流限制的程度时，nginx 会关闭这些流，同时保持连接可用。随后，请求清理会将保留的信用值恢复到 MAX 以上。

  2. 下一次连接 WINDOW_UPDATE 检查中的无符号减法会下溢。此后，反复被接受的 WINDOW_UPDATE 帧可以将该计数器提升到其 64 位范围的上半部分，而无需使加法发生回绕。

  3. 在已验证的 64 位构建中，nginx 会将这个过大的计数器解释为负的响应长度，并创建一个无效缓冲区。缓冲的 TLS 输出随后会将一个巨大的无符号字节数传递给内存复制函数 memcpy，从而导致越界读取和写入。

  4. 这些受约束的内存访问取决于构建方式和所选的复制例程。在采用合适内存布局的情况下，攻击者可以利用泄露的地址和受控覆写，以 nginx 工作进程的权限执行代码。

取消排队的 DATA 会恢复过多信用值

当 nginx 在 [3] 处将一个 DATA 帧加入队列时，它会先从连接信用值计数器中减去该帧的 DATA 长度，再从流的信用值计数器中减去该长度。这会在字节到达客户端之前保留信用值，并防止其他流消耗同一份连接信用值：

// src/http/v2/ngx_http_v2_filter_module.c
// ngx_http_v2_send_chain()
// ...
ngx_http_v2_queue_frame(h2c, frame);       // <--- [3]

h2c->send_window -= frame_size;            // <--- [4]
stream->send_window -= frame_size;
stream->queued++;

攻击者可以通过放慢或停止读取较早的服务器输出，使后续响应持续留在队列中。一旦传输层无法接受更多输出，nginx 就必须等待。这种状况称为传输层反压。攻击者需要制造足够多的反压，才能让选定的 DATA 帧保持未启动状态：该帧的任何字节都尚未进入 TLS 输出或套接字。停止读取响应并不会阻止客户端在另一个方向发送控制帧。

在 DATA 仍处于队列中时，客户端会发送一个连接 WINDOW_UPDATE，将 nginx 中已减少的计数器提高到 MAX。问题出现在拥有排队 DATA 的请求随后关闭时。其请求清理处理程序会移除未启动的 DATA，并返还保留的信用值：

// src/http/v2/ngx_http_v2_filter_module.c
// ngx_http_v2_filter_cleanup()
// ...
for ( ;; ) {
    frame = *fn;
    if (frame == NULL) {
        break;
    }
    if (frame->stream == stream && !frame->blocked) { // <--- [5]
        *fn = frame->next;
        window += frame->length;                      // <--- [6]
        if (--stream->queued == 0) {
            break;
        }
        continue;
    }
    fn = &frame->next;
}
// ...
h2c->send_window += window;                           // <--- [7]

[5] 处的测试会为该请求选择可移除且未启动的帧。局部变量 window 在 [6] 处累加这些帧的 DATA 长度。[7] 处的加法不会检查恢复这些字节是否会使连接计数器超过 MAX。

例如，在计数器达到 2,147,483,647 (0x7FFFFFFF) 后恢复 1,393 字节，会产生 2,147,485,040 (0x80000570)。根据 HTTP/2，此值无效，因为它超过了 MAX，尽管它仍能放入 64 位的 size_t 中；此时加法尚未发生回绕。[7] 处未经检查的恢复操作是该漏洞中的第一个无效状态。攻击者仍需要一种方法，在保留连接的同时关闭所选请求，以便再次使用过大的计数器。

SETTINGS 错误会关闭流，但连接仍可使用

当一个 SETTINGS 帧将 SETTINGS_INITIAL_WINDOW_SIZE 增加到足以使活动流的信用额度超过 MAX 时，nginx 会终止该流，但保持 HTTP/2 连接可用。客户端可以先发送一个流 WINDOW_UPDATE，使所选流的信用额度刚好低于 MAX，从而制造这种情况。然后发送一个 SETTINGS 帧，增加初始流窗口设置。例如，将该设置从 65,535 改为 65,537，会为每个活动流增加两个字节。已处于 MAX-1 的流将变为 MAX+1，尽管新的设置值本身是允许的。

RFC 9113 要求在这种情况下使用 FLOW_CONTROL_ERROR 结束连接。nginx 实际上会对每个受影响的流调用 ngx_http_v2_terminate_stream()。该函数发送 RST_STREAM，从而结束单个流并导致请求被清理。随后循环会继续使用同一连接：

// src/http/v2/ngx_http_v2.c
// ngx_http_v2_adjust_windows()
// ...
if (delta > 0
    && stream->send_window
          > (ssize_t) (NGX_HTTP_V2_MAX_WINDOW - delta))
{
    if (ngx_http_v2_terminate_stream(h2c, stream,
                                     NGX_HTTP_V2_FLOW_CTRL_ERROR)
        == NGX_ERROR)
    {
        return NGX_ERROR;
    }
    continue;                                      // <--- [8]
}

在这里，delta 是新旧设置值之差。请求清理会执行 [5] 至 [7]，而 [8] 处的 continue 会让 HTTP/2 连接保持打开。攻击者现在可以在该连接上发送更多帧，而其信用额度已经超过 MAX。

下一次 WINDOW_UPDATE 会导致整数下溢

当另一个连接 WINDOW_UPDATE 到达时，nginx 会尝试计算仍允许增加多少信用额度：

// src/http/v2/ngx_http_v2.c
// ngx_http_v2_state_window_update()
// ...
if (window > NGX_HTTP_V2_MAX_WINDOW - h2c->send_window) { // <--- [9]
    // ...
    return ngx_http_v2_connection_error(h2c,
                                        NGX_HTTP_V2_FLOW_CTRL_ERROR);
}
h2c->send_window += window;                            // <--- [10]

在此函数中，window 是从客户端接收到的增量。只有当存储的计数器不大于 MAX 时，[9] 处的减法才是安全的。如果清理操作恢复了 R 个超出字节，则预期的允许额度为 MAX - (MAX + R)，即 -R。无符号算术无法表示该负数结果。在经过验证的 64 位构建中，它会回绕为 2^64 - R，即一个非常大的正数。这就是 CWE-191 所标识的整数下溢。

错误的额度分配会让后续客户端增量通过检查。通过发送许多增量，且每个增量都不超过 MAX，客户端可以将计数器提升到 2^63 或更高，而加法本身不会发生回绕，如上文 [10] 所示。这样的值，其 64 位表示的最高位会被置位。它仍然是一个无符号值，但已不再能容纳于有符号 64 位整数中。当 nginx 准备下一个响应时，这一区别很重要。

这种放大效应解释了为何需要大量流量。一个 WINDOW_UPDATE 连接占用 13 个 HTTP/2 字节：一个9 字节帧头和一个4 字节载荷。该帧授予的额度并非实际传输的数据。从上文所述的小幅超额额度状态开始，以最大大小的增量达到 2^63 约需 2^32 个帧，即 52 GiB。达到已确认读/写路径所使用的接近 2^64 的值，约需 2^33 次增量，即 104 GiB。nginx 还会相对于其他接收数据限制控制帧流量。当前代码执行复现会额外发送约 15 GiB 的请求头流量，以保持在限制内，使其报告的明文总量达到约 119.02 GiB。TLS 和网络开销会进一步增加实际的线上流量。这些数字描述的是这条 64 位放大路径，而非每一种可能利用方式的通用最小值。

过高的额度会变成负的响应长度

客户端可以让具有可用额度的活动流处理普通响应正文。nginx 的 HTTP/2 输出过滤器决定在一个 DATA 帧中包含多少正文字节。在进行该计算之前，先定义它将创建的缓冲区。

内存中的 nginx 缓冲区由一个 ngx_buf_t 记录描述。其 pos 指针是下一个待发送字节的内存地址。其 last 指针是紧接可用数据之后的地址。对于 4 个可用字节，last 必须位于 pos 之后 4 个字节处；从 last 中减去 pos 可得出长度 4。因此，有效缓冲区不能出现 last 位于 pos 之前的情况。nginx 将这些缓冲区记录链接成输出链，即等待发送的数据列表。

在 ngx_http_v2_send_chain() 中，字节上限是一个 off_t，在经验证的构建中它是带符号的 64 位整数。过高的无符号连接计数器在 [11] 处被转换为该带符号类型。在此构建中，2^64 - d（其中 d 是一个较小的正字节数）会变为 -d：

// src/http/v2/ngx_http_v2_filter_module.c
// ngx_http_v2_send_chain()
// ...
if (limit == 0 || limit > (off_t) h2c->send_window) {
    limit = h2c->send_window;                         // <--- [11]
}
if (limit > stream->send_window) {
    limit = (stream->send_window > 0) ? stream->send_window : 0;
}
// ...
if ((off_t) frame_size > limit) {
    frame_size = (size_t) limit;                      // <--- [12]
}
// ...
rest = frame_size;
while ((off_t) rest >= size) {                        // <--- [13]
    // ...
}
if (rest) {
    cl = ngx_http_v2_filter_get_shadow(stream, in->buf,
                                       offset, rest); // <--- [14]
    // ...
}

流窗口检查不会拒绝负数 limit：它只会缩减过大的 limit。在 [12] 处，负数 limit 会变成一个巨大的无符号 frame_size。将同一个值转换回 off_t 会再次变为负数，因此 [13] 跳过了通常用于消耗并限制可用正文字节的循环。在 [14] 处，nginx 将无效长度传给一个辅助函数，其 size 参数同样是带符号的 off_t。

该辅助函数创建一个影子缓冲区：一条新的元数据记录，指向现有响应数据的一部分，但不复制响应正文本身。它使用传入的长度设置新的结束指针：

// src/http/v2/ngx_http_v2_filter_module.c
// ngx_http_v2_filter_get_shadow()
static ngx_chain_t *
ngx_http_v2_filter_get_shadow(ngx_http_v2_stream_t *stream, ngx_buf_t *buf,
    off_t offset, off_t size)
{
    // ...
    ngx_memcpy(chunk, buf, sizeof(ngx_buf_t));
    // ...
    if (ngx_buf_in_memory(chunk)) {
        chunk->pos += offset;
        chunk->last = chunk->pos + size;              // <--- [15]
    }
    // ...
}

由于 size 为负数，[15] 会将 last 置于 pos 之前。响应正文并未变大；其缓冲区元数据现在已失效。下一个输出阶段会信任这些元数据。

缓冲的 TLS 输出会越过缓冲区进行复制

对于缓冲的 TLS 输出，ngx_ssl_send_chain() 会在加密前将输出链中的字节收集到一个临时的暂存缓冲区中。它使用 last - pos 计算每个输入缓冲区的长度。无效缓冲区在 [16] 处产生一个负的有符号长度：

// src/event/ngx_event_openssl.c
// ngx_ssl_send_chain()
// ...
ssize_t send, size, file_size;
// ...
size = in->buf->last - in->buf->pos;                  // <--- [16]
if (size > buf->end - buf->last) {
    size = buf->end - buf->last;
}
if (send + size > limit) {
    size = (ssize_t) (limit - send);
}
// ...
ngx_memcpy(buf->last, in->buf->pos, size);            // <--- [17]
buf->last += size;
in->buf->pos += size;

两项检查都只会缩减过大的长度。两者都不会拒绝负长度。memcpy 接受无符号 size_t 字节计数，因此 [17] 会将 -d 转换回巨大数值 2^64-d。实际的源缓冲区和目标缓冲区要小得多。这就是无效连接信用首次到达越界原生内存访问的位置。

一次真正跨越如此巨大范围的复制通常会遇到不可访问的内存并使工作进程崩溃。然而在所测试的 x86-64 glibc 实现中，某些略低于 2^64 的长度会导致机器级的结束地址计算发生回绕（关于这一意外行为的更多细节，请参见下面的附录 A）。对于长度为 2^64-d 的情况，将该长度加到起始地址上可能产生一个位于其前方 d 字节的地址。优化后的复制在循环条件中使用这些结束地址，因此它可能在完成有限次数的读写后结束，而这些读写会到达预期缓冲区之外。如果其实际访问的所有位置都可访问，该复制就可能返回；其他长度、内存布局或复制实现则可能立即引发故障。如果复制返回，nginx 还会按该负的有符号长度将两个缓冲区位置向后移动。

利用

无效副本既可以读取也可以覆写 worker 内存。它并不会给客户端提供一个可以任意选择内存地址的 HTTP/2 字段。有用的地址取决于 nginx 在何处分配了响应缓冲区和 TLS 缓冲区、已经缓冲了多少输出，以及 C 库选择了哪个复制例程。这些是受限的读写能力，而不是无条件的任意读写。

在创建无效的 DATA 缓冲区之后，ngx_http_v2_send_chain()会更新其在原始响应中的位置，并记录仍待发送的字节：

// src/http/v2/ngx_http_v2_filter_module.c
// ngx_http_v2_send_chain()
// ...
offset += rest;                                       // <--- [18]
size -= rest;
// ...
if (offset) {
    cl = ngx_http_v2_filter_get_shadow(stream, in->buf,
                                       offset, size); // <--- [19]
    // ...
    in->buf = cl->buf;
    // ...
}

这里，offset是原始主体内的位置，size是其剩余长度。从偏移量零开始，表示 -d的同一个无符号值在已验证的构建中会使 [18] 将偏移量向后移动 d，并将剩余长度增加 d。因此，在 [19] 处创建的影子缓冲区具有正的长度，但起点位于原始响应之前 d 个字节处，终点则与原始响应的终点相同。如果超大副本和连接能够存活，之后的普通 DATA 帧就可以通过 TLS 将这些前面的字节携带给客户端。它们可能包含指向堆的指针（nginx 在堆上动态分配请求数据），或指向已加载库的指针。这些指针会泄露本应被地址空间布局随机化（ASLR）隐藏的地址。

在写入侧，nginx 将客户端提供的请求数据存储在堆分配中。只要分配布局合适，超大副本就可能取到这些攻击者选定的字节，并替换附近一个存活堆对象中的字段。一个有用的字段是回调：即 nginx 打算稍后调用的已存储函数指针。知道相关进程地址并能够覆写该字段的攻击者，可能将正常的 nginx 处理流程重定向到已有的可执行代码。该覆写无需包含新的机器代码。这解释了从泄露地址和受控字节通向代码执行的一般路径；这并不意味着每个构建都会暴露相同的对象或回调。执行将拥有 worker 的权限；尚未证实能以主进程或 root 权限执行。

概念验证首先从原始响应主体之前的内存中恢复堆地址，以及指向 nginx 和 GNU C 库（glibc）的指针。它利用这些地址和覆写来伪造 nginx 的请求与响应缓冲区对象，使其通过 HTTP/2 返回 glibc 已加载映像的选定部分。返回的 ELF 元数据被解析以在 ASLR 存在的情况下解析出 system()，随后请求池的清理回调被重定向以调用攻击者选定的命令。

附录 A：为何超大的 memcpy可以返回

通过 ngx_memcpy 进行的 TLS 复制（如上文 [17] 所示）收到的字节计数为 2^64-d，其中 d 是一个较小的正距离。实际遍历整个范围的例程通常会触发故障。本附录将解释为何某个经过优化的 glibc 实现反而能够在执行有限次数的越界访问后结束。

glibc 会根据 CPU 的能力在经过优化的复制例程之间进行选择。测试所用的 x86-64 例程使用 EVEX/YMM 指令，每次可移动 32 字节。在相应的 glibc 2.41 源码中，EVEX 包装器 包含一个共享的 memcpy/memmove 实现，而其 向量配置 将 VEC_SIZE 设为 32。向量是指由一条此类指令处理的字节块。

下面的摘录使用 AT&T 汇编语法，其中源操作数位于前面。CPU 寄存器 %rdi 保存原始目标地址，下文称为 D；%rsi 保存源地址 Q；%rdx 保存字节计数 n。当 D 与 Q 不同，且无符号差值 D-Q 小于 n 时，有一条路径会进入这个向后复制的分支。这包括普通情形：D 位于 Q 上方，且 n 接近无符号 64 位最大值。

// glibc 2.41: sysdeps/x86_64/multiarch/memmove-vec-unaligned-erms.S
// Function: CPU-selected memcpy implementation, backward-copy branch
// ...
L(more_8x_vec_backward):
    // ...
    leaq (VEC_SIZE * -4 + -1)(%rdi, %rdx), %rcx // <--- [20]
    // ...
    andq $-(VEC_SIZE), %rcx                     // <--- [21]
    // ...
L(loop_4x_vec_backward):
    // ... load and store four 32-byte vectors
    addq $(VEC_SIZE * -4), %rcx                 // <--- [22]
    cmpq %rcx, %rdi                             // <--- [23]
    jb L(loop_4x_vec_backward)
    // ... store the previously loaded leading and trailing vectors
    VZEROUPPER_RETURN                           // <--- [24]

完整的 glibc 汇编源码 展示了被省略的加载和存储。在 [20] 处，leaq 计算地址但不读取内存。其 64 位结果仅保留低 64 位。在 [21] 处，andq 将该地址向下舍入到 32 字节边界。将所得目标地址称为 cursor，计算方式如下：

cursor = align_down_32((D + n - 129) modulo 2^64)
       = align_down_32(D - d - 129), when n = 2^64-d

这里的 align_down_32 表示向下舍入到最近一个可被 32 整除的地址；这是说明性记法，并非 glibc 函数。对于普通堆地址和较小的 d，计算出的 cursor 已经低于 D。

该循环首先复制一个 128 字节块。指令 [22] 随后将 cursor 再向后移动 128 字节。[23] 处的比较和无符号跳转仅在 D < cursor 时重复循环。由于 cursor 已经低于 D，因此不会执行跳转。该例程写入剩余的前导和尾随向量，然后在 [24] 处返回。它并未复制所请求的巨大范围：地址回绕使循环在少量访问后停止。这些访问仍可能读取并覆写实际缓冲区之外的内存。
