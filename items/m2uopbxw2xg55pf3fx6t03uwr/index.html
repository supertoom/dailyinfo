中文原文

据安全软件公司 Aikido Security 表示，自周二起，攻击者利用从 4,837 个 GitHub 账户窃取的凭据，在这些账户有权写入的仓库中植入了一个秘密窃取器。

该窃取器旨在获取仓库的 CI 工作流能够访问的机密和云凭据。该公司表示，它已在至少 1,806 个仓库中运行，攻击者很可能已在那里收集了这些凭据。

每次攻击都从一个标题为 docs: dependency audit notes 的拉取请求开始，该请求通过名为 wfx-docs 的分支发起，用于测试该账户能否向仓库写入内容。这些测试拉取请求在 61,764 个仓库中被发起，而窃取器随后进入了其中一些仓库。

在另一项分析中，销售软件供应链安全工具的 SafeDep 研究人员统计出，从周二 12:46 UTC 到今天 04:36 UTC 期间，有 8,093 个仓库接收了恶意提交。该计数涵盖所有接收恶意提交的仓库，而不仅是运行了窃取器的仓库。研究员称，他们的搜索仅覆盖了公共仓库的默认分支，因此实际总数更高。

在其中 7,309 个仓库中，窃取器被添加到现有工作流中。在另外 771 个仓库中，它以 npm postinstall hook 的形式引入，该钩子也会在开发者运行 npm install 时在其计算机上执行。

推送窃取器后，攻击者通常会在几分钟内撤销更改。在窃取器运行过的仓库中，其日志被删除，通常连同这次运行记录一并删除。在这些仓库中，工作流可访问的每项机密和云角色都应视为已泄露。

该公司自己的 GitHub 搜索于周三结束后，The Hacker News 检查发现，今天早些时候又发起了更多标题相同的拉取请求。经检查的三个请求于 05:04 至 05:38 UTC 之间发起，均来自 wfx-docs 分支。尚不清楚窃取器是否随之进入。

Aikido 在其技术分析中表示，任何发起过攻击者测试拉取请求的账户都已泄露，即使窃取器从未运行。该分析未说明攻击者是如何获得这些凭据的。

SafeDep 的研究人员建议受影响仓库的所有者撤销提交作者持有的令牌、OAuth 应用授权、SSH 密钥和会话，并启用 2FA。所有者还应轮换仓库能够读取的每项机密和变量。任何在受影响提交上运行过 npm install 的人都应将该计算机视为已泄露，并轮换其密钥。

在大多数接收过测试的其他仓库中，之后没有推送任何内容，或者由于仓库设置或账户权限，窃取器未能运行。这些数字仅涵盖该公司能够看到的公共仓库。

这些测试还触及了受损账户并不拥有的仓库。在测试拉取请求中，有 10,431 个是通过协作者或组织访问权限提交的，据该公司检查时，其中 92% 仍处于开启状态。

仓库遭受攻击的迹象

从周二开始，检查你有权写入的任何仓库是否存在以下迹象：

  • 分支： wfx-docs
  • 分支： chore/[a-z0-9]{8}，短生命周期
  • 分支： ci-check-[0-9]{4}
  • 拉取请求标题： docs: dependency audit notes
  • 提交消息： ci: refresh build cache，向现有工作流添加了约 1,500 行
  • 提交消息： chore: add ci helper，在 package.json 中添加了一个 .ci-xxxxxx.sh 脚本和一个用于在任意 npm install 时运行该脚本的 postinstall 钩子
  • 提交消息： chore: add dependency audit workflow，在 chore/ 分支上添加了 .github/workflows/build-audit-xxxxxx.yml
  • 提交信息：chore: initial commit，在空仓库中新建工作流文件之前推送
  • 提交信息：ci: restore
  • 提交信息：ci: cleanup
  • SHA-256（窃密脚本）：89695abb392d5cfd4972672961e644bb46baa98aa1ed7173c2a2816c762735cf
  • IP：194.150.166[.]244:8080/exfil
  • IP：18.143.168[.]96:8080/exfil
  • IP：153.75.82[.]159:8080

即使仓库中没有任何 wfx-loot 构件、wfx- cache条目或 WFX-BEGIN步骤摘要，也可能已经发生数据丢失。攻击者提交记录中缺少运行编号，是窃密程序已经运行过的更可靠迹象。

SafeDep 研究人员发现，该窃密程序通过 HTTP POST 将数据发送至上述地址或某个 Telegram 聊天。在抽样的 200 个载荷提交中，约五分之一仅使用 Telegram。

据该公司称，该窃密程序旨在收集运行器上所有来源的凭据。其中包括 GitHub Actions 的 secrets 和 variables、工作流的 GITHUB_TOKEN、OIDC 和 Actions 运行时令牌、AI 服务密钥，以及运行器自身进程内存中的 secrets。它会从通常位置读取 AWS、Azure、GCP、Kubernetes、npm、PyPI、SSH 和其他工具的凭据文件。

它还会复制仓库、最近 100 次提交和近期工作流构件。在自托管运行器上，它还会从实例元数据中获取云凭据，以及 Docker 容器状态和 systemd 单元。

该窃密程序还具有针对私有仓库的设置，该公司表示，这表明它可能正在私有仓库中运行。

该窃密程序被设计为利用这些凭据进一步侵入云账户。它会将 GitHub OIDC 令牌交换为 AWS、GCP 和 Azure 会话；在 AWS 上，它可以为 IAM 用户创建长期访问密钥。

它的一些步骤旨在经受住凭据轮换。它可以重写 AWS 角色的信任策略，使该角色向任何 AWS 账户开放。

它还可以向 Azure AD 应用程序添加带有 wfx-ci- 前缀的联合身份凭据。这样一来，即使所有令牌都已轮换，已入侵仓库中的工作流仍可在不存储 secret 的情况下登录 Azure。

研究人员建议检查以下项目，以发现这些后门：

  • Entra ID：名称为 wfx-ci-* 且并非由你创建的联合身份凭据
  • AWS CloudTrail：名为 wfx-* 的 AssumeRoleWithWebIdentity 或 AssumeRole 会话，随后出现 CreateAccessKey 或 UpdateAssumeRolePolicy
  • GCP：来自你的 GitHub 工作负载身份池的 GenerateAccessToken 和 SignJwt 调用
  • Vault：来自 GitHub OIDC 颁发者的 JWT 登录

该窃密程序通过自动发布触发器，至少触及了一个 Packagist 软件包和一个 Go 模块。至少 50 名受影响的用户似乎会为 npm、Go、Packagist、PyPI 或 crates 发布软件包。

该公司表示，攻击者似乎意在窃取 CI secrets，而非试图通过软件包传播。

Packagist 软件包 digitalelvis/neuronai-studio 的 3.14.3 版本具有恶意性，该公司建议将任何安装或打开过该版本的计算机视为已遭入侵。其软件包列表显示，该版本于星期三发布。今天早些时候，该版本仍列于页面中，但附有一则通知，称该软件包的各版本已被标记为恶意软件。

研究人员发现，正常的 composer install 不会运行该窃密程序，但在这个软件包的 vendor 目录中运行 npm install 会运行它。用户应屏蔽 v3.14.3，并固定使用 v3.14.2 或更早版本。

Go 模块 github.com/onuragtas/docker-env 的两个版本 v1.0.278 和 v1.0.280 仅在一个 GitHub Actions 工作流文件中包含该窃取程序。Go 代码和发布二进制文件均未更改，而且 Go 构建不会运行工作流文件，因此该模块的用户可能未受影响。该公司仍建议移除这些版本。

研究人员还在另一个 Go 模块 github.com/vkuznet/gocurl 中发现了该窃取程序，位于伪版本 v0.0.0-20261111095532-8d5aad0cb0da 内的一个从未运行过的工作流中。用户应屏蔽该伪版本。

该窃取程序还通过以机器人账户 wdio-bot 身份提交的提交，入侵了 28 个 WebdriverIO 仓库。没有任何软件包发布受到影响，但应将该机器人的令牌视为已被窃取。

该公司发现，本周使用的账户与 GhostAction 10 月攻击潮中遭攻击的账户存在重叠；在那次攻击中，被盗的 GitHub 账户将窃取机密信息的工作流推送到了仓库中。

10 月遭攻击的账户本周被使用的可能性约为其他活跃账户的 1,000 倍。在 100 多个仓库中，新的窃取程序被添加到 10 月的工作流文件中，同时保留了原先用于外传数据的旧步骤。

Aikido 表示，“现阶段我们不将 11 月的攻击归因于同一行为体”，因为其基础设施、工具和方法均有所不同，而且被盗凭据往往会落入多个攻击者手中。

更正（2026 年 11 月 12 日）：本文早期版本称，该窃取程序仅通过 HTTP POST 将数据发送到两个地址，并且攻击者会在一分钟内撤销每项更改。第二次分析发现了第三个服务器、一个 Telegram 频道，以及保留时间更长的更改。
