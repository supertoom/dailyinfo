Barracuda 是什么，我们为什么非谈不可？

Barracuda 的电子邮件安全网关解决方案（ESG）可谓备受青睐，原因有几个：

  • 对许多人来说，它就是部署在组织邮件系统前端的设备，用来决定哪些邮件是垃圾邮件、哪些邮件携带恶意软件，以及哪些邮件可以放行。
  • 对另一些人来说，它还是在 UNC4841（据 Mandiant）利用 CVE-2023-2868 作为零日漏洞后，需要进行物理更换的设备。

无论你是谁，有一点在你的使用体验中始终不变：它又是一台位于边缘、检查所有内容，并以恰到好处且唯一的权限运行以拦截有关你博客文章的恶意邮件的设备。

好吧，但 CVE-2026-116606 和 CVE-2026-111560 是什么？

一如既往，CVE 编号总有一种出人意料的吸引力——这两个也不例外，正如 Barracuda 自己的公告所示，摘要如下：

CVE 漏洞 CVSS 受影响产品 修复版本
CVE-2026-116606 预身份验证授权绕过（编辑：lol？） 9.3 严重 Barracuda ESG 9.4.0.029
CVE-2026-111560 操作系统命令注入 8.6 高危 ESG、Load Balancer ADC、Message Archiver、WAF Control Center、Web Application Firewall、Web Security Gateway 9.4.0.029

单独来看，你完全可以以相当英式的方式形容其中任何一个为“不理想”。但情况如果串联起来会更糟——如果你很英式，就会把它们形容为“还行”。真是尖锐。

那么，毫不意外，这些漏洞正是今天这篇 watchTowr Labs 博客文章的主题——所以，我们去喝杯咖啡，然后散散步吧。

场景设定

为支持今天的分析，我们搭建了设备，并使用我们惯常的“到底改了什么”流程比较了两个版本：

  • 存在漏洞的版本：Barracuda ESG 9.4.0.027
  • 不同版本：Barracuda ESG 9.4.0.029

作为背景，在逐步介绍本文内容之前，需要指出的是，Barracuda 发布了多个补丁文件，用于修复 CVE-2026-111560 和 CVE-2026-116606。不过，我们只审查了其中两个，具体称为：

  • Patch-1（用于修复 CVE-2026-116606“预身份验证授权绕过”）
  • Patch-2（用于修复 CVE-2026-111560 操作系统命令注入）

没有什么比因漏洞而对机架式服务器进行实体“驱魔”更能让我们感到暖意了（是的，我们知道事情没这么简单）。

让我们将其拆解分析：

  • 当密码更改成功时（第 387 行），它在第 396 行以 return bailout(); 结束，而 bailout() 是“我们已经完成，在此停止请求”的信号。
  • 当它以 ERROR_PASSWD_CHANGE 失败时（第 399 行），则改为在第 406 行以 return $userrole; 结束。

这为什么重要？因为上述密码更改代码位于 _process_params内部，而调用它的方法是 response：

对 Backup2.pm 进行差异比较

简要分析后，Backup2.pm 中唯一看似有意义的更改是对这段补丁前代码块所作的修改：

if( -f "/home/product/code/config/tz" ) {
    my $system_timezone = Barracuda::Config::get('system_timezone');
    `sed -i 's#TZ=.*#TZ=$system_timezone#' /home/product/code/config/tz`;
}

当我们将视线转向补丁版本并查看其中的变化时，就能更清楚地了解这个问题。总体而言，Barracuda 将 shell 命令执行替换成了……一种更安全的方法：

 if( -f "/home/product/code/config/tz" ) {
     my $system_timezone = Barracuda::Config::get('system_timezone');
-    `sed -i 's#TZ=.*#TZ=$system_timezone#' /home/product/code/config/tz`;
+    if ($system_timezone && -f "/usr/share/zoneinfo/$system_timezone") {
+        open my $in, '<', '/home/product/code/config/tz' or die $!;
+        my @lines = <$in>;
+        close $in;
+        open my $out, '>', '/home/product/code/config/tz' or die $!;
+        for my $line (@lines) {
+            $line =~ s/^TZ=.*/TZ=$system_timezone/ if $line =~ /^TZ=/;
+            print $out $line;
+        }
+        close $out;
+    } else {
+        warn "Skipping tz restore: invalid system_timezone='$system_timezone'\n";
+    }

总结一下，这主要带来了三点：

  • 第一，厂商现在认为 system_timezone 足够不可信，因此要求在使用前必须将其解析为位于 /usr/share/zoneinfo/ 下的真实文件。
  • 其次，旧代码跨越了 shell 边界。Perl 反引号表示命令替换，因此 Perl 会构造一个字符串并将其交给 shell。单引号包裹该值看起来能提供保护，但它们只是生成的命令中的字符，并非 Perl 层面的安全边界。

形如以下内容的值会重写 shell 语法：

Region#';<attacker-command>;#

第一个引号会闭合预期的 sed 表达式，分号会启动一条新命令，而 # 会将其余内容注释掉。

  • 最后（也正是让我们警觉起来的部分），函数名称（finalize_restore）提供了一个相当明显的线索，说明我们或许可以利用这个漏洞。finalize_restore。

对 fix_tz.pl 进行差异比较

补丁差异比较中突出显示的第二个文件是 fix_tz.pl，它讲述了一个与命令注入有关的类似问题，具体与时区设置相关。

简而言之，我们发现了两个落地点：一个在 Backup2.pm 中，另一个在 fix_tz.pl 中。

实际上，Backup2::finalize_restore 会写入产品时区文件，而 fix_tz.pl 会写入操作系统时钟文件——并且，同一个看似可由攻击者控制和操纵的输入会到达两者。

“权限受限的用户无法写入此文件”——确实如此，但我们讨论的是安全设备。情况不同——这也正是上述代码使用 sudo 执行 fix_tz.pl 文件的原因。

if( -f "/home/product/code/firmware/current/bin/fix_tz.pl" ) {
    system('/usr/bin/sudo',
           '/home/product/code/firmware/current/bin/fix_tz.pl');
}

这不只是一个普通的操作系统命令注入漏洞，而是一个以 root 权限执行的漏洞。

从备份恢复到命令执行

当然，事情没这么简单，我们的第一个问题是：“好吧，那么备份文件实际上是什么样的？”

幸运的是，在这种情况下，备份是一个 tar 文件，其中包含一个列出各种详细信息的 backup.xml 文件。下面是我们构建的一个示例结构：

你可能从之前的补丁评论中认出了 Spam_Config。这是我们的线索，而且它作为 backup.xml 文件的一部分存在。

当设备恢复 Spam_Config 时，它会加载一个小型 MySQL 转储，并将定义的信息恢复到本地 MySQL 数据库中。

真是幸运，其中一行正是 system_timezone。你看出接下来要做什么了吗？

如果我们在 system_timezone 这一行的值末尾附加一条 shell 命令，然后恢复该值，会怎样：

打包备份

那么看起来很简单。我们只需在 XML 文件中放入一些 SQL 查询，将其打包成 tar 文件，然后恢复它。

但不行，生活要惩罚我们。

关于那个校验和

backup.xml 中列出的每个文件都有一个 checksum，恢复函数会认真校验该校验和……它会读取文件字节，计算自身的校验和，并在校验和不匹配时拒绝备份。因此，我们平时在这些字段中随便输入数字的方法在这里行不通。

但这里还有一件有趣的事。这个校验和的构建方式如下：

校验和就是 md5(file_bytes + secret + ".")。
