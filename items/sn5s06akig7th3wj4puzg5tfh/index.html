当你的 ps 列表干干净净、lsof 一无所获时，恶意进程可能仍在正常运行。Aqua Nautilus 的最新研究揭示了这样一个组件：它不靠删除数据来隐身，而是篡改“呈现给工具的数据”，让进程、文件、套接字从常规视图里“消失”。它同时出现在两起独立的供应链攻击事件中——npm 平台的 IronWorm 与 Arch AUR 的 Atomic Arch。

01 两条投递链，同一个内核组件

2026 年 6 月，开源软件供应链接连爆出两起大规模事件，攻击对象不同，技术路线却殊途同归：

  • IronWorm（JFrog 命名）：攻击者盗用 Arweave/WeaveDB 生态维护者 ocrybit 的凭据，通过被攻陷的 npm 账号 asteroiddao 重新发布了数十个包（典型样本 weavedb-sdk@0.45.3），利用 preinstall 钩子在依赖解析前直接执行一个 976KB 的 Rust 编写的 Linux ELF。JFrog 将其称为 Shai-Hulud 蠕虫“更锈的表亲”（rustier cousin）。
  • Atomic Arch（Sonatype 命名）：攻击者批量“收养”AUR 中被遗弃（orphaned）的软件包，篡改其 PKGBUILD，在安装阶段植入 npm install atomic-lockfile 一类的指令，借恶意 npm 包投递 Rust 编写的窃密载荷，波及上千个包。

两个事件表面上是 npm 与 AUR 两个生态、两套运营动作。Aqua Nautilus 在 11 月 17 日发布的研究中发现：两者投递的载荷中嵌入了同一个 eBPF Rootkit 组件，研究人员将其命名为 GhostMap。

组件共享的证据相当扎实：两份载荷中的 Rootkit 在记录执行数据后对比，共享 13 个 eBPF 程序名、10 个 map 名，全部 13 个程序的 helper 使用位图完全一致；外围植入体还表现出几乎一致的安装与服务行为，包括一个逐字节相同的 1,142 字节伪造 sudo 封装脚本，以及同样监听在回环地址 8738 端口上的本地收集器。

需要说明的是：这证实的是 Rootkit 组件本身的复用，而不等同于两起事件由同一运营方操纵。换言之，这是一个跨投递渠道复用的“隐身工具箱”。

02 GhostMap 如何落地：从安装钩到内核

GhostMap 不是独立传播的恶意软件，它是 IronWorm 这一更大植入体的一个功能组件：植入体负责安装、持久化与数据收集，Rootkit 负责隐匿与反调试。其落地链条如下：

1. 投递与初始执行。 在 npm 渠道，weavedb-sdk@0.45.3 的 package.json 声明了 preinstall: ./tools/setup，在安装依赖解析之前即触发二进制。该包的 npm 页面随后被标记为 deprecated，作者留言称“经由 Mini Shai-Hulud 蠕虫（TeamPCP）被攻陷，请升级到最新版本”——这是包作者在弃用警告中的归属表述，攻击者实际身份并无独立证据。

图2｜npm 弃用警告截图（记录弃用状态而非下架）

图源：Aqua Nautilus

在 AUR 渠道，被修改的 PKGBUILD 通过安装钩子拉起 atomic-lockfile 内嵌的 Linux 载荷。

2. 建立持久化。 实验环境中以 root 权限运行样本后，安装程序列举所有用户的 crontab，将自身复制到 /var/lib/<rand>/<rand>（观测到的实例包括 /var/lib/glugi/glugi、/var/lib/havebi/havebi，均为可变命名而非固定路径），创建并启用一个 Restart=always 的 systemd 服务（名称伪装成 dbus-daemon 一类），并向 ~/.local/bin/sudo 投放伪造的 sudo 封装。

3. 由服务加载 Rootkit。 关键细节在这里：systemd 启动的服务进程与原始安装程序文件哈希相同，但真正加载 eBPF 组件的是这个继任进程——如果只监控安装程序的直接子进程，就会漏掉真正的加载者。活动检查点上，GhostMap 由 13 个 eBPF 程序、10 个 map、13 个 link 构成。其中几个核心 map 直接说明了其工作方式：

03 进程隐匿：只改一个字节，让 ls 和 ps 集体失明

这是最精巧、也最能体现 GhostMap 设计思路的部分。

图4｜GhostMap 进程隐匿全流程与实验观测事实

图源：根据 Aqua Nautilus 研究数据绘制

Linux 通过 /proc 虚拟文件系统暴露进程信息，ps、ls 这类工具依赖 getdents64 系统调用读取目录条目。每个返回的记录带一个长度字段 d_reclen，告诉读取方“下一条记录在什么位置”。

GhostMap 挂接了两处钩子：enter_getdents 在进入时记下缓冲区地址，exit_getdents64 在系统调用返回时检查缓冲区里的数字名记录是否命中 hidden_pids。命中之后，它使用 bpf_probe_write_user helper 增大前一条记录的 d_reclen，让读取方的指针直接“跨过去”。

Aqua 的受控实验把欺骗过程量化了。在 11 月 10 日的一组对照实验中，研究者捕获了同一个目录缓冲区在 Rootkit 钩子处理前后的两份副本：

  • 受控目录里，前一条记录长度从 32 字节变为 56 字节；
  • 在 /proc 下，记录长度从 24 字节变为 72 字节，读取方一次跳过了恶意进程和测试进程两条记录；
  • 全部 6 次复现中，每个缓冲区只改动了一个字节——长度字段两字节的低字节；
  • 被隐藏记录的字节仍留在缓冲区里，系统调用返回的字节数也没有变化。

图5｜单字节篡改的实验测量数据

图源：Aqua Nautilus 

两个对防御至关重要的推论由此而来：

  1. “看不见”不等于“不存在”。实验中进入隐藏名单的进程从枚举结果里消失，但通过已知的 /proc/<PID> 路径仍可正常访问；Rootkit 停止后，这些进程重新出现在列表中。用 ps aux | grep 查不到目标，绝不能当作进程不存在的证据。
  2. 隐藏按“执行”而非“继承”生效。fork 出的子进程即使继承了同样的进程名也不会被隐藏；只有 exec 加载了匹配 comm 名的程序才会进入 hidden_pids。因此“父进程在 ps 里失踪、子进程却可见”可以作为一个有价值的排查线索，但它本身不构成 Rootkit 活动的证据。

04 网络隐匿：两套视图，一个对不上账

Linux 通过不止一种接口暴露套接字信息：/proc/net/tcp 是文本列表，而 Netlink 套接字诊断消息则以结构化形式供 ss 等工具解析。GhostMap 对两条路都做了手脚，但效果并不对称。

图6｜同一隐藏名单下两套读取视图的不同结局

图源：根据 Aqua Nautilus 研究数据绘制

在专门的监听器实验中，被隐藏的回环监听端口 8738 对应的 inode 进入 hidden_inodes：

  • /proc/net/tcp 侧完全得手：三次观测中该监听端口全部从文本列表消失，对照端口 8739 始终可见；
  • Netlink 侧露了马脚：GhostMap 把该套接字诊断消息的类型改成了 NLMSG_NOOP（无操作消息），但端口、标识和监听状态仍原样保留在消息负载里。受测的 ss 工具（iproute2 6.1.0-1ubuntu6.4）三次查询依然完整显示了该监听端口，只是丢了进程属主标注。上游源码可以解释这一点：ss 的解析路径即使收到改类型的消息，也能从保留的负载里读出套接字信息。

图7｜套接字隐匿双视图的对照实验数据

图源：Aqua Nautilus 

这组结果应当这样理解：Rootkit 的隐藏代码确实执行了，但在 ss 这个读取方上失效了。结论针对的是受测的 ss 版本，其他消费 Netlink 消息的工具可能有不同表现。实践含义很直接：不要依赖单一来源的套接字清单，互相印证不同接口的视图，缺失与差异本身就是信号。

05 反调试与本地收集

GhostMap 的第三个职能是干扰分析。受控测试中对受保护进程发起 PTRACE_ATTACH，附加操作的任务被以 SIGKILL 终止——这意味着用 gdb、strace 做常规调试的分析师，工具本身会先被杀掉。

与此同时，IronWorm 的本地收集器监听 127.0.0.1:8738，接收本机提交的文本记录。研究者用合成数据验证：7 条被接收的记录经 setxattr 系统调用被写入已安装可执行文件的一个扩展属性 user.d，读写回验精确匹配；静态分析显示这些数据与对外 C2 消息的构造相关联。（Atomic Arch 渠道的对比载荷还多出一个 19051 端口的回环监听点。）值得强调的是，实验确认了本地收集与存储，未观测到成功的外发投递或经认证的远程命令执行——GhostMap 负责隐藏活动，它并不实现收集器的输入解析或 C2 命令逻辑。

06 欺骗失效的地方：Tracee 的检测证据

以上所有实验里，Aqua 的开源运行时安全工具Tracee在 IronWorm 启动之前就已驻留监控。结果是：Rootkit 在用户态视图上做得再干净，没能逃过内核侧的原始遥测。

图8｜隐匿生效期间的运行时检测链路

图源：根据 Aqua Nautilus 研究数据绘制

GhostMap 的程序向内核挂载时，Tracee 立即告警，识别出三个携带内存写入能力的程序——exit_getdents、net_exit_read、exit_recvmsg，恰好对应目录隐匿与网络隐匿路径，告警均报告其使用了 bpf_probe_write_user helper。

图9｜Tracee 挂载时告警原始记录

图源：Aqua Nautilus 

在整个隐匿生效期间，48 次受测的目录读取调用全部被 Tracee 完整保留，研究者随后用独立的测量手段确定了被跳过的记录和被改动的字节。

这组实验回答了两个互补的问题：运行时遥测告诉你“什么可疑代码上线了”，缓冲区测量告诉你“它随后隐藏了什么”。Rootkit 能操纵的是工具看到的结果，而不是行为本身——这就是运行时安全的价值所在。

需要说明：该实验展示的是检测而非阻断；bpf_probe_write_user 这个能力本身也不等于恶意，仍需结合属主、挂载时机和观测行为综合研判。

07 给防守方的建议

  1. 不要把空搜索结果当作排除证据。对可疑 PID，对比枚举结果、/proc/<PID> 直接访问与历史执行遥测，交叉核对可执行文件身份、服务配置与 BPF 属主。
  2. 排查异常的 BPF 挂载。具备用户态内存写入能力的 eBPF 程序值得重点调查，可用 bpftool 审视系统上程序、map、link 及其属主。
  3. 比对多个独立的套接字视图。/proc/net/tcp 与 Netlink 诊断工具（如 ss）结果不一致时，差异本身即是线索。
  4. 取证时保留的不只是文件内容。收集样本时连同扩展属性等元数据一并保存，只拷贝普通文件字节会漏掉存放在 user.d 中的本地记录。
  5. 谨慎对待交互式调试。对受保护进程贸然附加调试器可能触发反制（附加任务被 SIGKILL），事先规划好采集顺序，先固定证据再处置。
  6. 核查安装与服务链路。对安装过相关恶意包的系统，回溯安装日志与 systemd 服务活动；移除服务或卸载 eBPF 程序之前先保全证据。
