AWS Sign-In 通过 EMA 和 ID-JAG 强化 AI Agent 对 AWS MCP Server 的访问授权

Secure agentic access to AWS with Enterprise-Managed Authorization

AI 导读

AWS Sign-In 新增 Enterprise-Managed Authorization（EMA），利用 Identity Assertion JWT Authorization Grant（ID-JAG），让组织通过现有企业 IdP（如 Okta）集中授权 AI 应用访问 AWS MCP Server。

正文 · 原文

AWS Sign-In is introducing support for Enterprise-Managed Authorization (EMA) using the Identity Assertion JWT Authorization Grant (ID-JAG), enabling organizations to securely authorize AI agents to access AWS MCP Server through their existing enterprise identity providers (IdPs), such as Okta. With this capability, organizations can centrally manage which applications can access Amazon Web Services (AWS) resources on behalf of their employees, without requiring users to manage additional long-term credentials or complete separate consent flows.

In our previous blog post, Introducing OAuth Support for AWS MCP Server, we introduced OAuth-based authorization, enabling AI agents to securely access AWS MCP Server through interactive sign-in or programmatic authentication using AWS credentials. EMA builds on these capabilities by enabling organizations to authorize AI agents through their existing enterprise IdPs. Because authentication to an AI application doesn’t automatically grant access to AWS resources, EMA provides a way to authorize access across these separate trust domains while maintaining existing AWS Identity and Access Management (IAM) permissions.

In this post, we explain how EMA and ID-JAG work with AWS Sign-In, discuss security best practices, and walk you through configuring Okta to authorize AI agents to access AWS MCP Server.

How Enterprise-Managed Authorization works with AWS Sign-In

Enterprise-Managed Authorization (EMA) is an extension of the Model Context Protocol (MCP) that enables organizations to centrally manage how AI applications access protected resources on behalf of employees. EMA uses the Identity Assertion JWT Authorization Grant (ID-JAG), an OAuth-based authorization grant that enables enterprise IdPs to authorize access across different trust domains. Rather than requiring employees to individually authorize each MCP server, administrators can define policies in their existing IdP to control which AI applications can access specific resources.

When an employee signs in to an AI application such as Claude using their enterprise IdP, the authentication establishes their identity within Claude but doesn’t automatically grant access to AWS resources. When the AI application requests access to an MCP server, the enterprise IdP evaluates its configured access policies and issues a short-lived, signed ID-JAG assertion for the intended resource. The AI application then exchanges this assertion with the authorization server configured for the MCP server to obtain an OAuth access token, without requiring the employee to complete an additional interactive authorization flow.

For AWS MCP Server, AWS Sign-In serves as the configured OAuth authorization server. The AI application presents the ID-JAG assertion to the AWS Sign-In OAuth token endpoint. As part of the authorization process, AWS validates the assertion against the trusted IdP and uses AWS Security Token Service (AWS STS) to evaluate the IAM role’s trust policy and establish the authorized role session. AWS Sign-In then issues an OAuth access token associated with the IAM role. IAM policies attached to the role determine which AWS operations the agent can perform, allowing organizations to manage agent authorization through their enterprise IdP while enforcing existing AWS permissions.

Figure 1 illustrates how an AI application, such as Claude, uses EMA with Okta and AWS Sign-In to obtain an OAuth access token and securely access AWS MCP Server using IAM role-based permissions.

Figure 1: Enterprise-Managed Authorization flow using Okta, AWS Sign-In, and AWS MCP Server

The authorization flow consists of the following steps, as illustrated in Figure 1:

  1. Employee authentication: The employee signs in to the AI application, such as Claude, using their enterprise IdP, such as Okta, through single sign-on (SSO).
  2. ID-JAG request: When the AI application needs to access AWS MCP Server, it requests an ID-JAG from Okta for the intended resource.
  3. Enterprise authorization: Okta evaluates the configured access policies to determine whether the employee and AI application are authorized to access AWS MCP Server. If authorized, Okta issues a short-lived, signed ID-JAG assertion.
  4. Token exchange with AWS Sign-In: The AI application sends the ID-JAG to the AWS Sign-In OAuth token endpoint. AWS Sign-In validates the assertion, including its issuer, signature, audience/tenant, expiration, and intended resource, and verifies the associated IAM role authorization before issuing an OAuth access token.
  5. Access AWS MCP Server: The AI application presents the AWS-issued OAuth access token to AWS MCP Server. The server validates the token, and access to AWS resources is governed by the permissions associated with the IAM role.

Configure Enterprise-Managed Authorization using Okta and AWS Sign-In

In this section, we walk you through configuring Enterprise-Managed Authorization (EMA) to enable an AI application, such as Claude, to securely access AWS MCP Server using an enterprise identity managed in Okta.

The configuration establishes trust between Okta and AWS, defines IAM permissions for accessing AWS resources, and configures enterprise authorization policies that govern AI application access. This walkthrough uses AWS MCP Server in the US West (Oregon) AWS Region (us-west-2).

Prerequisites

Before you begin, make sure you have the following:

  • An AWS account with permissions to configure IAM IdPs, roles, and policies.
  • An Okta organization with administrative permissions to manage applications and configure Cross-App Access policies.
  • An AI application, such as Claude, that supports EMA and ID-JAG.
  • Access to AWS MCP Server with support for OAuth-based Enterprise-Managed Authorization.
  • The AWS Region where you will configure the integration.

Step 0: Configure the AI application in Okta

Configure an application in Okta so that employees can sign in to the AI application through enterprise single sign-on (SSO). For this walkthrough, we use Claude as the AI application. If your organization already uses Claude with Okta SSO, you can use the existing application. This application is the requesting application when you configure Cross-App Access in Step 3.

  1. Create the Claude SSO application: In the Okta Admin Console, go to Applications, choose Create App Integration, and create an OIDC web application, for example Claude SSO, as shown in Figure 2.
    • If your agent was imported through an Okta AI Agent Provider, create the OIDC application by going to Directory, AI Agents, then navigating to User access from the selected agent.
  2. Choose the grant types: Select Authorization Code and Refresh Token. Claude uses the refresh token to request new ID-JAG assertions without asking employees to sign in again.
  3. Add the redirect URI: Set Sign-in redirect URIs to Claude’s SSO callback URL.
  4. Assign employees: Under Assignments, select which employees or groups can access the application.
  5. Confirm SSO works: Check that employees can sign in to Claude through Okta before you continue.

Figure 2: Creating the Claude SSO app integration in Okta

Step 1: Configure Okta as an OIDC IdP in IAM

Create an OpenID Connect (OIDC) IdP so that AWS trusts the ID-JAG assertions that Okta issues, as shown in Figure 3.

  1. Add the IdP: In the AWS Management Console for IAM, go to Identity providers, choose Add provider, and select OpenID Connect.
  2. Enter the provider URL: For Provider URL, enter your Okta org URL, for example https://integrator-1234567.okta.com. Okta issues ID-JAG assertions from the org authorization server, not from a custom authorization server.
  3. Enter the audience: For Audience, enter the AWS Sign-In authorization server for your Region, for example https://us-west-2.oauth.signin.aws, and choose Add provider.

Figure 3: Adding Okta as an OpenID Connect identity provider in IAM

Step 2: Create an IAM role and configure permissions

Create an IAM role that defines the AWS permissions granted to the AI application, as shown in Figure 4.

  1. Create the role: In the IAM console, go to Roles, choose Create role, and select Web identity as the trusted entity type. Choose the Okta IdP from Step 1 and its audience. This creates a trust policy that allows access only through assertions from that provider.
  2. Attach the AWS MCP Server permissions: Attach the AWS managed policy AWSMCPSignInOAuthAccessPolicy. It grants the signin:CreateOAuth2Token permission required for OAuth access to AWS MCP Server.
  3. Attach the AWS permissions the AI application needs: Attach other IAM policies that grant only the AWS permissions required by the AI application. For this walkthrough, we use a read-only role.
  4. Name and create the role: Enter a role name, for example OktaAwsMcpReadOnly, and choose Create role.
  5. Copy the role ARN: You’ll enter the role Amazon Resource Name (ARN) as the Audience/tenant ID in Okta in Step 3.

Figure 4: Reviewing the IAM role and its trust policy

Step 3: Configure Cross-App Access in Okta

In the Okta Admin Console, create a resource application that represents AWS MCP Server, and then connect Claude to it. The Claude SSO App from Step 0 stays the requesting application, so you don’t enable Cross-App Access on it.

  1. Create the AWS MCP resource application: Go to Applications, choose Create App Integration, and create an OIDC web application, for example AWS MCP (us-west-2). Okta doesn’t use this application’s sign-in redirect URI, so you can keep the default value.

    Figure 5: Creating the AWS MCP resource application in Okta

  2. Enable Cross-App Access on the resource application: On the Machine Assignments tab, edit the access method and enable Cross-App Access. Set Issuer URL to https://us-west-2.oauth.signin.aws and set Audience/tenant ID to the IAM role ARN from Step 2.

    Figure 6: Enabling Cross-App Access on the AWS MCP resource application

  3. Assign employees: On the Assignments tab, assign the employees or groups who can access AWS MCP Server through Claude.
  4. Register Claude as an AI agent: Go to Directory, AI Agents, and choose Register AI agent. Under User access, choose Select an existing app and pick the Claude SSO App from Step 0.
    • Skip this step if the agent was already imported via an Okta AI Agent Provider.
  5. Connect the AI agent to AWS MCP Server: On the AI agent page, add a resource connection with the Application resource type. Set Application instance to the AWS MCP resource application. Set the client ID registered in AWS MCP to the client ID that you configure in Claude in Step 4, for example anthropic-claude. Set Resource identifier to https://aws-mcp.us-west-2.api.aws/mcp.

    Figure 7: Connecting the Claude AI agent to the AWS MCP resource application

When Claude requests access, Okta checks that the employee is assigned access and issues an ID-JAG for AWS Sign-In that carries the IAM role ARN. AWS Sign-In validates the assertion and issues an OAuth access token associated with the IAM role.

Step 4: Configure Claude to access AWS MCP Server

  1. Add a custom connector: In Claude, open Admin settings, choose Connectors, and then choose Add, Custom connector. Enter a name and the AWS MCP Server endpoint, for example https://aws-mcp.us-west-2.api.aws/mcp.
  2. Configure OAuth authentication: For Authentication, choose Sign in when needed. For OAuth client, choose Use your own OAuth client, enter the client ID from the resource connection in Step 3 and leave the client secret blank.

    Figure 8: Adding AWS MCP Server as a custom connector in Claude

  3. Set up managed authorization: Open the connector, and on the Configuration tab, choose Set up next to Managed authorization.

    Figure 9: The connector’s Configuration tab

  4. Configure IdP-managed access: Choose IdP-managed as the identity source and confirm that the connection checks pass. Then choose Continue, select the Claude roles that connect through managed authorization, and choose Save.

    Figure 10: Setting up managed authorization with Okta as the identity source

When an employee accesses AWS MCP Server, Claude requests an ID-JAG assertion from Okta. Following successful policy evaluation, Okta issues the assertion, which Claude exchanges at the AWS Sign-In OAuth token endpoint for an OAuth access token associated with the configured IAM role. Claude uses this token to access AWS MCP Server without requiring an additional AWS sign-in.

Step 5: Validate access to AWS MCP Server

To validate the configuration:

  1. Sign in using enterprise SSO: Sign in to the AI application using your Okta identity.

    Figure 11: Signing in to Claude with SSO

  2. Connect to AWS MCP Server: Connect the AI application to AWS MCP Server.
  3. Verify OAuth token issuance: Confirm that Claude successfully connects to AWS MCP Server without requiring a separate AWS authorization flow. You can verify successful OAuth token issuance using AWS CloudTrail, as described in Step 6.
  4. Validate authorized access: Perform an AWS operation permitted by the configured IAM role.

    Figure 12: Calling AWS MCP Server from Claude Code

  5. Verify access restrictions: Attempt an operation outside the IAM role’s permissions and confirm that access is denied.

You can also validate enterprise authorization policies by attempting access using an employee who is not authorized in Okta and verifying that the ID-JAG request is denied.

Step 6: Verify authorization activity using AWS CloudTrail

AWS Sign-In and AWS MCP Server integrate with AWS CloudTrail to help organizations monitor OAuth authorization activity and API requests made by AI applications. CloudTrail provides visibility into token issuance, the applications requesting access, and operations performed through AWS MCP Server.

After successfully connecting your AI application to AWS MCP Server, you can verify the authorization activity in CloudTrail:

  1. Open the CloudTrail console and navigate to Event history.
  2. Select the AWS Region used for the integration.
  3. Filter events by Event source signin.amazonaws.com or Event name CreateOAuth2Token to locate OAuth token issuance activity.
  4. Review the event details, including the OAuth client identifier, target resource, authorization grant type, and token issuance status, where recorded.
  5. To review subsequent MCP activity, examine events from aws-mcp.amazonaws.com with the same session ARN and verify that the operations performed by the AI application match the permissions configured for the IAM role. Calls to global services such as IAM are recorded in US East (N. Virginia).

Best practices for securing AI agent access with EMA and AWS IAM

When configuring Enterprise-Managed Authorization (EMA), consider the following security recommendations to help protect AI agent access to AWS resources:

  • Use short-lived ID-JAG assertions: Configure your enterprise IdP to issue ID-JAG assertions with short expiration periods. This limits the time during which an assertion can be exchanged for an OAuth access token and reduces the risk associated with token exposure.
  • Use tenant-specific IdP issuers: In multi-tenant environments, configure tenant-specific issuer URLs to establish explicit trust relationships between AWS and the intended enterprise IdP. This helps prevent assertions issued for one tenant from being accepted in another tenant’s authorization context.
  • Restrict OAuth authorization using IAM condition keys: Use IAM condition keys to limit OAuth token issuance to approved AI applications, authorization flows, and AWS resources. For example, use signin:OAuthClientId to restrict access to approved AI applications, such as arn:aws:signin:::external-client/jwt-bearer/anthropic-claude and signin:OAuthGrantType to restrict the permitted grant type to urn:ietf:params:oauth:grant-type:jwt-bearer. Scope these permissions to the AWS MCP Server service principal to prevent unintended access to other AWS services.
  • Apply least-privilege IAM permissions: Grant the IAM role only the permissions required by the AI application. Use managed policies to control which AWS operations the agent can perform through AWS MCP Server, reducing the impact of unauthorized or unintended actions.

For more information about available IAM condition keys and permissions, see the AWS Sign-In condition keys reference and the AWSMCPSignInOAuthAccessPolicy documentation.

Conclusion

Enterprise-Managed Authorization (EMA) with AWS Sign-In enables organizations to securely connect AI agents to AWS resources using their existing enterprise IdPs. By combining centralized authorization policies with IAM permissions, organizations can control which AI applications access their resources while reducing the need for employees to manage AWS credentials or complete additional authorization flows.

Using ID-JAG, AWS Sign-In exchanges enterprise-issued identity assertions for short-lived OAuth access tokens associated with IAM roles. This approach helps organizations enforce least-privilege access, reduce credential exposure, and simplify how employees securely access AWS resources through AI agents.

To get started, see the Sign-in with OAuth 2.0, Configure EMA for MCP servers, and Introducing OAuth Support for AWS MCP Server to learn more about OAuth-based access to AWS resources.
