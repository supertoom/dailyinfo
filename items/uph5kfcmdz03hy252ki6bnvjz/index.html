Microsoft FORGE Lab 在 Rust 标准库（std 和 core）中发现了多个内存安全问题，其中包括完全使用安全 Rust 编写的代码也可能触发未定义行为的情况。该研究使用了 Hyenas，即 FORGE 的代号 MDASH 的前沿研究版本，这是一套由 AI 驱动的漏洞扫描系统。研究结果揭示了三种反复出现的对不安全代码的不当信任模式：相信代码不会发生 panic、相信用户提供的实现是正确的，以及信任底层系统。

Rust 的安全保证恰恰使这些发现颇具意义。其丰富的类型系统和所有权模型排除了整类内存安全问题，但标准库的许多安全 API 底层依赖不安全代码。当这些代码违反其安全契约时，即使是安全的 Rust 也可能遇到该语言本应防止的行为。

随着 Rust 成为数十亿人每天依赖的软件的一部分，其内存安全保证正变得愈发重要。据估计，数十亿人每天都在使用基于 Rust 的软件或操作系统，且往往并不知情。Microsoft 已将 Rust 与 C++、C# 和 TypeScript 一同列为 Tier-1 内部语言，GitHub 使用 Rust 重写了 Copilot 代理运行时，Bun、Android、Linux 内核和 Cloudflare也正在将代码迁移至 Rust。这些软件中的很大一部分都依赖 Rust 的基础库 core 和 std，以及这些库所提供的 API 的安全保证。这些库中的漏洞所造成的后果，可能远远超出漏洞最初出现的代码范围。

不安全 Rust 长期以来一直是我们的关注重点。我们的团队包括 Rudra背后的开发者，这是一款曾于 2021 年在整个 Rust 生态中查找内存安全漏洞的静态分析器。我们也使用 Rust 编写许多自有工具，因此对我们而言，Rust 的安全性不仅仅是一个研究主题。今年，我们更深入地审视了标准库，以了解如今其不安全代码中仍会出现哪些类型的错误。

在这篇文章中，我们分享了向 Rust 问题跟踪器报告的一些漏洞，并借此讨论 Rust 能保证和不能保证什么、编写正确的不安全 Rust 为何如此困难，以及即便 Rust 的内存安全并非完美无缺，其安全模型为何仍然重要。

我们如何发现并验证这些漏洞

在 Microsoft FORGE Lab，我们研究复杂软件中的漏洞，包括 Rust 标准库。我们的团队将多年的漏洞研究经验与 AI 辅助工具相结合，帮助我们调查代码并发现仅靠传统分析难以挖掘出的漏洞。

本文中的部分漏洞是在 Hyenas 的帮助下发现的，后者是我们代号 MDASH 的研究版本。我们的研究人员调查了底层代码、复现了漏洞、评估了其潜在安全影响，并与 Rust 维护者合作报告和修复了这些漏洞。

本文重点讨论标准库不安全代码中的可靠性漏洞。编译器本身的漏洞，例如错误编译和类型系统中的漏洞，属于另一个主题，本文不予讨论。

Rust 安全漏洞的模式

在最底层，Rust 使用 unsafe 块来处理原始指针并直接与操作系统交互。标准库的很大一部分，包括 Vec 和 String，都是由小型的不安全代码片段构建而成，并封装在安全 API 中。在 unsafe 块内，程序员需要负责编译器无法检查的保证，而且这一责任也延伸至围绕它构建的安全 API。该 API 必须是可靠的：无论安全代码如何使用它，都不可能触发未定义行为。

维持这一承诺并不容易。考虑这样一个函数：它可以从任何可被视为字节切片的类型中返回 idx 处的字节，并在自行完成边界检查后跳过重复的边界检查：

pub fn get<​S: AsRef<​[u8]>>(s: &S, idx: usize) -> Option<​u8> {
    if idx < s.as_ref().len() {
        Some(unsafe { *s.as_ref().get_unchecked(idx) })
    } else {
        None
    }
}

不安全 Rust 最难的部分在于知道什么可以信任。上面的函数看起来是正确的，但它假设两次调用 as_ref 会返回同一个切片。由于 S 由调用者选择，一个安全的 AsRef 实现可以第一次返回较长的切片，第二次返回空切片，从而导致越界读取。不安全代码必须谨慎对待它发出的每一次调用，而我们发现的漏洞可归为三种信任错置模式：信任代码不会发生 panic、信任用户提供的实现是正确的，以及信任底层系统。

模式 1：信任代码不会发生 panic

不安全代码经常会暂时打破某个不变量，随后再将其恢复；例如，它可能会分配一个未初始化的缓冲区并直接填充，从而避免先将内存清零的重复写入。只要函数能够运行到底，这没有问题。但 Rust 中的许多操作都可能引发 panic，从越界索引到调用用户提供的代码，而默认情况下 panic 会展开：它会在运行析构函数的同时提前退出函数。在该时间窗口内发生展开，就相当于一次无形的退出，会向信任该不变量的代码暴露它已被破坏的状态。这类漏洞称为 panic 安全漏洞。

MapWindows::clone（问题 #156501）

我们在 MapWindows::clone 中发现了一个panic 安全问题。夜间版 API Iterator::map_windows 会产生包含 N 个项的重叠窗口。它将当前窗口保存在 Buffer 中，其析构函数会丢弃从 start 开始的 N 个项。在 Rust 1.97.0 中，library/core/src/iter/adapters/map_windows.rs 将其定义为：

struct Buffer<​T, const N: usize> {
    // Invariant: `self.buffer[self.start..self.start + N]` is initialized,
    // with all other elements being uninitialized. This also
    // implies that `self.start <= N`.
    buffer: [[MaybeUninit<​T>; N]; 2],
    start: usize,
}

同一文件中的 Buffer::clone 会先构建新缓冲区，之后再填充：

impl<​T: Clone, const N: usize> Clone for Buffer<​T, N> {
    fn clone(&self) -> Self {
        let mut buffer = Buffer {
            buffer: [[const { MaybeUninit::uninit() }; N], [const { MaybeUninit::uninit() }; N]],
            start: self.start,
        };
        buffer.as_uninit_array_mut().write(self.as_array_ref().clone());
        buffer
    }
}

缓冲区构造完成后，它就破坏了自己的不变量：其插槽尚未初始化，但析构函数已经被启用。self.as_array_ref().clone() 调用会在写入插槽之前运行用户的 T::clone。如果该调用发生 panic，栈展开会丢弃 buffer，并对 N 个未初始化的值运行 drop_in_place。我们的概念验证仅使用安全代码：一种其 clone 始终会 panic 的元素类型，当析构函数访问未初始化内存时会导致崩溃。修复方案将新缓冲区保存在 ManuallyDrop 中，直到其被完整写入，因此栈展开时只会泄漏这个半构造的缓冲区，而不会将其丢弃。

普遍的教训是，应将每一次对不受你控制的代码的调用——例如 clone、drop、比较、闭包和迭代器方法——视为可能提前退出。要么在破坏不变量之前完成可能 panic 的工作，要么确保在展开过程中处于损坏状态的对象是安全的：将其保存在 ManuallyDrop 中，或者使用析构函数会恢复不变量的守卫，就像 Vec 内部的 SetLenOnDrop。The Rustonomicon 在异常安全一节中对此有所介绍。

分配器不得展开栈

最近稳定下来的 Allocator API 表明，要正确实现 panic 安全有多么困难。使用 std 时，分配失败默认会中止进程而不是展开栈，因此标准库中的许多 unsafe 代码都假定分配不会展开栈。自定义分配器可能破坏这一假设。在该 API 稳定期间，我们报告了BTreeMap::insert 中的一处位置，当分配器展开栈时会导致不安全；其他人还报告了更多问题（#159334、#159368、#159370）。逐一修复这些问题意味着必须审计所有会进行分配的代码，因此将于 11 月 12 日随 Rust 1.100 发布的稳定化改为要求实现者绝不能从该 trait 的方法或 drop 中展开栈。该提案指出：“从许多与分配相关的方法中展开栈被发现是导致不安全的普遍根源。”

模式 2：信任用户提供的实现是正确的

unsafe 代码经常调用调用方提供的代码：比较器、trait 实现或闭包。这些代码是安全的，但安全并不意味着正确，它可能返回不一致或明显错误的结果。问题是，当它这样做时由谁负责。在 C++ 中，答案是调用方。std::sort 要求其比较器构成严格弱序，违反该规则属于未定义行为。在 libstdc++ 中，使用 <= 对相等元素进行排序会读取到 vector 末尾之后：

std::vector<​int> v(100, 42);
// Bug: `<=` is not a strict weak ordering, since cmp(a, a) is true.
std::sort(v.begin(), v.end(), [](int a, int b) { return a <= b; });
// AddressSanitizer: heap-buffer-overflow in std::__introsort_loop

传递给 Rust sort_by 的同一个比较器只会导致逻辑错误。排序可能 panic，或者让切片处于未指定的顺序，但绝不会造成未定义行为。责任在于 unsafe 代码。该比较器是调用方提供的安全代码，因此排序内部的 unsafe 代码无论它返回什么都必须保持安全。对于用户可以实现的每一种安全 trait，同样如此：比较结果可能不一致，ExactSizeIterator 可能报告与其所产出项数不匹配的长度，而 Borrow 每次调用都可能返回不同的值。

使用自定义 Pattern 调用 str::replace（#156491）

我们的另一份漏洞报告显示，这种信任有多么容易会被忽略：str::replace 使用自定义 Pattern 时，可以创建非 UTF-8 的 String。字符串搜索 API 接受任何实现了 nightly Pattern trait 的类型，而模式可以通过 as_utf8_pattern 来描述自身。当把一个 ASCII 字节替换为另一个 ASCII 字节时，str::replace 会使用该描述走一条快速路径。在 Rust 1.96.0 中，library/alloc/src/str.rs 中的快速路径如下：

pub fn replace<​P: Pattern>(&self, from: P, to: &str) -> String {
    // Fast path for replacing a single ASCII character with another.
    if let Some(from_byte) = match from.as_utf8_pattern() {
        Some(Utf8Pattern::StringPattern([from_byte])) => Some(*from_byte),
        Some(Utf8Pattern::CharPattern(c)) => c.as_ascii().map(|ascii_char| ascii_char.to_u8()),
        _ => None,
    } {
        if let [to_byte] = to.as_bytes() {
            return unsafe { replace_ascii(self.as_bytes(), from_byte, *to_byte) };
        }
    }

replace_ascii，它位于同一个文件中，随后重写字节：

unsafe fn replace_ascii(utf8_bytes: &[u8], from: u8, to: u8) -> String {
    let result: Vec<​u8> = utf8_bytes.iter().map(|b| if *b == from { to } else { *b }).collect();
    // SAFETY: We replaced ascii with ascii on valid utf8 strings.
    unsafe { String::from_utf8_unchecked(result) }
}

CharPattern 分支会检查字符是否为 ASCII，但 StringPattern 分支却假定单字节字符串模式必然是 ASCII。对于 &str 模式而言，这一假定成立；但 StringPattern 存储的是 &[u8]，并且 as_utf8_pattern 是任何 Pattern 都可以实现的安全方法。在我们的概念验证中，自定义模式报告了单个字节 0x80，而该字节只会出现在多字节 UTF-8 序列内部：

impl Pattern for NonAsciiBytePattern {
    // ...
    fn as_utf8_pattern(&self) -> Option<​Utf8Pattern<​'_>> {
        static NEEDLE: [u8; 1] = [0x80];
        Some(Utf8Pattern::StringPattern(&NEEDLE))
    }
}

// "\u{d000}" is [ed, 80, 80]; the result is [ed, 3f, 3f], which is not UTF-8.
let corrupted = "\u{d000}".replace(NonAsciiBytePattern, "?");

str::replace 会重写连续字节并返回一个无效 UTF-8 的 String，之后依赖 UTF-8 的字符串操作将导致未定义行为。此修复将 StringPattern 改为保存 &str 而不是 &[u8]，因此类型本身现在就能保证 UTF-8。

当不安全代码依赖用户提供实现的某项属性时，不要盲目相信它。可以调用该实现一次并保留结果，验证其返回值，或者像此次修复那样，将该属性编码进安全代码无法伪造的类型中。如果这些方法都不可行，就应将 trait 设为 unsafe，让实现者明确承诺遵守该属性。

更多示例

join 展示了这类漏洞只得到部分修复有多么容易。2020 年，我们报告过它信任 Borrow::borrow 每次调用都返回相同字符串的问题（CVE-2020-36323），当时的修复处理了字符串在多次调用之间发生缩短的情况。2026 年 4 月，同一个函数又需要了一次修复：join 会借用第一个元素两次，如果它在第二次调用时增长，剩余长度的计算就会发生下溢，进而导致堆溢出。此前的修复从未涵盖这条路径。

今年还有其他人报告了 Pattern API 中的类似问题。安全的 Pattern 可以交回一个为另一个字符串构建的有效搜索器，而 strip_prefix_of 等使用者会在未经检查的情况下将其范围应用到原始字符串上，造成越界读取（#158265）。在有人报告 Searcher 契约没有明确规定 str::split 所依赖的规则（#164904）后，同一个问题又出现在 split_once 中（#165076）。这两个漏洞仍未修复。

模式 3：信任底层系统

前两种模式都局限在 Rust 代码内部。第三种模式位于与操作系统的边界处，其中不安全代码会信任进程级状态，例如信号栈、内存映射和环境变量，而其他线程、C 库或内核随时都可能修改这些状态。这类漏洞很难通过自动方式发现，因为静态分析器需要对所有这些周边行为进行建模。AI 智能体改变了这一局面：它们对代码运行所处环境有足够多的理解，使这一领域变得适合进行实际排查。我们开始探索这一领域，并发现了一些有趣的漏洞。

process::exit 与主线程的信号栈（#161018）

当线程的栈溢出时，Rust 会打印一条清晰的消息并中止，而不是仅以段错误崩溃：

thread 'main' (3307186) has overflowed its stack
fatal runtime error: stack overflow, aborting

这依赖于一些进程范围的状态。每个线程的栈都终止于一个保护页，即紧邻栈界限之外的一段不可访问区域：pthread 会为每个创建的线程预留一个保护页；在 Linux 上，内核自身的栈保护机制会为主线程发挥这一作用。触碰它会触发 SIGSEGV，而 Rust 会为该信号注册处理程序。处理程序无法在刚刚溢出的栈上运行，因此 Rust 还会为每个线程提供一个备用信号栈，即一个带有自身保护页的小型独立映射；当内核递送该信号时，会切换到这个栈。处理程序会检查故障地址是否位于保护页内，然后打印消息并中止进程。

我们发现，从子线程调用 process::exit 会在主线程仍在运行时拆除主线程的备用栈。process::exit 会先运行运行时的清理工作，再调用 libc 的 exit；在 Rust 1.98.0 中，该清理过程最终进入 library/std/src/sys/pal/unix/stack_overflow.rs：

pub unsafe fn cleanup() {
    if cfg!(panic = "immediate-abort") {
        return;
    }
    // FIXME: I probably cause more bugs than I'm worth!
    // see https://github.com/rust-lang/rust/issues/111272
    unsafe { drop_handler(MAIN_ALTSTACK.load(Ordering::Relaxed)) };
}

清理函数将 MAIN_ALTSTACK（主线程的备用栈）传递给 drop_handler：

// SAFETY: we warned the caller this disables the alternate signal stack!
unsafe { sigaltstack(&disabling_stack, ptr::null_mut()) };
// SAFETY: We know from `get_stackp` that the alternate stack we installed is part of
// a mapping that started one page earlier, so walk back a page and unmap from there.
unsafe { munmap(data.sub(page_size), sigstack_size + page_size) };

对 sigaltstack 的调用会禁用调用线程的备用栈，但随后对 munmap 的调用会取消映射主线程的备用栈。代码假定自己在主线程上运行，但当子线程调用 process::exit 时这一假定并不成立。主线程会继续运行，直到 libc 的 exit 完成，而其信号栈注册仍然指向已取消映射的内存。如果它在此期间发生栈溢出，内核将无法递送信号，我们的概念验证程序会因普通分段错误而终止，而不是显示 Rust 的消息。该缺陷可追溯至 2015 年，而修复完全停止清理主线程的备用栈。

我们还检查了此问题是否可能成为安全问题。理论上，它可能导致代码执行：如果某个可写映射恰好落在旧备用栈的地址上，内核就会将主线程的下一个信号递送到该映射上，而另一个线程可能会在处理程序运行期间覆盖其栈帧，例如返回地址。实际上，这些条件非常苛刻。所有事情都必须发生在 libc 的 exit 完成前的短暂窗口内，新映射必须具有恰好合适的尺寸才能复用该地址，而覆盖栈帧还需要在短暂的处理程序内部进行第二次竞态。对于问题 #161018，我们的测试在所考察的条件下未发现可靠的利用路径，并评估认为实际利用的可能性很低。此评估不会自动适用于讨论的其他问题。该问题的安全影响分析中提供了更多细节。

CommandExt::exec 与全局环境（#156951）

我们的另一份报告涉及进程环境。在 Unix 上，CommandExt::exec 会用新程序替换当前进程。当命令拥有自己的环境变量时，exec 会将进程全局的 environ 指向一个新数组，调用 execvp，并在 execvp 失败时恢复 environ。在 Rust 1.99.0 中，Command::exec 会在 library/std/src/sys/process/unix/unix.rs 中获取环境锁：

let _lock = sys::env::env_read_lock();

let Err(e) = self.do_exec(theirs, envp.as_ref());

随后，同一文件中的 Command::do_exec 会切换环境：

    _reset = Some(Reset(*sys::env::environ()));
    *sys::env::environ() = envp.as_ptr();
}

libc::execvp(self.get_program_cstr().as_ptr(), self.get_argv().as_ptr());
Err(io::Error::last_os_error())

Command::exec仅获取环境锁的读锁端，而 do_exec会写入进程全局的 environ。写入前，do_exec会保存旧值，以便在 execvp失败时恢复。 在读锁下写入 environ 会让其他线程进入。调用 env::var 的线程会获取同一个读锁，并可能看到仅供新程序使用的变量；两个竞争的失败 exec 调用可能使 environ 指向已释放的数组，之后由 env::vars_os() 读取。两个概念验证均仅使用安全的 Rust。2018 年的修复曾在此处持有独占锁，但当环境锁在 2021 年变为读写锁时，exec 仍保留读锁端。通过直接调用 execve 以避免访问 environ 的修复目前正在审查中。

环境此前曾引发问题。在一场始于 2015 年的讨论之后，2024 年版将 env::set_var 标记为不安全，因为大多数 Unix 平台上的 C 函数会读取环境，而不会经过 Rust 的锁。

process::exit 和线程局部析构函数（#164243）

正确划分这一边界并不容易，而且仍有更多问题尚未解决。在探索这一领域时，我们独立发现了一个安全代码中的双重释放问题，process::exit 可能通过线程局部析构函数触发该问题。该问题由其他人报告（#164243），但仍值得在此提及。按照 C++ 的要求，libc 的 exit 会先运行调用线程的线程局部析构函数，Rust 也以相同方式注册其析构函数。如果析构函数在替换线程局部变量期间调用 process::exit，libc 会第二次释放该线程局部变量。拟议的修复会将 process::exit 切换为 POSIX _exit，从而在不运行这些处理程序的情况下结束进程。

为什么 Rust 仍然重要，以及如何借助 AI 推进漏洞发现

每个 unsafe 代码块都依赖于对其周围代码的假设。本文中的错误源于三种错位的信任：

  • 代码不会在错误的时机发生 panic；
  • 调用方提供的实现会正确运行；以及
  • Rust 与操作系统和 C 库共享的进程级状态会保持代码预期的样子。

熟悉的模式仍然难以处理（模式 1 和模式 2）

前两种模式已得到充分研究。Rudra曾于 2021 年寻找这两种模式，而标准库早在 2015 年就开始修复 panic 安全缺陷（CVE-2015-20001）。这些模式仍难以避免，因为 unsafe 代码中的任何调用都可能展开栈或运行调用方提供的代码。

我们今年看到的情况喜忧参半。积极的一面是，nightly 流程正在发挥作用。许多报告在受影响的 API 仍处于不稳定状态时就被发现，还有若干问题在稳定化前通过更改设计得到了修复。StringPattern 现在保存 &str 而不是 &[u8]，Allocator 已稳定，并规定实现者不得展开栈。与此同时，这些模式中的缺陷仍会进入稳定版本，其修复也不总是完整的。join 于 2020 年得到修复，但 2026 年又需要了一次修复，以处理首次修复遗漏的路径。

系统边界缺陷如今已触手可及（模式 3）

第三种模式有所不同。其缺陷存在于 Rust 与下层机制交汇之处：通过 sigaltstack 和 munmap 等系统调用与内核交互；通过 environ 等进程级状态以及 libc 的 exit 所执行的清理过程与 C 库交互。要正确处理这些问题，需要掌握 Rust 类型系统之外的知识，因此传统静态分析很难发现这些缺陷。这也可能解释了它们为何能够长期存在。process::exit 的信号栈缺陷在标准库中存在了近 11 年，而 exec 自 2021 年以来一直在读锁保护下写入 environ。与前两种模式中的报告不同，这两种问题都会影响稳定版 Rust。

语言模型已经对这些接口的行为有了大量了解，因此代理式扫描器可以依据系统实际运行的环境检查不安全代码，而不只是检查语言本身。我们认为，这一边界是代理式安全研究最有前景的领域之一，不仅适用于 Rust，也适用于更广泛的技术领域。

Rust 的高标准很难达到，但值得保持

Rust 对其安全 API 的要求比 C 和 C++ 更严格。无论如何使用 API，安全代码都绝不能导致未定义行为。在 C++ 中，违反 std::sort 排序要求的比较器会引发未定义行为，而 Rust 的 sort 无论采用何种 Ord 实现都必须保持内存安全。POSIX 并不保证在另一个线程读取环境变量时调用 setenv 是安全的。因此，Rust 中的内存安全缺陷很难与其他语言中的缺陷一一对应。

出于同样的原因，标准库中的健全性缺陷并不会自动成为使用该库的程序中的漏洞。本文讨论的每个缺陷都需要不寻常的设置才能触发，例如恰好在错误时机引发 panic、实现被故意设计为行为异常，或者从子线程调用 process::exit。只有当真实程序以这种方式调用相关 API 时，它才会成为严重漏洞。

Rust 的安全标准严格且难以达到，但同时也很有用。它明确界定了哪些问题属于健全性缺陷，因此只需在库中集中修复并防止此类问题，而不必在每个使用该库的程序中分别处理。Rust 的安全模型在控制力、安全性和性能之间实现了恰当平衡，这也是众多项目选择它的原因。

实验室之外

在 Microsoft FORGE Lab，我们正在探索代号 MDASH 等技术如何帮助研究人员以更大规模发现本文所述的缺陷。Rust 标准库是我们应用这一方法的多个基础开源项目之一。

这项研究也延伸到了实验室之外。 它为代号 MDASH 的开发提供参考，而 MDASH 将代理式漏洞发现能力集成到 Microsoft Defender 中。这些发现还可以作为 Microsoft Perception（我们全新的多代理安全系统）的输入。在该系统中，专门化的代理会在更广泛的安全工作流中协同工作。例如，Web App Pen Test Agent 可以利用代号 MDASH 的发现来确定测试优先级，针对实时应用验证可利用性，并生成可供下游代理用于确定修复优先级和协助修复的可操作漏洞。这将 AI 驱动的代码分析与现实世界的安全验证和响应连接起来，帮助安全团队从识别潜在漏洞转向理解并应对实际风险。

我们的目标不只是发现更多漏洞，而是识别有意义的问题，将这些发现转化为可执行的研究，并提升开发者和组织所依赖的基础软件的安全性。
