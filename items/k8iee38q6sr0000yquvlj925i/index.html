Google Cloud 披露 LLMJacking 攻击链，攻击者转售被盗企业 LLM 资源

The Rise of LLMJacking: How Threat Actors Monetize Compromised Cloud and Model Resources

简介 

Mandiant 响应了 2026 年的多起安全事件，其中威胁行为者劫持了企业对大型语言模型（LLM）的访问权限，这种战术被称为“LLMJacking”。这些入侵涉及多种云和 LLM 提供商，影响了北美、南美和亚太地区横跨金融服务、零售、科技和运输行业的组织。 

与加密货币挖劫相关的渐进式资源消耗不同，LLMJacking 可在数小时内导致欺诈性云费用激增。在单个事件中，我们观察到与资源消耗相关的欺诈性费用在一天内超过 100,000 美元；一些组织的累计费用在访问权限被撤销前达到 100 万美元。

图 1：显示 LLMJacking 导致 API 请求量激增的使用情况图表

Google Threat Intelligence Group（GTIG）分析了这些前沿入侵背后的犯罪生态，并在 此前关于不断壮大的 LLM 凭据地下市场的报道基础上，识别出在全球多个地区活动的多样化 financially motivated threat clusters。

随着 LLMJacking 生态日益成熟，我们还观察到威胁行为者之间出现了分工：一类负责获取受攻击环境的初始访问权限，另一类则负责管理下游变现基础设施，后者被称为“LLM Mixers”。LLM Mixers 充当非法路由网关，为地下订阅者代理、聚合并转售未经授权的 LLM 访问权限。在一次调查中，GTIG 观察到两个不同的运营集群协同入侵企业 LLM 基础设施并将其变现，显示出该领域正在形成精细化的专业化分工。

在这篇博客文章中，我们介绍了近期 LLMJacking 调查中观察到的攻击生命周期，并提供可操作的检测、加固和修复指南，以帮助组织保护其基础设施。 

初始访问

虽然低层次资源窃取涉及利用 操控客户支持聊天机器人来执行代码生成等未经授权的任务，但实施 LLMJacking 的威胁行为者会绕过这些前端界面，直接针对后端模型资源。具体而言，他们专注于识别公开暴露的 LLM 端点，或获取有效的 LLM 应用程序编程接口（API）密钥。后一种情况的示例见图 1：威胁行为者使用自动化脚本调用 /api/create 端点进行验证，以独立运行自己的模型，而不知情的用户已将相关端点公开访问。未对这些服务采取保护措施，不仅会扩大组织的传统攻击面，还可能显著增加托管费用。

图 2：威胁行为者测试公开暴露的 Ollama 端点，并尝试注册自己的模型

然而，在多起 LLMJacking 调查中，主要的初始访问向量一直是泄露或被盗的云身份令牌——包括 IAM 凭据、Service Account 密钥、GitHub Personal Access Tokens (PATs) 和活动会话令牌——威胁行为者利用这些令牌在目标组织的基础设施中建立初步据点。

例如，在 2026 年中，UNC6993 通过配置不当的 Service Account 密钥入侵了一个云实例，并利用该访问权限进一步访问 LLM API。UNC6993 还托管了一个冒充应用程序门户的会话劫持页面，以吸引一组 LLM 用户加入。该页面诱骗用户导航至合法的 LLM 服务网站，并粘贴包含活动访问令牌的原始 JSON 载荷，随后该载荷会被发布到后端 API，从而绕过密码和多因素身份验证 (MFA) 控制。

在另一起事件中，一名威胁行为者将被盗的 Personal Access Token (PAT) 与对容器化云环境中运行的某个软件包疑似 Web 应用程序漏洞的利用结合起来，通过 PAT 访问私有代码仓库并获得初始入口。同样，另一名威胁行为者利用企业用户被盗的 IAM 凭据，使用云联合身份令牌以编程方式生成新的访问密钥，从而绕过 MFA 要求。在另一起独立事件中，首次观察到威胁行为者使用具有广泛项目权限的被盗云 Service Account 密钥访问环境。

除常规云身份凭据外，威胁行为者还会以 LLM API 密钥为目标。例如，威胁行为者 opportunistically 从公开 GitHub 仓库中收集暴露的企业 LLM API 密钥。该组织展示了先进的规避技术，使用仅含单个令牌的最小化请求进行自动化凭据验证扫描（max_tokens=1）。这使威胁行为者能够隐蔽确认被盗密钥是否可用，同时避免被受害者的终端检测与响应 (EDR) 和 SIEM 容量异常告警发现。

横向移动与持久化

在获得初步据点后，威胁行为者会有条不紊地提升权限、巩固访问权限并开展内部侦察，以确定目标并获取更多云凭据。

为扩大访问范围，威胁行为者枚举云服务、代码仓库和数据存储，以寻找敏感凭据。在一次入侵中，威胁行为者跨多个云区域开展内部侦察，以绘制可用服务和身份策略。在另一次入侵中，威胁行为者入侵了一个容器化云环境。进入该环境后，他们对代码仓库进行了广泛侦察，克隆敏感代码库以搜索硬编码机密、配置变量和开发者凭据。他们还扫描访问日志，以识别次级云环境的凭据。威胁行为者还执行有针对性的数据库查询以收集更多凭据；在一个案例中，威胁行为者查询了云数据仓库元数据表，搜索数据库凭据、管理员密码和敏感列，同时执行与定向数据窃取相关的云对象存储操作。

在多次入侵中，我们观察到威胁行为者滥用云身份权限和虚拟机配置来提升权限并维持持久访问。某威胁行为者利用与已受损工作负载关联的服务账户，通过令牌创建权限为高权限服务账户生成临时凭据，导致基础设施凭据、内部数据库密码和第三方 API 密钥从云密钥管理器中被外泄。其他威胁行为者则通过创建未经授权的 IAM 和服务账户，并向计算实例注入 SSH 密钥来建立持久性。具体而言，一名行为者通过将管理策略附加到服务角色来提升权限，创建具有完全管理员权限的未经授权 IAM 账户，并与运行中的虚拟机建立交互式管理会话，以将未经授权的 SSH 公钥注入主机配置文件。类似地，另一名威胁行为者创建了伪装成内部计费优化实用工具的欺骗性后门服务账户，并向计算实例元数据注入环境范围的 SSH 密钥。

除了利用传统云基础设施权限外，我们还观察到威胁行为者专门针对 LLM 路由软件中的漏洞实施权限提升。在一个案例中，后续攻击集群在从建立初始访问的威胁行为者处获取预先验证的 Virtual Keys 后，针对受害者的 LiteLLM 网关执行了有针对性的应用逻辑漏洞利用。该行为者利用 /key/regenerate 端点中的用户 ID 重新绑定漏洞（CVE-2026-40217），将标准 Virtual Keys 提升为完整的 PROXY_ADMIN 主管理员凭据，从而对已受损环境建立深入且持久的控制。

LLM 滥用

LLMJacking 的最终目标是对基础模型进行变现和资源劫持，行为者通过令牌代理、自动化模型流式传输和 GPU 硬件配置来实现这一目标。

威胁行为者经常启用各种托管式生成平台，并创建额外的 API 密钥以扩大其行动规模。在获取 LLM API 访问密钥后，UNC6993 试图在受害者的云项目中生成额外的 API 密钥并启用相关服务，迅速累积了超过 100,000 美元的计费费用。另一名威胁行为者将受害者账户订阅到按量付费协议，选择高级基础模型并启动高吞吐量的推理流。为绕过速率限制，该威胁行为者部署了“烧毁并轮换”策略，持续创建和删除短期服务账户，同时审核云提供商的计费界面以监控财务影响。

威胁行为者还利用其访问权限托管自己的代理端点和智能体工作负载。例如，一名威胁行为者启用了智能体，部署了公开可访问的反向代理，并使用自定义 Node.js 代理捆绑包暴露与多个前沿 LLM 兼容的端点，并以一个名为 D1337-KAIROS 的人物品牌进行包装。该行为者使用 Manus 智能体框架，将容器化后门部署到受入侵的云环境中；该后门查询上游 LLM，以推理指令并在本地执行生成的命令，同时由 SearXNG 元搜索和 agent-infra/sandbox 执行环境提供支持。为了扩展计算资源，该威胁行为者配置了配备强大 GPU 的计算实例，尝试在多个区域启动高端硬件，并通过云提供商的 API 申请提高配额。该行为者还在外部服务器上托管了 LiteLLM 网关，以管理和路由 API 流量。

GTIG 观察到，有证据表明威胁行为者并非仅将被劫持的计算资源用于自身运营，而是通过 LLM Mixer 出售对这些资源的访问权限，将被入侵的 API 配额变现。威胁行为者使用开源 API 网关和自定义中继基础设施来汇集被盗凭据、计量使用量并隐藏请求来源。例如，UNC6993 使用了 new-api（一个集中式模型中心和网关）以及 gcli2api（一种将命令行界面（CLI）工具转换为标准前沿模型端点的 API 代理工具）等开源工具，可能用于聚合被盗密钥并在不同账户之间平衡请求负载。我们认为，该威胁行为者通过地下商铺出售对这些工具的访问权限。

另一名威胁行为者在不到八小时内执行了超过 500,000 次 LLM API 调用，并利用被盗的第三方 API 密钥为令牌路由服务 jet-night.com提供支持。Jet Night 将近一百万美元的令牌成本转嫁给了受害组织。鉴于 Jet Night 向用户收取的每令牌成本远低于典型市场费率，GTIG 认为该服务依赖被盗密钥才能实现盈利。例如，Jet Night 提供每月约 60 美元的无限令牌套餐，据称可访问前沿模型，而此类面向消费者的服务通常每月需 100 至 250 美元。此外，该服务在其公开 Telegram 频道上宣传过多次中断，这很可能是因为受害组织发现各自遭到入侵后撤销了被盗密钥。

一名威胁行为者部署了自定义代理中继基础设施（ai-relay），并托管在具有欺骗性的仿冒域名上。例如，他们注册了一个域名 ，冒充受害者的合法内部主机。这套自定义中继基础设施被用于将高价值的商业 LLM 访问权限无缝导入非法的 newapi[.]pro 转售生态，直接消耗受害者企业账户的配额，以服务其地下客户。

展望

GTIG 预计，在新兴地下 LLM Mixer 的推动下，威胁行为者将日益优先考虑 LLMJacking，而非加密挖矿等传统资源窃取，因为前者能够实现即时且高利润率的变现。随着企业将更高层级的模型和智能体工作流集成到生产环境中，网络犯罪分子很可能会改进自动化侦察手段，攻击暴露的 API 令牌，并利用模型路由中间件中的漏洞。这种运营专业化将推动非法转售市场持续增长，使威胁行为者能够迅速耗尽企业配额，同时将费用转嫁给受害者，并在入侵被发现之前完成获利。

检测与威胁狩猎

如果安全措施已经失效，防御方必须能够尽早发现对云端 LLM 平台的滥用。防御方应优先检测对 LLM 账户和服务的修改，并将任何未经授权的启用行为视为严重安全事件。在 Mandiant 调查的多起事件中，入侵发生时 LLM 服务并未启用。访问密钥的滥用使威胁行为者得以修改并启用 LLM API 服务（例如 Bedrock、Gemini API 等）。一旦启用，威胁行为者只需几分钟或几小时就能利用这些 API 为该组织产生巨额账单。

Google Security Operations 客户可以通过 Cloud Threats、Mandiant Frontline Threats、Mandiant Hunting Rules 规则包访问这些宽泛类别的规则及更多内容。本博客文章中讨论的活动在 Google SecOps 中通过以下规则名称检测：

  • AWS Account Key Creation

  • AWS Create New Access Key

  • AWS Create User Account

  • AWS Delete User Account

  • Base64 Encoded Shell Command Execution

  • Create and Delete Firewall in Default Network

  • GCE Project SSH Keys

  • GCP Service Account Key Creation

  • GCP Create New Service Account

  • GCP Firewall Rule Created

  • Linux Archive Exfiltration via Curl or Wget

  • Persistence: Compute Set Instance or Project Metadata Startup Scripts or URLs

缓解与修复

为防止攻击者滥用 Cloud LLM 服务，防御方应优先关注身份与访问管理（IAM）和供应链安全，因为这是获取并滥用 Cloud 服务的两种最常见途径。 

  • 凭据卫生：使用集中式机密管理平台来控制敏感密钥和机密的管理与轮换。机密和密钥的自动化管理可以缩短泄露凭据的有效期。 

  • 最小权限：确保用户和服务账户仅拥有其特定角色及所需任务所必需的权限。拒绝所有未明确要求的权限，包括对 Cloud LLM 服务的访问权限。

  • 代码监控：在代码库（GitHub、Gitlab 等）中自动执行机密扫描，确保添加到源代码中的 API 密钥和机密能够被及时识别并移除。 

  • 例行配置审计：定期对 Cloud 服务执行全面的配置审计，以识别潜在攻击路径和端点的意外暴露。 

  • 速率限制：实施类似 Google’s Cloud Armor 的 WAF，对各个客户端连接强制执行速率限制。

  • 网络允许列表：在可行的情况下，通过 VPC 防火墙规则将云服务的出站连接限制为已知 IP 地址。

  • 预算告警：对 LLM 服务实施精细的 API 配额，以限制每个模型的请求量。利用支出上限设置预算，避免超支。

  • 多因素身份验证 (MFA)： 在所有云身份提供商、管理控制台和开发者平台上强制执行抗钓鱼的多因素身份验证，确保被盗凭据或会话令牌难以被利用。

  • 影子 LLM 发现： 利用安全配置管理工具自动扫描混合云环境，识别未经授权或未受监控的工具、模型和基础设施，确保完整掌握模型部署情况。

  • 精细的 API 密钥权限范围： 按特定模型端点、环境（开发/生产）和使用限制对 API 密钥进行限制和分段，确保基础实用模型的令牌即使被盗，也无法用于调用费用高昂的高级前沿模型。

  • 验证扫描监控： 监控模型网关和 API 访问日志中的异常低频请求（例如 max_tokens=1 或零温度探测请求）。攻击者经常使用此类微交易，在大规模基础设施滥用之前隐蔽地验证凭据。

  • 漏洞与 ML 供应链补丁管理： 在自定义应用程序代码、容器化工作负载和机器学习依赖项（如 PyTorch 和 Hugging Face 库）中集成自动化漏洞扫描（SAST/DAST/SCA），防止攻击者通过未修补的服务器漏洞获得初始访问权限。

  • 网关补丁管理： 将漏洞管理计划扩展至集中式模型代理和路由网关（例如 LiteLLM），确保能够快速修补权限提升和身份验证绕过漏洞（例如 CVE-2026-40217）。

  • 动态工作负载的沙箱执行： 如果你的 LLM 应用需要动态执行生成的代码或数据库查询，请在高度虚拟化、进程隔离的无服务器沙箱中隔离运行时环境。

  • 经过审查的模型存储库： 仅允许从可信的内部注册表或已批准的企业目录拉取模型和流水线依赖项，并强制执行此限制，防止开发者拉取包含预配置后门的受损模型。

  • 基于图的暴露面建模： 实施持续、基于图的风险优先级评估，将云资产、应用程序代码和数据流映射起来，自动识别并修复复杂的多跳攻击路径。

  • 对抗性暴露验证： 部署自动化进攻代理，持续测试外部攻击面、发现暴露的端点并模拟凭据验证扫描。

监控原生云审计日志 

    • AWS：监控 CloudTrail 日志中来自 bedrock.amazonaws.com 的 API 事件。基于历史上 LLM Jacking 事件的案例，在整个攻击生命周期中监控以下 API 操作：

      • 资源利用：监控通过 Converse、InvokeModel, 和 InvokeModelWithResponseStream API 操作直接执行 LLM 的行为。

      • API 限流与错误峰值：监控 ThrottlingException、ValidationException 或 ResourceNotFoundException 错误量是否出现高峰，这可能表明有自动化“喷洒”方法正在针对云基础设施。

      • 目标范围确定：监控潜在的侦察活动，识别通过 ListFoundationModels,ListInferenceProfiles 和 GetFoundationModelAvailability 操作发现的可用模型。此外，还要监控通过 PutUseCaseForModelAccess 和 CreateFoundationModelAgreement API 操作尝试解锁环境中新模型的行为。

      • 安全/规避：审查试图查看、修改或禁用日志配置以隐藏提示内容并逃避检测的行为。监控 GetModelInvocationLoggingConfiguration 操作，以及 PutModelInvocationLoggingConfiguration 和 DeleteModelInvocationLoggingConfiguration。任何非 IaC（基础设施即代码）主体为禁用日志而发起的调用都应视为严重程度高。

自动化工具：分析 User-Agent 字符串，识别直接与目标云基础设施交互的自动化工具和 SDK（例如 claude-cli、aws-sdk-rust 和 aws-sdk-go-v2）。

  • Azure：监控 Azure Activity Logs（控制平面）和 Diagnostic Logs（数据平面）中与 Microsoft.CognitiveServices 命名空间相关的事件。要搜寻或检测 LLM Jacking 事件，请监控以下操作：

    • 资源利用：监控直接执行 LLM 的行为。在 Azure 中，模型调用发生在数据平面，且需要启用 Diagnostic Logs。留意向 Completions 或 Chat Completions API 等推理端点发起的大量 POST 请求。在管理平面（Activity Logs）上，监控通过 Microsoft.CognitiveServices/accounts/deployments/write 操作未经授权创建新实例的行为。

    • 目标范围确定：监控潜在的侦察活动，识别通过 Microsoft.CognitiveServices/accounts/read 和 Microsoft.CognitiveServices/accounts/deployments/read 操作发现的可用 Azure LLM 资源、模型和部署。

    • 安全/规避：审查通过 Microsoft.Insights/diagnosticSettings/read、Microsoft.Insights/diagnosticSettings/write 或 Microsoft.Insights/diagnosticSettings/delete 操作查看或修改日志配置（以确认数据平面模型调用是否正被记录）的尝试。

  • GCP：监控 Cloud Audit Logging 中对 Gemini Enterprise Agent Platform 端点（aiplatform.googleapis.com）的调用。Gemini Enterprise Agent Platform 推理操作包含在 Data Access 日志中；由于日志量及摄取成本，这些日志默认处于禁用状态。您必须手动配置 IAM 审计策略以跟踪这些操作。

    • 启用 Agent Platform 服务：Alert，以发现通过 google.api.serviceusage.v1.ServiceUsage.EnableService 方法启用 Gemini Enterprise Agent Platform 服务的行为。

    • 资源利用：监控通过 Gemini Enterprise Agent Platform 直接执行 LLM 的情况，这需要启用 Data Access 审计日志。寻找 google.cloud.aiplatform.v1.PredictionService.Predict、google.cloud.aiplatform.v1.PredictionService.GenerateContent 和 google.cloud.aiplatform.v1.PredictionService.StreamGenerateContent 操作。

    • 目标范围确定：监控潜在的侦察活动，以通过 google.cloud.aiplatform.v1.ModelService.ListModels、google.cloud.aiplatform.v1.EndpointService.ListEndpoints 和 google.cloud.aiplatform.v1.PublisherModelService.ListPublisherModels API 操作发现可用模型和终结点。

    • 安全/规避：审查查看或更改日志记录及审计配置的尝试。监控诸如 google.iam.v1.IAMPolicy.GetIamPolicy（用于检查项目/资源上是否启用了 Data Access 日志）等操作，或通过 google.logging.v2.ConfigServiceV2.ListSinks 和 google.logging.v2.ConfigServiceV2.GetSink 审查日志导出的尝试。
