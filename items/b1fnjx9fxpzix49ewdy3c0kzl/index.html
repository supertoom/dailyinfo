Base64 的尾部

作者：Quang Luong

在受影响的 OpenJDK 构建中，格式错误的 Base64 数据可能导致已分配堆内存被常量值覆盖。通过远程堆风水（Heap Feng Shui），我们将这种覆盖转化为堆泄漏和远程代码执行。

发现

几个月前，我正在为某手机厂商开发一个 0 点击漏洞利用程序。这个漏洞受到限制：它是一个线性越界写入，而且我们没有办法绕过 ASLR。我几乎认为它无法被利用，直到我审计了 Android Runtime。结果发现，它具有一些可预测的内存分配模式，如果你从最初的内存破坏处恰到好处地对齐寄存器，就能让运行时解释攻击者的字节码。

完成那条漏洞利用链后，我受到启发（也感到无聊），决定研究一些完全不同的事情。于是我获取了官方 JVM 实现（OpenJDK HotSpot）并开始审计。Java 是一个成熟的平台，因此我知道在这里找到一个“优质”漏洞会很难，但无论如何我仍想尽最大努力尝试。

回想起我之前学到的教训——复杂系统以及跨越多个边界的代码很难处理正确——我将审计重点放在 JIT 编译器、内建函数、广泛可访问的 API 和密码学上。更准确地说，我让 Codex 像 2026 年任何严肃的安全研究人员那样检查这些领域。老实说，我并不期待能找到任何可轻易利用的东西，或许只会发现一些逻辑缺陷或侧信道问题。

Codex 最初带来的大多数结果都是粗制滥造之作，要么无法到达，要么利用条件完全不现实。这看起来像是一场我必输的赌局。但你知道，勇者自有天佑。于是我更加用力地提示它……

最终，Codex 给我带来了一个关于 Base64 解码器本身存在内存破坏的发现。我四处寻找铜，却凭借纯粹的坚持找到了黄金。但等等，它真的是黄金，还是 fool's gold（ fool's gold 指廉价代用品，此处保留双关）？

该漏洞

问题出在 OpenJDK HotSpot 的 x86-64 Base64 intrinsic 中。C2 是 Java 虚拟机中最激进的 JIT 编译器。具体而言，如果你反复触发某个函数，它就会将该函数编译为本地代码。即便如此，普通本地代码本身仍然不够快。现代 CPU 拥有专用指令，可以更快地处理数据。HotSpot 在称为 intrinsic 的优化例程中使用这些指令。x86-64 Base64 intrinsic 错误计算了带填充尾部的存储掩码，导致越界写入。

x86-64 Base64 intrinsic 以 256 字节块为单位遍历输入；如果输入不足 256 字节，则改用 64 字节块处理。当输入不足 64 字节时，它会使用 evmovdqub，即 VMOVDQU8 指令的 intrinsic。该指令接受一个 64 位掩码，用来决定从内存读取或向内存写入哪些字节。掩码首先根据输入和输出长度计算，然后更新以反映 Base64 编码字符串中的填充字节数（'='）。如下所示（伪代码）：

// Zero High Bits Starting with Specified Bit Position
input_mask := bzhiq(-1, input_length)
output_len := (input_length / 4) * 3

// handle padding
if input[input_length - 1] == '=':
    output_len -= 1
    input_mask >>= 1
    if input[input_length - 2] == '=':
        output_len -= 1
        input_mask >>= 1

output_mask := bzhiq(-1, output_len)

在上述代码中，如果剩余的 input 形式为 =, ==, X=, X==, XY= 或 ===，那么 output_len 将被计算为零。然而，由于存在填充，output_len 会递减，从而得到下溢值 -1 或 -2。由于 bzhiq(-1, output_len) 在 output_len >= 64 时不会改变任何位，因此结果为 output_mask == -1u64。

随后，代码使用 evmovdqub 一次读写多个字节。对于写入操作，如果掩码位为 1，则向量寄存器中该索引处的字节会被写入内存。因此，当 output_mask == -1u64 时，以下操作会写入全部 64 个字节：

evmovdqub(
	Address(dest, dp) /* Address: destination address addr */,
	k1 /* k1 == output_mask */,
	tmp /* XMMRegister src register/value to write */,
	true,
	Assembler::AVX_512bit /* vector length */
);

生成的桩代码返回其成功解码的字节数，并在检测到无效输入时提前返回。剩余字节由 Java 代码处理；如果输入无效，Java 代码会抛出 IllegalArgumentException。

在运行时，解码缓冲区长度计算为 (ceil(inp_len / 4) * 3) - padding。触发漏洞时，输入为 65 个字节（[64 bytes] + '='），该计算会分配一个 50 字节的缓冲区。在解码过程中，漏洞会为 output_mask == -1 制造 evmovdqub，因此从偏移量 48 开始写入 64 个字节，超出缓冲区末尾，形成越界写入。

在 OpenJDK 17 上，触发输入为 'A' * 128 + '=' 而不是 'A' * 64 + '='，因为到达该代码路径所需的长度阈值更高。

漏洞利用策略

这个 Base64 漏洞是金子，但不是那种躺在河床里等着被淘出来的金子。它属于深藏、阴暗且难以触及的类型。虽然我们获得了内存破坏，但由于它只向堆写入固定字节，漏洞利用看起来十分困难，甚至近乎不可利用，因为唯一可控的是越界写入的落点。

我们从缓冲区中原本应写入剩余 Base64 解码字节的位置开始，获得以下 64 字节写入：

  • 完全可控地写入字节 0（在界内）
  • 以 4 位粒度可控地写入字节 1（在界内）
  • 不可控地写入字节 [2, 63]。对于字节 48..63，其值将始终为 0x9a。

不可控的越界写入最终并未成为大问题。我们复用了 JavaScript 引擎中一种常见的漏洞利用原语，即经典的覆写缓冲区长度技术。

我们将被覆写长度的缓冲区称为 writer。一旦其长度被破坏，它仍会接受我们选定的字节。因此，如果我们在其后放置另一个数组或对象，就能用所有选定值破坏该相邻对象。这样便将固定写入升级为有边界、值可控的线性写入。

如果随后破坏另一个数组的长度，并且它的数据被复制回响应中，那么通过越界读取，我们就构建出了一个堆泄露原语 reader。此时，在任何代码执行之前，我们已经拥有 JavaBleed，即泄露 Java 堆内容的能力；堆中可能包含 PII、私钥、其他秘密密钥和令牌。

基于 writer 和 reader，本文其余部分将构建完整攻击。我们修复线性写入所破坏的对象，以保持 JVM 运行；对应用程序逻辑发动纯数据攻击；并将有界写入升级为任意写入，以触达 Code Cache 和 JVM 钩子并实现代码执行。

但首先，我们得让堆布局对我们有利。

堆风水（内存整备）

G1 将堆划分为固定大小的区域。在区域算术发挥作用之前，关键数组必须先离开各自线程的私有分配范围。

HotSpot 通常会为每个 Java 线程分配一个线程本地分配缓冲区（TLAB），即 Eden 的一块私有切片。不同请求线程创建的对象会推进不同的游标，因此，一个 TLAB 中的 Base64 解码器与另一个 TLAB 中的写入器之间并不存在对我们有用的顺序关系。

第一层堆布局控制分配路径。关键数组的大小以及 worker 的 TLAB 中剩余的空间，决定 HotSpot 是重新填充该 TLAB，还是采用攻击者偏好的 TLAB 外分配路径。

第二层控制布局。然而，我们无法选择 G1 的内存分配方式，也不知道当前的堆状态。为克服这一限制，Calif 采用了经过考验的“Spray and Pray”方法。

对象大小和填充固定了区域大小跨度内的偏移量。我们散布多个存活的 writer 和 reader 对，为解码器输出提供多个可能的相邻对象。当其所在区域恰好位于 writer 区域下方时，扩大后的 reader 会产生更大的应用响应。我们丢弃未命中结果并重试，直至成功。

漏洞利用开发早期的一个挑战是，AI 在堆布局原语开发过程中会陷入停滞。为了节省 token 和时间，Calif 编写了一个小型堆跟踪器和可视化工具，向智能体提供堆状态信息，并结合我们对具体案例的专业知识。

远程堆风水

为了执行远程堆布局，每个请求的数据都会被持续发送，直至发生关键的堆分配。通过确保先前发送的数据已获得 TCP 确认，漏洞利用便能控制截至当前的分配。一旦我们确信目前的数据已在目标上完成缓冲，就再发送剩余内容，完成 HTTP 请求。这既能实现堆分配控制，也能实现更精确的调度，因为传输小型网络数据包比传输大型数据包更稳定。

确切的分配和释放顺序调度取决于目标应用画像，而我们能够控制 adding、writer、reader 和 decoder 这些部分。

当前攻击对 RTT 和抖动等网络条件较为敏感。为了使攻击更加可靠，较低且稳定的往返时间更受青睐。在我们的受控环境中，我们通过公共 IP 地址在互联网上执行此次攻击，而不是仅仅假定完美的实验室条件。为了让当前攻击路径在漏洞利用中达到最佳稳定性和可靠性，Calif 借助物理学并利用资金来解决这一问题，而不是试验 TCP/IP 协议栈配置。换言之，Calif 在与目标相同的区域租用了另一台 VM。

预热、排练与重试

总结目前的利用链，我们将把 Base64 解码器预热到 C2 层。我们可以预先排练漏洞利用运行，以针对目标校准时序和响应，然后再引发破坏。一旦获得所需信息，就可以触发漏洞。放置错误可能导致 JVM 崩溃，但在许多情况下，我们可以直接重试。

预热
执行有效解码，直至 JIT 选择受影响的快速路径。不会破坏内存。
排练
可选的安全轮次，用于校准。
触发
发送畸形尾部。如果对象排列正确，固定的溢出写入会扩大 writer。
披露
继续 writer，使选定的字节扩大 reader，然后收集从响应派生的堆字节。
修复
当利用链存在修复路径时，使用已披露的原始数据来恢复临时标头和未受影响的相邻对象。
完成
进行应用特定更改，并通过实时请求进行验证。

限制

请求流式传输。 某些当前的梳理配置文件需要部分请求正文才能到达应用程序。等待完整正文的代理会消除其发布时间。nginx 默认会缓冲请求正文。

请求缓冲不是通用缓解措施。Elasticsearch 从一个完整请求运行，因此此设置无法阻止该利用链。在配置WebSocket 升级后，后续帧会通过隧道传输，请求正文缓冲不再适用于这些帧。

应用程序配置文件。 不存在通用有效载荷。每条利用链都需要一个解码器路由、一个实时写入器、一个返回的读取器或其他反馈路径、一个堆布局以及一个应用程序操作。每个目标都需要定制配置文件。该漏洞利用并非通用的即点即用工具。

概念验证

下面是一个自包含的概念验证。它会预热 Base64 解码器，直到使用存在漏洞的固有函数，然后将格式错误的 64 × "A" + "=" 输入解码到一个 4096 字节的数组中。在受影响的 JDK 上，它会输出 REPRODUCED：解码器拒绝了该输入，但解码输出之后 62 个字节（偏移量 50 至 111）已被覆盖。每次写入都位于真实数组内，因此可以安全运行此触发器。

import java.nio.charset.StandardCharsets;
import java.util.Arrays;
import java.util.Base64;

/** Bounded standalone trigger: every write stays inside a real 4096-byte array. */
public final class Base64Trigger {
    private static volatile int sink;

    public static void main(String[] args) {
        Base64.Decoder decoder = Base64.getDecoder();
        byte[] valid = "A".repeat(64).getBytes(StandardCharsets.US_ASCII);
        byte[] malformed = ("A".repeat(64) + "=").getBytes(StandardCharsets.US_ASCII);
        byte[] target = new byte[4096];

        for (int i = 0; i < 200_000; i++) {
            sink += decoder.decode(valid, target);
        }

        Arrays.fill(target, (byte) 0x5a);
        boolean rejected = false;
        try {
            decoder.decode(malformed, target);
        } catch (IllegalArgumentException expected) {
            rejected = true;
        }

        int changed = 0;
        int first = -1;
        int last = -1;
        for (int i = 50; i < target.length; i++) {
            if (target[i] != (byte) 0x5a) {
                changed++;
                if (first < 0) first = i;
                last = i;
            }
        }

        System.out.println("runtime=" + System.getProperty("java.runtime.version"));
        System.out.println("vm=" + System.getProperty("java.vm.name"));
        System.out.printf("rejected=%s changed=%d first=%d last=%d%n",
            rejected, changed, first, last);

        if (!rejected || changed != 62 || first != 50 || last != 111) {
            System.err.println("NOT REPRODUCED");
            System.exit(1);
        }
        System.out.println("REPRODUCED");
    }
}

我们目前暂不公开特定应用程序的漏洞利用。本篇文章介绍该漏洞及通用漏洞利用技术。针对各个产品的武器化利用链将保持私有，直到所有人都有机会完成升级。我们稍后会公开它们。

受影响产品

Java4Shell 影响 OpenJDK 17.0.6 或更高版本。

由于以下 Java 发行版基于 OpenJDK 构建，它们也存在漏洞：

  • Amazon Corretto
  • Eclipse Temurin
  • Microsoft Build of OpenJDK
  • Azul Zulu
  • BellSoft Liberica
  • SAP SapMachine
  • Red Hat OpenJDK
  • Oracle OpenJDK
  • Oracle Java SE
  • Oracle GraalVM for JDK

据 Oracle 称，以下 Oracle Java SE 版本存在漏洞：8u511b33-perf、17.0.21.0.3、21.0.13.0.3、25.0.5.0.3、27.0.1.0.3。感谢 Oracle 在发表前提供此信息。

由于存在漏洞的代码特定于硬件，Java4Shell 还需要支持 AVX-512 VBMI 的 x86-64 处理器。ARM64 CPU 不受影响。

以下主流 CPU 系列满足硬件要求：

  • Intel Xeon：Ice Lake、Sapphire Rapids、Emerald Rapids、Granite Rapids
  • AMD EPYC 和 Ryzen：Zen 4 或更新版本

在 Linux 上，你可以使用以下命令检查 CPU 是否存在漏洞：

grep -m1 '^flags' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(avx512f|avx512bw|avx512vbmi|bmi2)$'

输出必须包含全部四个标志。

建议

OpenJDK 发布了一份安全公告，Oracle 于 2026 年 11 月 17 日太平洋时间下午 1:00 发布了补丁。

所有 Java 用户都应立即更新。

你也可以使用以下任一选项启动 OpenJDK，以缓解 Java4Shell：

  • -XX:-UseBASE64Intrinsics，用于禁用硬件加速的 Base64 编码和解码；或
  • -XX:UseAVX=2，用于禁用 AVX-512。仅在 x86-64 主机上应用此标志。ARM 上的 OpenJDK 无法识别该标志，并将启动失败。
